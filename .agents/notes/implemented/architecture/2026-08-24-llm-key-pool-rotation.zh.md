# Agent Note：面向限流提供商的按路由 API 密钥池轮换

状态：已实现

[English](2026-08-24-llm-key-pool-rotation.md) | 中文

部分提供商按 API 密钥计量请求，且其每日窗口不会在当天内因等待而清零，因此对同一个密钥重试 429 只会把预算花在注定失败直到重置的尝试上。[有界恢复](2026-06-21-bounded-llm-request-recovery.zh.md)负责同请求重试的时机，但刻意不掌握凭据身份：其策略决定*何时*重试，从不决定尝试*以什么*认证。本笔记补上缺失的一半——一个为单一路由在多个密钥之间做选择、并将耗尽的密钥停用到其重置时刻的插件。

## 问题

密钥选择发生在 pi-ai 适配器基于 `ctx.credentials` 的每请求 `resolveApiKey` 闭包内部，没有任何扩展点允许其他插件影响该选择。恢复级联已经可以通过返回 `{ kind: 'retry' }` 而不委派来授权立即的同请求重试，但重新派发的请求会再次解析同一个单一引用。因此，包装层需要两个座位：恢复级联上的决策席位，以及对每请求密钥选择的控制权。

## 决策

### 轮换插件拥有自己的路由，而不是装饰凭据 seam

`@deepseek-ai/dsh-llm-key-rotation` 使用由 dsh-llm-pi-ai 导出的构件（`resolveProfiles`、`credentialStoreFrom`、`authContextFrom`）构建的 `PiAiAdapter`，把自身配置中列出的提供商路由注册到 `ctx.llm` 上，并带有具备池感知能力的 `resolveApiKey`。组合方把被轮换路由的行从普通适配器节移动到本插件；两次注册不能共享一个路由，若部署把该行留在两处，冲突会响亮地失败。Schema 通过 schemastery 的合并语义透传未声明的 profile 字段，因此 profile 校验完全由 pi-ai 解析器拥有并在加载时运行。

把这三个符号提升到 dsh-llm-pi-ai 根导出是有意的表面变更，而非泄漏：该包的凭据适配器本来就是为另一个适配器族复用而写的，而 profile 解析正是任何此类族否则都要分叉的部分。它的根封装测试现在把 `resolveProfiles` 与两个 seam 适配器一起列为受认可的复用对象，同时仍然禁止事件翻译辅助函数。

Cordis 拒绝对同一服务名的二次注册，因此装饰 `ctx.credentials` 将要求替换 `dsh-credentials-local`，捕获存储与 seam 的所有其他消费者去服务一个适配器族。在 dsh-llm-pi-ai 内部增加解析钩子同样被否决：那会把适配器组合与 agent-loop 恢复策略耦合起来，而重试决策刻意保持这条边界干净。

### 轮换乘坐在既有的失败步骤扩展点上，先于普通策略

监听器以 `prepend` 注册到 `agent/request-error`，因为激活顺序由服务可用性驱动，而挂载顺序不是稳定契约。无论组合顺序如何，prepend 都让轮换先于 dsh-llm-retry 等普通注册，所以被限流的密钥在任何策略安排同键退避等待之前就被停用并推进粘滞位置。对自己拥有的失败，监听器返回 `{ kind: 'retry' }` 而不调用 `next()`；循环立即重派同一个请求，新的派发解析下一个成员。单键池对所有失败原样委派，这正是它们今天与普通适配器逐字节等价的原因，包括退避与重试预算。

池状态是一个粘滞索引加上每个成员一条停用戳——何时停用、何时结束。停用是惰性的——过期戳在读取时丢弃，不存在定时器——重置时刻来自失败暴露的 `providerRetryAfterMs`，否则取界定每日配额的即将到来的 UTC 午夜。经 pi-ai 路径时，线上错误会被压平成消息文本（上游限制，见 `llm-pi-ai/src/stream.ts`），因此今天无法获得头等级的重置精度；回退方案正是为这一现实而存在。当没有可用成员时，监听器抛出代码为 `KEY_POOL_EXHAUSTED` 的 `LlmError`，列出每个密钥标签及其重置时刻，并原样作为步骤错误浮现。每次切换都通过标准日志器记录两个密钥与重置时刻；不存在会话事件，因为没有任何模型可见或回放表面事实发生变化，模型可见⟺已记录保持完好。

字面量 `value` 键被记载为仅限开发，加载时经 `assertUsableApiKey` 校验，且从不进入诊断信息；引用成员通过凭据 seam 按请求解析，并以启动环境作为无 seam 回退，因此已存密钥的变更无需重启即可到达下一个请求，与普通适配器完全一致。

### 停用记录持久化在凭据存储旁边的插件自有文档中

代理服务器并非全天候运行，纯内存的停用会在每次重启时复活已耗尽的密钥。因此每条停用都持久化在 harness 主目录下 `.credentials.yaml` 旁边的 `.llm-key-rotation-parks.json` 中（可用 `parkFile`/`dshHome` 覆盖），经由 dsh-atomic-write 以仅属主模式在每次停用或过期变更时写入，并在挂载时重读：过期行丢弃，命名当前配置不再拥有的路由或标签的行被剪除，活跃停用按路由和标签重新挂接，粘滞成员被停用的池从第一个可用密钥启动。文档只含标签与时间戳——绝无密钥值——因此其失败策略有意不对称：缺席即空状态（首次启动），而损坏或版本不符的文档会响亮地导致挂载失败，因为静默忽略状态恰恰会复活持久化所要拦住的那些密钥；写入失败从不使恢复失败，只响亮记日志，因为在内存状态上的轮换仍能保护运行中的进程。

该文档刻意不采用 `.credentials.yaml` 本身：那是 credentials-local 的写锁存储，其他插件不得向其格式与锁协议内写入。一个同级的自有文档保证每位属主一个写者。它也没有跨进程写锁，因此在并发进程间共享同一 `parkFile` 的部署会互相覆盖——这是一条已记载的限制，在受支持的姿态下（一个部署即一个进程）是可以接受的。

### 轮换状态通过提供的 face 读取，具有稳定的快照契约

其他插件通过 `ctx.get('llmKeyRotation').snapshot()` 读取轮换状态，沿用 storage-backend 的模式——函数插件提供服务 face 而非转成类插件。快照列出每个已配置路由的 `activeLabel` 及逐键条目，含 `label`、`source`（`reference` 及其引用名，或无引用字段的 `literal`）和 `status`：`{ state: 'usable' }` 或带 ISO 8601 UTC 时刻的 `{ state: 'parked', parkedAt, resetAt }`，设置页组件据此用 `resetAt` 与时钟求差即可渲染«лимит откатится через Nч Mм»（距限额回滚还剩 N 小时 M 分），无需触及插件内部。密钥值绝不出现。快照中的可用性是只读视图——过期的停用报告为可用但不改动池状态或文件——读者保持纯净，服务路径仍是除恢复之外的唯一变更者。

### 哲学：纯组合即可胜任

本设计是纯插件的。每一项行为都乘坐在已记载的扩展点上：`ctx.llm` 上的路由注册、经适配器自身 seam 的每请求凭据解析、用于恢复的 `agent/request-error` 级联，以及用于状态 face 的 `ctx.provide`。没有在 dsh-llm-pi-ai 或 dsh-llm-retry 中新建扩展点，也没有改动循环；dsh-llm-pi-ai 唯一的差异是把既有内部导出为第二个适配器族的受认可复用通道。

## 范围之外

- 跨提供商或跨模型的故障转移；请求仍然恰好指名一个显式的提供商与模型。
- 经 pi-ai 的头等级重置解析；在上游转发响应头或状态码之前推迟。
- 在并发下将每个失败请求关联到实际服务它的那个成员；池保持进程级粘滞性，单代理会话是受支持的姿态。

## 曾考虑的替代方案

- **装饰或替换 `ctx.credentials`** —— 否决：cordis 对同一服务名的二次注册抛错，替换本地提供商会劫持所有消费者的存储去惠及一个适配器族。
- **在尝试之间经设置改写路由的 `apiKeyEnv`** —— 否决：把配置文档当作恢复控制流来改写，混淆了配置平面与请求状态，并在飞行途中丢失响亮失败的引用语义。
- **在自定义 pi-ai transport 或 fetch 包装内轮换** —— 否决：pi-ai 的 `Transport` 选择线上协议而非 HTTP 客户端，`onResponse` 只观察响应而无法重发请求。
- **把轮折并入 dsh-llm-retry** —— 否决：该插件拥有失败的时机策略；凭据身份与停用是另一种能力、另一套配置，合并会迫使单键部署接受池语义。

## 验证

- 单元套件覆盖重置时刻选择（`providerRetryAfterMs`、缺失与非法提示、UTC 午夜翻转）、粘滞服务、推进与回绕、惰性停用过期、全停用时带标签重置的耗尽、成员来源校验（含空白与非头安全字面量）、停用文档位置解析与确定性渲染，以及文档解析拒绝（非法 JSON、错误版本、未知键、非数组 parks、畸形行、重复项）。
- 组合测试驱动真实 agent loop 打在一台可脚本化的 OpenAI 兼容服务器上：429 后成功即轮换到下一键并保持粘滞；连续三个 429 把池逼入逐一列出密钥与重置时刻的 `KEY_POOL_EXHAUSTED`；字面量与环境解析的成员在没有凭据服务时也能服务；有名未设的引用失败为 `MISSING_CREDENTIAL`；单键与非限流失败在保留 dsh-llm-retry 事件的前提下委派；先挂载 dsh-llm-retry 仍会轮换（prepend 之效）；外部路由委派；休眠挂载不注册任何东西（也不提供服务 face），而卸载会撤回路由。
- 持久化测试证明停用落在同级文档中、仅属主模式下且 `.credentials.yaml` 逐字节不变；耗尽密钥跨重启保持停用，使下一次请求直接从备用键开始；过期与陈旧行在挂载时丢弃且文件剪除它们；损坏或错误版本的文档响亮挂载失败并指名路径；不可写位置响亮记日志而轮换继续；快照以 ISO 时刻报告 usable/parked 状态——把过期停用视为可用且不改写文件。
- 真实 Loader 组合经发行循环启动 `cordis.yml` 行，证明线上请求携带相继的 bearer 令牌且轮换切换不产生 `llm/retry` 事件，以及持久化停用文档随后指名被停用的密钥。
- 包覆盖率报告每个 src 文件的语句、分支、函数与行均为百分之百。

## 后果

- 轮换一个路由要求把它的行移出任何普通 dsh-llm-pi-ai 节；这些路由不出现在可配置提供商目录中。
- 并发请求下，停用跟踪的是粘滞位置而非各请求实际服务的成员，罕见的交错可能停用一个他请求正在使用的位置；受影响的密钥在其重置时惰性恢复。
- 在上游暴露重置响应头之前，每日限额的停用持续到即将到来的 UTC 午夜，当部署跨越日界时可能让密钥闲置超过真实窗口。
- 未来的恢复策略经委派组合在轮换之后；必须持久观察限流切换的策略需要自己的会话事件，不能依赖本插件日志行。
- 停用文档是单写者的：指向同一 `parkFile` 的两个 harness 进程会互相覆盖停用，并发部署需要各自的位置。
- 状态 face 的消费者只依赖已记载的快照字段；设置页组件无需访问池、适配器或停用文档。
