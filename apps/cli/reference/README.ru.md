# Справочник по поведению CLI `dsh`

[English](README.md) | [中文](README.zh.md) | Русский

Этот справочник определяет режимы команд: profile, web-alias, управление плагинами и выгрузку конфигурации. Argv разбирается один раз через [`src/args.ts`](../src/args.ts), а [`src/bin.ts`](../src/bin.ts) динамически импортирует только выбранный runner.

## Загрузка profile

`dsh --profile <name>` загружает profile из `$DSH_HOME/profiles/<name>`. Эффективное дерево собирается поверх пустого корня последовательным применением: каждого bundle-патча из списка `dsh.profile.bundles` манифеста profile, собственного `cordis.patch.yml` профиля, домашнего `$DSH_HOME/cordis.patch.yml` (локальные для машины предпочтения, общие для всех profile, поэтому он старше per-profile-слоя) и каждой накладки `--patch <path>` в порядке argv. Поздние слои выигрывают построчно; патч заменяет полное значение `config` целевой строки, а не deep-merge-ит ключи, и может вставлять новые строки. Ошибка разбора, схемы, резолва или загрузки плагина сообщается, и процесс выходит с ненулевым кодом. SIGINT и SIGTERM освобождают ресурсы смонтированного корня перед выходом.

Имена bundle-ов резолвятся сначала от установки dsh, затем от каталога profile. Поэтому встроенные bundle-ы (`@deepseek-ai/dsh-base`, `@deepseek-ai/dsh-web-app`, `@deepseek-ai/dsh-headless`) всегда приходят из той же установки, что и работающий `dsh`; внешние bundle-ы берутся из pnpm-управляемого `node_modules` профиля. Голое имя плагина `name` в любой строке патча резолвится через Node parent-walk от каталога profile, который достаёт до сопровождаемого fallback установки `$DSH_HOME/profiles/node_modules` (по одному symlink на каждый пакет, от которого зависят приложение и bundle-ы установки; лечится при каждом запуске).

Profile `web` и `headless` автоматически инициализируются из поставляемых шаблонов при первом использовании (`web`: base + web-app; `headless`: base + headless). Любой другой отсутствующий profile падает громко с подсказкой выполнить `dsh plugin --profile <name> add <package>`.

### Аргументы приложения

Флаги лаунчера идут первыми и заканчиваются на первом нераспознанном токене; всё дальнейшее дословно передаётся загруженному profile через `ctx.cmdlineArgs`, где любой внедрённый app-плагин может его разобрать ([`dsh-cmdline`](../../../packages/boot/cmdline/README.md)). Поэтому `dsh --profile web --port 8080` доходит до `--port` веб-приложения, `dsh --profile web --help` печатает help того приложения и ничего не грузит, а `dsh --help` (некому передать) печатает help самого лаунчера. `-V`/`--version` печатает версию лаунчера, когда стоит до границы аргументов приложения.

Композиция монтируется один раз. Обычный плагин внедряет `cmdlineArgs`, разбирает аргументы этого приложения и предоставляет разрешённое как сервис; каждая строка, конфигурируемая флагами, внедряет этот сервис, и Loader ждёт его, прежде чем вычислить config строки (`port: !!js ctx.webStartup.port ?? 3080`). Поэтому флаг побеждает значение, записанное рядом с ним. Такой приоритет требует, чтобы строка сохраняла это выражение; пользовательский патч, заменяющий весь `config` литералами, убирает рантайм-чтение. Help и отклонённые аргументы запрашивают выход — ненулевой код при отклонении, 0 для help — не активируя строки, зависящие от сервиса провайдера. Живая правка `cordis.patch.yml` перевычисляет выражения против всё ещё поднятых сервисов, поэтому она не может сбросить обслуживаемый порт.

Флаги лаунчера должны идти перед аргументами приложения, а парсер лаунчера поглощает один `--`: аргумент приложения, который должен прийти как литеральный `--`, требует `-- --`. Первый аргумент приложения, равный `web` или `plugin`, выбирает вместо этого тот subcommand. `ctx.cmdlineArgs.get()` — общее неизменяемое чтение: несколько плагинов могут разобрать один снапшот, а profile без читателя игнорирует свои аргументы приложения.

Поставляемые приложения владеют этими командными строками:

| Profile | Аргументы |
|---|---|
| `web` | `--host`, `--port`, повторяемый `--trusted-host`, `--no-open` |
| `headless` | текст задания как позиционный аргумент |

Одноразовое задание (`dsh --profile headless "run the tests"`) создаёт одного свежего персистентного Agent через core-реестр, подаёт задание, ждёт quiescence и вычищает Session, прежде чем извлечь последний непустой текст ассистента и финальную причину `turn/end` из её долговечного интервала. Он печатает текст на stdout и выходит с кодом 0 при `completed`, иначе с 1. Вызов без задания — ошибка использования со стороны этого приложения. Поставляемый headless profile не монтирует ни ApiProxy, ни Host, ни HTTP-сервера, ни Web-рантайма, ни браузерного клиента; успешный прогон ничего не пишет в stderr и не открывает слушающего порта.

Осмотрите собранное дерево без его загрузки:

```sh
dsh --profile web --dump-default-config
dsh --profile web --patch ./extra.yml --dump-config
```

`--dump-default-config` печатает только слои bundle-ов; `--dump-config` добавляет `cordis.patch.yml` профиля, домашний `$DSH_HOME/cordis.patch.yml` и накладки `--patch`. Оба печатают комментарии, называющие файл-источник каждой строки и каждую изменившую её накладку; выражения `!!js` остаются невычисленными, а несопоставленные цели патчей сообщаются на stderr. Дамп никогда не запускает command-line-провайдеров приложения, поэтому показывает собранное дерево до разрешения любых аргументов приложения и отклоняет вызов, несущий аргументы приложения.

## Управление плагинами

`dsh plugin --profile <name> <args...>` инициализирует профиль, если его нет (поставляемый шаблон, или один `@deepseek-ai/dsh-base` для прочих имён), затем пересылает `<args...>` в `pnpm` с каталогом профиля в качестве рабочего каталога — `add`, `remove`, `why`, `update` и любой другой глагол pnpm работают без изменений; pnpm должен быть на PATH. Относительные спецификации путей (`.`, `../plugin` и их формы `file:`/`link:`) якорятся сначала к вызывающему каталогу, поэтому `add .` из checkout-а плагина устанавливает этот checkout, а не профиль. После каждого успешного прогона `dsh.profile.bundles` сверяется с установленным состоянием: каждая зависимость, резолвящаяся в пакет, чей манифест объявляет `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`, присоединяется к стеку слоёв (так что `update`, принесший объявление, активирует его), зависимость без bundle остаётся простой с однократным предупреждением, а удалённая зависимость покидает стек.

Провайдеры субагентов Codex и Claude Code — отдельные опциональные Bundle-ы. Добавьте любой из пакетов, оба одной командой или удалите любой пакет независимо:

```sh
dsh plugin --profile <name> add @deepseek-ai/dsh-subagent-codex
dsh plugin --profile <name> add @deepseek-ai/dsh-subagent-claude-code
dsh plugin --profile <name> add @deepseek-ai/dsh-subagent-codex @deepseek-ai/dsh-subagent-claude-code
dsh plugin --profile <name> remove @deepseek-ai/dsh-subagent-codex
dsh plugin --profile <name> remove @deepseek-ai/dsh-subagent-claude-code
```

Успешная операция pnpm меняет манифест Profile и список Bundle-ов на диске; работающий Profile сохраняет набор Bundle-ов от своего текущего старта. Перезапускайте этот Profile после добавления, удаления или обновления Bundle-а. Эта стартовая черта касается членства в Bundle-ах, тогда как обычные правки Profile- или домашнего `cordis.patch.yml` вступают в силу через hot reload. При следующем старте каждый установленный Bundle регистрирует только своего спящего Host-провайдера; скопированный Preset должен отдельно включить соответствующую строку инструмента для новых Agents. Исполняемым файлом, аутентификацией, payload и деталями отказов владеют [README провайдера Codex](../../../packages/subagent/subagent-codex/README.ru.md) и [README провайдера Claude Code](../../../packages/subagent/subagent-claude-code/README.ru.md); закрытием зависимостей по умолчанию владеет [справочник базового Bundle](../../../packages/bundle/base/README.md).

```sh
dsh plugin --profile tui add github:deepseek-harness/turtle-ui
dsh plugin --profile tui remove turtle-ui
dsh --profile tui
```

Git-плагины, поставляющие исходники, собираются при установке через скрипт `prepare`, который pnpm ≥10 блокирует, пока потребитель не разрешит сборку: первая команда `add` падает с подсказкой `allowBuilds` от pnpm (и указателем dsh на `pnpm-workspace.yaml` профиля); скопируйте напечатанный ключ туда и повторите. Установка собранного tarball или локального checkout разрешения не требует.

## Web alias

`dsh web` — жёстко прописанный alias для `--profile web`; флаги после него принадлежат веб-приложению, чей обычный bundle-провайдер их разбирает. `--host` и `--port` переопределяют собранные значения несущих их строк, повторяемый `--trusted-host` добавляет полномочия вызова через `ctx.webRuntime.trustedHosts` (выражение развёртывания конкатенирует свои собственные полномочия), а `--no-open` отключает передачу в браузер по умолчанию для этого вызова. HMR-приёмник клиентских плагинов смонтирован всегда и простаивает, пока отдельный watcher `pnpm run dev:web` не пересоберёт клиентские бандлы.

```sh
dsh web
dsh web --no-open
dsh web --patch ./extra.cordis.yml
dsh web --dump-config
dsh web --help
```

Production Web-runner требует собранных артефактов пакетов и фронтенда (`pnpm run build`). По умолчанию он обслуживает `http://127.0.0.1:3080` и при локальном запуске открывает этот канонический host-URL только после того, как уладится полное дерево Loader. Непустой унаследованный `SSH_CONNECTION` или `SSH_TTY` подавляет передачу в браузер, поскольку локальный перенаправленный адрес принадлежит SSH-клиенту или редактору; host-URL всё равно печатается. CLI намеренно пока не поддерживает `--host 0.0.0.0` и выходит с ошибкой использования. Непосредственно перед локальной передачей он печатает `dsh web: opening the default browser; pass --no-open to disable`; если передача силами операционной системы не удалась, диагностика на stderr называет причину, оставляет сервер работать и сообщает URL для ручного использования. `--trusted-host` добавляет именованные полномочия, принимаемые ограждением browser-trust на `/api`.

Завершение процесса даёт дереву плагинов до пяти секунд на освобождение ресурсов. Первый `SIGINT`/`SIGTERM` запускает грациозную вычистку — `SIGTERM` — это обычный запрос супервизора на остановку, он завершается с кодом 0 на любом surface, `SIGINT` сообщает 130; второй сигнал форсирует немедленный выход. Если нормальное завершение one-shot уже застряло в освобождении ресурсов, первый `Ctrl+C` становится эскалацией и выходит немедленно, вместо того чтобы быть проглоченным.

Все режимы считают вызывающий каталог корнем workspace по умолчанию, загружают применимые инструкции `AGENTS.md` или `CLAUDE.md` с бюджетом рендера 65 536 байт и используют индекс содержимого сессий на SQLite в памяти. Каждая загрузка profile следит за валидными правками обоих слоёв `cordis.patch.yml` (profile и home) и заново применяет их транзакционно; one-shot surface выходит через своё ограниченное завершение, которое освобождает watcher-ы.

Новые сессии по умолчанию получают preset разрешений `workspace-write`. Мутации bash и файловой системы ограничены workspace сессии и временными корнями платформы; чтения и сетевой доступ не ограничены, а видимость процессов зависит от выбранного sandbox-бэкенда — bwrap запускает команды в частном PID namespace, скрывающем процессы хоста, а Landlock и Seatbelt видимость процессов хоста не меняют. `DSH_PERMISSION_MODE` меняет process-fallback. Сохранённые разрешения General-settings влияют на будущие Web-сессии, а не на уже открытую.

`DSH_TOOLS_MODE` выбирает `native`, `code` или `both` для процесса; другое значение валит загрузку. Поставляемый agent-пресет `minimal` сохраняет эту презентацию развёртывания, фиксирует полный системный промпт на `You are a helpful software engineer assistant.` и собирает только персистентный `bash` плюс `str_replace_editor`. Выберите 极简模式 при создании Web-сессии; все прочие секции промпта и видимые модели плагины остаются вне этого агента, тогда как общий хост браузера, workspace, персистентности, песочницы и разрешений остаётся на месте.

## Общее поведение развёртывания

Базовый bundle монтирует нативный адаптер DeepSeek, провайдеров настроек и учётных данных, стабильный `web_search` и выключенную телеметрию сессий. Учётные данные провайдеров резолвятся из унаследованного окружения, `$DSH_HOME/.credentials.yaml`, `.env` вызывающего каталога, затем `$DSH_HOME/.env`; управляемый документ никогда не материализуется в `process.env`, тогда как оба файла `.env` — обычные слои среды запуска. Search использует `DEEPSEEK_API_KEY` и принимает `DEEPSEEK_SEARCH_BASE_URL`; `web_fetch` выключен, пока слой патча не вставит провайдера и не включит его.

Телеметрия сессий по умолчанию остаётся локальной. `DSH_TELEMETRY_MODE=FULL` передаёт потоком каждое проекционированное событие сессии как OTLP/HTTP-логи, а `DSH_TELEMETRY_MODE=FEEDBACK_ONLY` выгружает суффикс журнала сессии только при записи отзыва. `DSH_TELEMETRY_OTLP_URL` выбирает другой коллектор, и любое непустое `DSH_TELEMETRY_DISABLED` остаётся авторитетным жёстким opt-out. В поставляемой базе нет правила редактирования телеметрии, поэтому явно включённые выгрузки могут содержать текст сообщений, аргументы и результаты инструментов и пути workspace; тем решением развёртывания владеет [Agent Note о выключенности по умолчанию](../../../.agents/notes/implemented/feature/2026-08-10-telemetry-default-off.md).

Внешние plugin-bundle-ы устанавливаются через `dsh plugin --profile <name> add <package-or-git-spec>`. Установленный пакет владеет своими зависимостями и приносит свой объявленный слой `cordis.patch.yml`. CLI также поставляет `@deepseek-ai/dsh-mcp-client` как зависимость для слоёв патчей, но ни один MCP-сервер не включён по умолчанию, потому что каждая серверная команда — доверенный исполняемый код вне песочницы агента.

## Запуск из исходников

Из корня репозитория выполните `pnpm run build` отдельно после свежего checkout и всякий раз, когда артефакты нужно обновить, затем пользуйтесь `pnpm dsh <args...>`. Скрипт `package.json` запускает `apps/cli/src/bin.ts` через `node --import tsx/esm` без сборки и пересылает каждый аргумент. Отсутствующие Typert host-артефакты валят загрузку profile ошибками module resolution без указания собрать. Когда эти host-артефакты есть, отсутствующие bundle-ы фронтенда или клиентских плагинов валятся на старте с указанием выполнить `pnpm run build`. Лаунчер не проверяет свежесть, поэтому существующие устаревшие bundle-ы могут гонять старый браузерный код до пересборки. Процесс наследует среду запуска; задайте `NODE_USE_ENV_PROXY=1`, когда поддерживающая версия Node должна учесть `HTTP_PROXY` и `HTTPS_PROXY`. Установленная форма запускает собранный `apps/cli/lib/bin.js`, не пересобирая репозиторий.
