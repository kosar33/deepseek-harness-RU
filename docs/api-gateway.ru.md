# API-шлюз

[English](api-gateway.md) | [中文](api-gateway.zh.md) | Русский

Это актуальный справочник по Typert API-шлюзу. Он описывает, как бизнес-сервисы объявляют унарные Remote-методы, как сборка генерирует контракты Host и Client и как вызовы переиспользуют RPC соединения Connection и маршрут `/api`. События сессии, инкрементальные данные и прочие потоковые протоколы выходят за рамки этого документа: они могут использовать тот же Connection, но не используют дескрипторы методов Remote.

## Модель программирования

Бизнес-сервисы помечают декораторами `@Remote` или `@RemoteScope` методы, доступные Client. Непомеченные методы не попадают в сгенерированные типы Client и рантайм-вклады и не могут быть вызваны через `ctx.remote`.

`@Remote` означает вызов сервиса Cordis, зарегистрированного в корневом Host-контексте. Сложные Host-объекты не могут передаваться по протоколу напрямую: бизнес-пакет ДОЛЖЕН объявить их связь с протокольным идентификатором через `TypertLookupMap` и зарегистрировать в `ctx.typert.lookups` провайдера разрешения по умолчанию. Например, параметр `Agent` с именем `agent` в Host-сигнатуре порождает поле протокола `agentId`, и шлюз разрешает этот идентификатор в Host-объект перед вызовом бизнес-метода. Host-композиция может через `ctx.typert.lookups.configure()` переопределить политику разрешения для ключа lookup, не меняя имя параметра, поле протокола или канонический символ типа, принадлежащие бизнес-пакету.

`@RemoteScope(key)` сначала разрешает идентификатор в скоупленный контекст через `ctx.typert.contexts`, затем получает сервис из этого контекста и вызывает метод. Декоратор применяется, когда метод сам зависит от скоупленной композиции и не нуждается в явном получении объектов вроде `Agent`.

Обычно сервисы наследуют `TypertRemoteService`, чтобы конструктор явно привязывал ключ сервиса Cordis и пространство имён Remote по умолчанию. Сервис, у которого уже есть другой базовый класс, может вместо этого объявить `readonly typertRemote = bindTypertRemote(this, serviceKey)`; обе формы оставляют инспектируемую публичную привязку и не зависят от компилятора, внедряющего символ в конструктор.

```ts
import type { Agent } from '@deepseek-ai/dsh-agent'
import { TypertRemoteService, Remote, RemoteScope } from '@deepseek-ai/dsh-typert-protocol'
import type { Context } from '@deepseek-ai/cordis'

export interface CreateGoalRequest {
  objective: string
}

export interface CreateGoalResult {
  accepted: boolean
}

export class GoalService extends TypertRemoteService {
  constructor(ctx: Context) {
    super(ctx, 'goals')
  }

  @Remote('create')
  createForClient(
    agent: Agent,
    request: CreateGoalRequest,
    signal: AbortSignal,
  ): CreateGoalResult {
    signal.throwIfAborted()
    return this.create(agent, request)
  }

  @RemoteScope('agent', 'current')
  currentForClient(): CreateGoalResult {
    return { accepted: true }
  }

  private create(_agent: Agent, request: CreateGoalRequest): CreateGoalResult {
    return { accepted: request.objective.length > 0 }
  }
}
```

Remote-методы могут возвращать значение синхронно или возвращать Promise. Для кооперативной отмены последний параметр в Host-сигнатуре ДОЛЖЕН быть `signal: AbortSignal` с использованием глобального типа; он записывается в дескриптор вместо попадания в `args`, а сгенерированный метод Client принимает необязательный финальный `AbortSignal`.

Client использует конкретные функции на обычных объектах, а не JavaScript Proxy. Прямые и скоупленные вызовы доступны под `ctx.remote.<namespace>` и `agentCtx.remote.<namespace>`. Каждое пространство имён — отслеживаемый дочерний сервис Cordis, зарегистрированный как `remote.<namespace>`; сборка Client монтирует вклады через `ctx.remote.$mount()`, а пространство имён выгружается после отзыва последнего метода. Объявления зависимостей принадлежат фактическому вызывающему: только бизнес-пакет, читающий `ctx.remote.<namespace>` или `agentCtx.remote.<namespace>`, объявляет и `remote`, и `remote.<namespace>` в собственном `inject`; сборки, лишь монтирующие вклады, и рантаймы более высокого уровня, не вызывающие это пространство имён, не объявляют зависимость от него за бизнес-пакет. Когда метод `@Remote` имеет ровно один lookup-параметр и одноимённый `TypertContextMap` использует тот же протокольный идентификатор, сгенерированная скоупленная сигнатура опускает этот параметр-идентификатор. `@RemoteScope` генерирует только скоупленный интерфейс вызова.

```ts ignore-check
import type { SessionId } from '@deepseek-ai/dsh-session/types'
import type { AgentContext } from '@deepseek-ai/dsh-client-runtime/client'
import type { Context } from '@deepseek-ai/cordis'
import type {} from '@deepseek-ai/dsh-api-remotes/client'

export const inject = ['remote', 'remote.goals']

declare const ctx: Context
declare const agentCtx: AgentContext
declare const agentId: SessionId

await ctx.remote.goals.create(agentId, { objective: 'ship it' })
await agentCtx.remote.goals.create({ objective: 'ship it' })
```

Клиентские приложения собирают только `@deepseek-ai/dsh-api-remotes`. Этот пакет импортирует подпути `/remote` выбранных бизнес-пакетов как рантайм-значения, монтирует их вклады через `ctx.remote.$mount()` и реэкспортирует слияния объявлений из тех же файлов. Добавление Host-пакета Remote — явное решение владельца клиентской композиции; бизнес-компонентам не нужно отдельно загружать Typert-шлюз или Remote-JS бизнес-пакета.

Сборка `api-remotes` и контракт `ctx.remote` не зависят от React; Host-методы, видимые любой клиентской сборке, ограничены Remote-методами, отобранными на этапе генерации.

## Ответственности компонентов

| Расположение | Пакет или входная точка | Ответственность |
|---|---|---|
| Общий | `@deepseek-ai/dsh-typert-protocol` | Объявляет декораторы, привязки шлюза, расширяемые слиянием карты протокола, дескрипторы вызова и типы провайдеров; не запускает анализ TypeScript и не регистрирует сервисов Cordis |
| Сборка | `@deepseek-ai/dsh-typert-generator` | Строго анализирует Remote-сигнатуры, граф типов, lookup'ы, контексты и исходные позиции из Host `ts.Program`, затем генерирует артефакты Host и Host-for-Client |
| Host | `@deepseek-ai/dsh-typert-registry` и загрузчик | Помещает сгенерированные Host-дескрипторы, схемы и регистрации бизнес-пакетов в `ctx.typert` и хранит провайдеров lookup и контекстов |
| Host | `@deepseek-ai/dsh-api-remotes` | Владеет политикой идентичности Agent/Session приложения и конфигурирует соответствующие Typert lookup'ы |
| Host | `@deepseek-ai/dsh-api-gateway` | Предоставляет `ctx.typertGateway`, перехватывает Remote-эндпоинты, разрешает объекты или контексты, вызывает живые сервисы Cordis и валидирует значения запроса и возвращаемые значения |
| Client | `@deepseek-ai/dsh-api-gateway/client` | Предоставляет дочерние сервисы `ctx.remote` и `remote.<namespace>`, монтирует сгенерированные дескрипторы как конкретные методы, инициирует, валидирует и отменяет вызовы через Connection |
| Client | `@deepseek-ai/dsh-api-remotes/client` | Явно отбирает и монтирует разрешённые приложением вклады `/remote` и приносит соответствующие слияния объявлений в бизнес-код |
| Оба | `@deepseek-ai/dsh-client-connection` | Предоставляет носитель RPC, корреляцию запросов, границу доверия, отмену, конверт ответа и HTTP-мост `/api` |

Пакет API-шлюза владеет Host-диспетчером и Remote-эндпоинтом Client как равноправными входными точками, но две сборки никогда не попадают в один `ts.Program`. Host-вход не импортирует слияние `Context` Cordis для Client, а Client-вход не импортирует сервис Host-шлюза.

## Строгий конвейер генерации

Корневая сборка запускает `build:lib:host`, `build:lib:client` и `build:web` по порядку. Фаза lib Host сначала выполняет `tsc -b tsconfig.host.json`, затем `tsdown --env.DSH_BUILD_FACE host`; обычный граф Project Reference Host компилирует генератор Typert, который запускается во время этого прохода tsdown с агрегатом Host в качестве единственного входа `ts.Program`. Затем фаза lib Client выполняет `tsc -b tsconfig.client.json` и `tsdown --env.DSH_BUILD_FACE client`, используя свежесгенерированные декларации Remote Client и рантайм-вклады без повторного запуска Typert.

Оба прохода tsdown получают весь воркспейс и бандлят только JavaScript, эмитированный в `lib/types` соответствующей фазой tsc. Корневой конфиг не сканирует артефакты Client, не классифицирует имена пакетов и не передаёт поддерживаемый фильтр в tsdown; пакетные конфиги возвращают входные точки текущей фазы на основе `DSH_BUILD_FACE`. Обычный плагин Client производит и свою входную точку Node-загрузчика, и браузерный бандл во время фазы Client.

`api-remotes` — единственный пакет с разделёнными гранями TypeScript. Его Host-проект владеет политикой lookup Agent/Session, а его Client-проект зависит от деклараций `/remote`, сгенерированных для бизнес-пакетов во время Host tsdown; корневые агрегаты и прямые потребители ДОЛЖНЫ ссылаться на `api/remotes/tsconfig.host.json` или `api/remotes/tsconfig.client.json` соответственно. Функция `clientBundle(..., { hostPhase: true })` этого пакета производит его Host-вход во время Host tsdown и оставляет для Client tsdown только браузерную входную точку. Все остальные пакеты остаются зарегистрированными в одном агрегате.

Каждый бизнес-пакет-вкладчик пишет сгенерированные файлы в собственный каталог `lib/`, а не в каталог исходников:

| Файл | Потребитель | Содержимое |
|---|---|---|
| `typert.host.js` | Загрузчик Host | Рантайм-рефлексия грани Host, строгие дескрипторы вызова и значения регистрации схем |
| `typert.host.d.ts` | Система типов Host | Сгенерированные декларации для грани Host |
| `typert.remote-client.js` | `api-remotes` | Монтируемый `TypertRemoteContribution` со строгими дескрипторами и рантайм-кодеками |
| `typert.remote-client.d.ts` | Система типов Client | Слияния объявлений для `TypertRemoteNamespaceMap` и `TypertRemoteScopeMap`, плюс безопасные для Client ссылки на типы |
| `typert.remote-client.d.ts.map` | Редактор | Отображает сгенерированные свойства методов обратно на декларации Remote-методов в Host-пакете |

Бизнес-пакеты экспортируют входную точку загрузчика Host через `./typert`, а входную точку Host-for-Client — через `./remote`. Генератор также валидирует эти экспорты пакетов и списки публикуемых файлов; артефакты генерируются только для явных пакетов-вкладчиков, предоставляющих соответствующую входную точку.

Имена параметров в декларациях Remote Client берутся из полей протокола, а типы параметров и возвращаемых значений ссылаются на безопасные для Client типы, экспортируемые исходным бизнес-пакетом. Карта деклараций ведёт от сгенерированного свойства, стоящего за `ctx.remote.goals.create`, обратно к Host-методу в исходниках, помеченному `@Remote`, поэтому редакторы с поддержкой карт деклараций могут перейти в навигации от клиентского вызова к реальной реализации, а не остановиться на сгенерированном `.d.ts`.

Строгий анализ требует, чтобы Remote был публичным нестатическим методом экземпляра с конкретной реализацией. Метод не может быть дженериком; параметры ДОЛЖНЫ быть обязательными и именованными простыми идентификаторами и не могут использовать деструктуризацию, значения по умолчанию, rest-параметры или необязательные параметры. Typert генерирует строгие схемы для обычных JSON-представимых типов; сложные объекты, такие как классы воркспейса, ДОЛЖНЫ иметь уникальную декларацию `TypertLookupMap`. Пакеты lookup и контекстов отвечают и за статические слияния объявлений, и за рантайм-регистрацию провайдеров; если не хватает любой из сторон, падает сборка или падает первый вызов, которому нужен провайдер.

## Вызов в рантайме

Remote и API Proxy разделяют маршрут `/api` соединения Connection. Remote Client вызывает `connection.rpc.call('/api', '<namespace>/<method>', { args }, signal)`; HTTP-носитель отображает это в `POST /api/<namespace>/<method>` с полезной нагрузкой, содержащей только именованный объект `args`.

Connection выполняет единую проверку доверия для `/api` до HTTP-моста, затем диспетчеризует внутри общего FetchHandler в порядке перехватчиков. Typert-шлюз перехватывает только двухсегментные эндпоинты, у которых есть строгий дескриптор или активный маркер SRC; неперехваченные запросы уходят в существующий API Proxy. Connection владеет транспортом, идентификаторами RPC, конвертами ответов и отменой запросов, а шлюз владеет только протоколом данных Remote и бизнес-диспетчеризацией. Замена носителя Connection в будущем не потребует изменений в дескрипторах Remote или программном интерфейсе Client.

Для каждого вызова шлюз разрешает дескриптор и живой сервис из текущих реестров, а не кэширует бизнес-объекты. Он требует, чтобы поля в `args` точно соответствовали дескриптору, валидирует значения протокола кодеками, разрешает объекты или получатели через зарегистрированных провайдеров lookup или контекстов, вызывает метод сервиса, на который указывает привязка, и валидирует возвращаемое значение. Отсутствующий провайдер, неизвестная идентичность, несовпадение привязки, недостающий или лишний аргумент, ошибка схемы или отсутствующий метод приводят к отказу до входа в бизнес-код или после выхода из него.

`register()` провайдера lookup предоставляет и стабильную декларацию, и резолвер по умолчанию; `configure()` предоставляет резолвер, которым владеет Host-композиция, — он может исполняться асинхронно и ограничен временем жизни эффекта. Конфигурация может предшествовать монтированию провайдера; без провайдера вызов всё равно падает с `lookup-unavailable`, а выгрузка конфигурации возвращает политику провайдера по умолчанию. API Remotes владеет стандартной семантикой `agentFor()` для `agent` и `session`: он переиспользует живой Agent, автоматически возобновляет обычные холодные сессии, дедуплицирует параллельные возобновления и отвергает идентичности, принадлежащие subagent-маршрутизации; lookup `session` возвращает сессию этого Agent'а. Web API Proxy предоставляет свои значения Agent по умолчанию и настройку скоупов, затем использует тот же резолвер для legacy-методов. Отказы возобновления и барьеры владения проходят дальше без изменений как существующие RPC-ошибки, а не схлопываются в ошибку `internal` шлюза.

Выгрузка вклада Client удаляет его дескрипторы и конкретные методы вместе, прерывает его незавершённые вызовы и заставляет устаревшие дескрипторы методов, удерживаемые внешним кодом, отвергать дальнейшие вызовы. Отозванный на Host строгий эндпоинт также не деградирует до инференса SRC, что не даёт горячей выгрузке незаметно ослабить валидацию.

## SRC-фолбэк для разработки

Когда Host запускается из исходников через `node --import tsx/esm`, плагин компилятора Typert не исполняется. Стандартные инициализаторы декораторов всё ещё записывают имя метода и режим вызова в приватный для модуля `WeakMap`, а `TypertRemoteService` или `bindTypertRemote()` предоставляет явную привязку сервиса; поэтому шлюз может построить более слабый временный дескриптор без запуска `ts.Program`.

SRC-фолбэк разбирает простые имена параметров из живой функции. Когда имя параметра совпадает с `parameter` зарегистрированного lookup, например `agent` или `session`, он использует поле протокола `agentId` или `sessionId` этого lookup и разрешает объект на Host; остальные параметры проверяются лишь на отсутствие циклов, JSON-безопасность и отсутствие специального прототипа. `@RemoteScope` напрямую использует поле протокола зарегистрированного провайдера Host-контекстов. SRC не читает типы TypeScript, не генерирует схемы Zod, не выводит необязательные параметры и не поддерживает деструктуризацию, значения по умолчанию, rest-параметры или дублирующиеся имена параметров.

SRC решает только диспетчеризацию для Host-процесса, запущенного из исходников. Client не обнаруживает декораторы у работающего Host, а Remote Client отказывается монтировать SRC-дескрипторы без строгих кодеков; его типы, кодеки и значения регистрации Remote всегда берутся из последних сгенерированных артефактов `lib/typert.remote-client.*`.

## Режим разработки

Веб-разработка готовит актуальные артефакты Host, Client и Web командой `pnpm run build`, затем запускает Host из исходников и вотчер плагинов Client в отдельных терминалах:

```sh
pnpm dsh web
pnpm run dev:web
```

`dsh` запускает исходники Host через tsx, поэтому Host может использовать SRC-фолбэк; `dev:web` следит только за плагинами Client с декларацией `dsh.client` и перезаписывает их `lib/client.js`. Он не анализирует декораторы Host и не генерирует DTS Remote Client.

Изменение одного лишь тела реализации Remote-метода без изменения его контракта не требует перегенерации файлов Typert. После добавления или удаления декоратора либо изменения имени экспорта, пространства имён, параметра, возвращаемого значения, lookup, контекста или сигнатуры отмены перезапустите lib-сборку в заданном порядке, чтобы Host сгенерировал строгий контракт до того, как Client скомпилирует и забандлит новый вклад:

```sh
pnpm run build:lib
```

Работающий вотчер Client подхватывает эти сгенерированные файлы при пересборке. Если `pnpm run build:lib:host` уже обновил контракт Host, `pnpm run build:lib:client` может завершить сторону Client; чистый worktree не может пропустить фазу Host. Перекомпиляция одного лишь фронтенд-исходника не может вывести новые типы из декораторов Host. `pnpm run typecheck` выполняет фазу lib Host до tsc Client, а CI и релизные сборки используют тот же порядок.

## Границы

Remote обрабатывает только унарные вызовы методов с одним запросом и одним результатом. Потоки событий сессии, пагинация, инкрементальная свёртка, проекция и подпотоки сущностей требуют отдельного протокола данных и модели регистрации; даже переиспользуя Connection, они НЕ ДОЛЖНЫ маскироваться под Remote-методы или попадать в дескрипторы вызова.

Слои API организованы как `remotes → gateway → connection → webserver`. Слои BFF и Typert RPC живут под `packages/api`; Connection и WebServer живут в `packages/client/connection` и `packages/host/webserver`. API Proxy в `packages/host/apiproxy` обрабатывает эндпоинты без Remote-дескрипторов.

Политика lookup конфигурируется для каждого ключа, поэтому все параметры `agent` или `session` имеют общее поведение холодного возобновления. Приём только живых объектов потребовал бы явной политики для каждого параметра или эндпоинта, которой не существует; бизнес-метод НЕ ДОЛЖЕН угадывать, был ли объект получен при восстановлении.
