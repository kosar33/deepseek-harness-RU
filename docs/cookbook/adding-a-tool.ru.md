# Справочник по созданию инструментов

[English](adding-a-tool.md) | [中文](adding-a-tool.zh.md) | Русский

Справочник по контрактам, которым обязан удовлетворять инструмент, обращённый к модели. Для первого инструмента в упорядоченном виде пройдите руководство [«Создание инструмента»](../user/develop/basic/tool.ru.md). `packages/shell/tool-bash` — пример промышленного качества из трёх пакетов.

## Минимальная форма

```ts
import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'my-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'read_file',
    description: 'Read a file from disk.',          // what the model sees
    parameters: {
      path: { type: 'string', required: true, description: 'Absolute path' },
      limit: { type: 'number' },                     // optional by default
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args, exec) {
      // args is TYPED from the schema: { path: string; limit?: number }
      // exec carries immutable identity + token; signal is the operational field
      return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
    },
  }))
}
```

Регистрация основана на эффектах: освобождение ресурсов fiber плагина снимает инструмент с регистрации. Схемы автоматически попадают в сборку системного промпта.

## Правила контракта execute()

- **Аргументы проверяются за вас.** `defineTool` проверяет порождённые моделью `arguments` по единому `ParameterSchemaSpec` до запуска `execute` (типы, обязательные ключи, литеральные ограничения, объединения «ровно один» и вложенные значения — [валидация аргументов в рантайме](../../.agents/notes/implemented/architecture/2026-06-11-runtime-arg-validation.md)), поэтому внутри `execute` аргументы соответствуют `InferArgs`. Явные объектные узлы объявляют `additionalProperties: true | false`; неявный корень параметров остаётся открытым. Ограничения, которые DSL не выражает, — например непустые строки, положительные числа или межполевые правила, — вы по-прежнему проверяете вручную. Инструменты с сырой JSON-Schema, зарегистрированные напрямую, сами владеют валидацией входа.
- **Регистрация заимствует ваше readonly-определение.** Типизированный внутрипроцессный вклад — не граница сериализации; после регистрации не изменяйте его схему и не подменяйте callbacks. `schemas()` материализует только явную проекцию, обращённую к модели. Чтобы горячо заменить инструмент, освободите ресурсы владеющего эффекта и зарегистрируйте замену; изменяемое состояние внутри замыкания callback остаётся обычным состоянием плагина.
- **Идентичность исполнения защищена.** Реестр материализует `arguments` как отсоединённый lossless JSON за один рекурсивный проход, замораживает это значение до старта политик и назначает непрозрачный `exec.token`; `callId`, `name`, `arguments`, `agent`, `token`, обязательный `signal`, которым владеет вызывающий, и необязательный токен `parent` объемлющего транспорта остаются неизменными на всём протяжении диспетчеризации. `parent` служит только идентификацией и не раскрывает живое внешнее исполнение. Обращайтесь с `args` как с readonly-входом. Изменяемый вид получает только обёртка вокруг диспетчеризации, и она может заменить и вернуть обязательный `exec.signal`, чтобы навязать дедлайн, но не может его убрать.
- **Объявляйте и возвращайте одно каноническое значение JSON.** `output.schema` использует `ValueSchemaSpec` и может иметь корень-объект, массив, скаляр или null. `execute` возвращает только выведенное значение; реестр делает его снапшот как lossless JSON, проверяет, замораживает и передаёт в `output.render(args, value)`. Не возвращайте блоки содержимого из тела и не заставляйте вызывающих разбирать прозу ради идентификаторов и полей.
- **Бросок исключения или возврат недопустимого значения означают `isError`.** Реестр перехватывает броски и локализует сбои схемы, рендерера, проектора метаданных и lossless JSON до запуска наблюдателей. Бросайте исключения при сбоях инфраструктуры. Успешный доменный исход представляйте в каноническом значении, даже когда его Native-рендерер объясняет неидеальное состояние, например ненулевой код выхода процесса.
- **Уважайте `exec.signal`.** Отменяйте выполняющуюся работу, когда сигнал срабатывает.
- **Проецируйте долговечные данные карточек через `presentationMeta` (необязательно).** `output.presentationMeta(args, value)` выводит воспроизводимый JSON из того же канонического значения. Ядро сохраняет его на `tool/result` и передаёт в `presentResult`, поэтому карточке, которой нужны факты момента результата, — например применённые куски diff от `write`/`edit`, — воспроизведение доступно без сохранения канонического значения. Проектор пропускается для вложенных диспетчеризаций Code, потому что у тех нет карточек.
- **Используйте `exec.agent` для асинхронных уведомлений.** `agent.inject({ content, source: { kind: 'plugin', plugin: '<name>' } })` добавляет долговечный контекст, который увидит СЛЕДУЮЩИЙ запрос модели, — это не пробуждение (незанятый агент остаётся незанятым). Защищайтесь от освобождённых агентов (try/catch).

## Долго выполняющаяся работа

Ограждайте `run_in_background` конфигурацией производителя, затем регистрируйте через `ctx.jobs.start({ kind, label, owner: exec.agent, run })`. Реестр отвергает заранее прерванный вызов ещё до тела производителя; рантайм проверяет владение и доступность контроллера задач до того, как `run()` начнёт работу, затем предоставляет идентификатор, сессионную ограду, общие управляющие инструменты, уведомления и очистку со стороны владельца. Успешная фоновая ветвь возвращает типизированный канонический дескриптор вида `{ kind: 'background', jobId }`; его Native-рендерер может сохранять человеческую прозу вроде `started background job bash-1`, но Code Mode никогда не должен разбирать эту прозу ради восстановления идентификатора.

Производитель предоставляет синхронный `cancel`, неотвергающий `done`, который завершается после очистки ресурсов, и необязательный читающий `readOutput` с форматированием ограниченного вывода. Заранее прерванный вызов — отказ, потому что не существует задачи, чей идентификатор мог бы удовлетворить успешной выходной схеме. После того как `ctx.jobs.start()` опубликовал идентификатор, используйте сигнал отмены, которым владеет задача, а не `exec.signal`: последующая отмена внешнего вызова перестаёт дожидаться вызова, но не убивает опубликованную работу; за то время жизни отвечают `job_kill`, освобождение ресурсов владельцем и остановка сервиса. Работа на переднем плане остаётся связанной с `exec.signal`. См. [Agent Note о рантайме фоновых задач](../../.agents/notes/implemented/architecture/2026-06-20-generic-long-running-tool-runtime.md) и `dsh-tool-bash` как производителя потока.

## Политика исполнения и наблюдение

Предпочитайте не встраивать политику развёртывания в инструмент. Используйте `tools/pre-execute` для расширяемой политики allow/deny/ask ([пример шлюза разрешений](extension-cookbook.ru.md#плагин-хук-пример-шлюза-разрешений)), `ctx.tools.guard()` для финального монотонного запрета, который последующие слушатели не могут отменить, `tools/execute`, чтобы обернуть диспетчеризацию дедлайном, повтором или сбором метрик, `tools/post-execute`, чтобы заменить содержимое представления или возвращаемое значение, заблокировать результат или добавить обращённый к модели контекст, и `tools/result`, чтобы наблюдать неизменяемый нормализованный исход. Замена содержимого оставляет программный доступ к `value` нетронутым; политика конфиденциальности блокирует или заменяет значение. Реализация песочницы тоже может работать внутри реализации исполнителя инструмента; [README `dsh-tools`](../../packages/core/tools/README.md#extension-points) определяет входы, порядок, возвращаемые значения и поведение при сбоях каждой точки расширения.

## Code Mode достаётся вашему инструменту бесплатно

В [Code Mode](../../packages/core/tools/README.md) каждый видимый зарегистрированный инструмент доступен как `await tools.<name>(args)` без дополнительной интеграции. Порождаемые `ToolArgsMap` и `ToolOutputMap` выводят точные типы аргументов и канонического возврата из тех же схем, а вызовы вновь входят в обычный конвейер исполнения. Успешный вызов разрешается в финальное каноническое значение JSON после политик, а не в отрисованный Native-контент. Неудачный вызов отвергается настоящим `ToolCallError`; программы могут читать только его поля `name`, `toolName` и человекочитаемое `message`, но не внутренние коды ошибок и не объединение отказов.

Проектируйте `output.schema` как полезный программный API: возвращайте дескрипторы и поля напрямую, допускайте корни-скаляры, массивы и null, когда они честно отражают значение, и держите человеческое объяснение в `output.render`. Промежуточные значения локальны для исполнения, не персистируются и не обрезаются промптом, и у них нет байтового предела, поэтому честные пределы получения данных у производителя и память процесса по-прежнему важны. Только журналы и результат внешнего `run_code` пересекают настраиваемый предел вывода и обращённый к модели конвейер spill.

## Как ваш инструмент отображается в UI

`output.render` вашего инструмента возвращает обращённый к модели контент; его **карточка UI** — отдельная забота, объявляемая чистыми проекциями представления и необязательными методами `presentCall` / `presentResult`. Проектируйте их вместе с каноническим значением. Инструмент без UI-представления откатывается к общей карточке (заголовок = имя инструмента, сырые аргументы как вход).

Оба метода возвращают **намерение рендера с тегом `card`** — выберите вид карточки, отвечающий тому, что делает ваш инструмент:

- `presentCall(args)` → `ToolCallView` (карточка PENDING):
  - `{ card: 'generic', title, kind?, rawInput?, content?, locations? }` — вариант по умолчанию. Задайте `kind` для иконки (`read`/`search`/…); задайте `locations: [{ path, line? }]` для каждого файла, которого касается инструмент, чтобы способный редактор следовал за ним / переходил к нему.
  - `{ card: 'terminal', title, description?, cwd? }` — ваш вызов И ЕСТЬ команда shell. `title` — сама команда, `description` отображается над карточкой терминала. (tool-bash.)
  - `{ card: 'diff', title, diffs, locations? }` — ваш вызов создаёт или изменяет файл. `diffs: [{ path, oldText, newText }]` (`oldText: null` для нового файла) отображается карточкой встроенного diff. (tool-fs `write`/`edit`.)
- `presentResult(args, { content, isError, meta? })` возвращает завершённую карточку:
  - `generic` предоставляет необязательные заголовок и содержимое.
  - `terminal` предоставляет сырой вывод и необязательные метаданные выхода; каждый UI отображает свой полноценный или резервный вид.
  - `diff` предоставляет применённые куски, обычно выводимые `output.presentationMeta` и переносимые в персистентный `result.meta`, чтобы воспроизведение их повторяло. Мутирующие инструменты сохраняют результат-diff, потому что завершённый вид заменяет ожидающую карточку.
  - `search` предоставляет результат обнаружения, восстановленный из персистентного `result.meta`: сгруппированные по файлам совпадения (`shape: 'matches'`, grep) либо плоский список путей (`shape: 'paths'`, glob), плюс `truncated`/`total`, чтобы UI никогда не выдавал усечённый результат за полный. Вид не несёт текста результата (UI без карточки поиска откатывается к сырому содержимому результата), и вида вызова `search` нет — ожидающее состояние вызова обнаружения остаётся общей карточкой, поскольку совпадения существуют только после `execute`. (tool-fs-search `grep`/`glob`.)
  - `web` предоставляет завершённое веб-извлечение, различаемое полем `kind: 'search' | 'fetch'` (структурированные источники поиска либо сводка fetch) и выводимое из `result.meta`; оно не несёт текста тела, поэтому UI без возможности `web` откатывается к сырому содержимому результата. (tool-web `web_search`/`web_fetch`.)

Жёсткие правила (нарушение мгновенно даёт о себе знать):

- **Чистота.** Они исполняются и на живой потоковой передаче, И на ВОСПРОИЗВЕДЕНИИ журнала сессии, поэтому обязаны быть чистыми функциями от `args` (+ результата) — БЕЗ I/O, БЕЗ чтения состояния сессии, БЕЗ часов и случайностей. Diff выводится из аргументов (`write` использует `oldText: null`, потому что презентер в момент вызова не располагает прежним содержимым файла); контекст сессии поставляет адаптер UI, а не инструмент. Если внутри `presentCall` вам захотелось достать прежнее содержимое файла или рабочий каталог — остановитесь: место этим данным в долговечных метаданных результата или в адаптере, а не в презентере.
- **Форматирование только для UI не попадает в результат модели.** Ограда ` ```console `, diff, относительный путь — ничто из этого не должно попадать в каноническое значение или Native-контент лишь ради обслуживания UI. `output.render` владеет обращённой к модели прозой; `presentationMeta` плюс презентеры карточек владеют воспроизводимым состоянием UI. Вид результата `terminal` несёт сырой вывод, а любой резервный каркас добавляет адаптер.
- **`defineTool` мягко проверяет путь отображения.** Искривлённые или устаревшие залогированные аргументы заставляют обёртку вернуть `undefined` (общий резерв), а не бросить исключение, — отображение никогда не должно рушить воспроизведение.

Нейтральный словарь живёт в `dsh-tools`; инструменты никогда не импортируют тип UI или транспорта. Рантаймы host/client отображают каждый тег `card` в собственный вид. Замысел и обоснование — в [Agent Note об объединении намерений рендера](../../.agents/notes/implemented/architecture/2026-07-02-tool-render-intent-union.md); `dsh-tool-fs` (generic/diff) и `dsh-tool-bash` (terminal) — эталонные реализации.

## Проверка

Следуйте [тестовой политике репозитория](../testing.md) и тестовой документации владеющего пакета. Выпущенное изменение, видимое модели или UI, требует собранного покрытия, оговорённого там.
