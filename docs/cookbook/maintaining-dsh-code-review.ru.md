# Сопровождение скилла dsh-code-review

[English](maintaining-dsh-code-review.md) | [中文](maintaining-dsh-code-review.zh.md) | Русский

Скилл [`dsh-code-review`](../../.agents/skills/dsh-code-review/SKILL.md) поддерживается актуальным одним назначенным оператором, запускающим приватный периодический инструмент сопровождения. Этот cookbook — входная точка для того оператора, для любого, кто принимает роль, и для контрибьюторов репозитория, желающих понять, почему обновления скилла приходят небольшими периодическими PR, а не разовыми аудитами. Сам воркфлоу специфицирован в [Agent Note о сопровождении скилла с человеческим ревью](../../.agents/notes/proposed/process/2026-07-13-human-review-skill-maintenance.md).

## Что получает сопровождающий

Оператор запускает обёртку вручную, ежедневно с перекрытием в два UTC-дня; ручной недельный восстановительный запуск использует семидневное окно. Воркфлоу:

1. Он отбирает PR, слитые в выбранном окне (по умолчанию два UTC-дня для дневной каденции, семь для недельной), чей merge-коммит достижим из `origin/master`. PR с недостижимым merge-коммитом (стековые ветки, чей родитель был сквошнут) или превышающие лимит приобретения в 250 коммитов пишутся в `skipped-pulls.json` и пропускаются, а не прерывают запуск.
2. Он собирает до-merge обратную связь человеческого ревью с привязкой к коммитам (инлайн-комментарии и сабмиты ревью), затем сравнивает патчи PR на момент фидбека с финальными приземлёнными патчами. Он не приобретает комментарии обсуждения PR, потому что текущее состояние GitHub не может дать им устойчивый к force-push базлайн времени фидбека, и исключает изменения только целевой ветки из свидетельств принятия.
3. Два независимо сконфигурированных адаптера-ревьюера классифицируют, кто написал каждый пункт и приняло ли изменение его, затем классифицируют пункты, принятые по согласию обеих сторон, против текущего скилла.
4. Основной адаптер составляет полный переработанный `SKILL.md`; оба адаптера рецензируют один и тот же дифф; блокирующие находки зацикливаются, пока оба не одобрят.
5. `pnpm run doc-sync` и `pnpm run lint` прогоняются на кандидате, прежде чем инструмент объявит успех.

Каждый запуск хранит свои артефакты на машине оператора. Сохранённый дифф, кандидат `SKILL.md` и манифест продвижения попадают под `~/dsh-code-review-outputs/` с именами по метке времени. Манифест записывает исходный коммит master и blob скилла, ID и URL исходного фидбека, диапазоны приземлённых свидетельств, вердикты адаптеров и результаты гейтов; сырой по-адаптерный I/O остаётся в приватном временном каталоге, чей путь пишется в уведомление и в ежедневный лог под `~/Library/Logs/dsh-code-review-maintainer/`. Сам maintenance-worktree восстанавливается в чистое состояние после каждого запуска, чтобы у оператора не было соблазна править maintenance-копию на месте.

## Что оператор делает с диффом-кандидатом

Когда запуск производит кандидата, приходит уведомление macOS с подсказкой `dsh-code-review-promote <timestamp>`.

1. **Читайте дифф по его собственным достоинствам.** Не полагайтесь на «ревьюеры одобрили»: контракт сопровождающего состоит в том, что финальное решение принимает оператор. Ищите разрастание чеклиста, историческую прозу, неподкреплённую экстраполяцию из одного инцидента и дублирование покрытия с существующим скиллом или авторитетной документацией.

   ```sh
   ls ~/dsh-code-review-outputs/                         # every candidate ever produced
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.diff
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.SKILL.md
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.manifest.json
   ```

2. **Сверяйте с артефактами запуска.** Манифест продвижения отображает каждое предлагаемое правило на исходный фидбек и приземлённое свидетельство; детальный по-адаптерный I/O, консенсус и принятые свидетельства живут в приватном временном каталоге запуска (путь показан в логе). Выборочно проверьте хотя бы одного кандидата: действительно ли связанный человеческий комментарий поддерживает добавленное правило? Действительно ли связанный PR его принял?

3. **Примите одно из трёх решений:**
   - **Отбросить.** Удалите сохранённого кандидата. Инструмент заново рассмотрит тот же фидбек при следующем запуске согласно тому, что тогда будет говорить текущий скилл.

     ```sh
     rm ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.{diff,SKILL.md,manifest.json}
     ```
   - **Отложить.** Приберегите кандидата, если обновление маленькое и могло бы объединиться с будущим. Проверка исходного скилла всё равно применяется; перезапустите анализ или вручную выполните rebase и заново рецензируйте дифф, если сначала изменится `master`.
   - **Продвинуть.** Из чистого чекаута `master` репозитория запустите хелпер продвижения. Он обновляет `master`, проверяет, что текущий скилл совпадает с записанным исходным blob, применяет сохранённый дифф и открывает draft PR, чьё тело перечисляет URL или ID исходного фидбека, диапазон приземлённых коммитов, породивший запуск, проверки и правки оператора. Он останавливается при дрейфе скилла, а не перезаписывает более новое руководство; оператор всё равно рецензирует PR на GitHub и либо вливает его, либо закрывает.

     ```sh
     cd ~/path/to/deepseek-harness   # clean master
     dsh-code-review-promote 2026-07-16T02-00-00Z
     ```

4. **Не коммитьте вывод адаптеров дословно.** Небольшие правки при продвижении — уплотнение формулировок, удаление примера, который обретает смысл только в контексте исходного PR, вливание правила в существующее — ожидаемы и сохраняют «суждение ревьюера», на котором держится воркфлоу. Выполните amend ветки перед слиянием.

## Когда запуск не производит кандидата

Это обычный случай после того, как каждая непустая стадия классификации дала хотя бы один валидный результат адаптера. Инструмент записывает «no candidate» в ежедневный лог, не шлёт уведомления (во избежание усталости от оповещений) и идёт дальше. Дни без обновления скилла — это воркфлоу, ведущий себя правильно, а не затык.

## Прерывания и передача роли

Механизм живёт на одной машине. Прерывания, которые оператор разбирает по мере возникновения:

- **Пропущен ежедневный запуск.** Двухдневное окно перекрытия само ловит один пропущенный день; более длинные разрывы восстанавливаются ручным запуском обёртки с `DSH_CODE_REVIEW_SINCE=<Nd>`. Перекрывающиеся окна идемпотентны: руководство, уже присутствующее в текущем скилле, классифицируется как `covered` и не входит кандидатом повторно.
- **Отказ провайдера адаптера.** Инструмент отказывается запускаться, когда две команды ревьюеров резолвятся в побайтно идентичные исполняемые файлы. Одиночный батч, чей ответ адаптера проваливает валидацию схемы или id, фейл-клозится на уровне батча (каждый пункт батча помечается как неясный), и запуск продолжается; сырой вывод сохраняется для отладки. Если какой-либо адаптер не даёт валидного результата ни для одного непустого батча в операции, запуск падает, пишет запись об отказе и уведомляет оператора; он никогда не схлопывает полный отказ провайдеров в «no candidate».
- **Передача другому сопровождающему.** Откройте последующий Agent Note, superseding текущий: либо перенесите механизм в репозиторий, либо зафиксируйте приватную настройку нового оператора. Не передавайте инструмент молча — именно «bus factor единственного сопровождающего» из раздела Risks Agent Note требует задокументированного решения при передаче.

## Где живёт приватная настройка оператора

Исходники инструмента, адаптеры-ревьюеры, учётные данные провайдеров и планировщик — приватная инфраструктура оператора, вне этого репозитория по замыслу (см. раздел «Where the mechanism lives» Agent Note). Этот cookbook и Agent Note описывают, **что** воркфлоу гарантирует; **как** эти гарантии реализованы — вопрос частной инфраструктуры. Если вы новый оператор, секции `## Proposal` Agent Note — спецификация, под которую вы строите.
