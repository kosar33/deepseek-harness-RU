# Ответ на ревью в цепочке стековых PR

[English](responding-to-pr-review-on-a-stack.md) | [中文](responding-to-pr-review-on-a-stack.zh.md) | Русский

Комментарии ревью могут целить в несколько PR зависимого стека (`A ← B ← C …`). Держите эту цепочку связанной через официальную функцию stacked-PR GitHub. Это руководство владеет размещением и распространением исправлений по ревью; скилл [dsh-merging-stacked-prs](../../.agents/skills/dsh-merging-stacked-prs/SKILL.md) владеет проверками связности и приземлением.

## Основные правила

1. **Один worktree на ветку PR.** Исправления каждого PR происходят в его собственном worktree; параллельные исправления никогда не делят один чекаут.
2. **Объект стека GitHub авторитетен.** Базовые ветки устанавливают ожидаемый порядок зависимостей, а `PullRequest.stack` и `stackEntry.position` доказывают, что GitHub его признаёт. Не считайте совпадающую цепочку веток официальным стеком, не проверив эти поля.
3. **Исправление приземляется на PR, ВНЁДРИВШИЙ проблему, затем течёт вверх по стеку.** Когда комментарий на PR `B` указывает на код, внесённый `B`, чините на `B` и распространяйте `B` в `C` — даже если `C` тоже несёт файл. Рождение исправления ниже по стеку оставляет `B` с неисправленным кодом и скрывает исправление от ревьюера `B`.
4. **Каждое ревью-исправление остаётся отдельным коммитом.** Последующий rebase может сменить его OID, но не amend'ьте отревьюенное исправление из истории ветки. Amend — только собственную ещё не запушенную и не отревьюенную работу.
5. **Выбирайте merge-forward или rebase обдуманно.** Обе истории допустимы после ревью. Перезаписанный push **ДОЛЖЕН** быть защищён lease и **ДОЛЖЕН** прерваться, а не перезаписать параллельно продвинутую удалённую голову; голый `--force` запрещён.

## Разбирайте комментарии через стек

1. Триажьте каждый комментарий по существу до действий: сверьте утверждение с кодом — ревьюер, указывающий на верный симптом, всё же может неверно диагностировать причину.
2. Отобразите каждую принятую находку на породивший её PR и исправьте там.
3. Распространите исправленный слой через каждого затронутого ребёнка по порядку:
   - **Merge-forward:** влейте исправленную родительскую ветку в её ребёнка, провалидируйте ребёнка и продолжайте вверх. Сохраняйте каждый незавершённый чекпоинт согласно [решению об инкрементальном переназначении базы](../../.agents/notes/implemented/process/2026-07-26-incremental-pr-base-retargeting.md).
   - **Нативный каскадный rebase:** используйте `gh stack rebase`, провалидируйте перезаписанные слои, затем публикуйте через `gh stack push`; либо используйте `gh stack sync`, который может опубликовать первым и потому требует немедленной пост-синхронизационной валидации по [dsh-pre-push-checks](../../.agents/skills/dsh-pre-push-checks/SKILL.md).
4. Относитесь к делегированным исправлениям как к «доверяй, но проверяй»: отчёт суб-агента описывает намерение, не обязательно то, что приземлилось. Перепрогоните гейты сами на реальном дереве, а для регрессионной защиты докажите, что она ПРОВАЛИВАЕТСЯ на нечиненном коде (внесите регрессию, увидьте красное, откатите) — защита, проходящая в обе стороны, не защищает ничего. Суб-агент, переформулирующий проблему как уже решённую, — сигнал копнуть лично.
5. Отвечайте в ветке ревью (`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`), а не комментарием верхнего уровня, называя исправление и текущий коммит или голову, которые его несут.
6. После любого перезаписанного push перечитайте неразрешённые треды, аппрувы, mergeability и проверки. OID force-пушнутого коммита или устаревший инлайн-анкор — не актуальное свидетельство того, что находка остаётся resolved.
7. Приземляйте только через официальную процедуру стека. Если PR ещё не связаны, скилл приземления автоматически связывает цепочку одного автора, спрашивает перед связыванием разных авторов и жёстко останавливается, когда нативная поддержка стеков недоступна.

## Проверьте

- Текущий дифф каждого исправленного PR содержит задуманную коррекцию на слое, внёсшем проблему.
- GraphQL сообщает один официальный стек в ожидаемом порядке, и дифф каждого ребёнка против его родителя показывает только изменения этого ребёнка.
- Неразрешённые треды, аппрувы, mergeability и проверки были перепроверены после каждого перезаписанного push.
- Релевантные гейты проходят на каждом затронутом PR стека, а не только на верхнем.
