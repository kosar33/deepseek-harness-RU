# Руководство по разработке

[English](development.md) | [中文](development.zh.md) | Русский

Туториал по установке проводит нового контрибьютора от предварительных требований до проверенного checkout'а. Далее справочник контрибьютора охватывает структуру репозитория, ежедневный рабочий процесс и организацию CI. Обоснование решений и детали реализации принадлежат связанным Agent Note и скриптам.

## Туториал по установке

### Предварительные требования

- Node.js поддерживает 22.19+ и 24+. CI покрывает 22.19, 24 и 26; см. [Agent Note о минимальной версии Node](../.agents/notes/implemented/process/2026-07-06-node-engine-floor.md).
- pnpm с включённым Corepack. Репозиторий пинит `pnpm@11.7.0` в `package.json`; выполните `corepack enable`, если `pnpm --version` не резолвится через Corepack.
- Git 2.26 или новее; настройка хуков включает worktree-специфичное расширение конфигурации Git.
- Опционально: ключ DeepSeek API для демо Web, headless и ACP-автоматизации и для e2e-тестов с реальным API.

### Первичная настройка

Установите зависимости из корня репозитория:

```sh
pnpm install
```

Установка также настраивает worktree-локальные хуки Lefthook и Git merge-драйвер `dsh-translation-pairing` через `scripts/install-lefthook.mjs`. Контракт безопасности hook-путей задаёт [Agent Note о worktree-локальных хуках](../.agents/notes/implemented/process/2026-07-27-worktree-local-lefthook.md); merge-драйвер задаёт [Agent Note об автоматических pairing-слияниях](../.agents/notes/implemented/process/2026-08-08-automatic-translation-pairing-merges.md).

Если какая-то из интеграций отсутствует, потому что зависимости восстанавливались из кэша или `postinstall` был пропущен, установите их вручную:

```sh
node scripts/install-lefthook.mjs
```

Если обёртка отклоняет существующую конфигурацию Git или сообщает об устаревшем lock, следуйте её диагностике и связанному Agent Note, а не правьте метаданные worktree наугад. После переноса checkout'а перезапустите обёртку, чтобы регенерировать принадлежащий ей путь.

После свежего клона один раз запустите проверку типов:

```sh
pnpm run typecheck
```

Настройка завершена, когда `pnpm run typecheck` проходит успешно.

## Справочник контрибьютора

### Структура TypeScript-проектов

Репозиторий использует изолированные агрегаты Host и Client. Обычный пакет зарегистрирован ровно в одном агрегате: Host-пакеты в `tsconfig.host.json`, Client-пакеты в `tsconfig.client.json`.

| Файл | Роль | Образует программу? |
|---|---|---|
| `tsconfig.json` | Корень solution: `extends` базы, `files: []` и ссылки на два агрегата. Это точка обнаружения tsserver и точка входа для явного запуска полного графа Project Reference; через унаследованный `paths` это также конфигурация резолюции для tsx, запускающего `examples/` и `scripts/`. | Нет |
| `tsconfig.host.json` | Агрегат Host: Host-пакеты, примеры, тесты, скрипты, website и исключительный Host-проект `api/remotes`. | Да |
| `tsconfig.client.json` | Агрегат Client: пакеты `packages/client/*` и их тесты, `apps/web` и исключительный Client-проект `api/remotes`. | Да |
| `tsconfig.base.json` | Общие compilerOptions и исходная карта `paths`. Также фасад резолюции, на который указывают конфиги vitest через vite-tsconfig-paths: у него нет `include`, поэтому его `paths` применяются к каждому импортёру. | Нет |
| `tsconfig.base.client.json` | Браузерные настройки компилятора (`jsx`, DOM-библиотеки, `types: []`), которые расширяются агрегатом Client и каждым пакетом `packages/client/*`. | Нет |

Host и Client остаются двумя агрегатными программами, потому что обе стороны declaration-merge интерфейс `Context` cordis под одними ключами с разными сервисами; одна программа, увидевшая оба слияния, сообщает коллизию. Коллизия существует только внутри `ts.Program` — резолюция модулей никогда её не вызывает, — поэтому solution может ссылаться на оба агрегата, а один paths-фасад может охватывать обе стороны. Из этого следуют три дисциплины:

- `tsconfig.base.json` никогда не получает `include` или `files`: они утекли бы в каждый расширяющий пакетный проект и сузили бы универсальный охват фасада.
- Скрипт, строящий репозиторный `ts.Program`, явно использует в качестве стартового проекта `tsconfig.host.json` или `tsconfig.client.json` — никогда корневой solution, потому что объединение обоих агрегатов в одной программе вызывает коллизию слияний `Context`.
- Новый пакет регистрируется ровно в одном агрегате. Наличие одновременно Node loader-точки входа и браузерной — не причина делить пакет; обычный Client-плагин производит оба рантайм-артефакта во время фазы сборки Client.

`api/remotes` — единственный пакет репозитория с раздельными Host- и Client-tsconfig. Его Host-вход обязан участвовать в Typert-графе Host, а Client-вход импортирует декларации `/remote`, которые Host tsdown должен сгенерировать раньше. Поэтому `tsconfig.json` в корне пакета — только solution, а два агрегата и прямые потребители ссылаются соответственно на `tsconfig.host.json` или `tsconfig.client.json`. Гейт workspace-`constraints` обходит достижимый граф Project Reference и проверяет собственную грань компилятора каждого ссылающегося проекта: цель с единственным конфигом остаётся валидной с любой грани, а раздельная цель должна называть соответствующий лист, а не корень solution или противоположный лист; он обнаруживает раздельные пакеты по наличию обоих листовых конфигов, так что новый раздельный пакет подключается к гейту автоматически. Не копируйте эту структуру в другие пакеты; [README `api-remotes`](../packages/api/remotes/README.md) объясняет разделение Host/Client и порядок сборки.

Корневая сборка следует сгенерированному порядку зависимостей:

```sh
tsc -b tsconfig.host.json
tsdown --env.DSH_BUILD_FACE host
tsc -b tsconfig.client.json
tsdown --env.DSH_BUILD_FACE client
pnpm run build:web
```

Оба прохода tsdown используют один и тот же полный шаблон воркспейса. Они не сканируют артефакты сборки в поисках Client-пакетов и не ведут список фильтрации Host/Client-пакетов. Пакетно-локальные tsdown-конфиги выбирают входные точки для текущей фазы через `DSH_BUILD_FACE`: обычный Client-плагин производит и свой Node loader, и браузерный бандл во время фазы Client; `api-remotes` использует `hostPhase: true`, чтобы произвести свой Host-вход заранее, и во время фазы Client — только браузерный бандл. Tsdown использует только JavaScript, эмитированный в `lib/types` предыдущей фазой tsc.

Typert запускается только во время Host tsdown со стартовым проектом `tsconfig.host.json`. Он анализирует типы Host и генерирует и reflection-артефакты Host, и проекцию Host-for-Client Remote; Client tsdown Typert не запускает. Как следствие, `pnpm run typecheck` проходит полную lib-фазу Host перед Client tsc, а `pnpm run build` продолжается через Client tsdown и сборку Web. Это решение о порядке фиксирует [Agent Note о сборке сгенерированного контракта API Remotes](../.agents/notes/implemented/process/2026-08-08-api-remotes-generated-contract-build.md).

`pnpm run build` встраивает точное окружение `DSH_CLIENT_*` вызывающего и не использует публичных клиентских значений, когда те не заданы. `pnpm run build:official` — кроссплатформенный локальный эквивалент сборки артефактов CI и релиза. Каждый успешный полный сборочный проход пишет gitignored-запись, связывающую эти значения с выводом Vite и динамическими клиентскими бандлами; упаковка релиза и built Web-тесты отвергают отсутствующую запись или артефакты, изменённые более поздней частичной сборкой.

Статический анализ и тесты резолвят воркспейс-импорты через базовую карту `paths` в `src` и должны проходить на чистом дереве; гейты, использующие собранный вывод `lib/`, объявляют эту зависимость явно. Сгенерированные декларации Host-for-Client Remote — сознательное исключение: публичные команды `typecheck`, `lint` и `doc-typecheck` генерируют их первыми, а внутренние скрипты `*:contracts-ready` предполагают, что вызывающая публичная команда или гейт планировщика уже зависит от прохода генерации контрактов Typert или полной сборки. Настройку двух агрегатов см. в [Agent Note о корне solution](../.agents/notes/implemented/process/2026-07-22-tsconfig-solution-root-two-aggregates.md), владение эмиссией tsc-first — в [Agent Note ts-build-config](../.agents/notes/implemented/process/2026-06-17-ts-build-config.md), а контракт подготовки гейтов — в [Agent Note о Typert Remote](../.agents/notes/implemented/architecture/2026-08-02-typert-remote-method-calls.md).

Бизнес-сервисы объявляют вызываемые методы на Host через `@Remote` или `@RemoteScope`; сборка Host генерирует типы и рантайм-вклады Host-for-Client, а композиция `api-remotes` на Client загружает эти вклады под пространствами имён `ctx.remote` и скоупленным `agentCtx.remote`. Сгенерированные артефакты обеих сторон, их взаимосвязи при сборке, SRC-фолбэк для разработки и порядок сборки Web описаны в [API Gateway](api-gateway.md).

Если относящаяся к делу локальная проверка использует собранный вывод пакетов, сначала один раз соберите:

```sh
pnpm run build
```

`pnpm run hygiene` включает `publint`, проверяющий точки входа пакетов против собранных файлов `lib/*.js`, и `verify-node-next-types`, проверяющий собранные декларации против временного NodeNext-потребителя. Свежий worktree не содержит ни bundled JS, ни деклараций, пока не выполнен `pnpm run build`; обычные коммиты и пуши не требуют этой сборки, если выбранные проверки её не используют.

### Переменные окружения

Адаптер реального API DeepSeek и демо агентов, работающих по ключу, читают учётные данные из окружения или из gitignored `.env` в корне репозитория:

```sh
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_BASE_URL=https://... # optional
```

`DEEPSEEK_BASE_URL` опционален и по умолчанию указывает на публичный API. Никогда не коммитьте настоящие учётные данные. Наборы e2e с реальным API автоматически пропускаются, когда `DEEPSEEK_API_KEY` не задан.

### Интеграции Git

Pairing merge-драйвер выводит конфликтную запись `.i18n.yaml` из подтверждённого предка, текущего и противоположного owner-blob'ов, когда оба языковых файла используют текстовую стратегию Git по умолчанию и сливаются чисто. При конфликтах owner-blob'ов, нетекстовой merge-конфигурации или невалидных записях он отказывает; после уже остановленного слияния выполните `pnpm run resolve-translation-pairing-conflicts` — команда стейджит каждую безопасную парную запись и завершается неуспехом, если другие pairing-конфликты ещё ждут ручной работы. Точные файлы и состояния, которые принимает драйвер, перечислены в [контракте двуязычной документации](i18n/README.md#the-pairing-contract).

Инсталлятор проверяет конкретную точку входа драйвера Node/tsx, прежде чем публиковать worktree-конфигурацию. Если этот рантайм позже оказывается недоступным, независимый от Node лаунчер пишет обычный текстовый результат Git, оставляет sidecar неразрешённым и печатает путь восстановления; восстановите зависимости и выполните `pnpm run resolve-translation-pairing-conflicts` либо выполните `git merge --abort`. Если `pre-merge-commit` отклоняет в остальном чистое слияние, Git оставляет весь результат стейджнутым без коммита; почините причину и выполните `git commit` либо прервите слияние. Точные состояния индекса и `MERGE_HEAD` задаёт [Agent Note об автоматических pairing-слияниях](../.agents/notes/implemented/process/2026-08-08-automatic-translation-pairing-merges.md#failure-contract).

lefthook сконфигурирован в `lefthook.yml` как быстрый локальный чекпоинт:

- `pre-commit` сверяет стейджнутые парные записи против стейджнутых owner-blob'ов, валидирует стейджнутые файлы профилем без привязки к проекту `.oxlintrc.staged.json` и применяет исправления Oxlint с одним ограниченным ретраем, регенерирует `THIRD_PARTY_NOTICES.md`, когда среди стейджнутых файлов есть один из его входов, проверяет стейджнутый дифф на whitespace-ошибки и запускает проверку vendor-манифеста.
- `pre-merge-commit` выполняет ту же index-backed проверку парности до того, как Git создаст автоматический merge-коммит.
- `pre-push` выполняет `pnpm run typecheck`, который завершает lib-фазу Host, включая сгенерированные контракты Typert, до проверки типов Client.

Проверка vendor-манифеста удостоверяет, что изменения под `vendor/*/src` стейджатся вместе с соответствующим обновлением манифеста `vendor/README.md`. Перед правкой вендоренного кода см. `vendor/README.md`.

Помимо скоупленной проверки стейджнутых парных записей хуки намеренно не запускают тесты, снапшоты, проверки документации, сборки или hygiene. Контрибьюторы один раз запускают [проверки, относящиеся к изменившемуся поведению](../AGENTS.md#run-relevant-checks-locally); за исчерпывающее покрытие, смоуки собранных артефактов и матрицу совместимости Node 22.19, 24 и 26 отвечает CI.

Контрибьюторы могут включить полный набор локальных гейтов через `pnpm run check:all`. Команда независима от Git-хуков и не является инструкцией агенту.

### Гейты CI

Безключевой CI-воркфлоу ([ci.yml](../.github/workflows/ci.yml)) группирует независимые гейты в широкие lane'ы и запускает меньший сигнал совместимости по поддерживаемым версиям Node. Потребители артефактов ждут одну сборку внутри своего lane'а. Отдельный воркфлоу реального API выполняет `pnpm run test:e2e` с привязанным настроенным воркером. Актуальную опись гейтов и заданий см. в [scripts/run-gates.ts](../scripts/run-gates.ts) и файлах воркфлоу.

### Ежедневные команды

Корневые [инструкции контрибьютора](../AGENTS.md#commands) суммируют частые команды, а [`package.json`](../package.json) и [scripts/run-gates.ts](../scripts/run-gates.ts) содержат актуальные описи скриптов и гейтов. Выбирайте минимальный набор проверок, покрывающих изменившуюся поверхность. Для правок документации используется `pnpm run doc-sync`; правки поведения, публичного на уровне пакетов, также обновляют владеющий README или JSDoc, а проверки собранных артефактов требуют сначала `pnpm run build`.

### Демо

Перед использованием этих демо из checkout'а исходников отдельно выполните сборку репозитория:

```sh
pnpm run build
```

Одноразовый Headless coding-агент требует `DEEPSEEK_API_KEY` в окружении или корневом `.env` репозитория:

```sh
pnpm dsh --profile headless "summarize this workspace"
```

Самореферентное демо cordis умеет инспектировать и менять свой живой плагинный рантайм и требует тех же учётных данных (по умолчанию `web`, либо `acp`):

```sh
pnpm run demo:cordis
```

ACP-сервер автоматизации предоставляет свежие сессии агентов поверх JSON-RPC stdio и тоже требует `DEEPSEEK_API_KEY`:

```sh
pnpm run demo:acp
```

### Маркеры TODO

Помечайте известные проблемы в коде одним из трёх тегов комментариев, упорядоченных по срочности:

- `FIXME` — проблема, которая должна блокировать новый релиз. Релиз не должен выходить с открытым `FIXME`, если ревьюеры явно не согласились, что изменение можно слить и так.
- `TODO` — проблема, которую следует исправить в ближайшее время, когда появятся ресурсы.
- `XXX` — проблема, которую мы можем починить когда-нибудь; низший приоритет, без обязательств.

Выбирайте тег по срочности, чтобы любой, кто просматривает код, отличал блокер релиза от «когда-нибудь, может быть».

### Документирование типов дословно (`ts type-equiv`)

Страницы [подсистем](subsystems/README.md) вставляют эквивалентные исходнику декларации вместе с их оригинальным JSDoc, чтобы читатель видел точное определение типа и исходный контракт. Чтобы вставка не расходилась с источником при его изменении, оформите блок как ` ```ts type-equiv ` (вместо ` ```ts `) и зарегистрируйте его в `scripts/type-equiv.manifest.json` с указанием зеркалируемых исходного файла и символа:

```json
{ "doc": "docs/subsystems/session.md", "symbol": "SessionEvent", "source": "packages/core/session/src/types.ts" }
```

`pnpm run verify-type-equiv` (часть `doc-sync`) затем извлекает декларацию символа и приложенное JSDoc из источника парсером TypeScript и утверждает, что блок совпадает с обоими. Для класса, чьи тела реализаций не должны попадать в каталог, используйте ` ```ts public-api ` и задайте `"projection": "public-api"`; проверяемая проекция сохраняет публичные поля, конструктор, аксессоры, методы и оригинальный JSDoc класса и членов, опуская тела и приватные либо защищённые члены. Сравнение игнорирует whitespace и комментарии вне JSDoc, но требует наличия каждого оригинального JSDoc-комментария, включая документацию членов, чтобы читатель видел исходный контракт рядом с точным определением типа. Гейт требует взаимно-однозначного соответствия по документу, символу и проекции между основными блоками и записями манифеста; парный блок `.zh.md` переиспользует запись несуффиксированного соседа, только если вся отслеживаемая последовательность блоков байт-в-байт идентична и одинаково упорядочена. `doc-typecheck` применяет то же производное правило к компилируемым блокам, исключая оба вида source-equivalence-блоков и из компиляции, и из расчёта своей доли opt-out. Когда вы меняете документируемую декларацию или её JSDoc, гейт падает, пока вставка не будет обновлена; добавляя или убирая основной блок, обновите манифест тем же изменением.
