# Постмортем 0001: сервер ACP падал при подключении — `export default` отбрасывал `inject` плагина

[English](0001-acp-default-export-drops-inject.md) | [中文](0001-acp-default-export-drops-inject.zh.md) | Русский

Статус: разрешён (исправление в PR #41 `feat/acp-2-bridge`)

## Краткое резюме

Две ошибки интеграции сломали ACP вопреки полному юнит-покрытию: дефолтный экспорт заставлял загрузчик выбрасывать `inject`, а отслеживаемое чтение необязательного сервиса падало через теневую границу. Смонтированные вручную тесты обходили оба пути. Исправления добавили покрытие реальным загрузчиком без ключа API и пакетные правила для экспортов плагинов и доступа к необязательным сервисам.

## Сводка

ACP-сервер (`examples/acp-agent`, `@deepseek-ai/dsh-acp`) падал в момент, когда реальный редактор (Zed) подключался: первый запрос `session/new` возвращал `Internal error: cannot get property "agents" without inject`, а `session/load` — то же самое для `sessionPersistence`. Мост был полностью неработоспособен в продакшене несмотря на 178 зелёных юнит-тестов и 100% покрытие строк. За одной и той же строкой ошибки прятались два независимых бага, и тестовый набор пропустил оба по одной и той же причине: каждый тест монтировал плагин через путь, который не задействовал ни то, как плагин реально загружается, ни то, как реально разрешаются его сервисы.

## Влияние

ACP-сервер не мог создать или загрузить ни одной сессии — а это два RPC, которые редактор вызывает первыми. Любой, кто подключал агента к Zed, получал немедленный жёсткий отказ. Потери данных не было (до падения ничего не сохранялось); вся цена — «функциональность не работает» плюс время на отладку, чтобы выяснить почему, причём заплатили его дважды.

## Хронология

- Мост (RFC 010) пришёл с полным юнит-набором для кодека, транспорта в памяти, сгенерированных сообщений протокола, путей отказа и HMR; e2e с реальным API, требующим ключа; и e2e чистоты stdout без ключа. Всё зелёное, покрытие 100%.
- Реальная сессия в Zed мгновенно упала на `session/new` с ошибкой `cannot get property "agents" without inject`.
- Расследование сначала двигалось по теории Cordis о «traceable/shadow» (правдоподобно, и механизм реален — см. Баг №2), затем инструментировало фактический обход fiber в вендоренном `reflect.ts` и запустило реальный субпроцесс. Трассировка показала бросок на строке 179 в `apply()` *в момент загрузки плагина*, на ROOT-fiber без всякой тени — это опровергло теневую теорию для `session/new`.
- Найдена первопричина №1: лишний `export default apply`. Его удаление починило `session/new`.
- Это же удаление затем обнажило Баг №2: `session/load` продолжал бросать исключение на `sessionPersistence` — действительно отдельный механизм (теневой обход), что подтвердилось изоляцией исправления и повторным запуском реального субпроцесса.

## Первопричина №1 — `export default apply` отбрасывает `inject` плагина (ломала `session/new`)

`packages/acp/acp/src/index.ts` — *плагин-пространство имён*: он экспортирует `name`, `inject`, `Config` и `apply` отдельными именованными экспортами, как делает каждый другой плагин репозитория (`invariants`, `llm-deepseek`, `tool-bash`, `tui`, …). Но у него *также* оказалась одна лишняя строка, которой не было больше ни у кого:

```ts ignore-check
export const name = 'acp'
export const inject = ['agents', 'sessions', 'sessionPersistence']
export function apply(ctx: Context, config: AcpConfig): void { /* … */ }
// …
export default apply   // ← the bug
```

Когда плагин загружается из `cordis.yml`, загрузчик cordis нормализует импортированный модуль через `Loader.unwrapExports` (`vendor/loader/src/index.ts`):

```ts ignore-check
unwrapExports(exports: any) {
  if (isNullable(exports)) return exports
  exports = exports.default ?? exports        // ← prefers `.default`
  if (!exports.__esModule) return exports
  return exports.default ?? exports
}
```

При наличии дефолтного экспорта выражение `exports.default ?? exports` разрешается в **голую функцию `apply`**. У голой функции нет ни свойства `inject`, ни `name`, ни `Config` — все они жили *рядом*, именованными экспортами на пространстве имён модуля, а разворачивание до `.default` выбросило пространство имён прочь. Затем загрузчик построил fiber плагина с пустым `inject`.

Как следствие, `apply` исполнялся в fiber **без внедрённых сервисов**. Самая первая его строка, `const agents = ctx.agents`, обошла дерево fiber (ROOT → Include → Loader → ROOT) и, не найдя `agents` ни в одном хранилище fiber и дойдя до корневого fiber (`runtime === null`), бросила `cannot get property "agents" without inject`. Падение случилось *во время загрузки*, а не в более позднем обработчике запроса — запрос просто оказался тем, что инициировало загрузку в трассировке этого сбоя.

**Исправление:** удалить `export default apply`. Тогда загрузчик использует пространство имён модуля, учитывает `inject`/`name`/`Config`, и `apply` исполняется внутри fiber, который действительно выдаёт объявленные сервисы.

## Первопричина №2 — чтение необязательного сервиса спотыкается о inject-охранник через traceable-тень (ломала `session/load`)

С исправленной №1 `session/new` заработал, но `session/load` всё ещё бросал `cannot get property "sessionPersistence" without inject`. Этот случай *как раз* является механизмом traceable/shadow в Cordis, и его стоит понять точно.

`session/load` вызывает `agents.resume(...)`, который делегирует в `AgentLoop.resume()`, который читает `this.ctx.sessionPersistence`. Статический `inject` у `AgentLoop` намеренно НЕ включает `sessionPersistence`: внедрение заставило бы неперсистентные демо вечно ждать бэкенд, который никогда не загрузится. Сервис предоставляется отдельным соседним плагином/fiber и читается по мере доступности.

Доступ к сервисам в Cordis идёт через прокси контекста (`vendor/cordis/src/reflect.ts`). Когда метод сервиса вызывается через *traceable-прокси*, полученный от чужого fiber (здесь: fiber моста вызывает `ctx.agents.resume`, а реестр возвращает `this.factory` — `AgentLoop`, — заново завёрнутый свежим traceable-прокси, привязанным к вызывающему), `createShadowMethod` (`vendor/cordis/src/utils.ts`) перепривязывает `this` к *теневому* объекту, чей `ctx` несёт `[symbols.shadow]`, указывающий на собственный контекст конструирования `AgentLoop`. Внутри `resume`, таким образом, `this.ctx.sessionPersistence` разрешается так, что обработчик прокси начинает обход fiber от теневого fiber:

```ts ignore-check
// reflect.ts get handler
let fiber = (ctx[symbols.shadow] as Context ?? ctx).fiber   // ← starts at AgentLoop's fiber
while (true) {
  const impl = fiber.store?.[prop]
  if (impl) return getTraceable(ctx, impl.value)
  if (prop in fiber.inject) { /* inactive-context error */ }
  if (!fiber.runtime) throw error                            // ← reached root, throw
  if (fiber.parent[symbols.isolate][prop] !== key) throw error
  fiber = fiber.parent.fiber                                 // ← ancestor-only
}
```

Обход идёт **только по предкам**. `sessionPersistence` нет ни в fiber-хранилище `AgentLoop` (его нет в `static inject`), ни у какого предка на пути к корню (он живёт на *соседней* ветке), поэтому обход доходит до корневого fiber и бросает исключение.

Почему этого не поймали тесты возобновления in-memory `AgentLoop`? Потому что они вызывают `ctx.agents.resume(...)` прямо из тестового кода — *вне какого-либо plugin-fiber'а*. Там `ctx.fiber.runtime` равен `null`, поэтому обработчик прокси уходит в ранний обходной путь:

```ts ignore-check
if (!ctx.fiber.runtime) return ctx.reflect.get(prop, false)   // ← direct global-store lookup, no fiber walk
```

`ctx.reflect.get(name, false)` — прямой поиск в глобальном хранилище сервисов, где ключом служит isolate-символ: он полностью игнорирует топологию fiber и находит сервис. Поэтому из верхнеуровневого теста чтение работает, а изнутри настоящего plugin-fiber'а, достигнутого через тень, — бросает исключение. Мост — ровно второй случай.

**Исправление:** читать необязательный сервис через `ctx.get('sessionPersistence')`, что использует глобальное хранилище с ключами isolate, сохраняя проверки активного состояния. Прямые обращения к свойствам остаются уместными для сервисов из объявленного набора внедрения плагина.

## Почему каждый тест это пропустил (настоящий провал)

Оба бага делят один корневой пробел процесса: **ни один тест не прогонял плагин ни через его реальный путь загрузки, ни через его реальную топологию вызовов.**

- In-memory harness монтирует мост, вручную собирая объект плагина: `ctx.plugin({ name, inject, apply })`. Это подставляет `inject` вручную, поэтому воспроизвести Баг №1 такой монтаж не может в принципе — `unwrapExports` вызывается только *загрузчиком*, никогда `ctx.plugin`. Даже `ctx.plugin(NamespaceImport)` не поймал бы его.
- Тот же harness монтирует всё плоско на одном корневом контексте, поэтому resume `AgentLoop`, достигнутый оттуда, либо исполняется верхнеуровнево (обходной путь `!runtime`), либо через тень, чьё происхождение всё равно разрешается на корне, — маскируя провал обхода предков в Баге №2.
- Единственный e2e без ключа слал `initialize` и проверял чистоту stdout. `initialize` никогда не доходит до фабрики, поэтому он проплыл мимо обоих багов.
- Единственный тест, гонявший `session/new`/`session/load`, требовал ключа, поэтому CI (без ключа) его пропускал — а локально он «проходил» лишь потому, что устаревший собранный `lib/` (со старым кодом) случайно удовлетворял разрешению модулей.

100% покрытие строк выполнялось всё это время. Покрытие доказывает, что строки *исполнялись*; оно ничего не говорит о том, работает ли функциональность *так, как поставляется*.

## Добавленные ограждения

- **Удалён `export default apply`** (`packages/acp/acp/src/index.ts`) — исправление Бага №1.
- **`AgentLoop.resume` читает `this.ctx.get('sessionPersistence')`** (`packages/core/agent-loop/src/index.ts`) — исправление Бага №2, с комментарием, объясняющим ловушку теневого обхода.
- **E2e для `session/new` без ключа поверх реального stdio** (`examples/acp-agent/tests/acp.e2e.ts`): поднимает пример как субпроцесс через настоящий загрузчик и утверждает, что `session/new` разрешается. На Баге №1 это громко падает и без ключа API. Проверено, что тест падает, если вернуть `export default apply`.
- **`TSX_TSCONFIG_PATH` в spawn'е e2e**: субпроцесс исполняется из временного cwd, где tsx не может найти карту `paths` из tsconfig корня репозитория поиском вверх, — поэтому импорты dsh-* молча откатывались к собранному `lib/`. Указание tsx на tsconfig репозитория делает разрешение независимым от cwd и гарантирует, что тест исполняет *исходники*, а не потенциально устаревшую сборку.
- **Правило в [docs/testing.md](../testing.ru.md)**: «тестируйте настоящий путь входа», покрытие строк — не покрытие поведения — кодифицирует урок для каждого будущего плагина.

## Уроки

- Плагин-пространство имён и дефолтный экспорт взаимоисключают друг друга под загрузчиком cordis. Выбирайте форму пространства имён (`name`/`inject`/`Config`/`apply`) и не добавляйте `export default` — `unwrapExports` отбросит пространство имён.
- Для сервиса, который плагин читает по мере доступности, но НЕ объявляет в `static inject`, используйте `ctx.get(name)` и никогда `ctx.<name>`. Прокси свойств разрешается обходом fiber только по предкам; этот обход падает через чужую тень. `ctx.get(name)` — топологически независимый поиск (и строгий по умолчанию: неактивный бэкенд читается как `undefined`, а не выдаётся посреди teardown'а).
- Тест, конструирующий плагин вручную, не может проверить, как плагин загружается. Хотя бы один тест обязан гнать настоящий путь загрузки и экспорта end-to-end. Когда главная операция не вызывает модель, такому тесту не нужен ключ API — значит, ему место в CI, а не за ключевым гейтом.
- Доверяйте трассировке, а не теории. Изящное объяснение про тень было реальным, но оказалось *вторым* багом; *первым* была однострочная ошибка экспорта, которую `console.error` в обходе fiber нашёл за минуты после часов правдоподобных, но неверных рассуждений.
