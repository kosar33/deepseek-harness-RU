# Упаковка и установка плагина

[English](publish.md) | [中文](publish.zh.md) | Русский

Предыдущие туториалы загружали локальный плагин через оверлей `--patch`. Этот туториал упаковывает его в устанавливаемый **бандл**, устанавливает в **профиль** командой `dsh plugin add` и объясняет порядок слоёв, определяющий итоговую композицию. Предполагается, что CLI `dsh` установлен. Сначала завершите [конфигурацию плагина](./config.ru.md).

Чтобы вместо этого использовать свежий checkout исходников, пройдите раздел [запуска из исходников](../../../../README.ru.md#запуск-из-исходников), оставьте каталог `hello-plugin` этого туториала в корне репозитория и выполняйте остальные команды `dsh ...` оттуда как `pnpm dsh ...`. Сборку и поведение лаунчера см. в [исполнении из исходников](../../../../apps/cli/reference/README.md#source-execution).

## Два понятия, два манифеста

Установка строится на двух понятиях. Оба описываются `package.json`, но несут под ключом `dsh` разные типы манифестов и отвечают на разные вопросы:

- **Бандл** — это npm-пакет, поставляющий слой конфигурации. Его манифест объявляет `dsh.bundle`, отвечая на вопрос «что вносит этот пакет?»: patch-файл, вставляющий или переопределяющий строки плагинов.
- **Профиль** — это каталог под `$DSH_HOME/profiles/<name>`, описывающий одну запускаемую композицию. Его манифест объявляет `dsh.profile`, отвечая на вопрос «какие бандлы составляют эту конфигурацию и в каком порядке?».

Бандл — то, что вы создаёте и распространяете; профиль — то, с чем пользователь загружается командой `dsh --profile <name>`. Ничто не является тем и другим одновременно.

### Манифест бандла

Создайте каталог пакета:

```sh
mkdir -p hello-plugin
```

```
hello-plugin/
├── package.json       # declares dsh.bundle
├── cordis.patch.yml   # the layer applied when a profile lists this bundle
└── index.js           # plugin modules the patch rows reference
```

Создайте `hello-plugin/package.json`:

```json
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

Создайте `hello-plugin/index.js` с точкой входа плагина:

```js
export const name = 'hello-plugin'

export function apply() {
  console.log('[hello-plugin] plugin loaded!')
}
```

Создайте `hello-plugin/cordis.patch.yml`. Патч — это YAML-массив, как оверлеи `--patch`, которые вы писали, только строки плагинов ссылаются на пакет по имени, а не по относительному пути к исходнику, чтобы разрешение модулей Node нашло установленный код:

```yaml
- insert:
    - id: hello
      name: dsh-hello-plugin
```

Пакет без объявления `dsh.bundle` всё равно установится, но только как обычная зависимость: `dsh plugin` напечатает предупреждение и не активирует ни один слой. Такой формат пакета используйте для библиотеки, которую импортируют пакеты-плагины, а не для плагина, который включают пользователи.

### Манифест профиля

Каталог профиля содержит два файла:

- `package.json` — внешние зависимости плагинов профиля (управляются pnpm) плюс манифест `dsh.profile` с упорядоченным списком `bundles`.
- `cordis.patch.yml` — собственный патч-слой пользователя, применяемый после каждого слоя бандлов.

Манифест профиля вы никогда не пишете вручную: его создаёт и поддерживает `dsh plugin`. Результат показан в следующем разделе.

## Установка в профиль

`dsh plugin --profile <name> <args...>` перенаправляет команды в pnpm внутри каталога профиля, поэтому работает каждая подкоманда pnpm. Из каталога, содержащего `hello-plugin`, установите checkout пакета:

```sh
dsh plugin --profile demo add ./hello-plugin
```

При первом использовании профиль инициализируется (с `@deepseek-ai/dsh-base` в качестве первого бандла), pnpm линкует checkout, а `dsh` дописывает бандл в `dsh.profile.bundles`, потому что пакет объявляет `dsh.bundle`:

```json
{
  "name": "dsh-profile-demo",
  "private": true,
  "dependencies": {
    "dsh-hello-plugin": "link:/path/to/hello-plugin"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "dsh-hello-plugin"
      ]
    }
  }
}
```

Проверьте слой без запуска, затем запустите dsh:

```sh
dsh --profile demo --dump-config   # shows a "# == dsh-hello-plugin" layer
dsh --profile demo
```

`dsh plugin --profile demo remove dsh-hello-plugin` убирает и зависимость, и слой.

## Порядок загрузки

Итоговая конфигурация собирается поверх пустого корня последовательным применением:

1. Каждый бандл-патч, названный в списке `dsh.profile.bundles` профиля, в порядке списка — сначала `@deepseek-ai/dsh-base`, затем каждый установленный бандл в порядке добавления.
2. Собственный `cordis.patch.yml` профиля.
3. Домашний `$DSH_HOME/cordis.patch.yml` — локальные для машины предпочтения, общие для всех профилей.
4. Каждый оверлей `--patch <path>`, в порядке argv.

Аргументы приложения — не дополнительный патч-слой. surface-бандл может разрешить их через обычный сервис, принадлежащий приложению; см. ниже.

Побеждает поздний слой построчно, причём патч заменяет значение `config` строки целиком, а не сливает ключи рекурсивно. Два следствия для авторов бандлов:

- Ваш патч может переопределять строки ранних слоёв по `id` — так же, как [бандл `dsh-web-app`](../../../../packages/bundle/web-app/cordis.patch.yml) переопределяет строки `dsh-base`, — но обязан повторить каждый нужный строке ключ, а не только изменённый.
- Пользователи могут переопределить ваши строки в `cordis.patch.yml` своего профиля, не трогая ваш пакет, поэтому предпочитайте значения по умолчанию, которые пользователи, скорее всего, оставят, а остальное несите в схеме.

Имена встроенных бандлов всегда разрешаются из самой установки dsh; pnpm управляет только внешними пакетами, поэтому ваш бандл может полагаться на присутствие и актуальность `@deepseek-ai/dsh-base`.

## Дайте поверхностному бандлу собственную командную строку

Бандл, определяющий запускаемое приложение, монтирует обычный плагин-провайдер:

```yaml
- id: hello-startup
  name: 'dsh-hello-plugin/startup'
```

Плагин экспортирует `inject = ['cmdlineArgs']`, вызывает `parseCmdline` из [`@deepseek-ai/dsh-cmdline`](../../../../packages/boot/cmdline/README.md) со своей программой commander и предоставляет принадлежащий приложению сервис из действия программы. Лаунчер передаёт каждому плагину один и тот же неизменяемый снапшот аргументов после флагов лаунчера, поэтому специфичные для приложения флаги не требуют изменений лаунчера, и несколько плагинов могут парсить этот снапшот. Строке Loader не нужны маркер лаунчера или особый тип.

Строки, настраиваемые этими аргументами, внедряют сервис провайдера и читают его из собственных опций `!!js`, со значением развёртывания рядом как fallback:

```yaml
- id: my-app
  name: '@example/my-app'
  inject: [myAppStartup]
  config:
    port: !!js ctx.myAppStartup.port ?? 8080
```

При `--help` провайдер не публикует сервис, поэтому такие строки никогда не активируются. Loader монтирует композицию один раз, ждёт обычных внедрений каждой строки и только затем вычисляет `!!js`-конфигурацию строки против её внедрённого контекста.

## Установка с GitHub: ловушка build-скрипта

Публикация в реестр не обязательна — пользователи могут устанавливать прямо с git-хостинга:

```sh
dsh plugin --profile demo add github:you/hello-plugin
```

Но git-установка забирает **исходники, а не собранные артефакты**: никто не запускает ваш скрипт `build`, поэтому TypeScript-пакет оказывается без вывода `lib/` и не загружается. Нужно две вещи, по одной с каждой стороны:

- **Автор** поставляет скрипт `prepare` — pnpm запускает его после git-установки, — который собирает публикуемые точки входа из исходников самодостаточно: он не должен полагаться на dev-контекст вроде соседнего checkout монорепозитория. [turtle-ui](https://github.com/deepseek-harness/turtle-ui) — рабочий пример: его `prepare` запускает отдельную конфигурацию tsdown, которая транспилирует `src/` без project references и проверки типов.
- **Пользователь** разрешает сборку. pnpm ≥10 отказывается выполнять `prepare` git-зависимости, пока она явно не разрешена, поэтому первый `add` падает; `dsh` указывает на исправление — скопируйте точный ключ пакета, напечатанный pnpm, в `pnpm-workspace.yaml` профиля:

  ```yaml
  allowBuilds:
    dsh-hello-plugin: true
  ```

  и повторите `add`.

Считайте это разрешение тем, чем оно является: **правом исполнять код пакета на вашей машине в момент установки**, вне любой песочницы, в которой работает агент. Разрешайте только пакеты, исходникам которых доверяете, и фиксируйте коммит (`github:you/hello-plugin#<sha>`), чтобы последующий push не мог молча изменить то, что будет исполняться.

Если не хотите просить пользователей об этом разрешении, распространяйте собранные артефакты — ни одна из форм не требует прав на сборку:

- **Публикуйте в npm** с собранным `lib/` на момент `pnpm publish`; `dsh plugin add your-package` тогда установит уже собранный код.
- **Поставляйте tarball** из `pnpm pack`; пользователи выполнят `dsh plugin add ./hello-plugin-0.1.0.tgz`.
