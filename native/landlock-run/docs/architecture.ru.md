# Архитектура

[English](architecture.md) | Русский

Этот репозиторий владеет *механизмом* ограничения, а не политикой: потребители (агентские harness и возможности песочниц) решают, какие пути запуск может читать и писать, а это семейство пакетов поставляет лаунчер, приводящий выданные права в исполнение, и JavaScript API, которое разрешает его путь и общается с ним. Упаковка следует модели перплатформенных пакетов [`node-addon-require-builtin`](https://www.npmjs.com/package/@esplus/node-addon-require-builtin) (и esbuild), адаптированной с Node-аддонов на самостоятельные статические исполняемые файлы.

## Семейство пакетов из двух слоёв

Семейство — один входной пакет плюс бинарые пакеты по платформам:

- **Входной пакет** (`@deepseek-ai/node-addon-landlock-run`): ESM JavaScript. Владеет контрактом CLI инструмента — разрешением пути (`launcherPath`), функциональным probe (`probe`), построением grant-argv (`grantArgs`) и константами контракта. Возит C-исходники в своём tarball ради проверяемости. Перечисляет каждый платформенный пакет в `optionalDependencies`.
- **Платформенные пакеты** (`@deepseek-ai/node-addon-landlock-run-linux-{x64,arm64}`): один прекомпилированный статический бинарник под `bin/`, объявляющий его `prebuilds.json` — и ни строчки JavaScript. Поля `os`/`cpu` npm выбирают подходящий пакет при установке, а входной пакет разрешает его до файлового пути — импортировать нечего.

Поскольку парсер CLI и бинарник версонируются вместе в одном семействе пакетов, парсер не может отстать от версии бинарника. Именно предотвращение этого рассогласования — смысл существования разделения пакетов.

Общего loader-пакета нет: платформенным пакетам нечего загружать. Если второму инструменту когда-нибудь понадобится общий JavaScript, выделите его тогда, а не заранее.

## Разрешение пути и доступность

`launcherPath()` разрешает `@deepseek-ai/node-addon-landlock-run-<platform>-<arch>` и возвращает `<package>/bin/landlock-run`. Когда пакет неразрешим, функция возвращает детерминированный запасной путь внутри собственного `node_modules` входного пакета, которого заведомо не существует. Существование в обоих случаях намеренно не проверяется: `probe()` — единственный сигнал доступности, а отсутствующий бинарник даёт `unusable` ровно как ядро без принудительного исполнения. Потребители получают один путь деградации, а не два.

Probe функционален — лаунчер строит и применяет настоящий максимальный набор правил в короткоживущем потомке, потому что проверки версий пропустили бы ядро, у которого syscalls есть, но принудительное исполнение отказывает.

## Fail-closed во всём

При любой ошибке уровня лаунчера тот выходит с кодом `125`, не запуская команду через exec: ошибка использования, ядро без принудительного исполнения, неоткрываемый корень выдачи прав, неудавшийся exec. Частичное ограничение (старый ABI Landlock, покрывающий лишь подмножество доступов) принимается, сообщается на stderr и проявляется в probe как `partial` — потребитель решает, что обещает его словарь режимов на каждом уровне. Ни бинарник, ни входной пакет не читают переменные окружения: какой бинарник изолирует процесс, никогда не должно решаться окружающей средой.

## Модель сборки и релиза

Сборки только нативные. `scripts/build.ts` компилирует бинарники текущей архитектуры дистрибутивным `musl-gcc` (статически: никаких ожиданий loader'а или libc у потребителей, один бинарник для дистрибутивов glibc и musl); CI-раннеры по архитектурам — канонические сборщики, а кросс-тулчейна в репозитории нет. Ревью охватывает C-исходник и CI-задачу, собравшую каждый бинарник; закреплено это тремя гейтами: prepack платформенных пакетов отвергает отсутствующие или чужие по ELF бинарники, prepack входного пакета отвергает несобранную `lib/`, а релизный пайплайн сверяет установленные бинарники байт-в-байт со сборками workspace, из которых они были упакованы.

Матрица пакетов — закоммиченные метаданные (`prebuilds.json` плюс поля `os`/`cpu`); `scripts/github-matrix.mjs` выводит матрицы CI и Release из них, поэтому добавление платформы расширяет автоматизацию без правки workflow-файлов.

## Добавление платформы

Новая платформа добавляет один пакет `packages/<platform>/` (`package.json` с `os`/`cpu`, `prebuilds.json`, README, LICENSE), запись раннера в `scripts/github-matrix.mjs` и строку в [support-matrix.ru.md](support-matrix.ru.md) — и только вместе с нативным GitHub-раннером, который её собирает и доказывает её работоспособность (правило отсутствия кросс-тулчейна). Соседние лаунчеры для иных механизмов ограничения живут в собственных репозиториях по этому же шаблону, а не вторыми инструментами здесь.
