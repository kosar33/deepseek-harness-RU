# `@deepseek-ai/dsh-session-reference`

[English](README.md) | [中文](README.zh.md) | Русский

`ctx.sessionReferenceResolver` готовит ограниченные, доступные только для чтения снапшоты других сессий как обращённый к модели контекст с указанием источника. Он использует `ctx.sessionQuery` и независимый от бэкенда маркер чекпоинта компакции; SQLite FTS не требуется. Хосты, поддерживающие межсессионные упоминания, могут подключить этот сервис по собственному желанию.

## Открытый API

- `listCandidates(agent, query?, limit?)` перечисляет сессии кроме `agent.id`, фильтрует без учёта регистра по id, cwd или последнему заголовку из журнала и ранжирует записи: сначала того же cwd, затем без cwd, затем чужого cwd, сохраняя порядок создания `listSessions()` внутри каждой группы. Каждый выбранный кандидат использует этот заголовок как метку упоминания и возвращается к id сессии, когда заголовок отсутствует или нечитаем; тела сообщений не ищутся. Унарный Remote-метод `sessionReferenceResolver/candidates` даёт ту же выборку в пределах сконфигурированного лимита кандидатов и прикрепляет каноническое упоминание каждого кандидата, поэтому браузерные потребители вызывают `ctx.remote.sessionReferenceResolver.candidates` без маршрута в API Proxy.
- `prepare(agent, content, references, signal?)` сохраняет порядок первого упоминания, дедуплицирует идентификаторы, отвергает ссылку на себя и превышение сконфигурированного лимита различных источников, читает все источники параллельно и возвращает отсоединённое содержимое плюс ноль или один агрегированный, идентифицированный контекст `UserMessage`. Сервис вызывает его для канонических упоминаний в прямых сообщениях пользователя после того, как нижестоящие слушатели `agent/pre-step` примут шаг.
- `encodeSessionReferenceUri()` и `decodeSessionReferenceUri()` реализуют схему `dsh-session:<base64url(JSON.stringify(sessionId))>`, поэтому любой строковый id JavaScript проходит полный цикл кодирования-декодирования без искажений. `formatSessionReferenceMention()` испускает `@[label](uri)`, а `parseSessionReferenceText()` заменяет Markdown-упоминания или голые канонические URI читаемым текстом `@label`, попутно возвращая структурированные ссылки. Явные Markdown-упоминания отвергают любой искажённый URI; голый текст считается ссылкой, только когда за схемой следует непустой payload формы base64url, и совпадающий неканонический кандидат всё равно ведёт к отказу. Пустые или состоящие из одних знаков препинания упоминания со схемой остаются обычным текстом обсуждения.

## Семантика снапшотов

Подготовка вызывает `ctx.sessionQuery.readSurface()` по одному разу на каждый различный источник, когда целевое сообщение доходит до `agent/pre-step`. Сообщение, стоящее в очереди, поэтому фиксирует состояние источника на входе в шаг модели, и полученный контекст после этого момента неизменяем. Из свёрнутой текущей поверхности проекция оставляет только прямые пользовательские `user/message`, текст ассистента и чекпоинты `user/message`, несущие канонический маркер источника `dsh-compaction`. Сообщения session-reference с отдельным источником — это внедрённый контекст, и они исключаются, что предотвращает рекурсивное распространение снапшотов. Затенённые до компакции события, инструменты, рассуждения, прочие сгенерированные плагинами сообщения пользователя — кроме помеченных чекпоинтов компакции — и незавершённые куски ассистента тоже исключаются. Компактированный источник поэтому даёт свой последний чекпоинт плюс удержанную последующую беседу, а не восстановленный затенённый текст.

Источник контекста — `{ kind: 'session-reference', version: 1, references }`; каждая ссылка записывает id и метку своего источника, seq захвата, наличие компакции, счётчики удержанных/опущенных сообщений, опущенные байты UTF-8 и состояние усечения. Внешний слушатель `agent/pre-step` сервиса пост-обрабатывает принятые прямые сообщения пользователя, сохраняет их id сообщений и вставляет каждый снапшот сразу после цитировавшего его сообщения. Правки очереди и перенос queue-to-steer не требуют специальной для ссылок обработки, потому что разбор происходит после финального захвата inbox. Неверные упоминания, неудавшиеся чтения, отмена и провалы бюджета завершают тот ход прежде, чем его сообщения войдут в видимую модели историю. Журнал цели записывает читаемое прямое `user/message`, а следом его контекстное `user/message` с указанием источника; мутация источника после захвата не может изменить воспроизведение у цели.

## Конфигурация

| Ключ | По умолчанию | Контракт |
|---|---:|---|
| `maxReferences` | `3` | Максимум различных исходных сессий в одном подготовленном сообщении; должно быть не больше `3`. |
| `candidateLimit` | `50` | Количество кандидатов по умолчанию, возвращаемое хосту. |
| `maxReferenceBytes` | `65536` | Максимум сериализованных байтов JSON для одного объекта-ссылки. |

Удержание применяет `maxReferenceBytes` независимо к каждому источнику, сохраняет чекпоинты компакции и новейшее сообщение, прежде чем отбрасывать более старые не-чекпоинтовые единицы, и использует головное/хвостовое усечение `dsh-output-retention` с точным UTF-8-уведомлением об упущенном. Если фиксированные сериализованные поля одного источника не помещаются, подготовка падает с `SESSION_REFERENCE_BUDGET_EXCEEDED` вместо возврата частичного контекста.

## Опыт модели

### Фон упомянутых сессий

#### Что видит модель

Модель видит два подряд идущих сообщения роли user: текущее сообщение с его читаемой меткой `@label`, затем недоверенный снапшот `## Referenced sessions`. Предупреждение запрещает следовать инструкциям, заявлениям о разрешениях или просьбам вызвать инструменты из снапшота, если текущий пользователь явно не повторил их. Метки, значения cwd, идентификаторы и текст беседы сериализуются как JSON внутри тегов `<referenced-sessions>`; каждый встречающийся в данных `<` испускается беспотерным JSON-эскейпом `\u003c`, поэтому текст источника не может собрать тег обрамления.

#### Влияние на токены

Каждое упомянутое сообщение добавляет фиксированное предупреждение плюс до трёх сериализованных снапшотов, каждый из которых независимо ограничен `maxReferenceBytes`. Точный снапшот остаётся в истории цели, пока компакция цели его не затенит или не суммирует; изменения сессии-источника больше не добавляют токенов.

#### Влияние на KV-кэш

Запрос и снапшот — подряд идущие append-only сообщения цели, сохраняющие предыдущую кэшируемую историю. Другие ссылки или другое содержание захвата источника меняют лишь новый суффикс; последующая компакция цели может инвалидировать переиспользование от своей границы замены.

## Известные ограничения и отложенная работа

- **Нет поиска по телам** — кандидатные запросы смотрят свёрнутые заголовки, но не ищут в телах сообщений. Непустой запрос может инспектировать каждый видимый персистентный журнал сессий через ограниченный, отменяемый батч сервиса session-query; выделенный индекс заголовков может заменить этот путь обнаружения, не затрагивая контракты URI, снапшотов и персистентности.
- **Граница доверенного вызывающего** — сервис предполагает, что его хост авторизован читать каждую сессию, предоставляемую `ctx.sessionQuery`; он не является обращённым к модели поисковым инструментом.
- **Только текстовая проекция** — нетекстовые блоки пользователя и ассистента между сессиями не переносятся.
- **Никакой живой связи** — ссылки являются снапшотами, а не fork, возобновлениями, подписками или мутациями сессии-источника.
