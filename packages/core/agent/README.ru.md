# dsh-agent

[English](README.md) | [中文](README.zh.md) | Русский

Интерфейс агента, реестр, внутрипроцессный скоуп инициатора и словарь событий `agent/*`. Каждый плагин (UI, хуки, оркестраторы) программирует против определённого здесь дескриптора `Agent` — у того нет никакой зависимости от цикла, поэтому сам цикл заменяем.

Необязательный спутник `@deepseek-ai/dsh-agent/invariant` регистрирует проверки переходов статуса агента этого пакета в `ctx.invariants`. Корневой сервис агентов не подгружает диагностику неявно.

## Сервис: `AgentRegistry` (ключ контекста: `agents`)

Отслеживает живых агентов и проносит инициирующего Agent сквозь асинхронную работу драйверов, не импортируя конкретный пакет цикла.

### Публичный API

Регистрируемая в скоупе поверхность: `Agent.ctx` — это скоуповый контекст агента (`dsh-scope`, ключ = сам агент); через него инструменты, секции, переменные и слушатели регистрируются только для этого агента, и всё сворачивается при освобождении ресурсов. `agentEvents(ctx, agent)` — объединённый диспетчер обычных операций с субъектом-агентом (carrier и внедрённый субъект одним движением); его режим уведомления вызывает каждого слушателя и охватывает и синхронные броски исключений, и отклонения возвращённых промисов. Пара жизненного цикла реестра переиспользует один стабильный носитель маршрутизации. `assembleContextFor(agent)` собирает сборочный контекст отдельного агента (`agent` + `scope` вместе). `installModelSelection(agentCtx, selection)` снимает изменяемый выбор провайдера/модели/уровня рассуждений в снапшот во время сборки промпта, применяет его провайдера и модель к переменным промпта и применяет полный выбор к маршрутизации запроса на один шаг; отсутствующий выбранный уровень снимает унаследованный уровень, так что вступают умолчания адаптера или провайдера. `CreateAgentOptions.setup(agentCtx)` и `ResumeAgentOptions.setup(agentCtx)` компонуют скоуповый мир свежего или возобновлённого агента, пока оба объекта остаются неопубликованными. Setup — доверенный внутрипроцессный код, только композиция: управляйте агентом лишь после разрешения создания.

`AgentOptions` задаёт начальный маршрут провайдер/модель и необязательный положительный потолок вывода `maxTokens`. Конкретный цикл разрешает любой умолчательный для точной модели адаптерный потолок, записывает действующий потолок в заголовок запроса и применяет его к каждому запросу разговорной модели; явная опция агента побеждает, а её отсутствие оставляет власть за умолчанием маршрута адаптера или провайдера.

- `ctx.agents.register(agent: Agent): () => void` — записывает **уже сконструированного** агента. Освобождается вместе с fiber вызывающего.
- Расширенный упорядоченный жизненный цикл: `enter(agent, owner): () => void` требует `agent.id === agent.session.id`, выполняет авторитетную проверку коллизии идентификаторов и вставляет без объявления; `owner` явно фиксирует живое отношение создателя и агента (или `undefined` для корня), независимо от долговечной родословной сессии. `announce(agent)` испускает `agent/created` ровно один раз. Отсоединение, синхронно запрошенное слушателем создания, откладывается до распускания этой диспетчеризации, а каждое отсоединение проверяет захваченный объект записи, поэтому устаревшая возможность не может удалить позднейшую замену с тем же идентификатором. Этим разделением пользуется асинхронная фабрика; обычные плагины вызывают `register()`.
- `ctx.agents.get(id: SessionId): Agent | undefined`
- `ctx.agents.isOwnedBy(id: SessionId, owner: Agent): boolean` — создана ли именно эта живая запись через скоуповый контекст того родительского агента; владение во время исполнения независимо от долговечной родословной сессии.
- `ctx.agents.list(): Agent[]`
- `ctx.agents.roots(): Agent[]` — живые агенты, созданные без владеющего контекста агента; возобновлённая сессия с родословной всё равно может оказаться корнем времени исполнения.

#### Скоуп инициатора

`AgentLoop` проводит полное время жизни каждого конкретного драйвера внутри границы инициатора. Параллельные драйверы остаются изолированными: продолжения дочернего драйвера несут ребёнка, тогда как родительское продолжение возвращает родителя, как только `withInitiator()` вернулся; учёт drain продолжается до урегулирования Promise дочернего драйвера. Создание, загрузка персистентности и неопубликованный setup остаются вне границы ребёнка, поэтому setup, инициированный родителем, наследует родителя, пока `agentCtx.agent` явно называет ребёнка.

- `ctx.agents.currentInitiator(): Agent | undefined` — читает унаследованного инициатора, не требуя его.
- `ctx.agents.requireInitiator(): Agent` — читает его или бросает `no initiating agent is active`.
- `ctx.agents.withInitiator(agent, operation)` — исполняет операцию с одним точным Agent и сохраняет её точное синхронное значение или Promise.
- `ctx.agents.withoutInitiator(operation)` — прячет унаследованного инициатора для посторонней внутрипроцессной работы.

Скоуп несёт сам `Agent` и живёт внутри одного процесса. Присутствие в окружении — ни доказательство живости, ни полномочие; явные поля Agent остаются авторитетными на границах сервиса, воркера, процесса, персистентности и протокола. Разборка отвергает новые границы, даёт внедрённым зависимым и границам возвращённых Promise доразрешиться, затем отключает нижележащий `AsyncLocalStorage`; невозвращённая работа остаётся во владении отсоединившей её подсистемы. Если унаследованная цепочка async какой-то границы запускает выгрузку владеющего Cordis-fiber, эта вложенная цепочка границ выпускается из drain, чтобы выгрузка не могла ждать сама себя; её продолжения после разборки наблюдают уже освобождённый сервис. Подробный контракт границ и разборки описывает [решение о скоупе инициатора](../../../.agents/notes/implemented/architecture/2026-07-15-agent-initiator-scope.md).

#### Фабричный API (создание)

*Создание* агента предоставляет плагин, реализующий `AgentFactory` (`dsh-agent-loop`) и зарегистрированный через `setFactory`. Благодаря этому создание остаётся на интерфейсе `dsh-agent`: потребители (UI, мост ACP) программируют против `ctx.agents`, не завися от конкретного пакета цикла. Реестр канонизирует уже оттрассированный Service до его конкретной цели и перетрассировывает каждый вызов через контекст вызывающего; это избегает вложенных теней Cordis, передавая простым фабрикам явный привязанный к вызывающему `ownerCtx`.

- `ctx.agents.setFactory(factory: AgentFactory): () => void` — регистрирует фабрику создания (цикл вызывает это при конструировании). Вторая фабрика бросает исключение; slot очищается при освобождении ресурсов.
- `ctx.agents.create(options: CreateAgentOptions): Promise<AgentHandle>` — создаёт сессию и агента, дожидается необязательного setup в неопубликованном состоянии, затем публикует через финальные проверки `SessionStore.enter()` и `AgentRegistry.enter()`. Параллельное создание с одним идентификатором не поддерживается: готовиться может несколько операций, но войти — одна; каждый проигравший откатывает свой частный скоуп, сессию и драйвер. Необязательный `signal`, действующий только при создании, отменяет неопубликованный setup и отсоединяется до возврата дескриптора; последующая отмена идёт через `handle.dispose()` или `agent.cancel()`. Публикация покрыта откатом, и каждое доставленное ребро создания при откате получает парное. Без зарегистрированной фабрики операция отклоняется.
- `ctx.agents.resume(options: ResumeAgentOptions): Promise<AgentHandle>` — загружает персистентную сессию ([персистентность сессий](../../../.agents/notes/implemented/architecture/2026-06-14-session-persistence.md)), отчеканивает свежий неопубликованный скоуп агента, дожидается необязательного setup и использует ту же финальную последовательность публикации входа. Его необязательный `signal` тоже действует только при создании. Операция отклоняется, если фабрика не зарегистрирована или персистентность сессий не настроена.

`AgentHandle = { agent: Agent; dispose(): Promise<void> }`. Освобождающая сторона — **возможность потребителя**: наблюдатель, держащий голую запись реестра, разобрать агента не может. Fiber вызывающего и зарегистрированный провайдер фабрики — структурные совладельцы: выгрузка вызывающего требует структурированного владения, а выгрузка фабрики обязана остановить старые экземпляры, потому что их скоуповая поверхность зависимостей принадлежит этому провайдеру. `dispose()` от любого владельца приходит в одну мемоизированную границу quiescence: он останавливает цикл, дожидается его выхода, разрегистрирует агента, удаляет его сессию из хранилища и напоследок сворачивает его скоуповый мир. `ctx.agents.get(id)` по-прежнему возвращает голый `Agent`; мост ACP и внутрипроцессные subagent-бэкенды держат потребительские дескрипторы, а созданные конфигурацией агенты уже принадлежат fiber цикла.

### Живые события

`dsh-agent` объявляет живой координационный словарь `agent/*`, чтобы плагины не зависели от конкретного цикла. Точные сигнатуры, режимы диспетчеризации, правила фильтрации по скоупу и контракты полезных нагрузок живут в генерируемой области [core.ru.md](../../../docs/subsystems/core.ru.md#cordis-surface); [поток хода в архитектуре](../../../docs/architecture.ru.md#поток-хода) показывает их порядок относительно долговечных событий сессии.

У рёбер жизненного цикла есть два важных локальных предостережения. `agent/created` исполняется после скоупового setup и после существования обеих записей — сессии и реестра агентов. Setup — доверенный код только композиции; непосредственно следующее за ним уведомление `agent/session-start` без права вето — первая поддерживаемая точка инъекции при старте. `agent/disposed` всегда означает, что именно этот агент покинул реестр. AgentLoop испускает его после достижения драйвером quiescence, тогда как упорядоченная разборка ещё может отсоединять сессию и сворачивать скоуп; собственные агенты, зарегистрированные напрямую, сами владеют любым более сильным контрактом порядка драйвера.

Большинство точек перехвата — кооперативные каскады. `agent/pre-step` получает полезную нагрузку с субъектным `agent`, эксклюзивно захваченным `UserMessage[]` и предложенными `turn`, `step` и сигналом отмены `signal`; его партия может быть пустой, когда инструменты уже требуют другой запрос. Ходовые точки расширения в объёме агента несут свой явный `AbortSignal` в полезной нагрузке; остальные ходовые точки расширения получают его через значение своего запроса. Слушатели могут сотрудничать с сигналом, но **НЕ ДОЛЖНЫ** удерживать его как власть над другим ходом. `agent/request-error` — восстанавливающий каскад неудавшегося запроса к модели: он получает координаты запроса, нормализованные факты сбоя, политику повторов обслуживающей регистрации, когда она доступна, и сигнал. Слушатель, владеющий восстановлением, возвращает `{ kind: 'retry' }`, не вызывая `next()`. `agent/turn-stopping` исполняется перед закрытием хода, который иначе завершился бы. Время жизни сигнала описывает [решение об явной отмене](../../../.agents/notes/implemented/architecture/2026-07-16-explicit-turn-cancellation.md); скоуповую диспетчеризацию и финальное урегулирование описывает [Agent Note о runtime-дизайне скоупа агента](../../../.agents/notes/implemented/architecture/2026-07-12-agent-scope-runtime-design.md#three-execution-boundaries-are-deliberately-one-way).

`PreStepDecision` — либо `{ kind: 'reject' }`, либо `{ kind: 'enter', messages }`. Ветвь enter — это полная опознанная замороженная партия для предложенного шага. Слушатель, оборачивающий вход ниже по течению, сохраняет эту партию, если намеренно её не заменяет; добавления следуют естественному порядку возврата каскада. Захват уже удалил предложенные сообщения из инбокса, поэтому отказ их не удерживает. Сообщения, вставленные после захвата, остаются ожидающими до более поздней границы.

Живые уведомления инбокса нарочно помесные и минимальные: `agent/inbox/inserted { message }`, `agent/inbox/claimed { message, turn }` и `agent/inbox/discarded { message }`. Они дополняют долговечную проекцию `agent/inbox/spliced`, не добавляя ещё одного конверта жизненного цикла.

Границы ходов и шагов и поток токенов модели — долговечные факты `session/event`, а не зеркалирующие уведомления `agent/*`. Потребители читают `turn/*`, `step/*` и `assistant/chunk` из ленты сессии; наблюдение политики инструментов и исходов принадлежит полному конвейеру, документированному [`dsh-tools`](../tools/README.ru.md).

`foldConsumedWork(events)` читает эту ленту обратно ради единственного вопроса, на который последовательность ходов сама не отвечает: что стало с работой, которую поглотил журнал. Он возвращает последний `turn/end`, учитывающий поглощённую работу, — ход, вошедший в шаг модели, либо ход, захвативший вход инбокса, а затем сбойнувший, остановленный или отвергнутый до достижения шага, — плюс признак того, была ли принятая работа позже отменена из инбокса неисполненной. Оба факта берутся из журнала, поэтому отмена читается одинаково, кто бы её ни выпустил. Ход без шага, ничего не взявший, либо опустошивший свой захват и завершённый, работы не описывает и пропускается; конец `blocked` поверх захваченного входа — учётная запись, ведь отказ этот вход отбросил.

### Интерфейс агента (`types.ts`)

Дескриптор, против которого программирует каждый плагин:

- `agent.inbox` — принадлежащая агенту проекция долговечных событий `agent/inbox/spliced`. `nextTurn` и `nextStep` выставляют ожидающие значения `UserMessage`. `append`, `prepend`, `replace`, `remove`, `clear`, `splice` и `claim` их изменяют; `replace(messageId, newMessage)` и `remove(messageId)` находят ожидающее сообщение по обоим спискам. Замена может сменить идентичность и публикует старое сообщение как discarded, а следом новое как inserted. Обычные удаления и `clear()` — долговечные отмены, они испускают `agent/inbox/discarded`. `claim(target)` удаляет следующую предложенную партию чистыми deletion-сплайсами; затем цикл испускает `agent/inbox/claimed`. `MessageId` — единственная идентичность вхождения и обязана оставаться уникальной, пока сообщение ожидает.
- `agent.followup(message)` — ставит в очередь обычное сообщение `next-turn` и будит драйвер. Дескриптора завершения он не возвращает: идентификатор сообщения опознаёт факты вставки в инбокс, захвата и отбрасывания, а не последующий вывод или `turn/end`.
- `agent.steer(message)` — ставит в очередь пробуждающий вход `next-step`. Простой агент начинает ход синхронно; работающий драйвер потребляет более поздний steering на ближайшей границе шага.
- `agent.inject(message)` — ставит в очередь непробуждающий контекст `next-step`. Работающий драйвер захватит его на ближайшей более поздней границе pre-step; простой драйвер оставляет его ожидающим, пока `followup()` или `steer()` не разбудят драйвер. Он может пропустить запрос, чей pre-step уже захватил свою партию.
- `agent.cancel(cause, options?)` — отменяет активный драйвер и, если не задан `options.keepInbox`, долговечно отменяет всю ожидающую работу инбокса. Отмена в простое — отсутствие операции.
- `agent.whenIdle()` — наблюдает quiescence всего агента, включая подменяющую работу, назначенную до ухода текущего драйвера. Никакое конкретное сообщение он не урегулирует.
- `agent.session`, `agent.status`, `agent.options`, `agent.id`, `agent.ctx`

`running` описывает интервал drain в масштабе драйвера, а не доказательство, что ход ещё открыт; он может накрывать закрытие хода, чекпоинт долговечности и подряд стоящие ходы из очереди. Итогом прогона вправе назвать интервал лишь вызывающий, которому принадлежит весь интервал целиком ([решение](../../../.agents/notes/implemented/architecture/2026-07-30-followup-enqueue-and-owned-runs.md)).

### Точки расширения

- Создание агентов: `AgentLoop.create()` — конкретная реализация конфигурационного пути (в `dsh-agent-loop`), тогда как программные потребители создают и возобновляют собственных агентов через `ctx.agents.create()` / `ctx.agents.resume()`. Замените цикл, реализовав `Agent` и зарегистрировав его через `ctx.agents.register()`.
- Слушатели событий: все события `agent/*` объявлены здесь — зависимость от пакета цикла не нужна.
- Делегирование subagent — не метод `Agent`; провайдеры создают или ведут обычные дескрипторы через фабричный API, поэтому транспорты делегирования остаются вне ядра интерфейса агента.

## Model Experience

### Сообщения пользователя, steering и внедрённые сообщения

#### What the model sees

`send`, `steer` и `inject` питают владеющую сессию. `agent/pre-step` и прочие объявленные события позволяют плагинам отвергнуть предложенный шаг или добавить долговечный материал запроса; сам этот интерфейс никакого фиксированного текста не вносит.

#### Token effect

Принятое содержимое становится удержанной историей или повторяемым префиксом сессии; заблокированное не добавляет токенов запроса. Размер зависит от вызывающего и плагинов.

#### KV Cache effect

Принятая история и steering append-only; заблокированная подача запроса не отправляет. Префикс сессии остаётся стабильным внутри одного экземпляра цикла, тогда как новый или возобновлённый экземпляр может установить другой префикс.

### Композиция запроса в объёме агента

#### What the model sees

Регистрации через `agent.ctx` могут затенять секции промпта или инструменты и могут ставить перехватчики только-для-агента во время неопубликованного setup.

#### Token effect

Сам пакет не добавляет ни токена; скоуповые вклады касаются только этого агента и исчезают при освобождении ресурсов.

#### KV Cache effect

Стабильность префикса сохраняется, пока скоуповые регистрации агента неизменны. Setup или перезагрузка, меняющая секции промпта, определения инструментов или слушателей запроса, может сделать переиспользование недействительным начиная с первого затронутого токена запроса.

## Известные ограничения и отложенная работа

- **Скоуп инициатора живёт внутри одного процесса** — воркеры, дочерние процессы, HTTP, долговечные очереди и перезапуски материализуют любую требуемую идентичность явно.
- **Окружающая идентичность может пережить живость** — потребители по-прежнему проверяют `agent.status`, отмену и контракт владеющей возможности перед работой, чувствительной к жизненному циклу.
- **Межагентские каналы помимо делегирования** — разделяемое состояние, потоковая выдача потомка и семантика background/poll остаются вне нынешнего синхронного seam `ctx.subagents`.
- **`agent/session-start` не может привратить старт** — он остаётся синхронным уведомлением без права вето; асинхронная композиция, которая должна завершиться до публикации, вместо этого принадлежит транзакции `setup(agentCtx)` фабрики.
- **`cancel()` по умолчанию очищает инбокс** — он прерывает текущий ход плюс работу в очереди и steering; `cancel(cause, { keepInbox: true })` прерывает только ход и сохраняет ожидающие элементы. Прерывания только шага, при котором текущий ход продолжает исполняться, по-прежнему нет ([Agent Note о stop-API](../../../.agents/notes/implemented/simplification/2026-06-20-public-agent-stop-api.md)).
- **Каждый дополнительный `UserMessage` несёт ровно один `MessageSource`** — вклады нескольких плагинов, слитые в один вызов инструмента, схлопываются под одним источником, поэтому сообщение не может назвать нескольких производителей.
- **`SessionStartSource` резервирует `'clear'`/`'compact'` без эмиттера** — встречаются только `'startup'`/`'resume'`, пока не появятся движущие подсистемы (`TODO(compaction)`).
