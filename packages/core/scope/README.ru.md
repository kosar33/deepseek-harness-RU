# dsh-scope

[English](README.md) | [中文](README.zh.md) | Русский

Примитив скоупированной регистрации. `createScope(ctx, key)` создаёт помеченный контекст Cordis, чья несущая fiber владеет каждой регистрацией, сделанной через него. `scopeOf(ctx)` читает метку, а `scopeTarget(base, key)` маршрутизирует скоупированные события слушателям с тем же ключом, оставляя нескоупированных слушателей глобальными. Ключи образуют необязательную родительскую цепочку (`bindScopeParent`): представления регистрации наследуют ВНИЗ по ней — дочерний скоуп видит слои предков, ближайшее затенение перекрывает дальнее, — а допуск событий простирается ВВЕРХ — слушатель, помеченный предком, получает события ключа-потомка и никогда наоборот. Цикл агента создаёт один скоуп на каждого живого агента, а постоянный монтаж агентского пресета — родительский скоуп над его агентами, но механизм безразличен к ключам, поэтому пакеты нижних уровней могут пользоваться им, не завися ни от того, ни от другого.

## Публичный API

- `createScope(ctx: Context, key: ScopeKey, options?): Scope` Создаёт скоуп под fiber'ом `ctx`. Допускает синхронное использование (сбор эффектов регулируется uid; разрешение сервисов переходит на поверхность зависимостей создающего плагина). Типизированный внутрипроцессный ключ доверен; неактивный создающий контекст всё равно отказывает через Cordis (`INACTIVE_EFFECT`). `options.parent` привязывает охватывающий скоуп через `bindScopeParent` до того, как скоуп станет пригодным; привязка остаётся внутренней.
- `bindScopeParent(key, parent): ScopeParentBinding` / `scopeParentOf(key)` / `scopeChainOf(key)` Родительское отношение, стоящее за обоими направлениями цепочки. Привязка однократна: ключ, у которого уже есть родитель, бросает исключение, и только `rebind(parent)` возвращённой привязки может перелинковать его — операция перекомпоновки пустой сессии, корректная лишь пока ничего, произведённого под старым родителем, не удерживается (контракт держателя — это отношение не видит, что сессия залогировала). И привязка, и каждый rebind отвергают связь, замыкающую цикл. `scopeChainOf` возвращает `[key, parent, …]` от ближайшего.
- `Scope.ctx` Помеченный контекст: регистрации через него видимы в скоупе И живут его жизненным циклом. Производные контексты (`extend`, fiber, смонтированная под ним) наследуют метку; вложенные скоупы затеняют (выигрывает ближайшая метка).
- `Scope.rawDispose` Точный Cordis-диспоузер несущей fiber — составной (генераторный) эффект отдаёт ЭТУ функцию, чтобы вложить разборку скоупа в позицию yield (Cordis дедуплицирует вложенные эффекты по идентичности функции; отдача обёртки оставит скоуп освобождаться как параллельный сиблинг).
- `Scope.dispose(): Promise<void>` Идемпотентная, общая граница quiescence для каждой регистрации, сделанной через скоуп. Конкурирующие/повторные вызовы дожидаются одной и той же разборки, в том числе когда `rawDispose` первым вызвал одноразовый Cordis-диспоузер.
- `scopeOf(ctx: Context): ScopeKey | undefined` Метка, которую несёт контекст (или любой контекст, из него производный); `undefined` = глобальный для контекста.
- `scopeTarget(base: T, key: ScopeKey | undefined): Scoped<T>` Строит непрозрачный диспетчерский `thisArg` для скоуп-фильтрованного события. Он компонует существующий `Context.filter` базы со скоуп-предикатом (слушатель без метки ⇒ допущен; с меткой ⇒ допущен, только если его метка — сам ключ или его предок; `key === undefined` ⇒ только немеченые). Носитель содержит лишь состояние маршрутизации; настоящий субъект несут аргументы события. Слушатели `{ global: true }` обходят фильтрацию (семантика Cordis).
- `Scoped<T>` Бренд-носитель, непрозрачный на этапе компиляции: скоуп-фильтрованные события требуют его как тип своего `this`, поэтому диспетчеризация голым субъектом — ошибка компиляции. Параметр типа записывает тип субъекта, но не раскрывает его свойств.
- `isScopeCarrier(value)` / `carrierKeyOf(value)` Рантайм-метки носителя; dev-инварианты используют их, чтобы утверждать, что каждая скоуп-фильтрованная диспетчеризация несёт носитель, чей ключ соответствует субъекту, названному её аргументами.
- `ScopeLayer` Агрегатный контракт для полного глобального или точно-скоупового вклада одного реестра; `isEmpty()` управляет освобождением скоуповых слоёв.
- `ScopedLayers<L>` Владеют одним жадным глобальным слоем и ленивыми точно-скоуповыми слоями. `peek()` ничего не создаёт и слеп к цепочке (СОБСТВЕННЫЕ вклады скоупа — ограничения, guard'ы — не должны молча подхватывать вклад предка), `chainLayers()` возвращает существующие оверлеи от самого дальнего предка, `merge()` материализует упорядоченные по вставке именованные затенения вдоль цепочки, а `effect()` выводит видимость и владение из того же контекста, возвращая точный Cordis-диспоузер.
- `NamedEntries<V>` Упорядоченное по вставке именованное хранилище с диагностикой дубликатов, поиском и живой итерацией на стороне вызывающего внутри одного непустого поколения таблицы; опустошение таблицы отцепляет существующие итераторы от поздних вставок, а `insert()` возвращает идемпотентный точечный откат записи.
- `AnonymousEntries<V>` Упорядоченное по вставке анонимное хранилище, чьи уникальные внутренние ключи держат равные значения как независимые регистрации; оно использует ту же границу итератора опустошённого поколения, а `append()` возвращает идемпотентный точечный откат записи.

Необязательный компаньон `@deepseek-ai/dsh-scope/invariant` владеет тем рантайм-утверждением. Он использует сгенерированную карту резолвера `scoped-events.generated.ts`, чтобы требовать носитель для каждого объявленного скоупового события и — когда полезная нагрузка раскрывает свой субъект маршрутизации — требовать совпадения с ключом носителя. Генератор на основе Program выводит карту из объявлений событий и реальных вызовов `scopeTarget(base, key)`.

## Контракт дизайна

Регистрационный контекст определяет сразу видимость и владение, не позволяя регистрации быть видимой в одном скоупе, а освобождённой с другим. Скоупы маршрутизируют доверенные внутрипроцессные плагины; они не песочницы и не границы полномочий. Обоснование и нецели безопасности см. в [Agent Note об agent-скоупе](../../../.agents/notes/implemented/architecture/2026-07-08-agent-scope-contexts.md#security-and-authority-are-non-goals).

Сервисы, учитывающие скоупы, определяют конкретный `ScopeLayer`, агрегирующий их разнородные таблицы и доменные помощники. `ScopedLayers.effect()` принимает одно синхронное действие, возвращающее один синхронный откат, устанавливает этот откат перед необязательным уведомлением и освобождает точно-скоуповый слой, только когда пуст весь агрегат. `notify` по умолчанию `true`; переданный колбэк решает, бросают ли неудачи наблюдателей исключение или локализуются. `EntryValues` остаётся внутренним, классы хранилищ импортируются из корня пакета, а не из подпути `/store`, и общее хранилище не определяет фильтрацию или политику итерации конкретного реестра. См. [Agent Note об общем хранилище скоуповых слоёв](../../../.agents/notes/implemented/architecture/2026-07-12-scoped-layers-store.md).

Раздача скоупированного контекста раздаёт и API разрешения сервисов создающего плагина (разрешение идёт по цепочке зависимостей fiber'а создателя, а не держателя) — создавайте скоуп из того плагина, чьи зависимости должны разрешаться для скоупированных регистраций.

## Известные ограничения и отложенная работа

- **Состояние изолируют только API, учитывающие скоупы** — реестры обязаны вести учёт по `scopeOf()`, а события обязаны диспетчеризоваться через `scopeTarget()`; произвольный Cordis-сервис остаётся глобальным для контекста лишь потому, что вызывается через скоупированный контекст.
- **Контекст несёт один ближайший ключ скоупа** — иерархия живёт в родительском отношении уровня ключей, а не в метках контекстов; вложенные контексты скоупов всё же затеняются до одной метки, а наборы политик со множественным членством остаются неподдержанными.
- **Достижимость сервисов идёт от создателя скоупа** — раздача `Scope.ctx` раздаёт и внедрённые сервисы создающего плагина, поэтому более широкий создатель не может быть позже сужен держателем.
