# dsh-tools

[English](README.md) | [中文](README.zh.md) | Русский

Реестр инструментов и пайплайн их исполнения. Инструментальные плагины регистрируют свои схемы и исполнителей; цикл агента проводит каждый вызов через `tools/pre-execute` (расширяемый гейт allow/deny) → монотонных зарегистрированных стражей → `tools/execute` (around-обёртку диспетчеризации для плагинов таймаутов, повторов и метрик) → `tools/post-execute` (осмотр/замена результата, присоединение контекста) → принадлежащую определению границу `finalizeContent` → уведомление `tools/result`, доступное только для наблюдения. Реестр также владеет тем, КАК его инструменты предъявляются модели: его конфигурация `mode` выбирает нативный вызов функций, [Code Mode](#code-mode) или оба варианта сразу, а отдельный агент перекрывает это умолчание для себя методом `presentAs`.

## Сервис: `ToolRuntime` (ключ контекста: `tools`)

### Конфигурация

```yaml
tools:
  mode: native   # native (default) | code | both
```

`native` публикует видимые инструменты как определения функций. `code` добавляет зарезервированный транспорт `run_code`, генерируемую секцию `tools:sdk` и правило `tools:code-only`, согласно которому напрямую можно вызывать только `run_code`, — исполнитель затем обеспечивает его соблюдение, превращая прямой вызов модели любого другого инструмента в `UNKNOWN_TOOL` ещё до запуска политики; `both` добавляет обе формы и не вводит никакого такого правила, потому что его нативные вызовы действительно исполняются. Это умолчание для агентов, не объявивших собственного выбора, — пресет агента выбирает свой вариант через [`dsh-agent-tool-presentation`](../agent-tool-presentation/README.md). Зарезервированный транспорт нельзя зарегистрировать, перекрыть, ограничить или удалить, и его имя остаётся зарезервированным при любом настроенном режиме, ведь любой агент может выбрать кодовый режим. Ненативные режимы требуют `ctx.codeRuntime`, чей `language` имеет зарегистрированный рендерер SDK, — TypeScript поставляется через [`dsh-code-runtime-worker-thread`](../../code-runtime/code-runtime-worker-thread/README.md), рендерер Python встроен и работает с любым рантаймом, сообщающим `language: 'python'` (штатный бэкенд `dsh-code-runtime-python` поставляется отдельно). Язык рантайма без рендерера приводит к громкому отказу сборки промпта, а запись `systemPrompt.toolOrder` для инструмента, которого режим не добавляет, делает сборку промпта невозможной. Слушатель `system-prompt/assemble` может заменить вклады реестра; возвращённая им сборка авторитетна, поэтому именно такой слушатель отвечает за сохранение пригодного протокола Code Mode.

### Публичный API

- `ctx.tools.register(definition: ToolDefinition): () => void` регистрирует доверенное типизированное внутрипроцессное определение с обязательным каноническим объявлением `output`. Слой — это scope вызывающего контекста: обычный контекст плагина регистрирует глобально, а `agent.ctx` агента — только для этого агента, перекрывая там одноимённый глобальный инструмент. Дубликаты имён в одном слое бросают исключение; ненативные режимы вдобавок отвергают зарезервированное имя транспорта `run_code`. Отсутствующее или неподдерживаемое объявление вывода, а также неположительный или нефинитный `timeoutMs` отклоняются при регистрации. Необязательный синхронный колбэк `finalizeContent` фиксируется в снапшот при старте вызова и может заменить только финальное содержимое, адресованное модели, после нормализации каждого исхода конвейера — включая ошибку, обнаруженную при материализации другого поля результата. Освобождается вместе с fiber вызывающего.
- `ctx.tools.presentAs(mode: ToolPresentationMode): () => void` задаёт этому агенту презентацию для модели, перекрывая конфигурацию `mode` только для него; из обычного контекста он бросает исключение (общепроцессная презентация — поле конфигурации), равно как и повторное объявление в том же scope. Кодовый режим вдобавок регистрирует этому агенту его собственную секцию `tools:sdk`. Каталог не меняется — `schemas(agent)` по-прежнему сообщает о возможностях агента; схлопываются только инструменты в сборке. Освобождается вместе с fiber вызывающего.
- `ctx.tools.restrict(filter)` накладывает на глобальные инструменты маску allow/deny в объёме агента и из обычного контекста бросает исключение. Фильтр фиксируется в снапшот при регистрации; несколько масок пересекаются, а инструменты, локальные для scope, подмешиваются после. Маски deny допускают появившиеся позже глобальные инструменты, которых они не называют, а маски allow исключают все имена, добавленные позже. Неизвестные, локальные или зарезервированные имена и пустые фильтры отвергаются. Это живая композиция видимости, а не граница полномочий; см. [non-goal о безопасности и полномочиях](../../../.agents/notes/implemented/architecture/2026-07-08-agent-scope-contexts.md#security-and-authority-are-non-goals).
- `ctx.tools.get(name: string, scope?: ScopeKey): ToolDefinition | undefined` — разрешение с точки зрения одного scope (с применёнными перекрытиями; вытесненный ограничением глобальный инструмент выглядит отсутствующим); презентеры передают вызывающего агента, чтобы карточка соответствовала тому, что реально исполнилось.
- `ctx.tools.schemas(scope?: ScopeKey): ToolSchema[]` — схемы всего, что видит scope (без функций `execute`). Схемы штатных инструментов каталогизированы в [docs/tool-catalog.md](../../../docs/tool-catalog.ru.md), который генерируется загрузкой каждого инструментального плагина и сбором результатов этого метода (см. [Agent Note о каталоге схем инструментов](../../../.agents/notes/implemented/process/2026-07-02-tool-schema-catalog.md)).
- `ctx.tools.guard(guard: ToolGuard): () => void` регистрирует монотонный синхронный страж исполнения после `tools/pre-execute`: возвращённая причина запрещает вызов, `undefined` оставляет его без изменений. Страж из обычного контекста действует глобально, страж из `agent.ctx` — только на этого агента. Позднейшие слушатели каскадов не могут превратить отказ стража обратно в разрешение. Освобождается вместе с fiber вызывающего.
- `ctx.tools.execute(exec)` делает беспотерьный снапшот аргументов и замораживает их, назначает непрозрачный токен, прогоняет полный конвейер политика/диспетчеризация/результат и независимо снимает отдельный снапшот авторитетного исхода перед финальным наблюдением. Невалидные аргументы идут тем же путём результата, не достигая ни политики, ни тела. Around-обёртки могут заменять только `signal`; непосредственно перед телом реестр заново подставляет исходный сигнал вызывающего.
- `ctx.tools.executionMode(exec)` возвращает `parallel`, только когда классификатор `isConcurrencySafe(exec.arguments)` видимого определения вернул ровно `true`; неизвестная, скрытая, необъявленная, невалидная или завершившаяся исключением классификация означают эксклюзивность.

### Внедряемые сервисы

`SystemPrompt` — реестр сам подаёт свои схемы инструментов в сборку системного промпта через `ctx.systemPrompt.tools()`. Seam одобрения вместо этого используется по возможности (`ctx.get('approval')`, без статического внедрения): развёртывание без него сохраняет деградацию ask→deny, и в обоих случаях реестр остаётся работоспособным.

### Отмена

Отмена кооперативна и выполняется через quiescence. Каждое типизированное обращение передаёт принадлежащий вызывающему `AbortSignal`; тела инструментов получают его как обязательный readonly `exec.signal`, и лишь обёртки `tools/execute` могут временно заменить обязательный сигнал. Реестр сохраняет отмену вызывающего сквозь замену сигнала и никогда не перебивает гонкой уже начатый внутрипроцессный промис. Отмена до вызова тела даёт `ABORTED_BEFORE_DISPATCH`; отмена после вызова способна заменить только успешный исход на `ABORTED`. Отказ стража, падение обёртки, ошибка инструмента, сбой после политики или принадлежащий таймауту `TOOL_TIMEOUT` остаются более специфичными исходами. Заранее отменённый вход материализует и замораживает аргументы, затем пропускает все фазы политики и диспетчеризации и публикует один результат. Каждый асинхронный инструмент обязан наблюдать или пересылать сигнал и завершаться, только когда собственная работа остановлена. Полный контракт и предел жёсткого завершения описывает [Agent Note об отмене инструментов](../../../.agents/notes/implemented/architecture/2026-07-19-cooperative-tool-cancellation.md).

### События живого конвейера

Живой конвейер реестра — три преобразуемых каскада, затем принадлежащий определению финализатор содержимого, затем наблюдающее событие `tools/result`; изменения реестра намеренно остаются неотфильтрованными уведомлениями о разделяемом состоянии. Точные сигнатуры, режимы диспетчеризации, фильтрацию по scope и контракты локализации сбоев описывает генерируемая область [tools.ru.md](../../../docs/subsystems/tools.ru.md#cordis-surface), а полный порядок визуализирует генерируемый [пайплайн исполнения инструментов](../../../docs/tool-execution-pipeline.ru.md). `tools/result` — живое событие; похоже названное `tool/result` — долговечное событие сессии, которое цикл агента дописывает следом.

### Ключевые типы

- `ToolDefinition` — `ToolSchema` плюс обязательное `output { schema, render, presentationMeta? }` плюс `execute(args, exec)`, необязательные колбэки финального содержимого и презентации, кооперативный `timeoutMs` и необязательная классификация отдельного вызова `isConcurrencySafe(args)`. Тело возвращает только каноническое JSON-значение, объявленное схемой вывода, и кооперативно останавливается через `exec.signal`. `finalizeContent(exec, result)` исполняется ровно один раз для каждого нормализованного результата, включая сбои, обходящие пост-политику, и может заменить только `content`; он обязан быть синхронным и тотальным.
- `ToolExecutionInput` — переданное вызывающим описание вызова: `{ callId, name, arguments, signal, agent?, parent? }`; `signal` обязателен и readonly, вызывающий вправе передать непрозрачный токен объемлющего исполнения как `parent`, а собственный токен нового исполнения вызывающий не выбирает никогда.
- `ToolExecutionToken` — свежий брендированный `Symbol`, назначаемый реестром. Он поддерживает только корреляцию по равенству и никогда не пересекает границу модели, журнала или воркера.
- `ToolExecution` — readonly-представление конвейера: неизменяемые `{ token, callId, name, arguments, signal, agent?, parent? }`; исходный сигнал вызывающего реестр отдельно хранит и заново подставляет. `ToolDispatchExecution` — доступное только для `tools/execute` представление, чей обязательный сигнал изменяем: обёртка вправе заменить и затем восстановить его, но не удалить. `parent` вложенного вызова — это `ToolExecutionToken`, а не объект исполнения.
- `ToolRunContext` — исполнение, передаваемое телу инструмента, расширяющее `ToolExecution` методом `deferContext(context)`. Он откладывает один контекст до момента, когда финальный результат инструмента достигнет цикла, — обычно это контекст вложенной диспетчеризации, переносимый композитным инструментом, либо свежая инструкция плагинового происхождения, созданная листовым инструментом (wrap-up из `tool-goal`), — и делает это даже когда инструмент затем бросает исключение или побеждает отмена; немедленного внедрения не происходит никогда.
- `ToolExecutionResult` — дискриминированный исход в масштабе исполнения. Успех — `{ isError:false, value:JsonValue, content, meta?, additionalContexts? }`; неудача — `{ isError:true, error:{ message, info? }, content, meta?, additionalContexts? }` и значения не имеет. Идентичность вызова остаётся на неизменяемом `ToolExecution`. Реестр делает снапшот канонического значения, валидирует и замораживает его до рендеринга, а долговечные поля презентации материализует до финального наблюдения. `ToolFailure.info` несёт внутренние `{ name, code }` для `HarnessError`; `additionalContexts` сохраняет каждый отложенный либо выявленный на этапе post-execute `UserMessage` для FIFO после результата в цикле.
- `PreToolDecision` — `{kind:'allow'}` | `{kind:'deny', reason}` | `{kind:'ask', reason?}`. Переписывание входа намеренно не предлагается; `ask` обслуживается [`ctx.approval`](../../interaction/user-approval/README.md), когда тот смонтирован, иначе деградирует до deny.
- `PostToolDecision` — accept может заменить `content` или `value`, но никогда оба сразу, и может присоединить `additionalContexts`; block превращает обратную связь в неудачу без значения. Замена содержимого сохраняет каноническое значение и метаданные. Замена значения ревалидируется и перерисовывает содержимое и метаданные. Accept сохраняет отложенные инструментом контексты перед контекстами решения; block отбрасывает отложенные инструментом контексты и предоставляет только те, что явно передало блокирующее решение.
- `ToolGuard` — `(execution) => string | undefined`; возвращённая строка — финальная монотонная причина отказа, оцениваемая после переставляемого каскада pre-execute и до диспетчеризации.
- `ToolCallView` / `ToolResultView` — независимые от провайдера намерения рендера с тегом `card`, которые инструмент возвращает из `presentCall` / `presentResult`, чтобы самому решать, КАК UI отображает ЕГО вызовы (см. «Презентация UI, принадлежащая инструментам»).

### Точки расширения

- Инструментальные плагины вызывают `ctx.tools.register()` — схемы автоматически стекаются в сборку.
- `tools/pre-execute` — переставляемый гейт allow/deny/ask; `ctx.tools.guard()` добавляет после него монотонную политику владельца.
- `tools/execute` оборачивает нормализованную каноническую диспетчеризацию ради таймаута, повтора или метрик. Обёртки могут заменять только операционный сигнал; успех, созданный обёрткой, нормализуется через действующее объявление вывода инструмента. Каждый канонический результат принадлежит одному неизменяемому токену диспетчеризации, поэтому кешированный результат другого вызова или инструмента ревалидируется по активному объявлению.
- `tools/post-execute` может заменить презентационное содержимое, заменить каноническое значение, заблокировать с обратной связью или присоединить упорядоченные контексты. Затем необязательный `finalizeContent` определения отвечает за свой последний инвариант «только содержимое» как на нормальных результатах, так и при внешних сбоях конвейера; `tools/result` наблюдает неизменяемый финальный исход. Замена содержимого — не граница конфиденциальности: блокируйте или заменяйте значение, когда программные потребители не должны его получать.
- Точные сигнатуры и порядок находятся в генерируемой области [tools.ru.md](../../../docs/subsystems/tools.ru.md#cordis-surface) и [пайплайна](../../../docs/tool-execution-pipeline.ru.md).
- MCP-серверы: один плагин на сервер, обнаружение инструментов, вызов `ctx.tools.register()` со схемами сервера.

### Типизированные схемы параметров инструментов

Штатные авторы плагинов могут использовать помощник `defineTool()` (экспортируется этим пакетом) для типизированных схем параметров инструментов:

```ts
import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

declare const ctx: Context

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true, description: 'Absolute file path' },
    offset: { type: 'number' },
    limit: { type: 'number' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args, exec) {
    // args is typed: { path: string; offset?: number; limit?: number }
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))
```

Единый DSL схем использует `ParameterSchemaSpec` для неявного открытого объекта параметров и `ValueSchemaSpec` для любого корня JSON-значения. Он поддерживает `string`, `number`, `integer`, `boolean`, `null`, `array`, `object`, доступный только автору `json` и `oneOf` с ровно одной ветвью; скалярные значения `enum`/`const` проверяются на соответствие типу. Каждая явная DSL-запись декларирует `additionalProperties: true | false`, тогда как неявный корень параметров и сырой JSON Schema сохраняют стандартное открытое умолчание. Записи схем принимают только собственные перечислимые строковые ключи, а массивы схем обязаны быть плотными обычными массивами. Компиляция, валидация, отсоединение от реестра и рендеринг схема→TypeScript используют явные рабочие стеки, поэтому обработка валидных глубоких схем в рантайме ограничена памятью, а не стеком вызовов; `InferValue` сохраняет точные типы через 16 уровней контейнеров, а затем переключается на `JsonValue`, так что сам TypeScript остаётся стеково-безопасным.

Определение `defineTool` валидирует аргументы модели до исполнения и превращает отсутствующие обязательные значения, неверные примитивы, недопустимые элементы enum и вложенные нарушения в `ToolArgsError` (`INVALID_ARGS`) для обычного пути ошибочного результата. Оно также выводит тип возврата тела и чистые проекторы вывода из `output.schema`; реестр делает снапшот возвращённого беспотерьного JSON и валидирует его до презентации. Неявный корень параметров открыт; явный объект принимает лишние ключи только при `additionalProperties: true`, а закрытый объект без объявленных свойств принимает только `{}`. Сырые объекты JSON Schema остаются открытыми, пока явно не задано `additionalProperties: false`. Значения по умолчанию не подставляются; открытые объекты без `properties` и массивы без `items` получают только проверку типа контейнера. Инструменты, зарегистрированные сырыми, сами владеют валидацией входа, но по-прежнему объявляют и получают контролируемый реестром вывод.

Подробности см. в публичном API: `defineTool`, `validateArgs`, `ToolArgsError`, `ValueSchemaSpec`, `ParameterSchemaSpec`, `InferValue`, `InferArgs`, `valueSchemaSpecToJsonSchema` и `parameterSchemaSpecToJsonSchema`.

Необязательный `timeoutMs` должен быть положительным и конечным; это метаданные политики, а не видимая модели схема.

Необязательный `isConcurrencySafe(args)` получает типизированные, мягко валидируемые аргументы. Ровно `true` разрешает параллельные диспетчеризацию и исполнение тела; невалидный вход и все прочие исходы остаются эксклюзивными. Тела, выбравшие такое поведение, не мутируют состояние, принадлежащее родителю, а гонки разделяемого состояния обязаны коммутировать либо вести себя по принципу fail closed. Полный контракт безопасности описывает [Agent Note о параллельных вызовах инструментов](../../../.agents/notes/implemented/feature/2026-07-10-parallel-tool-call-execution.md).

### Обязательное подмножество сырого JSON Schema

`JsonSchemaNode` — общий сырой аналог для выводов инструментов, генерации Code Mode, субагентов и воркфлоу. Он допускает любой JSON-корень, неограниченный узел JSON, содержащий только аннотации, и `oneOf` с ровно одной ветвью; аннотации обязаны оставаться беспотерьным JSON. `assertSupportedJsonSchema()` отвергает неподдерживаемые конструкции, а `validateJsonSchemaValue()` возвращает нарушения с указанием пути. Субагенты и воркфлоу сохраняют требование объектного корня, заданное вызывающим, через `assertObjectJsonSchema()` и `ObjectJsonSchema`, а не через ограничение общего словаря.

### Презентация UI, принадлежащая инструментам

Инструменты опционально владеют чистыми намерениями рендера `presentCall()` и `presentResult()`, так что UI не заводит особых случаев по именам инструментов:

- Представления вызова — `{ card: 'generic', title, kind?, rawInput?, content?, locations? }`, `{ card: 'terminal', title, description?, cwd? }` или `{ card: 'diff', title, diffs, locations? }`.
- Представления результата — `{ card: 'generic', title?, content? }`, `{ card: 'terminal', title?, output?, exitCode?, signal? }`, `{ card: 'diff', title?, diffs }`, `{ card: 'search', shape, title?, truncated, total, … }` (завершённый поиск — совпадения, сгруппированные по файлам, для `shape: 'matches'` (grep) либо плоский список путей для `shape: 'paths'` (glob); `truncated`/`total` не дают UI выдать усечённый результат за полный; представление не несёт текста результата, и у поиска нет аналога `card: 'search'` на этапе вызова), `{ card: 'read', title?, path, offset, lines, totalLines, lang?, content? }` (завершённое чтение файла → просмотр кода с номерами строк и опциональной подсветкой синтаксиса; `offset` — первая строка окна в нумерации с единицы, сохраняется даже при пустых `lines`; `lines` — `{ number, text }[]`, хранящее настоящие номера строк файла, а `content` — текст без конверта, на который переключается UI без поддержки чтения) или `{ card: 'web', kind: 'search' | 'fetch', title?, … }` (завершённое веб-извлечение; ветви `kind` несут структурные источники поиска либо сводку fetch, а UI без возможности `web` переключается на сырое содержимое результата).

Возврат `undefined` включает универсальный запасной вариант. Презентеры зависят только от своих аргументов и долговечного результата, потому что UI вызывает их и при живой потоковой трансляции, и при воспроизведении журнала. `output.presentationMeta(args, value)` выводит JSON-метаданные для прямых верхнеуровневых вызовов; эти метаданные сохраняются вместе с `tool/result` и возвращаются в `presentResult`, тогда как само каноническое значение остаётся локальным для исполнения и никогда не воспроизводится. Вложенные диспетчеризации Code Mode метаданные не вычисляют. `defineTool` мягко валидирует аргументы из старых журнальных записей и переключается на запасной вариант, а не ломает воспроизведение. Эталонные реализации — `dsh-tool-bash` и `dsh-tool-fs`; разделение значения и презентации описывает [Agent Note о каноническом выводе](../../../.agents/notes/implemented/architecture/2026-07-20-canonical-tool-output-contract.md), а словарь карточек — [Agent Note о намерении рендера](../../../.agents/notes/implemented/architecture/2026-07-02-tool-render-intent-union.md).

### Code Mode

При `code` или `both` реестр предоставляет зарезервированный транспорт `run_code` и детерминированный SDK для текущего scope, порождаемый на языке загруженного рантайма, — рендерер выбирается по `ctx.codeRuntime.language` (`typescript` → приведённый ниже TypeScript SDK, `python` → Python SDK). SDK декларирует точные типы аргументов и канонического вывода для каждого видимого инструмента (`ToolArgsMap`/`ToolOutputMap` в TypeScript, именованные `TypedDict` в Python), и каждая привязка резолвится в каноническое JSON-значение инструмента. Каждый беспотерьный JSON-вызов привязки заново входит в полный конвейер инструментов под нативным контрактом планирования (конкурентно-безопасные вызовы могут перекрываться до `maxParallelSubCalls`; эксклюзивные исполняются в одиночку как барьеры порядка) с журнальной корреляцией к внешнему вызову. Отказы и другие неудачные результаты отклоняются с реальной `ToolCallError`, видимой программе и несущей только `toolName` и `message`; нативное содержимое и внутренние коды ошибок остаются за пределами контракта Code Mode. Внешние логи программы и её возвращаемое значение заново входят в контекст модели; когда финальный нативный контент успешно завершившегося подвызова содержит изображение, мост также проводит это полное упорядоченное содержимое через родительский результат, чтобы изображение не потерялось за JSON-привязкой. Финальная блокировка post-execute или замена содержимого авторитетны. Обычные побочные эффекты не откатываются, а `additionalContexts` подвызовов проводятся через родительский результат, сохраняя смежность вызова и результата. Завершение прогона отменяет и дожидается все незакрытые привязки; сбои рантайма проявляются как `CodeRunFailedError`.

При `code` — в отличие от `both` — транспорт также единственная точка входа, доступная модели: прямой вызов модели, называющий другой видимый инструмент, превращается в `UNKNOWN_TOOL` при создании исполнения, до `tools/pre-execute`, одобрения `ask` и стражей, так что никто не наблюдает и не одобряет заведомо неудачный вызов. Текст отказа называет обратный маршрут (`only \`run_code\` is callable directly — call \`<name>\` from inside a \`run_code\` program instead`), потому что тот же промпт объявляет этот инструмент, а голое «unknown tool» читается как сломанное развёртывание. Поддиспетчеризации SDK несут токен `parent` внешнего исполнения и являются исключением, поэтому программы сохраняют каждую объявленную SDK привязку. См. [замечание о схлопывании исполнителя](../../../.agents/notes/implemented/bug-fix/2026-08-07-code-mode-executor-collapse.md), [основание Code Mode](../../../.agents/notes/implemented/feature/2026-06-15-code-mode.md), [контракт типизированных возвратов](../../../.agents/notes/implemented/feature/2026-07-20-code-mode-typed-tool-returns.md) и [code-runtime seam](../../code-runtime/README.md). Попробуйте `pnpm run demo:code-mode`.

- **Секция SDK** (`tools:sdk`, порядок 150): ленивая секция промпта, заново генерирующая текст SDK на нужном языке при каждой сборке. В варианте TypeScript она выдаёт `JsonValue`, точные `ToolArgsMap` / `ToolOutputMap`, `ToolName`, объявление `ToolCallError` и отображённый namespace `tools` для видимых конечных возможностей scope вызывающего (экзотические имена — через ключи в кавычках), плюс фиксированные инструкции по использованию; варианту Python (`ctx.codeRuntime.language === 'python'`) соответствуют именованные `TypedDict` и объект `tools` с теми же инструкциями по использованию. Детерминированно: лексикографический порядок инструментов, побайтно идентичный текст для неизменного набора инструментов (дружественно к префиксному кешу). Оба кодогенератора экспортируются и никогда не бросают исключений при сборке промпта: `jsonSchemaToTs` обрабатывает любую конструкцию единой схемы и деградирует неподдерживаемые сырые конструкции до `unknown`; `jsonSchemaToPy` делает то же, деградируя до `Any` (и целого объекта до `dict[str, Any]`, когда имя поля — недопустимый атрибут `TypedDict`, либо всякий раз за пределами рендера SDK, который поставляет контекст именования, необходимый объявлению `TypedDict`).
- **Мост диспетчеризации** (execute у `run_code`): каждый вызов привязки сериализуется в беспотерьный JSON до диспетчеризации (`undefined`, `BigInt`, циклы, разреженные массивы, `-0` и экзотические объекты отвергают именно этот вызов), планируется через пул на прогон, переиспользующий нативный контракт конкурентности, — вызовы стартуют строго в порядке подачи, подряд идущие вызовы с `isConcurrencySafe` перекрываются до валидированного конфигурацией `maxParallelSubCalls` (по умолчанию 10; `1` возвращает серийную диспетчеризацию), а вызов с эксклюзивной классификацией опустошает пул, исполняется один и закрывает дорогу последующим, — получает непрозрачный токен внешнего исполнения как `parent` и проходит полный конвейер pre-execute → стражи → execute → post-execute → result. Успех возвращает финальное каноническое значение после политики; неудача доходит до воркера одним сообщением и становится `ToolCallError(toolName, message)`. Каждый стартовавший подвызов журналирует на входе конвейера событие `tool/code-dispatch-start` (детерминированный id `<parent>:code:<n>`, нумерация по порядку подачи) и завершается одним событием `tool/code-dispatch`, несущим полный видимый модели исход `content`/`isError` (словарь `tool/result`, поэтому UI отображает подвызовы через нативный путь — поля `time` пары несут тайминги отдельных подвызовов); вызов, оставшийся в очереди при завершении прогона, не журналирует ни того, ни другого. `deriveMessages()` не раскрывает ни одно из этих событий и не сохраняет каноническое значение. Корреляция токенов позволяет наблюдателям в стиле фиксации отложить внутренний успех до финального результата `run_code`, не раскрывая живое внешнее исполнение; обычные побочные эффекты инструментов не откатываются. Каждая запись `additionalContexts` подвызова и каждая успешная финальная последовательность содержимого с изображением проводятся через внешний `ToolRunContext` в порядке диспетчеризации; цикл дописывает эти контексты только после родительского результата `run_code`, сохраняя смежность и атрибуцию источника, даже если программа затем падает.
- **Дисциплина завершения**: мост владеет отменой в масштабе прогона, которая наследует внешний сигнал и срабатывает, когда прогон завершается по любой причине, поэтому исчерпание бюджета отменяет выполняющийся под-инструмент, а не оставляет его осиротевшим; затем мост ДО возврата опустошает свою очередь, так что каждое `tool/code-dispatch` попадает в открытый ход. Неудачный прогон бросает `CodeRunFailedError` (`code: 'CODE_RUN_FAILED'`, message = вид сбоя + захваченные логи), который конвейер превращает в структурированный `isError`, по которому модель самостоятельно исправляется.
- **Размер результата**: промежуточные значения привязок передаются в процесс воркера целиком и не имеют побайтового потолка на отдельную привязку. `run_code` возвращает каноническое `{ logs: string[], result?: JsonValue }`; строки выводятся как есть, любой другой присутствующий JSON-корень выводится через стеково-безопасный обход с форматированием (pretty print), общий отступ которого ограничен десятью символами (более глубокие поддеревья остаются компактными), `null` остаётся явным, а отсутствие `result` означает, что программа вернула `undefined`. Настраиваемый `maxOutputBytes` воркера (по умолчанию 64 МиБ) применяется только к суммарной сериализованной полезной нагрузке внешнего массива логов, значения-результата или сообщения о сбое; фиксированный синтаксис конверта результата и пробелы презентации в этот лимит не входят. Невалидные и сверхлимитные завершения явно приводят к ошибке, и лишь этот внешний результат допускается к обычному spill.

### Параллельное исполнение

Цикл агента собирает подряд идущие `parallel`-вызовы в ограниченный скользящий пул и трактует каждый `exclusive`-вызов как барьер порядка. Перекрываются только диспетчеризация и тело; политика, долговечные результаты и контекст сохраняют порядок модели. Привязки Code Mode переиспользуют ту же классификацию через собственный пул моста. Штатные объявления и обоснования описывает [Agent Note о параллельных вызовах инструментов](../../../.agents/notes/implemented/feature/2026-07-10-parallel-tool-call-execution.md).

## Model Experience

### Обычные схемы инструментов

#### What the model sees

В обычном режиме модель видит точное имя, описание и JSON-схему каждого видимого определения; штатные определения записаны в генерируемой [карте пакетов инструментов и секциях схем](../../../docs/tool-catalog.ru.md#карта-пакетов-инструментов). Ограничения, перекрытия и регистрации расширений в объёме агента меняют набор конечных инструментов именно этого агента.

#### Token effect

Фиксированная стоимость на запрос, пропорциональная видимым определениям. Ограничения, скрывающие инструменты, убирают всю стоимость их схем для этого агента.

#### KV Cache effect

Префикс стабилен, пока видимые определения и их порядок неизменны. Регистрация, освобождение ресурсов или ограничение scope способны инвалидировать переиспользование от первого изменившегося токена схемы.

### Схема и системный промпт Code Mode

#### What the model sees

Code Mode предоставляет генерируемую [схему `run_code`](../../../docs/tool-catalog.ru.md#deepseek-aidsh-tools), приведённые ниже инструкции SDK и сгенерированный точный SDK-блок на языке загруженного рантайма (TypeScript-блок `declare const tools` либо Python-объявление `tools`). `both` предоставляет обычные схемы и этот API Code Mode. При `code` промпт вдобавок несёт правило `tools:code-only`, упорядоченное раньше блока рекомендаций по отдельным инструментам, чтобы модель прочитала, какие инструменты ей можно вызывать, прежде чем она прочитает, зачем нужен каждый; `both` выводит его пустым. Инструкции и SDK-блок соответствуют языку загруженного рантайма; ниже показана версия TypeScript (через [`dsh-code-runtime-worker-thread`](../../code-runtime/code-runtime-worker-thread/README.md)), а версия Python (для любого рантайма, сообщающего `language: 'python'`) предлагает те же операции и типы в синтаксисе Python (`await tools.name(args)`, доступ по индексу для экзотических имён, `print(...)` и `return` верхнего уровня).

##### Инструкции SDK Code Mode

```markdown
## Writing code for run_code

`run_code` takes two required arguments: `code` — the body of an async TypeScript function (erasable syntax only — no `enum` or namespaces; type annotations are advisory, the code runs type-stripped) — and `description`, a short summary of what the program does. Inside the program:

- Call tools as `await tools.name(args)` — quoted access for exotic names: `tools["my-tool"](args)`. Every call resolves to the tool's typed canonical JSON value. Tool arguments must be lossless JSON.
- A FAILED tool call rejects with `ToolCallError`, whose `toolName` identifies the failed tool and whose `message` is human-readable — `try/catch` it to handle and continue.
- Independent read-only calls MAY overlap under `Promise.all` (safe calls run concurrently; mutating calls run alone, in submission order). Sequence dependent work with `await`.
- Emit results with `return` and/or `console.log(...)`. ONLY what you print or return comes back to you — intermediate tool results never enter the conversation, so extract just what you need.

The available tools:
```

#### Token effect

Фиксированная стоимость на запрос, пропорциональная видимым определениям. Code Mode разменивает схемы конечных инструментов на сгенерированный текст SDK плюс одну схему транспорта, не обещая универсального сокращения.

#### KV Cache effect

Префикс стабилен, пока неизменны выбор Code Mode, сгенерированный SDK, схема транспорта и набор видимых инструментов. Смена режима или фильтра способна инвалидировать переиспользование от первого изменившегося токена промпта или схемы.

### История вызовов инструментов и результаты

#### What the model sees

Цикл удерживает сгенерированные моделью аргументы и финальный контент реестра. Любой вызов, завершившийся исключением или отклонённый, становится ровно `Error: <message>`. Code Mode выводит напечатанные строки внешней программы и её возвращаемое значение, `(run_code completed with no output)`, когда пусты оба, или `Error: code run failed (<kind>): <message>` с условным продолжением `Captured output:` и захваченными строками. Внутренние события диспетчеризации остаются только в журнале, тогда как успешный под-результат с изображением дописывается после внешнего результата как контекст с атрибуцией источника; слушатели post-execute могут дописать другой контекст с атрибуцией на той же границе.

#### Token effect

Аргументы, результаты и дополнительный контекст зависят от данных и отправляются повторно до компакции. Ограничения, скрывающие инструменты, убирают и их схемы прежде, чем модель успеет их вызвать.

#### KV Cache effect

Append-only; новое видимое содержимое следует за переиспользуемым префиксом запроса и не инвалидирует существующие записи KV-кеша.

## Known Limitations and Deferred Work

- **Политика конкурентности — не событийный гейт** — `executionMode()` читает действующее определение инструмента напрямую; плагины способны объявить классификатор только на определениях, которыми владеют.
- **`tools/pre-execute` намеренно не может переписать `exec.arguments`** — записанные и отрисованные аргументы разошлись бы с тем, что исполнилось; дизайн переписывания — [предлагаемый Agent Note](../../../.agents/notes/proposed/feature/2026-06-30-pre-tool-input-rewrite.md).
- **Структурированные выводы субагентов и воркфлоу, задаваемые вызывающим, остаются объектно-корневыми** — это защита на уровне потребителей; общий словарь схем и выводы инструментов поддерживают любой JSON-корень.
- **`timeoutMs` на определении — только декларация** — реестр никогда не контролирует соблюдение сроков; принудительное применение требует обёртки `@deepseek-ai/dsh-tool-call-timeout-policy`.
- **Язык SDK Code Mode следует за единственным загруженным рантаймом, а презентация действует на агента, а не на инструмент** — `mode: code`/`both` отвергает сборку промпта, пока у `ctx.codeRuntime.language` нет зарегистрированного рендерера SDK (TypeScript или Python); ограничения/перекрытия в объёме scope и `presentAs` определяют для каждого агента его видимые привязки и их форму, но внутри одного агента ни один инструмент не может быть доступен только нативно, пока другой — только в кодовом режиме.
- **Промежуточные значения Code Mode локальны в масштабе исполнения и не ограничены по байтам** — канонические типизированные значения нельзя восстановить из воспроизведения сессии, и они способны исчерпать память процесса или воркера; жёсткий настраиваемый потолок воркера применяется только к внешнему выводу `run_code`. Долговечная журнальная копия каждого подвызова ОГРАНИЧЕНА: каскад `tools/code-dispatch-log` позволяет политике spill заменить чрезмерно большое содержимое `tool/code-dispatch` превью + локатором ([rationale](../../../.agents/notes/implemented/feature/2026-07-26-code-dispatch-log-spill.md)).
- **Состояние `run_code` создаётся заново на каждый прогон** — постоянное REPL-ядро отвергнуто для MVP (состояние между вызовами было бы невидимо для журнала); см. [Agent Note о Code Mode](../../../.agents/notes/implemented/feature/2026-06-15-code-mode.md).
