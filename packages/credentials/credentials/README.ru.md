# dsh-credentials

[English](README.md) | [中文](README.zh.md) | Русский

Service Definition учётных данных (`ctx.credentials`). Одна доктрина, три следствия:

**Конфигурация несёт ссылки на секреты, но не сами секреты.** Секция настроек или запись `cordis.yml` говорит `apiKeyEnv: DEEPSEEK_API_KEY`; значение за этой ссылкой живёт у провайдера учётных данных. Поэтому документ настроек остаётся безопасным для синхронизации и показа в UI конфигурации, `describe()` может ответить на вопросы «настроено ли это, откуда, могу ли я записать», ни разу не удерживая значения, а ротация секрета не затрагивает ни одного конфигурационного файла.

**Потребители разрешают ссылку на каждую операцию.** `resolve(ref)` вызывается в начале каждой операции (LLM-адаптеры разрешают один раз на каждый запрос к модели) и никогда не кэшируется между операциями — именно это чтение доводит изменившиеся учётные данные до самого следующего запроса без перезапуска какого-либо плагина.

**Пустое сохранённое значение означает отсутствие.** Везде: `resolve` его пропускает, `describe` сообщает о нём как о ненастроенном. Пустота никогда не может сойти за настроенный секрет.

## Два пространства ключей, два вопроса

`CredentialRef` отвечает на вопрос *что стоит за этим именем переменной окружения*, наслаиваясь на окружение процесса, управляемое хранилище и `.env`-файлы. Всё сказанное выше описывает эту половину.

`CredentialKey` отвечает на вопрос *какими учётными данными этот плагин владеет для этого идентификатора*. Наслаивать здесь нельзя — у гранта авторизации нет окружения, из которого можно читать, — поэтому само наличие записи и есть весь факт, и правило пустого значения не применяется: запись `api-key`, не несущая ни ключа, ни значений окружения, утверждает, что её владелец подтвердил внешнюю аутентификацию, а это и есть «настроено».

Ключ имеет вид `<scope>/<id>`, где scope — **зарегистрированное имя плагина-владельца**. Scope — это владелец, а не домен, потому что payload гранта записан в формате своего владельца: иначе два плагина под одним именем провайдера читали бы payload друг друга, а запись, брошенную удалённым плагином, было бы не отличить от живой. Разделитель `/` вдобавок держит две грамматики непересекающимися, поэтому пространства ключей не могут столкнуться. Потребитель, чей идентификатор приходит откуда-то ещё — ключ словаря настроек, собственный идентификатор провайдера библиотеки, — спрашивает `isCredentialKeySegment` прежде чем строить ключ: идентификатор вне грамматики никогда не мог иметь сохранённой записи и должен читаться как «ничего не сохранено», а не бросать исключение на адресе.

## API сервиса

```ts
import type { Context } from '@deepseek-ai/cordis'
import { credentialKey, credentialRef } from '@deepseek-ai/dsh-credentials'

declare const ctx: Context

const ref = credentialRef('DEEPSEEK_API_KEY')            // POSIX shell identifier, branded
const hit = await ctx.credentials.resolve(ref)           // { value, source } | undefined
const info = await ctx.credentials.describe(ref)         // { configured, source?, writable } — never the value
await ctx.credentials.set(ref, 'sk-…')                   // rejects while a read-only source shadows the ref
await ctx.credentials.unset(ref)                         // no-op when absent; same shadowing rule

const key = credentialKey('llm-pi-ai', 'openai-codex')   // <owner>/<id>, branded
await ctx.credentials.readRecord(key)                    // CredentialRecord | undefined
await ctx.credentials.describeRecord(key)                // { configured, kind?, writable } — never the value
await ctx.credentials.listRecords()                      // [{ key, kind }] — never values
await ctx.credentials.modifyRecord(key, async () => ({ kind: 'grant', payload: { token: '…' } }))
await ctx.credentials.deleteRecord(key)                  // no-op when absent
```

`modifyRecord` — единственный путь записи, потому что корректная запись зависит от текущего значения: обновление токена — это «прочитай-реши-замени», и мутация должна видеть запись в том виде, в каком она стоит в момент, когда запись становится исключительной. Исключительность действует между процессами — именно она не даёт двум из них ротировать один refresh-токен и затереть запись той, что сработала первой. Возврат `undefined` из мутации оставляет запись нетронутой и ничего не объявляет.

`listRecords` существует, хотя половина ссылок по дизайну не допускает перечисления. Ссылки обнаруживаются по схемам настроек (поля `apiKeyEnv`); у записей такого пути нет, поэтому интерфейс, который не умеет их перечислять, не покажет, на что авторизован пользователь, и не найдёт осиротевшую запись, оставленную удалённым плагином.

`payload` записи-гранта непрозрачен: seam никогда не читает, не проверяет и не переформатирует его. Единственное ограничение — переживание полного круга JSON, которое провайдер требует и на входе, и на выходе: значение, которое хранилище не может прочитать назад в точности как записано, отвергается, а не сохраняется с потерями.

`credentials/reference-updated (ref)` срабатывает после зафиксированного изменения контролируемого провайдером источника — `set`, `unset` или внешнего изменения, замеченного в хранилище. Изменения окружения процесса ненаблюдаемы и никогда не испускают событие. Потребителям событие не нужно (они повторно разрешают ссылку на каждую операцию); оно существует для UI конфигурации, обновляющих значок «настроено». Его объявление живёт в безопасном для клиента экспорте субпути `./types` вместе с называемым им типом `CredentialRef` (корень пакета реэкспортирует тип), поэтому потребитель, компилирующийся вне агрегата Host, читает именно ту сигнатуру, которую испускает Host, вместо того чтобы переписывать её.

Правило затенения для `set`/`unset` — сознательный fail-loud: когда ссылку сейчас поставляет источник только для чтения (живое окружение процесса у локального провайдера), запись выглядела бы успешной, хотя разрешение продолжало бы возвращать затеняющее значение, — вместо этого seam отказывает, а `describe().writable` позволяет UI заранее показать ссылку как доступную только для чтения.

## Провайдеры

[`dsh-credentials-local`](../credentials-local/README.ru.md) наслаивает унаследованное окружение процесса поверх управляемого документа `$DSH_HOME/.credentials.yaml`, с проектным и пользовательским слоями `.env` лаунчера в качестве резервов. Форма seam оставляет место провайдерам на базе keyring, вспомогательной команды или KMS; удалённому провайдеру настроек носить секреты никогда не требуется.

## Опыт модели

Косвенно, через потребляющие LLM-адаптеры: разрешённое значение авторизует их запросы к провайдеру, а каждое видимое модели представление принадлежит адаптеру.

#### Влияние на KV-кэш

Прямой инвалидации нет; учётные данные никогда не входят в префикс запроса.

## Известные ограничения и отложенная работа

- **Ссылки не перечисляются** — seam отвечает на вопросы о тех ссылках, которые ему даны; интерфейсы конфигурации узнают их из схем настроек, поэтому `list()` над этой половиной не имеет текущего потребителя. Записи перечисляются — по причине выше.
- **Ссылки имеют форму переменных окружения** — одно плоское пространство POSIX-идентификаторов, потому что ссылка заодно служит именем окружения, через которое разрешается. Записи несут более выразительную адресацию `<owner>/<id>`.
- **Изменения окружения процесса невидимы** — событие для них произойти не может; UI перечитывает `describe()` только при собственной навигации.
- **Владелец записи — это её scope, и ничто не проверяет смонтированность scope** — seam сохраняет то, что ему дано, и сообщает то, что сохранил. Распознать осиротевшую запись — задача вызывающего: связать `listRecords()` с тем реестром, которому принадлежит этот scope; собственного реестра для сверки у seam нет.
