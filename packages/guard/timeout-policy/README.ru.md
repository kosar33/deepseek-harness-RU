# dsh-tool-call-timeout-policy

[English](README.md) | [中文](README.zh.md) | Русский

Механизм принудительного применения таймаутов вызовов инструментов: одиночный around-dispatch слушатель `tools/execute`, который взводит на вызов кооперативный дедлайн через `exec.signal` для инструмента, объявившего `timeoutMs` в своём `ToolDefinition`, и возвращает структурированный результат `TOOL_TIMEOUT`, когда дедлайн выигрывает. Бюджет читается из собственного объявления инструмента (`ToolDefinition.timeoutMs`, задаётся плагином — владельцем инструмента), поэтому этот плагин **не требует конфигурации**. Это эталонная обёртка `tools/execute` и место принудительного применения обращённых к модели бюджетов на вызовы инструментов ([Agent Note о библиотеке таймаутов](../../../.agents/notes/implemented/architecture/2026-07-06-timeout-deadline-library.md)).

## Плагин (namespace: `timeout-policy`)

Функциональный/namespace-плагин (`name` / `inject` / `apply`), а не сервис. Он не регистрирует инструмент и не принимает конфигурацию — он использует каскад `tools/execute` у `ctx.tools` (который реестр `dsh-tools` всегда предоставляет) и читает объявленный `timeoutMs` каждого диспетчируемого инструмента из реестра (`ctx.tools.get(exec.name)`).

```yaml
- id: timeout-policy
  name: '@deepseek-ai/dsh-tool-call-timeout-policy'
```

Бюджет каждого инструмента объявляется плагином этого инструмента (например конфигурация `fetchTimeoutMs`/`searchTimeoutMs` у `dsh-tool-web`, прикрепляемая как `ToolDefinition.timeoutMs`); этот плагин лишь обеспечивает его соблюдение, поэтому опечатка в имени инструмента невозможна.

### Поведение

Для инструмента, **объявляющего `timeoutMs`**, слушатель:

1. Читает бюджет из собственного объявления инструмента в реестре (`ctx.tools.get(exec.name)?.timeoutMs`) и взводит `deadline(exec.signal, timeoutMs, 'TOOL_TIMEOUT')` — один сигнал, объединяющий отмену вызывающего с таймером этого плагина (`@deepseek-ai/dsh-timeout`).
2. Подменяет этот производный сигнал на `exec` для нижележащей диспетчеризации, затем восстанавливает собственный сигнал вызывающего (cordis `next()` игнорирует переданные аргументы, поэтому обёртка мутирует общий `exec` на месте; благодаря восстановлению `tools/post-execute` видит сигнал вызывающего).
3. После диспетчеризации, если `timeoutOf(d.signal, 'TOOL_TIMEOUT')` совпадает — сработал собственный таймер этого плагина — заменяет результат структурированным результатом инструмента `TOOL_TIMEOUT`: `{ isError: true, error: { message, info: { name: 'ToolTimeoutError', code: 'TOOL_TIMEOUT' } }, content: 'Error: tool call timed out after <ms>ms' }`.

Инструмент, **не объявляющий бюджета**, делегируется нетронутым (без дедлайна).

Базовый `next()` каскада `tools/execute` — это thunk диспетчеризации с нормализацией из реестра, поэтому когда сигнал таймаута достигает провайдера, бросающего собственную ошибку upstream-abort, диспетчеризация сначала превращает её в обычный результат-ошибку, а эта обёртка затем заменяет её на `TOOL_TIMEOUT`. Именно этот порядок объясняет, почему замена ключуется по сигналу (`timeoutOf`), а не по форме диспетчеризованного результата.

### Кооперативность, а не жёсткое завершение

Производный сигнал только **уведомляет**; завершение остаётся за инструментом и возможностью, которой он передаёт `exec.signal` (библиотека `dsh-timeout` не владеет механизмом принудительного завершения). **Поэтому объявление `timeoutMs` означает «кооперативность с `exec.signal`»**: инструмент, игнорирующий сигнал, по таймауту не остановится. Объявлять его должны только инструменты, передающие сигнал — поставляемые `web_fetch`/`web_search` (передающие через `ctx.web` провайдерам) служат эталоном. `TOOL_TIMEOUT` не нуждается в событии сессии для реконструируемости: это финальный обращённый к модели `tool/result`, уже зажурналированный циклом.

### Композиция с другими обёртками `tools/execute`

Несколько слушателей `tools/execute` компонуются порядком регистрации cordis. В сочетании с будущей обёрткой повтора/песочницы/метрик порядок регистрации выбирает семантику — «таймаут покрывает всю операцию повтора» (таймаут зарегистрирован снаружи) против «таймаут покрывает каждую попытку» (таймаут зарегистрирован внутри).

## Влияние на модель

### Условный результат инструмента

#### Что видит модель

Этот плагин не добавляет ни промпта, ни схемы. Если объявленный дедлайн выигрывает, он заменяет результат провайдера на `Error: tool call timed out after <ms>ms` плюс структурированный `TOOL_TIMEOUT`; иначе исходный результат проходит без изменений.

#### Влияние на токены

Ноль токенов на вызовах без таймаута. Таймаут добавляет один небольшой удерживаемый результат-ошибку и может не допустить попадания в контекст более объёмного запоздалого результата провайдера.

#### Влияние на KV-кэш

Append-only; новое видимое содержимое следует за повторно используемым префиксом запроса и не инвалидирует существующие записи KV-кэша.

## Известные ограничения и отложенная работа

- **Кооперативно, никогда не жёсткое завершение** — дедлайн только уведомляет через `exec.signal`; инструмент, игнорирующий сигнал, по таймауту не останавливается (см. § Кооперативность, а не жёсткое завершение).
- **Никакого общего бюджета** — дедлайн получают только инструменты, объявившие `timeoutMs` в своём `ToolDefinition`; реестрового умолчания для необъявивших инструментов нет (поставляемые `bash`/`read`/`write`/`edit` намеренно ничего не объявляют).
