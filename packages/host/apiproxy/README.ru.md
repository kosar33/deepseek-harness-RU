# @deepseek-ai/dsh-host-apiproxy

[English](README.md) | [中文](README.zh.md) | Русский

Общий для всех клиентов API-шлюз состоит из контракта TypeScript API (`src/api/`, без Node-зависимостей, импортируемого из браузера), пары fetch-carrier (`src/fetch/`: `toFetchHandler` на стороне хоста, `AbstractApiClient` плюс платформенные подклассы на стороне клиента) и реализации на стороне хоста (`src/api-proxy.ts`: `createApiProxy` плюс экспортируемый по умолчанию плагин-шлюз `ApiProxyService` — конфигурация `{nativeOpen?, sessionExportCompressionLevel?, coldBlankProbeMaxBytes?}`, предоставляет `ctx.apiProxy`). Этот пакет не регистрирует маршрутов; carriers вроде HTTP оборачивают `ctx.apiProxy` сами. Поставляемая веб-композиция живёт в [`packages/bundle/web-app/cordis.patch.yml`](../../bundle/web-app/cordis.patch.yml), а выбор модели Agent по умолчанию принадлежит [`@deepseek-ai/dsh-agent-default-model`](../../core/agent-default-model/README.md) из базового бандла.

## Общий агентский дефолт (секция настроек `agent-default-model`)

`ApiProxyService` использует `ctx.agentDefaultModel`; он не владеет ни конфигурацией провайдера/модели, ни собственной секцией настроек. Общий сервис регистрирует `{provider, model, reasoningEffort?}` под именем `agent-default-model`: запись композиции базового бандла — нижний слой, а `settings.yaml` накладывает поверх неё пользовательский выбор.

Сессия разрешает свой выбор модели при каждом обращении по трём ярусам: выбор, сделанный в этом процессе, иначе последнее записанное в журнал сессии `request/header`, иначе это значение по умолчанию. Сессия, выполнившая хотя бы один ход, выводит выбор из своего журнала, тогда как пустая сессия наблюдает значение по умолчанию, сохранённое уже после её создания.

`session.selectModel` сохраняет принятую смену как значение по умолчанию всего развёртывания; отдельного жеста для этого нет. Он записывает разрешённую `ModelSelection`, включая материализованный адаптером уровень усилия по умолчанию. Запись полной секции стирает сохранённый уровень усилия, когда у выбранной модели его нет. Сбой хранилища журналируется без отмены выбора сессии. Развёртывание без провайдера настроек сохраняет запись композиции, и смена остаётся локальной для сессии.

У секционного `reasoningEffort` намеренно нет аналога в конфигурации плагина agent-default-model: seam сливает пользовательский слой с записью композиции по полям, поэтому отсутствующий ключ не может переопределить присутствующий, а заданное композицией усилие пережило бы любую последующую смену на модель без него. Значение усилия по умолчанию для развёртывания принадлежит профилю адаптера, который разрешает его по модели.

Сохранённый выбор независим от членства в каталоге. Дефолт, называющий недоступного провайдера, всё равно попадает в `session.models` как `current` сессии, позволяя селектору запросить замену вместо молчаливого выбора другой модели. И наоборот: адаптер может обслуживать модель, которую его каталог не объявляет.

## Слой контракта (`/api`)

Сообщения wire-протокола образуют размеченное объединение четырёх квадрантов — кто инициирует × запрос/ответ — отвязанное от физического канала: `ClientRequest` (тело POST `/api/<method>`), `ServerResponse` (тело ответа того же POST), `ServerRequest` (кадр SSE), `ClientResponse` (тело POST `/api/respond`). Ответы всегда возвращают `rpcId` соответствующего запроса и никогда не выпускают новый. Структуры параметров и результатов методов живут только в сигнатурах доменных интерфейсов (`SessionsApi`, `HostApi`, `EventsApi`); `RpcMethodMap` регистрирует методы, а все остальные позиции выводятся через `RequestPayload<K>`/`ResponseValue<K>`. Zod-схемы заякорены через `satisfies z.ZodType<Wire<T>>` и разбирают данные на двух уровнях: сначала конверт, затем полезная нагрузка, с диспетчеризацией по методам. Бизнес-ошибки передаются в ветке ошибки `RpcResult` (`RpcErrorDetailsMap` замыкает набор кодов); HTTP-статус выражает только carrier. Каждый POST на `/api` должен объявлять медиатип `application/json` — всё прочее отвергается с 415 до диспетчеризации, чтобы межсайтовые «простые» запросы (которые браузеры отправляют без CORS-preflight) никогда не могли вслепую исполнить метод с побочными эффектами.

Решения о расслоении и протоколе записаны в [RFC о расслоении GUI и RPC-протоколе](../../../.agents/notes/implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.md); архитектура потребления на стороне браузера — в [RFC об архитектуре веб-клиента](../../../.agents/notes/implemented/architecture/2026-07-19-gui-web-client-architecture.md).

Ответы на вопросы сверяются со своим ожидающим запросом прежде, чем первый ответ предъявит на него права. Элемент множественного выбора может нести как запрошенные метки опций в `selected`, так и непустой текст `custom`; элемент одиночного выбора обязан использовать что-то одно. Дублирующиеся метки, неизвестные метки, несовпадающие id, неполные наборы и пустой текст `custom` отвергаются как `bad-response`.

`session.history` читает подключённую Session в памяти или осматривает холодный журнал через персистентность, не возобновляя и не публикуя Agent, а затем разбивает результат на страницы по границам сообщений, возникшим добавлением. `maxMessages` считает события `user/message` и `assistant/message`, попавшие на поверхность добавлением, поэтому чисто модельная копия-замена квоту не расходует. Каждая страница остаётся одним непрерывным диапазоном исходных событий, благодаря чему запись компакции `compaction/summary`, существующая только в журнале, оказывается на той же странице, что и цитирующая её замена.

Хвостовая страница `session.history` (без `beforeSeq`) дополнительно несёт необязательный блок `projections` — снапшот watermark каждой единицы, зарегистрированной в `ctx.sessionProjections` (`@deepseek-ai/dsh-session-projection`), где `asOfSeq` — последний seq события, который отражают значения (`-1` на пустом журнале). Шлюз также подписывается на ленту изменений реестра и выпускает mux-кадр `session/projection` на каждую изменившуюся единицу (`{sessionId, key, value, seq}` — живое push-состояние, в журнал не попадающее никогда; клиенты держат одно универсальное хранилище значений на сессию по правилу «побеждает больший seq»). Carrier не знает ничего о чужих доменах (каждое значение прошло собственную схему своей единицы внутри реестра; wire-схемы держат `values`/`value` широкими); страницы loadOlder никогда не несут этот блок, а композиция без реестра отдаёт истории без обеих поверхностей. Шлюз владеет двумя единицами: `sessionListMetadata` кэширует монотонный переход «пустое → непустое» и время последнего человеческого промпта, которыми пользуется `session.list`, а `imageLimits` публикует конфигурацию вложений, применяемую при допуске промпта, как константу одного запуска (`apply` сохраняет ссылку состояния, поэтому её несут одни базовые снапшоты — кадров изменений нет), чтобы клиенты могли отвергнуть превышающий лимит ввод ещё до отправки и подписывать элементы загрузки; вторая активируется, лишь когда скомпонованы и реестр, и сервис вложений.

Экспорт журнала сессии — поверхность скачивания только на хосте, а не RPC: `GET /api/session.export?sessionId=…&includeDescendants=true` передаёт ZIP потоком, чьи файлы — дословный текст сохранённых артефактов каждой сессии (`readRaw` бэкенда персистентности — точные долговечные байты, декодированные из физической кодировки, никогда реконструкция из разобранных событий), корень под исходным базовым именем плюс каждый потомок-субагент под `subagents/<id>/` и все изображения, на которые ссылается любой включённый журнал, под `media/<attachmentId>.<ext>` (читаются и проверяются из хранилища вложений; общее изображение появляется один раз). `HEAD` выполняет ту же подготовку корня и возвращает статус и заголовки без тела ответа, чтобы браузерные клиенты обнаруживали сбои до начала потока раньше, чем отдадут GET нативному менеджеру загрузок. Каждый живой корень или потомок пересекает авторитетный барьер долговечности `SessionStore.flush` непосредственно перед чтением своего исходного артефакта; холодным сессиям сбрасывать в памяти нечего. Сжатие выполняется на хосте потоковым Zip API fflate на проверенном `sessionExportCompressionLevel` 0–9 (по умолчанию 6), так что развёртывания могут разменивать процессор и задержку на размер архива; ответ отдаётся чанками по мере производства, и хост никогда не держит весь архив в одном буфере. Когда очередь ответа достигает верхней границы в 64 КиБ, генерация ждёт, пока потребительская выборка не восстановит положительную ёмкость; синхронный колбэк fflate способен превысить эту границу лишь на выход одной ограниченной порции входных данных. Прерывание запроса и отмена тела ответа останавливают работу по родственной линии и артефактам, завершают активный компрессор и распространяются как отмена, а не HTTP 500. Экспорту требуются сервисы персистентности, session-query и вложений: развёртывание без любого из них отвечает 500, бэкенд персистентности без посессионных исходных артефактов отвечает 501, отсутствующая корневая сессия отвечает 404, а потомок без сохранённого артефакта или ссылка на нечитаемое изображение прерывают поток с явной ошибкой (fail-loud, а не тихий недоэкспорт). Эндпоинт монтирует carrier; реализует его `ApiProxy.downloads.sessionLog`.

Заголовки сессий идут в общей паре проекций, как всякий другой домен, — блок `projections` хвоста истории плюс кадры `session/projection` под ключом `title`. Заголовки не входят в `session.list`; холодные сессии остаются там только метаданными, пока открытие или возобновление не подключит их журналы. `session.rename` принимает явный пользовательский заголовок (сначала возобновляя холодную сессию) и делегирует в `ctx.sessionTitle.rename` — принятое событие `session/title` фиксирует заголовок против автогенерации; метод возвращает нормализованный заголовок вместе с seq его события, чтобы клиент обновил свою ячейку проекции `title` раньше push-кадра; заголовок, нормализующийся в пустоту, возвращает `title-invalid`.

`session.fork` отображает необязательный якорь события на первый `turn/end` в нём или после него, позволяя действию над сообщением захватить весь ход этого сообщения. Опущенный или ушедший за конец якорь выбирает последний завершённый ход; якорь внутри журнала, чей ход ещё открыт, возвращает `fork-unavailable`, а не обрезает назад. Опубликованный ребёнок наследует предзаполненную историю источника, cwd, последнюю записанную `ModelSelection` и линию родства, прежде чем присоединиться к Workspace источника. Если подключение Workspace терпит неудачу, `workspace-attach-failed` несёт уже опубликованный id ребёнка, чтобы клиенты могли его согласовать. [Решение о fork в SessionStore](../../../.agents/notes/implemented/feature/2026-06-30-session-store-fork-api.md) объясняет, почему якорь отображается именно на тот `turn/end`.

Выбор модели сессии — контракт домена сессий. `session.models` возвращает текущую `ModelSelection` отдельно от сгруппированных по провайдерам справочных моделей, метаданных рассуждений для конкретных моделей и локальных для провайдера отказов lookup. Выбор может отсутствовать в группах и никогда не инъецируется синтетической строкой; клиенты могут запрашивать другой выбор, не превращая каталог в whitelist маршрутизации. `session.selectModel` проверяет необязательное принадлежащее адаптеру усилие рассуждений и назначает полную смену для следующей сборки промпта. Членство в каталоге — не валидация: адаптер может разрешить незанесённую в список модель, тогда как недоступный провайдер или неподдерживаемое усилие возвращает `model-unavailable`. `session.models` дополнительно сообщает `routable`: обслуживает ли адаптер выбранного провайдера прямо сейчас. Это намеренно невыводимо из групп, потому что адаптер может обслуживать необъявленную модель. `session.prompt` отказывает на том же факте с `model-unavailable` до открытия хода; заблокированный композер — клиентское удобство, и метод остаётся вызываемым.

`session.prompt` и `subagent.prompt` принимают необязательный локальный для запроса маркер происхождения `clientTimeZone`. При наличии Host проверяет и канонизирует `UTC` или зону IANA Area/Location до входа в Agent, отвергает неверный ввод с `invalid-time-zone` и записывает каноническое значение на самом этом сообщении `user-rpc` рядом с его `rpcId`. Значение не является состоянием Session, соединения, создания, возобновления или fork; небраузерные вызывающие могут его опускать.

Ввод, ожидающий в очереди, — живой контракт управляющей плоскости, а не история диалога. Шлюз выводит полную очередь `next-turn` из долговременных мутаций `agent/inbox/spliced` и рассылает авторитетные снапшоты `session/queue` после каждого изменения и при переподключении; ожидающий steering `next-step` остаётся вне этой веб-проекции. Внутри `next-step` сообщения пользовательского происхождения несут размещение `steering`, а инъецированный контекст (уведомления о согласованиях, завершение задач, приложенные снапшоты) несёт `context` и не показывается, пока его не востребуют. Локальные для сообщения уведомления `agent/inbox/inserted`, `claimed` и `discarded` остаются доступными наблюдателям жизненного цикла, но вид очереди не строят. `session.updateQueue` адресует один `MessageId`; правка и удаление мутируют подключённого Agent через `Inbox.splice()`. Чисто удаляющий splice востребования выигрывает гонки ещё до допуска перед шагом, поэтому последующая операция возвращает `queue-item-not-found`. `session.cancel` прерывает только активный ход и сохраняет ожидающую работу inbox; после того как отмена достигнет quiescence и закрывающийся ход сбросится, AgentLoop востребует следующее проснувшееся сообщение в порядке FIFO, и браузер сам его никогда не перешлёт и не продвинет. Операции над очередью никогда не возобновляют холодную сессию, и клиент никогда не выводит выбытие сообщения из событий хода или статуса.

Фоновые задачи едут в том же живом push-режиме. Когда скомпонован `ctx.jobs`, шлюз подписывается на ленту его изменений и рассылает полный снапшот `session/jobs` после каждого коммита реестра, меняющего видимое сессии, — регистрацию, переход к остановке, расчёт и удаление при освобождении владельца, — плюс базовую линию подписки для каждой сессии, у которой задачи уже есть (отсутствующая базовая линия — пустое множество; изменение, опустошающее множество, всё равно шлёт `[]`). Изменение с владельцем читается через именно того Agent, поэтому push остаётся корректным, пока его область разбирается на части; базовая линия читает `ctx.agents.get(sessionId)`, что даёт только бесхозные задачи для сессии без живого Agent и никогда не возобновляет холодную. Бесхозное изменение веером расходится во все подписанные сессии, потому что бесхозные задачи видимы каждому вызывающему. Формат протокола `JobView` отбрасывает `ownerSession`, `reported` и `outputLimitBytes`: первое несёт собственный `sessionId` кадра, а остальные два — внутреннее уведомление и политика показа модели. Композиция без реестра таких кадров не испускает.

Списки Workspace и Session — раздельные базовые линии переподключения. `workspace.create({ path })` усыновляет существующий канонический каталог и позволяет повторяться именам, выведенным из basename. `workspace.insertBefore({ workspaceId, beforeWorkspaceId? })` коммитит один перенос порядка реестра и отвечает полным порядком; чистая перестановка испускает `host/workspace-order-changed` с тем полным порядком, а неизвестные источник или якорь возвращают `workspace-not-found`. `workspace.delete` удаляет только регистрацию Workspace, `session.create` принимает необязательный заранее выделенный id сессии, а `host/workspace-changed`, `host/workspace-removed` и `host/session-added` несут закоммиченные приращения в любом порядке прибытия. `workspace.archiveSession` добавляет одну сессию в глобальный для реестра архивный набор и отвечает полным обновлённым набором; `workspace.list` несёт этот набор как базовую линию переподключения, а `host/archived-sessions-changed` пушит полный снапшот после каждого долговременного изменения. Архивация прячет сессию из поверхностей группировки, не трогая ни её журнал, ни её счёт workspace; сессия, которая ни жива, ни персистентна, падает с `session-not-found`. Удаление регистрации сохраняет каталог и журналы сессий; её сессии остаются в `session.list` и становятся Ungrouped. `SessionSummary.blank` и кадр `host/session-added` несут признак начавшегося хода: клиенты прячут пустые сессии и повторно используют их по workspace, переключают blank при первом `host/session-status(running:true)` и считают `session.list` авторитетом переподключения. Подключённые сводки сворачивают живой журнал. Холодная сводка доверяет кэшированному `blank: false`, но трактует кэшированное `true` и промах кэша как непроверенные; когда `locate()` сообщает артефакт не крупнее порога допустимости `coldBlankProbeMaxBytes` (по умолчанию 1 КиБ), шлюз читает сессию через `readFrom()` и сворачивает и пустоту, и последний человеческий промпт. Более крупный, без местоположения, исчезнувший или нечитаемый артефакт остаётся видимым. После асинхронного холодного чтения сессия, подключившаяся тем временем, сводится из своего живого журнала. `updatedAt` использует живую свёртку, точную свёртку малого артефакта или кэш проекции в этом порядке, откатываясь к `createdAt`; границы pickup и прочие записи никогда не повышают сессию.

`session.search` — ограниченная проекция поиска по содержимому над сессиями, видимыми через `session.list`. Шлюз спрашивает необязательный сервис `ctx.sessionQuery` о глобально ранжированных совпадениях пользователя, ассистента и steering на текущей поверхности, использует этот поток, пока не наберёт не более 20 видимых пар сессия/фрагмент плюс одну lookahead, и перепроверяет каждое попадание против выведенного из списка множества полномочий перед возвратом. Страницы провайдера стартуют с 20 попаданий; когда запрос первой страницы отвергает такой лимит, шлюз пробует 10, 5, 2, затем 1 и сохраняет выученный размер для продолжений и перезапусков устаревшего поколения. Возвращаемые фрагменты содержат не более 240 кодовых точек Unicode, и схема ответа независимо закрепляет эту границу на каждом клиентском рубеже. Держать множество полномочий в памяти Host — значит избегать потолка переменных SQLite для больших валидных корпусов, не ослабляя ни видимость, ни ранжирование.

Устаревшее продолжение отбрасывает все частичные результаты, записи дедупликации и курсоры той попытки провайдера, затем перезапускается с первой страницы против исходного выведенного из списка снапшота видимости, не отбрасывая выученный размер страницы провайдера. Пробы лимита и устаревшие повторы делят один предел — не более 100 вызовов провайдера (значит, не более 2000 осмотренных попаданий); страница крупнее запрошенного лимита, повторяющийся курсор продолжения или не исчерпавшийся поток при таком бюджете вызовов завершается отказом в безопасную сторону — бизнес-ошибкой `internal`. Сигнал запроса carrier отменяет листинг персистентности, сбор холодных сводок и каждый поисковый вызов, включая отвержение по лимиту или устареванию, замеченное одновременно с отменой. Развёртывание без сервиса, как и любая невосстановленная ошибка индекса/запроса, тоже возвращает бизнес-ошибку `internal`, чтобы клиенты могли удерживать совпадения только по метаданным.

Выбор каталога делегируется скомпонованному бэкенду `ctx.directoryPicker` ([seam выбора каталога](../directory-picker/README.md)); метод, вызванный вне рода скомпонованной возможности, падает с `directory-picker-unavailable` (клиенту не нужно объявления — собственная клиентская половина скомпонованного пакета-выборщика рисует соответствующее взаимодействие). Под `native` метод `host.pickDirectory` открывает один нативный выборщик и возвращает выбранный путь (`null` при отмене); этот управляемый пользователем метод не использует дефолтный 30-секундный унарный таймаут, при этом прерывания вызывающего/соединения всё равно доходят до нативного процесса. Под `browse` метод `host.listDirectory` возвращает один отсортированный по имени уровень каталога с breadcrumb-родословной, якорем `home` и принадлежащими хосту флагами `hidden` (отсутствующий путь = домашний каталог), а `host.createDirectory` создаёт один проверенный дочерний сегмент; типизированные отказы бэкенда отображаются 1:1 на коды `directory-unreadable`/`directory-exists`/`directory-create-failed`. Ограда доверия браузерного carrier, широкая на весь префикс (dsh-client-connection), покрывает всё это, как и любой другой запрос `/api`.

`host.openPath` открывает путь файловой системы приложением операционной системы по умолчанию (`open` на macOS, `Invoke-Item` на Windows, `xdg-open` на настольном Linux). Для `.html`, `.htm`, `.xhtml` и `.svg` macOS и настольный Linux предпочитают названный браузер по умолчанию и откатываются к передаче приложению по умолчанию, когда браузер назвать нельзя. WSL переводит каждый Linux-путь через `wslpath -w` и вручает получившийся Windows/UNC-путь Windows-команде `Invoke-Item`, включая документы, пригодные к показу в браузере, вместо предположения о Linux-ассоциации рабочего стола. `host.describe.home` — домашний каталог учётной записи хоста. Веб-клиент использует его, чтобы показывать пути с POSIX-корнем дома как `~`; значения Windows по-прежнему сообщаются и не сокращаются. `host.describe.canOpenPath` объявляет, способен ли этот переход добраться до видимого пользователю рабочего стола: явный `nativeOpen` шлюза побеждает, инъецированный opener пригоден по определению, а иначе детекция платформы принимает macOS, Windows, WSL или Linux с дисплеем и отвергает headless/container Linux. Браузерный carrier применяет то же loopback-ограничение одного origin, что и `host.pickDirectory`; клиенты складывают оба факта, прежде чем показать нативное действие.

Домен `agentPreset.list` раскрывает ростер пресетов развёртывания, чтобы браузер мог предложить выбор при старте сессии; каждая строка несёт свой `trust` (пресет `user` ровно настолько же привилегирован, насколько названные им плагины), является ли он текущим значением по умолчанию и — когда пресет не может собрать сессию — причину `broken`, ведь повреждённый каталог всё равно занимает свой id, и поверхность должна уметь показать и удалить его, а не предлагать его и срывать старт сессии. Развёртывание, не собирающее ни одного пресета, отвечает пустым ростером, а не ошибкой, ведь разделять хостовую композицию — валидное развёртывание. `agentPreset.select` пересобирает агента одной сессии из другого пресета и допускается, только пока сессия пуста: раз ход выполнен, эта история произведена инструментами пресета, и их подмена бросила бы на произвол судьбы записанные вызовы инструментов, поэтому попытка отвечает `agent-preset-locked`. Агент и сессия выживают — меняется только композиция, а неудавшаяся подмена возвращает прежнюю.

Методы `agentPreset.read`, `copy`, `openDocument` и `remove` управляют самими композициями. `read` сообщает текст вместе с его `trust` для read-only просмотрщика. Создание — только копированием: `copy` берёт `{ from, agentPreset, name? }` — два id, которые Host разрешает относительно собственных корней, плюс необязательное отображаемое имя — и копирует весь каталог источника, поэтому никакой текст композиции не попадает в формат протокола, а копия ровно так же загружаема, как её источник; id, не содержащийся ни в одном корне, или уже занятый получает отказ `agent-preset-invalid`, а `remove` отказывает поставляемому пресету как `agent-preset-read-only`. `openDocument` вручает платформенному открывателю КАТАЛОГ одного локально сочинённого пресета — запрос несёт id, никогда путь, поэтому никакая браузерная нагрузка не может выбрать произвольную цель файловой системы; там, где у развёртывания нет нативного opener, ответ — `{ opened: false, path }`, который поверхность показывает текстом; поставляемый пресет отвергается, как и в `remove`; а конфигурация `nativeOpen` шлюза пришпиливает возможность там, где детекция платформы (`canOpenNativePath`) ввела бы в заблуждение. Эти четыре пришпилены к loopback в [`dsh-client-connection`](../../client/connection/README.md): композиция называет плагины, которые исполняет сессия, так что чтение одной — разведка, а copy/remove/openDocument управляют ростером и ведут дела на хостовом рабочем столе. `list` и `select` остаются обыкновенными — ростер несёт id и trust, нужен каждому выборщику пресетов, а выбор пресета не даёт ничего сверх того, что давал собственный `agentPreset` у `session.create`, поверх дефолта, который уже несёт bash. `list` сообщает два свободных от путей флага возможности: `authorable` — настраивает ли развёртывание корень, куда можно скопировать новый пресет, и `hasDocument` — открыл бы `openDocument` документ нативно, а не ответил путём.

Домены `command.*` и `skill.*` раскрывают клиентам хостовый реестр команд и каталог скиллов. Каждый метод адресует агента одной сессии по `sessionId` (обслуживаемая сессия всегда имеет Agent; `command.*` возобновляет холодные сессии тем же путём, что и `session.*`, тогда как `skill.list` разрешает корень проекта из заголовка сессии, не трогая реестр Agent). `skill.list` обслуживает меню композера: он возвращает каждый вызываемый пользователем скилл с его флагом `modelInvocable`, чтобы меню помечало записи только для пользователя (`disable-model-invocation`), чей единственный путь вызова — слэш-жест. Листинг — единственный RPC домена скиллов; сам вызов — обычный `session.prompt`, в котором распознаваемые по границам пробелов токены `/имя` узнаются пакетом `dsh-tool-skill` на рубеже пред-шага и получают ответом инъецированный контекст `<skill_content>`, поэтому каждая точка входа (Web, TUI и ACP) делит один детерминированный путь — включая рукописный текст — без выделенного вызовного канала. `command.execute` исполняет слэш-строку команды на стороне хоста с чистой семантикой допуска: ответ сообщает, разрешилась ли строка в обработчик, и, если да, выпущенный жизненный `commandId` (согласуя подтверждение с узлом потока), тогда как исход едет в паре жизненного цикла `command/run`/`command/done`, записанной в журнал и транслируемой в mux-потоке. Обработчики команд могут законно переживать 30-секундный транспортный предел здоровья, поэтому `command.execute` несёт только отмену вызывающего/соединения; этот сигнал отменяет работающий обработчик. `commands/change` едет в кадре пересланного события как сигнал инвалидации каталога на весь реестр: клиенты перезапрашивают `command.list` вместо диффинга. Пересланный `agent-preset/selected` — его посессионная пара, испускаемая из записанного коммита выбора: пересборка агента пустой сессии перепривязывает его scope без какой-либо регистрации, поэтому оба каталога, которые решает композиция той сессии (`command.list`, `skill.list`), устаревают без изменения реестра, которое можно было бы анонсировать.

Домены `settings.*`, `credentials.*` и `llm.*` — провод страницы конфигурации. Домен настроек обслуживает каждое зарегистрированное пространство имён: плагин, распространяемый вне этого репозитория, становится настраиваемым из браузера простой регистрацией своей секции, без изменений здесь, и этот прокси не добавляет границы от себя — имя, на которое не отвечает ни одна регистрация, складывается в собственный `settings-rejected` этого seam. Какая поверхность рисует пространство имён — решение браузера (страница конфигурации плагинов ключует свои карточки по пространству имён), но никогда этого прокси. `settings.describe` возвращает сериализованную schemastery-схему каждого пространства имён, отредактированные слоёные значения (resolved/`base`/`user` — присутствие поля в `user` отмечает его как переопределённое пользователем), список slot'ов `secrets`, `revision` секции и логический флаг возможности `hasDocument`. Браузер не получает пути Host: свободный от путей `settings.openDocument` просит провайдера материализовать его документ, затем передаёт разрешённый Host результат нативному открывателю, поэтому никакая браузерная нагрузка не может выбрать произвольную цель файловой системы. `settings.update`/`settings.replace` пишут пользовательский слой; `settings.mutate` применяет операции по путям (`set`/`unset`) к секции, как она хранится, — это путь удаления для клиента, держащего отредактированный вид, ибо пересборка секции из него и замена целиком стёрли бы секреты, которые формат протокола никогда не возвращал. Любая запись может нести `expectedRevision`; устаревший отвечает `settings-conflict` с обеими ревизиями, не затирая писавшего, который приземлился первым, а всякий другой отказ seam складывается в `settings-rejected`. Значения секретных ролей никогда не едут ни в каком ответе ни в каком слое; секрет пересекает провод ровно в одном направлении — внутри нагрузки `update`/`mutate` или `credentials.set`. `credentials.describe` возвращает виды без значений (`configured`/`source`/`writable`), а `credentials.set`/`credentials.unset` отображают отказ по затенённой ссылке в `credential-rejected`. `llm.providers` сливает каталог настраиваемых провайдеров с живыми маршрутами (спящие записи несут `active: false`; необъявленные живые маршруты добавляются без адреса настроек), а `llm.models` — независимый от сессии каталог. `llm.discoverModels` допрашивает эндпоинт провайдера, который страница ещё только проектирует: `settingsNs` выбирает семейство адаптеров, знающее, как читать листинг, а эндпоинт, протокол и ключ приходят из формы, а не из хранилища. Метод ничего не пишет — ответ есть кандидаты, и лишь позднейший `settings.mutate` решает, чему служит маршрут, — поэтому его `apiKey` — третья нагрузка, на которой секрету разрешено ехать, рядом с `settings.update`/`mutate` и `credentials.set`. Хост никогда не хранит и не возвращает его; как и остальные два, он едет в исходящем конверте клиента, который видят наблюдатели `subscribeEnvelopes()`, а глушить эту точку наблюдения — изменение сразу всей конфигурационной плоскости, а не одного этого метода. Всякий отказ (необслуживаемое пространство имён, протокол без читаемого листинга, недостижимый эндпоинт, отвергнутый credential) складывается в `model-discovery-failed`, чьё сообщение — собственный текст адаптера, а детали называют спрошенный эндпоинт, но никогда предложенный credential. Инвалидации держат все поверхности сходящимися без опроса. `settings/document-updated` и `credentials/reference-updated` едут в дословном кадре пересланного события (см. ниже), поэтому сырое изменение настроек, чьё разрешённое значение не поменялось, всё ещё доходит до клиентов, а инвалидация credential несёт только имена ссылок, никогда значения. `llm/adapters-updated` пересылается рядом с `settings/document-updated`; конкретные потребители моделей подписываются на оба события-владельца напрямую, потому что топологические коммиты и документы настроек могут независимо менять свои каталоги. Браузерный carrier ограничивает всю плоскость конфигурации, включая чтения и нативные действия (`settings.describe`/`openDocument`/`update`/`replace`/`mutate`, `credentials.describe`/`set`/`unset`), loopback-запросами одного origin — это привилегированный набор `host.pickDirectory`. Композиция без провайдера настроек или credentials отвечает этим доменам действенной ошибкой `internal`, называющей недостающий плагин.

## Слой carrier (`/client` + root)

`AbstractApiClient` держит все протокольные инварианты — выпуск rpcId, заворачивание и разворачивание конвертов, zod-разбор, декодирование SSE-кадров, унарный таймаут, батчируемое микрозадачами наблюдение конвертов (`subscribeEnvelopes`) — тогда как платформенные подклассы поставляют только транспортный аспект `doFetch`. `InProcessApiClient` над `toFetchHandler(api)` остаётся изоморфной точкой для вызывающих и тестов carrier, которым нужен полный путь сериализации и валидации формата протокола без сети. Продуктовый `dsh --profile headless` — прямой вход в core, и этот пакет не монтирует.

## Известные ограничения и отложенная работа

- **Пересланные Remote-события паразитируют на этом устаревшем объединении кадров** — `host/remote-event` живёт в `HostFrame`, чтобы путь доставки мог переиспользовать существующий хостовый поток вместо открытия третьего нисходящего канала, из-за чего читается так, будто этот пакет владеет контрактом Remote-событий. Он им не владеет: allowlist принадлежит `dsh-api-remotes`, а потребительский глагол — `ctx.remote.$on`. Когда хостовый поток съедет с этого пакета, кадр съедет вместе с ним, и потребительский контракт не пострадает ([обоснование](../../../.agents/notes/implemented/architecture/2026-08-10-remote-event-delivery.md)).
- **Состояние ожидающего взаимодействия живёт на стороне хоста** — формат протокола использует POST `/api/respond` плюс `RpcReceipt`; таблица в `src/api-proxy.ts` обрабатывает только вопросы и не имеет записей согласований.
- **Ожидающий вопрос не переживает рестарт хоста** — реестр держит собственные `resolve`/`reject` ожидающего вызова инструмента, так что это память процесса хоста. `events.mux` переигрывает каждый всё ещё ожидающий вопрос при каждом повторном открытии, что покрывает перезагрузку браузера и переподключение; рестарт хоста забирает с собой ожидающий ход, и заново открытая Session не предлагает композера для того вопроса. Восстановление через рестарт хоста требует долговременной записи ожидающего взаимодействия и отложено.
- **Зарезервированные seam'ы остаются вне `RpcMethodMap`** — `prompt.mode: 'inject'`, `job.list` и описывающий `hostInstanceId` — документированные резервирования; обнаружение моделей использует `llm.models`. Неизвестный метод падает с явной ошибкой на разборе конверта, а не получает код not-implemented.
- **Поля версии протокола нет** — клиент и хост поставляются вместе; `host.describe` получит поле согласования версий, лишь когда появится независимо выпускаемый клиент.
- **Отказы поиска включают диагностику провайдера** — шлюз есть локальный однопользовательский сервис. Carrier, предоставляющий его нескольким пользователям, обязан заменить внутренние детали поиска диагностикой, пригодной для публикации.
- **Нативный выборщик Linux требует настольного инструментария** — под возможностью `native` метод `host.pickDirectory` сообщает действенную ошибку, когда не установлен ни Zenity, ни KDialog; бэкенд browse остаётся запасным вариантом на уровне композиции (см. [README нативного бэкенда](../directory-picker-native/README.md)).
- **Подсказки холодного списка деградируют только в сторону видимости и более старого упорядочивания** — промах кэша проекции или устаревший `lastPromptAt` откатываются к `createdAt`, если только подходящий малый артефакт не даст точную свёртку, поэтому недавно работавшая крупная Session может сортироваться слишком низко до следующего чекпоинта. Пустой артефакт крупнее `coldBlankProbeMaxBytes` или артефакт от бэкенда без `locate()` остаются видимыми. Порог проверяется перед `readFrom()`, а не закрепляется персистентностью, поэтому конкурентный рост артефакта может увеличить стоимость чтения одной пробы, не меняя безопасность определения пустоты. Этим направлением безопасности владеет [решение об ограниченной проверке пустоты](../../../.agents/notes/implemented/bug-fix/2026-08-13-bounded-cold-blank-verification.md); авторитетный точный индекс свежести остаётся в рамках [предложения last-activity-index](../../../.agents/notes/proposed/architecture/2026-07-29-durable-last-activity-index.md).
