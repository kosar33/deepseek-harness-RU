# @deepseek-ai/dsh-llm-deepseek

[English](README.md) | [中文](README.zh.md) | Русский

Адаптер chat-completions DeepSeek для LLM-seam'а харнесса: прямой `fetch` + SSE (разбор кадров через `eventsource-parser`), переводящий официальный формат протокола (источник истины: документация API — guides/thinking_mode, guides/tool_calls, api/create-chat-completion) в протокол `StreamChunk`.

Вторая, основанная на библиотеке реализация того же seam'а существует в `@deepseek-ai/dsh-llm-pi-ai`. Этот пакет владеет маршрутом провайдера `deepseek-official` — намеренно отличным от каталожного имени pi-ai `deepseek`, — чтобы одна композиция могла держать оба пути DeepSeek рядом; попытка зарегистрировать другой адаптер для самого `deepseek-official` по-прежнему приводит к ошибке `LlmError('DUPLICATE_ADAPTER')`.

Корень пакета экспортирует контракт плагина Cordis и `DeepSeekAdapter`; вспомогательные функции сериализации протокола, разбора SSE и перевода чанков не входят в этот корневой контракт.

## Конфигурация

```yaml
- id: llm-deepseek
  name: '@deepseek-ai/dsh-llm-deepseek'
  config:
    apiKeyEnv: DEEPSEEK_API_KEY  # default; resolved per request via ctx.credentials, then the environment
    baseURL: https://api.deepseek.com # optional; $DEEPSEEK_BASE_URL then the public API when omitted
    thinking: enabled        # optional; provider default is enabled
    reasoningEffort: high    # optional; off | low | high | max — omitted ⇒ high
    maxTokens: 256000        # optional positive per-request output cap; this is the default
    streamIdleTimeoutMs: 300000 # optional; positive finite Node timer delay; five-minute default
    maxRequestFilesBytes: 134217728 # optional positive integer; 128 MiB raw request-image default
    maxInlineRequestImageBytes: 20971520 # base64 fallback high watermark; 20 MiB default
    maxImagesPerRequest: 600       # provider request image-count limit
    imageOffloadByteQuantum: 67108864 # oldest-image removal advances in 64 MiB steps
    inlineImageOffloadByteQuantum: 10485760 # fallback removal advances in 10 MiB steps
    imageOffloadCountQuantum: 20      # count overflow advances in 20-image steps
    filesApiTimeoutMs: 60000           # per-image Files resolution deadline; one-minute default
    fileExpiresAfterSeconds: 604800   # uploaded image lifetime; 1 hour to 30 days
    fileRefreshMarginSeconds: 3600    # replace ids with less lifetime remaining
    fileQuotaCleanupBatch: 100        # oldest harness-owned files deleted before one quota retry
    retryPolicy:             # optional; omission uses normal mode with five retries
      mode: always           # normal | always
      backoff:
        initialDelayMs: 500
        maxDelayMs: 10000
        jitterRatio: 0.1
    defaultContextWindow: 1000000 # optional positive-integer fallback; this is the default
    models:                  # optional; defaults to V4 Flash, V4 Pro, and V4 Flash Vision Exp
      - id: deepseek-v4-flash
        name: DeepSeek-V4-Flash
      - id: deepseek-v4-flash-vision-exp
        name: DeepSeek-V4-Flash-Vision-Exp
        inputModalities: [text, image]
        imagePixelBudget: 640000
        imageMaxBytes: 1048576
      - id: private-reasoner
        description: Company-hosted reasoning model
        contextWindow: 512000
```

Плагин регистрирует единственный маршрут провайдера `deepseek-official` вместе с разрешённой политикой повторов `retryPolicy`; пропуск означает обычный режим с пятью повторами. Запрос выбирает его через `provider: deepseek-official`; поле `model` передаётся дальше как строка `model` протокола, поэтому смена моделей DeepSeek не требует регистрации на этапе жизненного цикла. Без `models` объявляются `deepseek-v4-flash`, `deepseek-v4-pro` и поддерживающая изображения `deepseek-v4-flash-vision-exp`, каждая с контекстным окном в 1 000 000 токенов; явный список замещает эти значения по умолчанию, а `models: []` не объявляет ничего. Записи каталога доступны через `ctx.llm.listModels('deepseek-official')` для клиентов вроде редакторов ACP и веб-селектора, но остаются справочными: необъявленные id моделей по-прежнему проходят без изменений как маршруты только с текстом. Пропущенное имя записи по умолчанию равно её id, а пропущенные `inputModalities` означают только `text`.

Запись каталога с поддержкой изображений объявляет `inputModalities: [text, image]` и может задавать `imagePixelBudget`, `imageMaxBytes` или `imageDetail: low`. Обычные значения по умолчанию — 640 000 суммарных пикселей и 1 МиБ закодированных байтов; низкая детализация по умолчанию составляет 512 на 512 суммарных пикселей. Хранилище вложений масштабируется по `min(1, sqrt(pixelBudget / (width * height)))` с округлением внутрь, чтобы число пикселей оставалось в пределах жёсткого потолка, поэтому нормализованное вложение 2048 на 1024 превращается примерно в 1130 на 565, а не в принудительный квадрат. Кодировщики запроса работают лениво: изображения с малым числом цветов пробуют PNG (только палитра, без альфы), затем WebP 85 и 80; прочие изображения с альфой пробуют WebP 85, затем 80; прочие непрозрачные — JPEG 85, затем 80; размеры уменьшаются, лишь когда обе попытки качества превышают 1 МиБ. Параллельная генерация одного `variantId` использует одно общее преобразование. Вызывающий может отменить своё ожидание, не прерывая других ожидающих; когда ожидающих не остаётся, преобразование прекращается. Обычно адаптер загружает точные производные байты запроса через `POST /files` и отправляет блоки `{type: "file", file_id}`. Неудавшееся или не уложившееся в срок разрешение file id перестраивает весь запрос чата с теми же версиями запроса в виде base64 data URL; один запрос никогда не смешивает file id и встроенные изображения. Перед каждым удержанным изображением стоит стабильный текст, называющий полный id вложения и фактические размеры изображения запроса. Эту проекцию используют запросы пользователя, результатов инструментов, цикла агента, компакции и прямые вызовы `ctx.llm.stream`. Маршруты только с текстом получают стабильные плейсхолдеры вложений, а долговременная история сохраняет свои ссылки на изображения.

`maxRequestFilesBytes` и `maxImagesPerRequest` ограничивают удерживаемые версии запроса по умолчанию 128 МиБ и 600 изображениями. Квант по байтам и квант по количеству не должны превышать соответствующих им пределов. Перед чтением вложений адаптер использует байтовый потолок версии запроса каждого маршрута как консервативную верхнюю границу и удаляет старейший сверхбюджетный префикс; читаются и преобразуются только удержанные нормализованные вложения. Точные производные длины проверяются вновь без восстановления опущенных изображений. При переходе через байтовый предел старейший префикс сдвигается за следующую границу 64 МиБ: 129 одномегабайтных изображений удаляют старейшие 65 и удерживают 64 МиБ, и этот префикс остаётся неизменным, пока долговременная история не превысит 192 МиБ. Переполнение по количеству сдвигается независимо шагами `imageOffloadCountQuantum`. Удалённые изображения превращаются в фиксированный видимый модели плейсхолдер `[image omitted to keep the request within its image limit; older images are omitted first. If this image is still needed, read its file again when a path is available; otherwise ask the user to attach it again.]`. Такая проекция с верхней отметкой позволяет не менять старый префикс запроса после каждого нового изображения.

У встроенного резервирования независимый бюджет base64. `maxInlineRequestImageBytes` по умолчанию равен 20 МиБ, а `inlineImageOffloadByteQuantum` — 10 МиБ, поэтому история из 21 одномегабайтной полезной нагрузки base64 удаляет старейшие 11 и удерживает 10 МиБ. Расчёт использует длины в развёрнутом base64. Подготовленные версии запроса переиспользуются байт-в-байт; резервирование не декодирует и не сжимает изображение заново. Успешные сопоставления, созданные до отказа более позднего изображения, остаются проиндексированными для будущих запросов.

Загруженные id индексируются под `DSH_HOME` по области эндпоинт/API-ключ и по `variantId` запроса. Вариант охватывает нормализованный id вложения, версию преобразования, пиксельный и байтовый бюджеты маршрута и параметры кодировщика, так что Files API и встроенное резервирование ссылаются на одни и те же детерминированные байты. Загрузки по умолчанию запрашивают семидневный срок жизни и сохраняют серверное `expires_at`. Локальное сопоставление, у которого остаётся не более часа, заменяется до использования; адаптер не проверяет каждый удалённый файл перед чатом. Если чат сообщает об истёкших, удалённых, отсутствующих или недействительных file id и называет один или несколько использованных запросом id, адаптер удаляет ровно эти сопоставления. Если провайдер указывает на устаревшее состояние файлов, не называя id, адаптер удаляет все сопоставления файлов, использованные этой попыткой чата. Затем он заново загружает затронутые версии запроса и повторяет чат однократно. Второй отказ из-за устаревших файлов очищает сопоставления, названные этим ответом, и возвращается без третьей попытки чата. Ответ загрузки без полного объекта файла, совпадающего числа байтов и `expires_at` никогда не индексируется; последующий запрос поэтому загружает заново, вместо того чтобы доверять несогласованному локальному состоянию. Искажённый локальный индекс загрузок трактуется как пустой кэш и замещается следующей успешной загрузкой. Разрешение файла, включая доступ к локальному индексу и удалённую загрузку, имеет по умолчанию предельный срок — одну минуту на изображение. Поэтому пятиминутный предел простоя потока оставляет время для встроенного резервирования; развёртывание может настроить более короткий предел простоя потока, если хочет, чтобы внешний предел завершил запрос первым. Каждое успешное разрешение освежает внешний сторожевой таймер простоя. Любой сбой разрешения переключает этот запрос во встроенный режим, тогда как явные публичные операции управления файлами продолжают сообщать о собственных сбоях.

Параллельное разрешение одного ограниченного областью `variantId` использует одну общую загрузку Files с отменой на уровне отдельных ожидающих. Одиночный сбой загрузки по квоте сначала постранично собирает настроенное количество старейших файлов `dsh-`, затем удаляет этот набор перед одной повторной попыткой загрузки. `DeepSeekFilesClient.delete`, `DeepSeekFileStore.release` и `releaseAll` предоставляют явное освобождение пространства на удалённой стороне. Представляемые этим пакетом актуальные ограничения провайдера: 128 МиБ на загрузку Files, 32 МиБ на изображение, упомянутое в чате, 10 000 хранимых файлов и 25 ГиБ на API-ключ; версия запроса по умолчанию в 1 МиБ остаётся ниже обоих пофайловых пределов.

`contextWindow` необязателен для каждой настроенной модели и не раскрывается через справочный каталог. `ctx.llm.resolveModelInfo('deepseek-official', model).context` сначала возвращает точное значение модели, затем `defaultContextWindow` для записи без ёмкости или для необъявленного сквозного id. Адаптер по умолчанию использует 1 000 000, поэтому плагины, чувствительные к заполнению контекста, получают принадлежащую развёртыванию ёмкость, не считая селектор моделей авторитетным. Регистрация другого адаптера для `deepseek-official` приводит к ошибке `LlmError('DUPLICATE_ADAPTER')`.

`maxTokens` — настраиваемый на адаптере потолок вывода для запросов беседы, по умолчанию 256 000. Запись каталога может нести собственный `maxTokens`, который выигрывает для своей модели; запись без него и любой необъявленный сквозной id разрешаются в значение профиля, поэтому добавление потолка для отдельной модели меняет одну модель, а не маршрут. Разрешение по точной модели выдаёт победителя как `defaultMaxTokens`; `LlmRuntime` подставляет это значение в `GenerateOptions.maxTokens` до того, как цикл агента запишет `request/header`, поэтому запрос протокола остаётся восстановимым. Явное значение в запросе или `AgentOptions.maxTokens` выигрывает и сериализуется как `max_tokens`. Адаптер не ограничивает этот бюджет запроса по `contextWindow`; развёртывания с меньшим контекстом или лимитом вывода провайдера должны настроить совместимый `maxTokens`.

Тот же результат точной модели выдаёт упорядоченные усилия `off`, `low`, `high` и `max` в поле `reasoning` для каждой сквозной модели, когда политика развёртывания разрешает thinking. `reasoningEffort` выбирает значение по умолчанию для развёртывания и при пропуске возвращается к `high`. `agent/request` может заменить его на каждом шаге беседы; разрешённое значение журналируется в `request/header`. Значения `low`, `high` и `max` включают thinking и сериализуются как то же официальное верхнеуровневое значение `reasoning_effort`; принадлежащий адаптеру `off` вместо этого сериализует `thinking.type: disabled` и опускает `reasoning_effort`. Неподдерживаемое значение приводит к ошибке `UNSUPPORTED_REASONING_EFFORT` до сетевого ввода-вывода.

`thinking: disabled` — блокировка на уровне развёртывания, публикующая только `off` со значением по умолчанию `off`. Пропуск `reasoningEffort` или настройка его в `off` допустимы; настройка `low`, `high` или `max` приводит к ошибке загрузки плагина, а прямая попытка включить thinking на отдельном запросе завершается неудачей до сетевого ввода-вывода. Запрос с `GenerateOptions.purpose: 'session-title'` также принудительно отключает thinking и опускает уже разрешённое усилие, резервируя ограниченный вывод под видимый текст заголовка, не меняя значений по умолчанию для беседы и компакции.

`streamIdleTimeoutMs` ограничивает каждое незавершённое чтение от провайдера, включая исходный `fetch`, не считая времени, которое потребитель проводит между чанками. Комментарии SSE DeepSeek и успешные разрешения файлов перезаводят незавершённое чтение как транспортную активность, но никогда не становятся значениями `StreamChunk` или событиями журнала сессии. Один стабильный сигнал отмены достигает запроса и читателя тела на всём протяжении вызова; истечение срока останавливает транспорт и выбрасывает `LlmError('TIMEOUT')`, тогда как более ранний отменяющий сигнал вызывающего выбрасывает `LlmError('ABORTED')`. Обычно адаптер выполняет один запрос чата на вызов `stream()` и делает второй только для восстановления после устаревших файлов. Сбой разрешения файла до первого чата отправляет один встроенный запрос. Если замещающее разрешение не удалось после ответа об устаревших файлах, встроенный запрос и есть единственная дозволенная повторная попытка. Он регистрирует настроенную политику повторов как метаданные провайдера, а `dsh-llm-retry` отдельно исполняет эту политику на долговременных границах шагов агента.

## Динамическая конфигурация (настройки + учётные данные)

Факты соединения не замораживаются при загрузке. `resolveAdapterOptions` — единственный явный шаг разрешения из сырой конфигурации в проверенные факты, и адаптер перечитывает их через thunk **один раз за операцию**: базовый URL, каталог, значения запроса по умолчанию, политики изображений и Files, и бюджет простоя вступают в силу на следующем запросе, тогда как незавершённый поток сохраняет факты, с которыми начался. Этот thunk питают три необязательных seam'а:

- **`ctx.settings`** — плагин регистрирует пространство имён `llm-deepseek` с той же схемой `Config`, а запись своего `cordis.yml` — базой композиции, поэтому секция `llm-deepseek:` в пользовательском документе настроек переопределяет любое поле без перезапуска. Без смонтированного сервиса настроек адаптером управляет одна конфигурация записи, без изменений. Живой снапшот настроек, прошедший схему, но нарушивший выходящее за её пределы ограничение (дублирующийся каталожный id, сломанная пара thinking/усилие), сохраняет последние корректные факты и журналирует сбой; сама конфигурация записи по-прежнему приводит к ошибке загрузки плагина.
- **`ctx.credentials`** — API-ключ разрешается на каждом вызове потока из *того же* разрешённого снапшота, что поставляет эндпоинт. Конфигурация несёт только `apiKeyEnv`, никогда литеральный ключ: ссылка разрешается через credential-seam, а без смонтированного seam'а — через доверенные слои окружения. Поскольку факты учётных данных перемещаются вместе с фактами соединения, снапшот настроек, отвергнутый резолвером, не даёт ни эндпоинта, ни ключа: всё предыдущее поколение продолжает обслуживать. Каждый разрешённый ключ проходит проверку формата перед использованием, поэтому значение, которое не способен нести ни один HTTP-заголовок, отвергается с `LlmError('INVALID_CREDENTIAL')`, называющим отказавшую точку входа конфигурации, — никогда какую-либо часть ключа, — вместо того чтобы проявиться непрозрачной `TypeError` от `fetch`. Если ключ недоступен нигде, запрос завершается ошибкой `MISSING_CREDENTIAL`, называющей все точки входа конфигурации, при этом маршрут остаётся зарегистрированным, а каталог просматриваемым — первичный онбординг выглядит как «посмотри модели, сохрани ключ, спроси снова», без перезапуска между шагами.
- **`ctx.attachments`** — запросы изображений разрешают этот сервис в момент запроса, поэтому порядок загрузки Cordis не замораживает необязательную доступность изображений. Отсутствие отвергает входные изображения с `UNSUPPORTED_CONTENT`; вызовы только с текстом сервис не требуют.

Единственный факт, захватываемый при регистрации, — политика повторов: когда её разрешённое значение меняется, плагин перерегистрирует маршрут на месте (тот же экземпляр адаптера, одна синхронная секция), поэтому `ctx.llm.providerRetryPolicy('deepseek-official')` всегда сообщает актуальную политику.

Плагин также объявляет свой маршрут в каталоге конфигурируемых провайдеров (`ctx.llm.listConfigurableProviders()`): провайдер `deepseek-official`, пространство имён настроек `llm-deepseek`, пустой путь настроек — вся секция и есть профиль. Интерфейсы конфигурации используют эту запись, чтобы предлагать адаптер рядом со спящими провайдерами pi-ai.

## Атрибуция приложения

Каждый запрос чата и Files API несёт общий заголовок атрибуции из `attributionHeaders()` dsh-llm — обязательную базовую строку `User-Agent`, идентифицирующую харнесс (см. [dsh-llm, «Атрибуция приложения»](../llm/README.ru.md#атрибуция-приложения-attributionts)). Прямые запросы DeepSeek и запросы к OpenAI-совместимому шлюзу не получают зависящих от провайдера заголовков атрибуции приложения в рамках контракта этого адаптера; атрибуция приложения OpenRouter отложена до будущего явного адаптера или режима OpenRouter. Запрос, чей `GenerateOptions.purpose` равен `compaction` (вспомогательный вызов суммирования dsh-compaction-basic), дополнительно несёт `x-deepseek-harness-compact: 1`, чтобы хост мог отделить трафик компакции от запросов беседы.

Идентичность запроса DeepSeek отделена от атрибуции приложения. После разрешения учётных данных каждый запрос к провайдеру несёт `x-deepseek-harness-user-id` со стабильным анонимным id из [`@deepseek-ai/dsh-anonymous-user-id`](../../identity/anonymous-user-id/README.md); запрос, несущий `GenerateOptions.sessionId`, также отправляет это точное значение как `x-deepseek-harness-session-id`, тогда как прямой вызов без сессии опускает заголовок сессии. Оба заголовка уходят на разрешённый `baseURL`, включая настроенный шлюз, и остаются вне тела запроса и видимого модели содержимого.

## Замечания о формате протокола

- Только потоковая передача (`stream_options.include_usage` всегда включён). `usage` может прийти прикреплённым к чанку завершения или как замыкающий чанк только с usage — переводчик откладывает оба до `[DONE]`, поэтому `usage` всегда предшествует `finish`, и ничто не следует за `finish`.
- Принадлежащее адаптеру усилие `off` отображается в `thinking: {type: 'disabled'}` и никогда не передаётся как `reasoning_effort: 'off'`.
- Первый чанк режима thinking несёт `reasoning_content: ""` — обработано (без ложного блока рассуждений).
- **Правило возврата рассуждений**: каждый ход ассистента, нёсший рассуждения, сериализует `reasoning_content` обратно в историю. Режим thinking требует его на ходах с вызовами инструментов; DeepSeek игнорирует его в остальных случаях, а шлюз, перекодирующий беседу для другого вендора, восстанавливает исходную подпись thinking того хода хешированием воспроизведённого текста.
- Сообщения пользователя с поддержкой изображений сохраняют порядок текста и изображений. Содержимое роли инструмента остаётся строкой; последовательные изображения результатов инструментов группируются в следующее сообщение пользователя с префиксом `Attached image(s) from tool result:`.
- Учёт кэша: `cacheReadTokens` ← `prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens`; метрику записи кэша DeepSeek не сообщает.

## Ошибки

Ответы вне 2xx выбрасывают `LlmError` со стабильными кодами: `AUTH` (401/403), `QUOTA` (ответ, чьи детали провайдера указывают на исчерпанную квоту, баланс или кредиты), `RATE_LIMIT` (прочие 429), `CONTEXT_WINDOW_EXCEEDED` (400, чей код, тип или сообщение провайдера указывают на переполнение контекста), `INVALID_REQUEST` (прочие 400 и 413), `SERVER` (5xx), иначе `HTTP_<status>`. Его сериализуемое поле `failure` сохраняет HTTP-статус плюс действительную положительную задержку `Retry-After` в секундах или датой, а также `x-request-id` / `x-deepseek-request-id`, когда они присутствуют. Если DeepSeek отвергает нормализованное изображение, основное сообщение называет вложение или отображаемое имя, позицию сообщения и изображения в долговременной истории, нормализованный медиатип, 8-битную глубину sRGB/sRGBA, размеры и сообщение провайдера. При нескольких кандидатах и отсутствии file id в деталях провайдера перечисляется каждое возможное изображение, вместо того чтобы приписывать сбой первому. Сырой ответ остаётся `cause` ошибки; он никогда не бывает единственным видимым пользователю диагностическим сообщением. Чтения вложений сохраняют свой стабильный код сбоя вложения, а не превращаются в транспортные сбои. Транспортный сбой до ответа (DNS, отказ в соединении, TLS, прокси) выбрасывает `TRANSPORT`, называющий настроенный эндпоинт и присоединяющий исходный отказ как `cause`; отмены вызывающего выбрасывают `ABORTED`, и сигнал отмены цикла остаётся авторитетным. Нарушения протокола выбрасывают `STREAM_CLOSED` (нет `[DONE]`) или `MALFORMED_RESPONSE` (испорченная полезная нагрузка JSON). Неизвестные протокольные причины завершения (`finish_reason`, например `content_filter`, `insufficient_system_resource`) превращаются в чанки `finish {kind: 'error', failure}`, а завершившийся поток, финальный `finish` которого (`stop` или отсутствующий) не открыл ни одного блока содержимого, становится `finish {kind: 'error'}` с кодом `EMPTY_RESPONSE` (повторяется политикой по умолчанию).

## Влияние на модель

### Запрос DeepSeek

#### Что видит модель

Выбранная модель DeepSeek получает системный промпт харнесса, историю сообщений, схемы инструментов, стоп-последовательности и конфигурацию вызова. Визуальная модель обычно получает удержанные изображения пользователя и результатов инструментов как ссылки Files API рядом со стабильными дескрипторами вложений и размерами изображений запроса; сбой разрешения Files отправляет все удержанные изображения как встроенные data URL. Старое сверхбюджетное изображение представлено документированным плейсхолдером. Содержимое рассуждений из предыдущего хода ассистента передаётся обратно дословно, вызвал ли тот ход инструмент или нет.

#### Влияние на токены

Точное входное содержание в токенах текста и изображений определяет токенизация провайдера. Возврат рассуждений переносит цепочку рассуждений каждого хода с рассуждениями в позднейшие запросы, а вытеснение сверхбюджетных изображений избавляет от повторной оплаты этих токенов; расход чтения из кэша сообщается, когда доступен.

#### Влияние на KV-кэш

Неизменённый собранный префикс, включая детерминированно закодированные удержанные изображения и плейсхолдеры, допускает повторное использование кэша DeepSeek, которое этот адаптер сообщает в расходе токенов. Смена маршрута модели или любое изменение вышестоящего промпта, схемы, префикса, истории или бюджета изображений могут пресечь повторное использование с первого изменённого токена; возврат рассуждений дописывает на каждом ходу с рассуждениями.

### Ответ DeepSeek

#### Что видит модель

Рассуждения, текст и сырые строковые аргументы инструментов переводятся в чанки харнесса, которые цикл журналирует и собирает.

#### Влияние на токены

Сгенерированные токены следуют залогированному усилию рассуждения запроса и его `maxTokens`; на позднейший вход влияют только удержанные циклом блоки.

#### Влияние на KV-кэш

Удержанные циклом блоки ответа дописываются к следующему запросу и сохраняют его более ранний пригодный для повторного использования префикс; отброшенные блоки не имеют позднейшего эффекта на кэш. Смена провайдера или модели выбирает другой домен кэша.

## Известные ограничения и отложенная работа

- **Список `models` из настроек замещает список композиции целиком** — слияние слоя настроек идёт по полям, а массивы — одно поле; слияние каталога по записям потребовало бы структуры с ключами.
- **`tool_choice` не отображается** — не входит в основной словарь ядра (урезано на этапе MVP, общее с парным пакетом pi-ai).
- **Запросы используют сырой `fetch`, а не `@cordisjs/plugin-http`** — нет общей конфигурации прокси/перехвата; внедрение отложено, пока его не захочет второй адаптер (`TODO(http)`).
- **Добавленные плагинами типы блоков содержимого пропускаются** — сериализуются основные текстовые и поддерживаемые графические блоки, а пустой вывод инструмента попадает в протокол как литерал `(no output)`.
- **Изображения — долговечные вложения, работающие только на вход** — прямые внешние URL и вывод изображений ассистентом не поддерживаются; вход DeepSeek обычно пользуется Files API, а встроенный base64 — только для восстановления в пределах одного запроса.
