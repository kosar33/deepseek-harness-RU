# `@deepseek-ai/dsh-llm-key-rotation`

[English](README.md) | [中文](README.zh.md) | Русский

Функциональный плагин: позволяет уже существующему маршруту провайдера переживать по-ключевые ограничения 429 ротацией нескольких API-ключей. Он присоединяется к маршрутам, которые обычные семейства адаптеров — dsh-llm-pi-ai и dsh-llm-deepseek — уже зарегистрировали, подменяет только разрешение учётных данных настроенных маршрутов упорядоченным пулом ключей и восстанавливает ограниченный запрос на каскаде `agent/request-error` агентного цикла раньше любой политики повторов. Все остальные поля профиля остаются у домашней секции маршрута.

Каждый элемент в `providers` ключуется идентификатором существующего маршрута и несёт только упорядоченный список `keys`. Каждый ключ называет ровно один источник: ссылку на учётные данные (`apiKeyEnv`, разрешается при каждом запросе через шов credentials) или литерал `value` (попадает в файл композиции дословно, только для разработки). Необязательный `label` называет ключ в логах; по умолчанию это имя ссылки или позиция с единицы. При загрузке плагин проверяет каждый элемент: отсутствующий или двойной источник ключа, дубликаты меток, кривые ссылки и пустые литералы роняют монтирование; поле `apiKeyEnv` на элементе маршрута отвергается — оно принадлежит собственному профилю маршрута. Маршрут, который не обслуживает ни одно семейство, оставляет инертный пул: безвредно и достижимо только правкой композиции вручную, ведь веб-редактор пишет ключи лишь на живые карточки провайдеров.

Подмена идёт через необязательный сервис `llmApiKeyOverride`, который предоставляет плагин; семейства адаптеров спрашивают его до собственного разрешения креденшела и уходят в него при ответе `undefined`. Регистрация адаптеров потому не трогается вовсе — регистрирующее семейство остаётся единственным владельцем маршрута, и ротация провайдера не может создать дублирующую регистрацию. Ключ пула, чья ссылка не разрешается, роняет запрос с `MISSING_CREDENTIAL`, называя ключ пула, а не молча откатывается к нативному одиночному ключу: неверно настроенный пул не имеет права тихо прекратить ротацию.

На каждый процесс — одна липкая позиция. При `RATE_LIMIT`-сбое много-ключевого маршрута слушатель откладывает обслуженный ключ до момента сброса — `providerRetryAfterMs` от адаптера, когда тот его отдаёт, иначе первая разбираемая подсказка из тела (ISO-штамп `reset_at`/`x-ratelimit-reset`, секунды в `retry-after` или формулировка OpenAI «try again in Ns»), иначе ближайшая полночь UTC, ограничивающая дневные квоты, — сдвигается на первый не отложенный ключ и возвращает `{ kind: 'retry' }`, так что цикл немедленно повторяет идентичный запрос следующим ключом без планового ожидания. Каждая переключение пишется стандартным логгером — оба ключа и момент сброса; в журнал сессии ничего не попадает. Когда отложены все, ошибка несёт код `KEY_POOL_EXHAUSTED` и перечисляет каждый ключ с моментом сброса — каждая запись дополнена укороченным фрагментом апстрим-текста, вызвавшего откладывание. Откладывания истекают лениво при чтении: таймеров нет, и отложенный ключ возвращается в строй ровно в свой момент сброса.

Два вида сбоев ротируют без откладывания. Лимит, чьё сплющенное тело называет общий апстрим-пул шлюза (`limit_source: upstream_provider_shared_pool`), оставляет ротацию нетронутой для обычного бэкоффа на том же ключе: обслуженный ключ ни при чём. Сбой, читаемый как ретрансляция шлюзом ошибки его апстрим-вендора («Provider returned error»), сначала передаётся обычной экспоненциальной цепочке ретраев на том же ключе — видимые строки ретрая с сырой сетевой ошибкой — и лишь когда цепочка исчерпана, ротация сдвигается на следующий ключ и повторяет там; парковки нет ни на одном шаге.

Откладывания переживают рестарт. Каждый сохраняется в `.llm-key-rotation-parks.json` рядом с `.credentials.yaml` в home harness — местоположение переопределяет `parkFile`, а исходимый home — `dshHome`. Документ хранит только метки и метки времени, никогда значения ключей; переписывается атомарно в режиме owner-only при каждом изменении откладываний или их истечении. При монтировании истёкшие строки выбрасываются, строки с исчезнувшими маршрутами или метками обрезаются, живые откладывания заново прикрепляются по маршруту и метке, а пул с отложенной липкой позицией стартует с первого пригодного ключа. Отсутствие документа — пустое состояние; битый или чужой версии документ роняет монтирование громко, с названным путём. Неудавшаяся запись персистентности лишь громко логируется, и ротация продолжает работу в памяти до конца запуска.

Слушатель регистрируется с `prepend`, поэтому ротация всегда впереди обычных политик восстановления независимо от порядка монтирования: отложенный ключ обходится прежде, чем dsh-llm-retry успеет назначить тот же ключу бэкофф на этот самый сбой, а повторная попытка при новой неудаче входит в dsh-llm-retry свежей. Одно-ключевые пулы делегируют любой сброй нетронутым — поведение совпадает с нативным разрешением, включая политику повторов и бэкофф. Не-`RATE_LIMIT` сбои и сбои маршрутов без пула делегируются как есть. Как есть делегируется и `RATE_LIMIT`, чьё сплющенное тело называет ограничителем общий апстрим-пул провайдера (`upstream_provider_shared_pool` — так OpenRouter сообщает о троттлинге, не связанном с ключом вызывающего): парковка отправила бы все здоровые ключи в простой до запасного горизонта, тогда как квота самого обслуженного ключа не тронута, а настоящее лекарство — короткое ожидание, то есть обычный бэкофф на том же ключе.

```yaml
# The route itself lives in its home section, as any provider does:
- id: llm-openrouter
  name: '@deepseek-ai/dsh-llm-pi-ai'
  config:
    providers:
      openrouter:
        displayName: OpenRouter
        api: openai-completions
        baseURL: https://openrouter.ai/api/v1
        models:
          - id: anthropic/claude-sonnet-4.5
            name: Claude Sonnet 4.5
            contextWindow: 200000

# This plugin adds only the rotating keys for that same route id:
- id: llm-openrouter-keys
  name: '@deepseek-ai/dsh-llm-key-rotation'
  config:
    providers:
      openrouter:
        keys:
          - apiKeyEnv: OPENROUTER_KEY_1
          - apiKeyEnv: OPENROUTER_KEY_2
          - apiKeyEnv: OPENROUTER_KEY_3
            label: spare
```

Значения ссылок кладутся в `$DSH_HOME/.credentials.yaml` под `refs:` (этот документ пишет веб-страница «Моделей») либо экспортируются в окружении запуска; композиция без шва credentials опирается только на окружение.

## State surface

Плагин сразу при композиции предоставляет state face, который другие плагины читают через `ctx.get('llmKeyRotation')`. Метод `snapshot()` рендерит каждый настроенный маршрут; пригодность в снапшоте — view-only: чтение не трогает ни состояние пулов, ни файл. Значений ключей здесь нет. `resetParks(route)` снимает все живые парковки одного маршрута разом — и в памяти, и в файле: аварийный выход для ложных парковок, например вызванных троттлингом апстрима; возвращает признак того, было ли что снимать.

```json
[
  {
    "provider": "openrouter",
    "activeLabel": "OPENROUTER_KEY_2",
    "keys": [
      {
        "provider": "openrouter",
        "label": "OPENROUTER_KEY_1",
        "source": "reference",
        "reference": "OPENROUTER_KEY_1",
        "status": {
          "state": "parked",
          "parkedAt": "2026-08-24T12:00:00.000Z",
          "resetAt": "2026-08-25T00:00:00.000Z"
        }
      },
      {
        "provider": "openrouter",
        "label": "OPENROUTER_KEY_2",
        "source": "reference",
        "reference": "OPENROUTER_KEY_2",
        "status": { "state": "usable" }
      }
    ]
  }
]
```

Каждый элемент `keys` несёт `provider`, `label`, `source` — `reference` с именем в поле `reference` либо `literal` для дев-литерала (поля reference нет вовсе) — и `status`: `{ state: 'usable' }` или `{ state: 'parked', parkedAt, resetAt }` с моментами ISO 8601 UTC. Виджет настроек рендерит «лимит откатится через N ч M мин», вычитая текущее время из `status.resetAt` — без каких-либо внутренних деталей плагина. `activeLabel` называет позицию, которой следующий запрос будет аутентифицироваться; когда отложены все — застрявшую позицию, с которой запрос упадёт. Лицо отсутствует, пока плагин спит (ни одного настроенного маршрута).

## Model Experience

### Model-request recovery

#### What the model sees

Ни ротация, ни откладывание, ни момент сброса, ни личность ключа модели не видны. Повторный запрос несёт идентичные историю сообщений, инструменты и конфигурацию вызова; меняется только значение заголовка `Authorization`.

#### Token effect

Каждое переключение ключа повторяет один запрос провайдера с биллингом входных токенов до всякого вывода; само переключение и есть восстановительное действие `{ kind: 'retry' }`, в журнал сессии оно не пишется. Откладывание прекращает траты на исчерпанные ключи до их сброса вместо траты повторов на них.

#### KV Cache effect

Повторный запрос сохраняет прежний префикс и может попасть в кэш провайдера по его правилам. На провайдерах с почаккаунтовым кэшем разные ключи обычно держат отдельные кэши.

## Known Limitations and Deferred Work

- **Точность сброса зависит от того, что пережило сплющивание** — на пути pi-ai сетевые ошибки приходят сплющенными до текста сообщения: заголовки теряются, поэтому `providerRetryAfterMs` отсутствует и точность держится на маркерах, которые провайдеры кладут в сам payload (`reset_at`, `retry-after`, «try again in Ns»); тело без единого маркера откладывается до ближайшей полуночи UTC, а pass-through апстрим-пула читает то же сплющенное тело по стабильному маркеру-подстроке.
- **Откладывание следит за липкой позицией, а не за запросом** — параллельные запросы делят один общепроцессный липкий индекс, и сбой может отложить позицию, из которой обслуживался другой находящийся в полёте запрос; одноагентные сессии не затронуты.
- **Опечатанный id маршрута даёт молчаливый пул** — пулы цепляются к маршрутам по совпадению имени, и композиция с маршрутом, который не обслуживает ни одно семейство, сохранит пул, который никто не читает; редактор настроек избегает этого, записывая ключи только на живые карточки.
- **Персистентность — один писатель на документ** — у файла откладываний нет межпроцессной блокировки записи, и два процесса harness с одним `parkFile` затирают откладывания друг друга; при нужде давайте каждому развёртыванию своё место.
