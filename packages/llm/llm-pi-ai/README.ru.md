# @deepseek-ai/dsh-llm-pi-ai

[English](README.md) | [中文](README.zh.md) | Русский

Универсальный мультипровайдерный адаптер для LLM-seam'а харнесса на базе [`@earendil-works/pi-ai`](https://www.npmjs.com/package/@earendil-works/pi-ai). Один экземпляр плагина владеет словарём провайдерских профилей, где ключом служит маршрут; каждый запрос выбирает профиль через `GenerateOptions.provider` и разрешает `GenerateOptions.model` по настроенному каталогу этого маршрута. Маршрут, называющий установленный провайдер pi-ai, наследует его эндпоинт, протокол обмена и каталог моделей как значения по умолчанию и переопределяет их поле за полем; маршрут, которого pi-ai не поставляет, объявляется напрямую, поэтому OpenAI-совместимый шлюз, самохостинговый сервер или провайдер новее установленного каталога — вопрос конфигурации, а не изменения кода.

Корень пакета экспортирует контракт плагина Cordis, `PiAiAdapter` и `supportedProtocols()`; разрешение профилей, материализация каталога, конструирование провайдеров, преобразование воспроизведения и преобразование потока остаются внутренним делом пакета.

## Конфигурация

Учётные данные, каталог моделей и зависящие от развёртывания транспортные настройки задаются по каждому провайдеру, с ключом по самому маршруту провайдера. Каждый профиль может задать `retryPolicy`; пропуск означает обычный режим с пятью повторами. `apiKeyEnv` — это *ссылка* на учётные данные, разрешаемая при каждом запросе, так что секрет не попадает в этот файл. Её пропуск оставляет маршрут без аутентификации, что для маршрута установленного каталога означает штатное автоматическое обнаружение провайдера pi-ai в окружении; настроенная ссылка, которая не разрешается ни во что, отклоняет запрос с `MISSING_CREDENTIAL`, потому что тихое переключение означало бы аутентификацию любым посторонним ключом, оказавшимся в окружении. Одни учётные данные обслуживают все модели своего маршрута.

```yaml
- id: llm
  name: '@deepseek-ai/dsh-llm-pi-ai'
  config:
    providers:
      # Catalog route: endpoint, protocol, and models all come from pi-ai.
      openai:
        apiKeyEnv: OPENAI_API_KEY
        baseURL: https://proxy.example.com:8443
        reasoning: high
        requestImagePixelBudget: 4194304 # total pixels; 2048 by 2048 default
        requestImageMaxBytes: 1048576    # raw bytes before base64 expansion
        maxRequestImageBytes: 20971520   # accumulated base64 payload
        retryPolicy:
          mode: normal
          maxRetries: 3
          backoff:
            initialDelayMs: 500
            maxDelayMs: 10000
            jitterRatio: 0.1
      # Catalog route with its catalog narrowed to one model and that model's
      # capacity corrected; every unset field still comes from the catalog.
      anthropic:
        apiKeyEnv: ANTHROPIC_API_KEY
        streamIdleTimeoutMs: 300000
        models:
          - id: claude-sonnet-4-5
            contextWindow: 200000
      # Catalog route with one model reshaped in place; the rest of the
      # catalog keeps serving (a models list would replace it instead).
      deepseek:
        apiKeyEnv: DEEPSEEK_API_KEY
        modelOverrides:
          deepseek-v4-pro:
            reasoningEfforts:
              off:
              high: high
      # Hand-declared route: pi-ai ships nothing under this key, so the profile
      # supplies the whole provider.
      acme-gateway:
        displayName: Acme Gateway
        apiKeyEnv: ACME_GATEWAY_API_KEY
        api: openai-completions
        baseURL: https://gateway.acme.example/v1
        # Request shape for an endpoint whose URL pi-ai cannot recognize; it
        # would otherwise be addressed as though it were OpenAI itself.
        compat:
          thinkingFormat: deepseek
          supportsDeveloperRole: false
          maxTokensField: max_tokens
        models:
          - id: acme-large
            name: Acme Large
            contextWindow: 65536
            maxTokens: 4096
          - id: acme-think
            name: Acme Think
            contextWindow: 262144
            maxTokens: 32768
            # key = selectable level, value = its wire spelling; only off may
            # leave the value empty (supported, send nothing).
            reasoningEfforts:
              off:
              high: high
              max: ultra
```

Форма словаря делает дублирующиеся маршруты непредставимыми, а до-релизная форма массива (с полем `provider` у каждого профиля) падает при загрузке с указаниями по миграции. `providers` может также быть пустым или вовсе опущенным: тогда адаптер монтируется **спящим** — ноль маршрутов, никаких дополнительных записей каталога, — и регистрирует маршруты в тот же момент, когда секция настроек `llm-pi-ai:` поставляет профили, снова сбрасывая их при её опустошении. Спящий он или нет, плагин объявляет каждого установленного провайдера каталога в справочнике настраиваемых провайдеров (`ctx.llm.listConfigurableProviders()`, путь настроек `providers.<provider>`), присоединяя к ним каждый маршрут, который объявляют текущие профили, чтобы поверхности конфигурации могли предлагать весь каталог ещё до существования какого-либо маршрута и могли адресовать и объявленный вручную. Каждая запись несёт `declared`: поставляет ли pi-ai что-нибудь под этим ключом. Поле следует за установленным каталогом, а не за документом настроек, потому что сужение списка моделей поставляемого провайдера тоже сохраняет профиль, а такой маршрут остаётся известен pi-ai, — различить эти два случая способен только адаптер, потому справочник и отвечает сам, вместо того чтобы оставлять поверхности выводить это самостоятельно. Какие адаптеры существуют — вопрос композиции; какие провайдеры работают, может целиком решать документ настроек пользователя. Регистрация в `ctx.llm` атомарна: коллизия с любым маршрутом провайдера, уже принадлежащим другому адаптеру, срывает загрузку плагина, не зарегистрировав остальных маршрутов. Идентификаторы моделей — не конфигурация жизненного цикла; модель, которую маршрут не настраивает, отклоняется до любого обращения к провайдеру с `LlmError('UNKNOWN_MODEL')`.

## Разрешение каталога

Список `models` профиля *замещает* установленный каталог маршрута, а не расширяет его; его пропуск (или пустота) отдаёт этот каталог без изменений. Каждая запись наследует незаполненные поля от установленной модели с тем же `id`, поэтому сузить маршрут каталога до двух моделей, поправить одну ёмкость или добавить модель новее установленного каталога — правки в одну строку, — но объявление любого списка `models` означает, что каждая модель, которую маршрут должен продолжать обслуживать, **ДОЛЖНА** в нём появиться, причём записи из одного `id` достаточно. Настраиваемые поля записи: `id`, `name`, `contextWindow`, `maxTokens`, `reasoningEfforts` и `compat`. Ценообразование и модальности входа не имеют потребителя в харнессе и сохраняются в установленной записи либо отсутствуют.

`modelOverrides` перестраивает отдельные модели установленного каталога без этой цены: каждый ключ — это `id` модели каталога, каждое значение — те же поля, что берёт запись `models`, но с `id` в самом ключе, а остальной каталог продолжает обслуживание без изменений, — «поправь одну модель, сохрани остальные тридцать семь» правкой в три строки. Переопределение становится конфигурацией той записи каталога, поэтому ёмкости, уровни рассуждения и compat разрешаются тем же путём, с той же диагностикой и с той же семантикой умолчаний запроса, что и запись `models`. Переопределения осмыслены только на маршруте каталога, обслуживающем свой каталог: набор рядом со списком `models` (который уже замещает каталог), на маршруте, объявленном вручную (чьи модели полностью выписаны в `models`), или указывающий на модель, которую каталог не описывает, отвергается, а не пропускается, потому что молча неизменённая модель — опечатка, которую иначе пришлось бы вылавливать.

### Уровни рассуждений для отдельной модели

`reasoningEfforts` объявляет выбираемые уровни мышления модели: каждый ключ — уровень, который предлагают селекторы, его значение — написание, которое диспетчеризация отправляет в протоколе, так что `high: high` передаёт каноническое имя как есть, а `max: ultra` переименовывает его для шлюза с собственным словарём. Ключи берутся из набора уровней pi-ai (`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`); необъявленный уровень не предлагается. Пропуск поля сохраняет возможность из записи установленного каталога (у объявленной вручную модели её нет, и она не рассуждает); `false` объявляет нерассуждающую модель — так профиль убирает рассуждение у модели каталога, которую её шлюз обслужить не может; пустое объявление отвергается, а не разгадывается между этими двумя смыслами.

Объявление переводится в `Model.reasoning` + `thinkingLevelMap` pi-ai с явным решением по каждому уровню, — необъявленные уровни фиксируются как неподдерживаемые, а не оставляются собственным умолчаниям pi-ai, которые асимметричны (отсутствующий ключ означает «поддерживается» для пяти базовых уровней, но «не поддерживается» для `xhigh`/`max`) и знать которые автору профиля не требуется. `off` — единственный ключ с тремя состояниями: оставленный в стороне, он лишает селекторы варианта Off, а явный запрос Off отвергается — запрос, в котором уровень не назван, всё равно уходит без параметра, так что то, что затем делает провайдер, есть его собственное умолчание; если ключ объявлен без значения (`off:`), Off предлагается, и его выбор не отправляет ничего — для диалекта `deepseek` это явное `thinking: {type: "disabled"}`, — что покрывает и запрос, вовсе не называющий уровня; если ключ объявлен со значением (`off: none`), это значение уходит в протокол как параметр уровня. Написания для возврата ключа карты каталога к «не задано» не существует: объявление есть предложение целиком, поэтому выпишите заново уровни каталога, которые вы сохраняете.

### Переключатели совместимости с протоколом

pi-ai формирует каждый запрос из `id` провайдера и `baseURL`: какая роль несёт системный промпт, какое поле ограничивает вывод, как передаётся уровень мышления. URL частного шлюза ничего не говорит, а для эндпоинта, которого pi-ai не распознаёт, автоопределение отвечает так, словно перед ним сам OpenAI, — системный промпт рассуждающей модели уходит как `developer`, предел вывода как `max_completion_tokens`, уровень мышления как `reasoning_effort` без дополнений, — и большинство OpenAI-совместимых шлюзов отвергают хотя бы одно из этого. Поэтому `compat` настраивается на маршруте (умолчание его моделей) и по модели (побеждает по полю) с разрешением модель → маршрут → запись установленного каталога → собственное определение pi-ai; переключатель уровня маршрута затеняет значение записи каталога для каждой читающей его модели, и написания для возврата поля каталогу, кроме повторного вписывания его значения, нет.

Каждый переключатель принадлежит тем протоколам, чей compat-тип pi-ai его объявляет, и группировка следует за compat-*типом*, а не за именем протокола: три Responses-протокола (`openai-responses`, `azure-openai-responses`, `openai-codex-responses`) разделяют один compat-тип, поэтому переключатель, задаваемый на одном, допустим на всех трёх. `supportsDeveloperRole` задаётся на `openai-completions` и на тех трёх; `thinkingFormat` — только на `openai-completions`; `supportsTemperature` — только на `anthropic-messages`; `supportsStrictMode` достигает ещё и `bedrock-converse-stream`. Переключатель уровня модели, которого его протокол не принимает, срывает разрешение, называя то, что протокол действительно предлагает; переключатель уровня маршрута ложится на читающие его модели и пропускает остальные, а отвергается лишь когда ни одна модель маршрута прочесть его не может вовсе.

Три рода ключей отвергаются, а не выбрасываются: ключ, который не объявляет ни один протокол (опечатка); ключ, которым установленный каталог pi-ai владеет для конкретного вендора (`openRouterRouting`, `zaiToolStream`, `deferredToolsMode`, `sessionAffinityFormat`, `supportsOpenAIGrammarTools`, `supportsToolSearch`, `supportsExplicitPromptCacheMode`, `supportsToolReferences`, `vercelGatewayRouting`, `sendSessionAffinityHeaders`), — маршрут, которому нужен собственный переключатель вендора, это маршрут каталога, который **СЛЕДУЕТ** так и называть; и ключ, выписанный вовсе без значения (`supportsDeveloperRole:`), который schemastery пропускает как null и который иначе заместил бы значение установленного каталога ничем. Предлагаемый набор закреплён за четырьмя compat-типами pi-ai гейтами против дрейфа, протоколы, несущие их, выводятся из самого `Model.compat`, а тип каждого поля выводится из апстрима, а не переписывается, поэтому обновление, которое добавляет поле, даёт compat-тип ещё одному протоколу или расширяет объединение значений, срывает сборку, пока кто-нибудь не классифицирует произошедшее.

Модель, размеров для которой нет ни у записи, ни в установленном каталоге, получает `defaultContextWindow` (262 144) и `defaultMaxTokens` (32 768) маршрута, поэтому перечисление, раскрывающее одни лишь id, всё же даёт пригодный к работе маршрут. Оба запасных значения по построению — догадки, потому они и являются полями маршрута, которые развёртывание, чей шлюз обслуживает меньшие модели, поправит один раз, а не константами, зашитыми в адаптере; запасное значение задаёт размер модели и никогда не становится пределом отдельного запроса.

Модальности запроса разрешаются как `input` записи → запись установленного каталога → `defaultInput` маршрута (по умолчанию `[text]`) — тот же порядок и та же роль запасного значения, что у ёмкостей выше. Поэтому модель каталога хранит модальности, записанные для неё каталогом, и более узкое умолчание маршрута никогда их не срезает; шлюз, чьи *неописанные* модели все принимают изображения, объявляет `[text, image]` один раз на маршруте, а не на каждой записи. Пустой список записи означает то же, что отсутствующий, — он описывает модель, не принимающую ничего, поэтому ответа не даёт, и разрешение идёт дальше него, чем и сохраняются собственные модальности модели каталога, когда запись `models` называет её, ничего не объявляя. Значение маршрута пустым быть не может, поскольку ниже него никого нет, кто ответил бы вместо него.

`[text]` — отсутствие объявления, а не догадка об эндпоинте, отчего запасное значение здесь консервативно там, где запасные ёмкости всего лишь правдоподобны. Никто не допрашивает шлюз о том, что тот принимает, и два неверных ответа обходятся неодинаково: харнесс отвергает изображение до прикрепления, когда модальности модели его не упоминают, поэтому занижение требований стоит отказа с именем модели, а завышение впускает изображение, которое провайдер затем отвергнет посреди хода, — после того как сообщение уже сохранено, и сессия остаётся повторять запрос, который не может удаться.

Разрешение по-прежнему завершается явной ошибкой, называя виновные маршрут и модель, когда маршрут невозможно обслужить вовсе: маршруту, которого каталог не поставляет, нужны `api`, `baseURL` и непустой список `models` из моделей с уникальными идентификаторами. Это разрешение выполняется внутри схемы секции, поэтому необслуживаемый профиль отвергается **там, где выписан**, — `settings.mutate` отвечает `settings-rejected`, называя маршрут и модель, — а не сохраняется, чтобы потом молча отключить каждый маршрут пространства имён. Seam настроек хранит для уже сохранённой секции, потерпевшей неудачу, последнее корректное значение пространства имён, так что развёртывание из-за этого не блокируется. `api` принимает протоколы из `supportedProtocols()` и нужна лишь тогда, когда каталог не может поставить протокол: модель, отсутствующая в каталоге, наследует протокол, общий для её поставляемых соседок, поэтому добавление модели к однопротокольному маршруту каталога не переписывает ничего.

`baseURL` задаёт эндпоинт каждой модели маршрута, поэтому частные прокси вроде `https://proxy.example.com:8443` по-прежнему поддерживаются; маршрут каталога, опустивший её, сохраняет собственный эндпоинт каждой модели каталога. Указание `api` на маршруте каталога перенаправляет весь маршрут на этот протокол — так развёртывание переводит провайдера между, скажем, Responses и Chat Completions.

`supportedProtocols()` намеренно у́же полного множества потоковых API pi-ai: он содержит лишь протоколы, которые профиль может описать *целиком* ключом, эндпоинтом и заголовками. Bedrock подписывает через SigV4 поверх учётных данных AWS и региона, Vertex требует проект, локацию и учётные данные application-default, Azure требует окружение провайдера плюс api-version, а Codex аутентифицируется через OAuth, — предлагать их значило бы вернуть маршрут, который не сможет аутентифицироваться. Маршруты каталога всё же получают доступ к ним через их собственного провайдера; отвергается лишь явное переопределение.

## Динамическая конфигурация (settings + credentials)

Адаптер читает свои профили через thunk **один раз на операцию**, а не замораживает их при конструировании. Плагин регистрирует пространство имён `llm-pi-ai` на необязательном seam'е `ctx.settings` с той же схемой `Config` и своей записью в `cordis.yml` в качестве композиционной базы (base), и поскольку `providers` — словарь, база и пользовательская секция настроек `llm-pi-ai:` сливаются **по провайдеру**: пользователь может добавить маршрут, переопределить одно поле композиционного маршрута или перевести маршрут на другой прокси — всё вступает в силу со следующего запроса без перезапуска. Без смонтированного сервиса настроек адаптером правит одна лишь входная конфигурация, без изменений.

Учётные данные разрешаются при каждом вызове потока через `apiKeyEnv` и необязательный seam `ctx.credentials`; без этого seam'а адаптер читает ровно ту переменную окружения, на которую указывает ссылка. Профиль, вовсе не называющий учётных данных, — и только этот случай, — полагается на автоматическое обнаружение pi-ai в окружении. Каждый разрешённый ключ подрезается и проверяется на формат перед использованием, поэтому значение, которое не может нести ни один HTTP-заголовок, отвергается, вместо того чтобы всплыть непрозрачным `TypeError` из `fetch`; отказ бросает `LlmError('INVALID_CREDENTIAL')`, называя сбойный маршрут и ссылку на учётные данные, но никогда ни одной части ключа. Набор маршрутов и захваченная политика повторов каждого маршрута — факты уровня регистрации: когда меняется любое из двух, плагин атомарно заменяет свою регистрацию (тот же экземпляр адаптера, кандидатный набор проверяется первым), поэтому маршрут, уже принадлежащий другому адаптеру, оставляет прежние маршруты обслуживающими, а возврат к рабочей конфигурации применяется заново. Порядок ключей провайдеров изменением никогда не считается. Секция, которую этот адаптер не смог бы обслужить, отвергается там, где выписана, — зарегистрированный `validate` разрешает весь набор профилей, поэтому `ctx.settings.mutate` отвергает с собственной ошибкой резолвера (проводная поверхность сообщает её как `settings-rejected`), и ничего не сохраняется. Сохранённая секция, ставшая необслуживаемой каким-то иным путём, — внешняя правка `settings.yaml`, — держит на seam'е настроек последнее корректное значение пространства имён и предупреждает. Входная конфигурация сама по себе по-прежнему срывает загрузку плагина, а маршрут, который llm-реестр отверг (уже принадлежащий другому семейству адаптеров), логируется, пока прежде зарегистрированные маршруты продолжают обслуживание.

Адаптер предоставляет модели каждого настроенного маршрута через `ctx.llm.listModels(provider)`. Это независимые от провайдера метаданные селектора, читаемые из той же коллекции `Models` pi-ai, которой пользуется путь запроса, поэтому обнаружение не создаёт второго реестра моделей. `ctx.llm.resolveModelInfo(provider, model)` выполняет ровно этот поиск дескриптора единожды и возвращает идентификатор модели, окно контекста, настроенный предел вывода и выбираемые уровни мышления, храня авторитетные метаданные на адаптере, владеющем маршрутом, а не у его потребителей. **Настроенная** `maxTokens` модели становится `defaultMaxTokens` seam'а, поэтому запрос, не называющий предела вывода, несёт тот, который выбрало развёртывание; значение, унаследованное от установленного каталога, есть *возможность* вывода модели и само по себе умолчанием запроса никогда не становится.

Модель, несущая метаданные рассуждения — из установленного каталога или из `reasoningEfforts` своей записи, — предоставляет упорядоченный результат `getSupportedThinkingLevels(model)` pi-ai без фильтрации и нормализации, включая `off` и зависящую от модели доступность `xhigh` или `max`. Харнесс предоставляет каждый канонический уровень pi-ai как непрозрачный идентификатор; написания для протокола конкретных провайдеров и моделей остаются внутри `thinkingLevelMap` pi-ai.

Модель **без** таких метаданных — объявленная вручную, чья запись не объявляет `reasoningEfforts`, и модель каталога, которую pi-ai помечает как нерассуждающую, — не раскрывает рассуждение вовсе. pi-ai сообщает о такой модели как поддерживающей единственный уровень `off`, но `off` переводится в *опущение* опции `reasoning`, а это побайтно тот же запрос, который и так получается, когда уровень не назван: выбрать его — ничего не отключить, поэтому провайдер, который по собственному умолчанию думает, продолжил бы думать, пока `off` показан выбранным. Сообщение о возможности как недоступной оставляет поверхность, предлагающую умолчание провайдера, и ничего, что его искажало бы. Значение `reasoning` профиля, включая `off`, будучи настроенным, служит умолчанием развёртывания; его пропуск сохраняет умолчание провайдера. Указанный в запросе `GenerateOptions.reasoningEffort` имеет приоритет, и уровень, отсутствующий в возможности конкретной модели, срывает ЗАПРОС с `UNSUPPORTED_REASONING_EFFORT` до сетевого ввода-вывода, вместо того чтобы обрезаться. Описание модели так никогда не падает: модели одного провайдера расходятся в том, какие уровни принимают, поэтому `resolveModel` сообщает профильный уровень, который конкретная модель принять не может, как полное отсутствие умолчания, а не бросает исключение. Бросок там убрал бы весь провайдер из каждого каталога моделей, построенного над ним, — одно неверно заданное поле профиля прятало бы даже модели, поддерживающие этот уровень, — поэтому плохая конфигурация всплывает там, где на неё опираются, а не там, где её описывают. Общие потоковые опции pi-ai представляют `off` опущением `reasoning`.

Поддерживаемые поля профиля: `apiKeyEnv`, `displayName`, `api`, `baseURL`, `models`, `modelOverrides`, `compat`, `defaultContextWindow`, `defaultMaxTokens`, `defaultInput`, `headers`, `reasoning`, `thinkingBudgets`, `cacheRetention`, `transport`, `timeoutMs`, `websocketConnectTimeoutMs`, `streamIdleTimeoutMs`, `maxRequestImageBytes`, `requestImagePixelBudget`, `requestImageMaxBytes` и `retryPolicy`. Разрешённая политика повторов каждого профиля захватывается вместе с его маршрутом провайдера; пропуск использует общее ограниченное умолчание обычного режима в пять повторов. Интервал простоя потока — положительная конечная задержка таймера Node, по умолчанию пять минут, покрывает только незавершённое чтение от провайдера, а не время размышления потребителя. Каждый маршрут с изображениями выводит детерминированную версию запроса из независимого от провайдера нормализованного вложения под `requestImagePixelBudget` (по умолчанию 2048×2048 суммарных пикселей) и `requestImageMaxBytes` (по умолчанию 1 МиБ сырых байтов). До чтения вложений `maxRequestImageBytes` применяется к консервативным верхним границам версии запроса и замещает старейшие сверхбюджетные изображения фиксированным текстом; точные длины base64 проверяются вновь после генерации удержанных версий. Умолчание 20 МиБ способно удержать пятнадцать версий максимального размера 1 МиБ после расширения base64, оставляя запас телу запроса. Та же версия идёт в инлайн-base64, и её стабильный дескриптор раскрывает id вложения и фактические размеры изображения запроса. Атрибуция приложения харнесса имеет приоритет над конфликтующим настроенным именем заголовка.

Адаптер принудительно ставит `maxRetries` SDK pi-ai в нуль, поэтому один вызов `stream()` делает один запрос к провайдеру. Удалённые поля профиля `maxRetries` и `maxRetryDelayMs` срывают загрузку, вместо того чтобы молча множить или прятать отдельно скомпонованный бюджет повторов уровня агента. Истечение простоя прерывает стабильный сигнал запроса SDK и всплывает как `TIMEOUT`; более ранний abort вызывающего остаётся `ABORTED`.

## Опрос эндпоинтов

Плагин предлагает `ctx.llm.registerModelDiscovery('llm-pi-ai', …)`, отвечающий на вопрос «какие модели этот провайдер способен обслуживать?» для маршрута, который поверхность конфигурации редактирует или готовит в черновике. Это намеренно *не* обновление каталога: ничего не сохраняется, и ответ есть кандидаты, которые поверхность предлагает к принятию. Решать, что обслуживает маршрут, остаётся единственным образом `settings.yaml`.

Запрос, называющий маршрут, который **поставляет установленный каталог, отвечается из этого каталога** без сетевого вызова: реестр pi-ai — авторитетный список его собственных провайдеров, и в нём есть окна контекста и пределы вывода, которых перечисляющий эндпоинт обычно не раскрывает. Такому маршруту `baseURL` не нужна вовсе. Только маршрут, которого каталог не описывает, — шлюз, самохостинговый сервер — допрашивается по сети, а маршрут без названного эндпоинта получает указание задать его или ввести модели вручную.

Черновик несёт введённые пользователем учётные данные, если есть; маршрут, уже сохранивший свои, показывает поверхности конфигурации лишь обезличенный дескриптор, поэтому опрос разрешает `apiKeyEnv` этого маршрута, вместо того чтобы уходить без аутентификации и докладывать 401 эндпоинта как неверный ключ. Введённый ключ выигрывает, так как именно он под проверкой. Разрешение выполняется только на пути, доходящем до сети, поэтому маршрут каталога отвечает, не трогая учётных данных вовсе. Поданный или сохранённый пробный ключ подрезается и проверяется на формат так же, поэтому значение, которое не может нести ни один HTTP-заголовок, немедленно отвергается как `LlmError('INVALID_CREDENTIAL')`, не доходя до `fetch`, где оно всплыло бы непрозрачным отказом `ByteString`, неотличимым от недостижимого эндпоинта.

Опрос поддерживает `openai-completions` и `openai-responses`, чья форма `GET /models` с bearer-аутентификацией — та, на которой сходятся шлюз, самохостинговый сервер и официальные эндпоинты. Azure исключена, несмотря на OpenAI-родословную, — она аутентифицируется заголовком `api-key` и требует параметр запроса `api-version`, — а Codex пользуется OAuth; любой другой протокол отвечает `DISCOVERY_UNSUPPORTED`, поэтому поверхность откатывается к ручному вводу, вместо того чтобы докладывать отказ аутентификации как провайдера без моделей. `baseURL` трактуется как префикс, а не URL, относительно которого разрешаются пути, поэтому путь развёртывания вроде `https://gateway.example/openai/v1` сохраняет свои сегменты.

Большинство перечислений раскрывают `id` и ничего больше; `context_window`/`context_length` и `max_output_tokens`/`max_tokens` читаются, когда шлюз их передаёт, записи без пригодного `id` пропускаются, а не срывают всё перечисление, а обо всём остальном по-прежнему заботится принимающая поверхность. Ответ читается с потолком в четыре мегабайта, применяемым к фактически полученным байтам, — эндпоинт есть введённый пользователем URL, поэтому заявленная длина проверяется первой, но никогда не считается границей. Недостижимый эндпоинт, отвергнутые учётные данные, тело не-JSON и тело без массива `data` — всё даёт ошибку `DISCOVERY_FAILED` с сообщением, называющим эндпоинт, а для одного лишь 401 или 403 ещё и учётные данные. Отмена посреди чтения тела всплывает как `ABORTED`, подобно отмене до ухода запроса.

## Маршрутизация провайдер/модель и воспроизведение

Каждое разрешение производит один **неизменяемый** снапшот — профили плюс коллекцию `createModels()`, держащую `Provider`, построенный каждым маршрутом, — и каждая операция захватывает целый снапшот до первого `await`. Изменение конфигурации строит *новую* коллекцию, а не мутирует используемую: `Models.streamSimple()` разрешает своего провайдера лениво, при первом использовании потока, что происходит после ожидания учётных данных, поэтому мутированная коллекция позволила бы запросу, начавшемуся под одной конфигурацией, закончиться под другой или упасть на провайдере, которого больше нет. Именно это заставляет заморозку вызова на шаг у seam'а (`llm.prepareCall()`) держаться от начала до конца, — переключение моделей посреди ответа вступает в силу на следующем шаге и никогда внутри уже выполняющегося. Запросы доходят до своего провайдера через `Models.streamSimple()`. Маршрут каталога, сохраняющий протокол своего каталога, повторно использует установленного провайдера с заменённым списком моделей, потому что тот провайдер владеет реализациями API, которые этот пакет реконструировать не может, — Bedrock загружает свой модуль Smithy через отдельную точку входа, — поэтому пересборка его из частей молча сузила бы круг работающих провайдеров. Всякий иной маршрут строится `createProvider()` по таблице протоколов за `supportedProtocols()`, чьи записи — те же фабрики, которыми пользуются собственные фабрики провайдеров pi-ai.

Ключ `apiKeyEnv` маршрута по-прежнему разрешается через seam харнесса прежде, чем запрос дойдёт до pi-ai, и передаётся как опция `apiKey` запроса, которую pi-ai считает переопределением аутентификации высшего приоритета, — семантика ссылок с отказом fail-loud остаётся за харнессом. Под этим переопределением коллекция несёт хранилище учётных данных этого плагина и контекст аутентификации из окружения: сохранённый вход (OAuth-грант или ключ, введённый в собственный логин-промпт pi-ai) аутентифицирует свой маршрут через них и обновляется под межпроцессной блокировкой хранилища. Хранилище адресует записи как `llm-pi-ai/<provider id>`, и ключ объявленного вручную маршрута вне той грамматики записей (прописные буквы, точки, подчёркивания) читается как «ничего не сохранено», а не как ошибка адресации; в такой маршрут войти нельзя — запись для него отвергается с `LlmError('UNSTORABLE_PROVIDER_ID')`, — аутентифицируется же он через `apiKeyEnv` или настройки провайдера из окружения. Маршрут, вовсе не называющий учётных данных, разрешается как «настроен, но без ключа» и оставляет требование протоколу — там, где оно и находится.

Выбранный дескриптор модели поставляет реализацию протокола. Это включает нативные различия API, например модели OpenAI, чей дескриптор использует Responses API вместо Chat Completions; адаптер харнесса не зашивает выбор эндпоинта по имени модели.

Успешные ответы ассистента сохраняют версионированное состояние воспроизведения в формате JSON без потерь рядом с породившими их провайдером и моделью, как `ReplayEnvelope`: половину уровня ответа (kind, версия, API, маршрут, идентификаторы ответа, нативная причина остановки) плюс по одной записи на блок для каждого потокового блока, несущей сигнатуры этого блока. Выравнивание по блокам — то, что `BlockAssembler` подрезает, когда сборка отбрасывает блок (вызов инструмента по `max-tokens`), поэтому сохранённые записи всегда описывают сохранённый контент, — удержанные блоки хранят свои сигнатуры. Во время запроса `LlmRuntime` передаёт состояние воспроизведения лишь тогда, когда исторический маршрут провайдера и целевой маршрут провайдера в данный момент принадлежат этому же экземпляру `PiAiAdapter`. Адаптер валидирует состояние и восстанавливает идентификаторы ответов pi-ai и сигнатуры провайдера, даже когда меняются целевой провайдер или модель; pi-ai затем решает, какие метаданные его целевой API может переиспользовать. История без состояния воспроизведения переводится как чужой независимый от провайдера контент и никогда не выдаёт себя за нативный ответ pi-ai.

Долговечный контент — авторитетная запись; состояние воспроизведения лишь восстанавливает нативную точность. Сохранённое состояние, которого эта сборка использовать не может, — чужой kind, другая версия (включая плоскую до-конвертную форму, которую несут старые журналы), искажённые метаданные, несовпадения провайдера/модели между сообщением и состоянием воспроизведения или несовпадения контента/блоков, — деградирует то единственное сообщение ассистента до того же чужого независимого от провайдера преобразования вместо отказа всего запроса, а плагин логирует диагностику `INVALID_REPLAY_STATE` через свой хук `onReplayDegrade`.

## Различия словарей

- Аргументы вызовов инструментов pi-ai — разобранные объекты; харнесс хранит сырые строки JSON. Адаптер разбирает вход и заново сериализует выход.
- Об отказах pi-ai сообщается как о событиях ошибки внутри потока; они отображаются в чанки `finish {kind:'error'|'aborted', failure}`. Привязанный к провайдеру текст ошибки отличает терминальный `QUOTA` от преходящего `RATE_LIMIT`, а текстовые и usage-сигналы, оценённые против окна контекста разрешённой модели, нормализуют переполнение в `CONTEXT_WINDOW_EXCEEDED`. Терминальный `stop`, чьё сообщение не несёт блоков содержимого, отображается в `finish {kind:'error'}` с кодом `EMPTY_RESPONSE` (повторяется политикой по умолчанию) вместо успешного пустого сообщения.
- pi-ai складывает токены рассуждений в расход выходных токенов; отдельного счётчика рассуждений, который надо было бы отображать, нет.
- Уровень мышления `off` pi-ai пересекает capability seam харнесса неизменным и становится опущенной общей опцией `reasoning` pi-ai при диспетчеризации.
- `GenerateOptions.stop` отвергается с `UNSUPPORTED_OPTION`, потому что общий потоковый UI pi-ai не может гарантировать его для всех провайдеров.

## Атрибуция приложения

Каждый запрос несёт общий заголовок атрибуции из `attributionHeaders()` dsh-llm, объединяемый через потоковую опцию `headers` pi-ai. Привязанные к провайдерам заголовки атрибуции приложения не синтезируются. См. [dsh-llm § App attribution](../llm/README.md#app-attribution-attributionts).

## Вес зависимостей

pi-ai устанавливает несколько SDK провайдеров и лениво загружает тот, что выбран моделью каталога. Вес зависимостей изолирован в этом opt-in пакете-адаптере.

## Model Experience

### Запрос к провайдеру через pi-ai

#### What the model sees

Выбранная модель каталога получает `GenerateOptions.system`, историю, инструменты и поля сэмплирования, которые поддерживает общий потоковый API pi-ai. Перед каждым сохранённым изображением стоит стабильный текст, указывающий его полный id вложения и фактические размеры изображения в запросе. Когда накопленная полезная нагрузка base64-изображений превышает `maxRequestImageBytes` маршрута, каждое вытесненное изображение (начиная с самого старого) замещается фиксированным текстом, предписывающим модели заново прочитать файл, когда путь станет доступен, либо попросить пользователя приложить его заново. Вытесненные нормализованные вложения не читаются и не преобразуются. Метаданные воспроизведения, нативные для провайдера, восстанавливаются, только когда адаптер валидирует их для исторического контента.

#### Token effect

Точное входное содержимое определяется токенизацией провайдера. Сохранённые изображения добавляют стабильный дескриптор вложения и координат; плейсхолдер вытеснения замещает визуальные токены опущенного изображения. Метаданные воспроизведения могут позволить нативному API переиспользовать состояние на стороне провайдера.

#### KV Cache effect

Преобразование сохраняет логический порядок запроса, не добавляя текста, а повторное использование определяют сериализация выбранного провайдера и состояние воспроизведения. Смена экземпляра адаптера, провайдера, модели или любого более раннего токена запроса может прервать повторное использование, начиная с первой разницы. Пересечение границы изображений переписывает более раннее сообщение (вновь вытесненное изображение становится текстом-плейсхолдером), поэтому повторное использование обрывается на этом сообщении, пока вытесненный префикс не стабилизируется.

### Ответ провайдера

#### What the model sees

События pi-ai становятся чанками харнесса: рассуждением, текстом, вызовом инструмента, расходом токенов и завершением. Адаптер передаёт разобранные аргументы инструментов харнессу сырыми строками JSON.

#### Token effect

Сгенерированный контент влияет на последующие входы лишь после того, как цикл его запишет. pi-ai включает токены рассуждений в расход выходных токенов, когда провайдер не сообщает их отдельно.

#### KV Cache effect

Записанный контент ответа дописывается к следующему запросу и не аннулирует его более ранний повторно используемый префикс. Незаписанные транспортные метаданные и учёт расхода не влияют на идентичность кэша.

## Known Limitations and Deferred Work

- **`maxRequestImageBytes` считает только полезную нагрузку base64 изображений** — текст, инструменты, дескрипторы и структура JSON находятся за пределами границы, поэтому он **ДОЛЖЕН** оставаться ниже лимита тела запроса шлюза с запасом. Вытеснение — детерминированная проекция запроса и не записывается как событие сессии.
- **Вход существует только в процессе, который его начал** — попытка авторизации не долговечна, поэтому перезагрузка страницы посреди входа отбрасывает её, и человеку приходится начинать заново. Выход — это вызов `deleteRecord` для сохранённой записи: она забывается локально, без уведомления эмитента.
- **Обнаружение, нативное для провайдера, отвечает через окружающий контекст этого плагина** — маршрут, в котором не указаны учётные данные, полагается на собственное разрешение учётных данных провайдером каталога, которое запрашивает значения переменных окружения (`AZURE_OPENAI_API_KEY`, `AWS_PROFILE` и собственный набор каждого провайдера) и локальные файлы учётных данных. Оба вопроса решаются здесь: seam учётных данных опрашивается прежде окружения процесса, а существование файла проверяется по файловой системе процесса-хоста с развёрнутым `~`. Чего здесь нельзя, так это *читать* содержимое файла учётных данных — провайдер, сам разбирающий `~/.aws/credentials`, делает это напрямую, вне seam'а.
- **Настройки могут добавлять или переопределять маршруты, но не убирать композиционные** — пользовательский слой вливается поверх композиционной базы `base`, поэтому удаление провайдера, предоставленного `cordis.yml`, является изменением композиции; `replace` на пространстве имён сбрасывает лишь пользовательский слой.
- **Послойное слияние не умеет удалять ключи словаря** — seam настроек вливает композиционную базу и пользовательский слой по ключам рекурсивно, поэтому уровень `reasoningEfforts`, запись `modelOverrides` или поле `compat`, объявленные базой, пользовательским слоем не убираются, а лишь переопределяются, — причём для `reasoningEfforts` отсутствие *и есть* смысл («не предлагается»), так что объявленный базой уровень продолжает предлагаться. Это срабатывает только когда конфигурация записи `cordis.yml` объявляет помодельные поля рассуждения для той же модели, которую правит пользовательский слой; поддерживаемая позиция — оставить их документу настроек (поставляемая композиция монтирует адаптер спящим), а список `models` — массив, замещающий прежний список целиком, что и служит легальным обходом.
- **`headers` может нести учётные данные, которых механизм цензуры никогда не увидит** — словарь `headers` профиля состоит из простых строк, поэтому заданные там `Authorization` или `api-key` возвращаются дословно отцензурированным `describe()` и рендерятся любым интерфейсом конфигурации. Храните учётные данные как ссылки `apiKeyEnv`; превращение словаря в write-only отложено вместе с остальной [работой над границей протокола](../llm/README.md#known-limitations-and-deferred-work).
- **Каталог маршрута никогда не обновляется сам** — каталог — то, что указано в `settings.yaml`, поэтому список моделей актуален настолько, насколько свежа его последняя правка. Здесь ничто не спрашивает провайдера о том, какие модели он обслуживает; маршрут получает модель, когда кто-то её вписывает.
- **Один протокол обмена на маршрут** — `api` применяется ко всему маршруту, поэтому маршрут каталога со смешанными протоколами (каталог в духе OpenAI, охватывающий и Responses, и Chat Completions) не может вместить модель другого протокола, а добавление модели, которой нет в таком маршруте, требует назвать `api` и перенести на него каждую модель. Обход — разбить провайдера на два ключа маршрутов.
- **Объявление модальностей не проверяется** — ничто не опрашивает эндпоинт о том, что тот принимает, поэтому модель, объявляющая `image`, который её шлюз не обслуживает, отвергается провайдером после принятия промпта. Изображение остаётся записанным в истории, и та же неверно объявившая себя модель может упасть снова. Переключиться на текстовую модель остаётся возможным, потому что общий LLM-рантайм проецирует ссылки на изображения в стабильный текст для этого конкретного запроса.
- **Неаутентифицированный маршрут зависит от своего протокола** — маршрут, не указывающий учётных данных, разрешается как «настроен, но без ключа», однако OpenAI-совместимая реализация pi-ai всё равно требует API-ключ или заголовок `Authorization`, поэтому локальному серверу без ключа нужны фиктивные учётные данные, на которые указывает `apiKeyEnv`, либо запись `Authorization` в `headers`.
- **`GenerateOptions.stop` не поддерживается** — общие потоковые опции pi-ai не могут гарантировать поведение stop-последовательностей единообразно для всех провайдеров, поэтому адаптер отвергает поле.
- **Исторические сообщения `system` используют общее преобразование контекста pi-ai** — привязка к провайдеру следует за pi-ai, а не за протокольным переопределением, принадлежащим харнессу.
- **HTTP-статус провайдера недоступен** — события ошибок pi-ai не раскрывают HTTP-статус, единый для всех провайдеров; отказы несут лишь стабильные коды ошибок харнесса.
- **Политика повторов принадлежит провайдеру, а не SDK** — каждый профиль провайдера может задать вложенную `retryPolicy`; при пропуске действует обычный режим с пятью повторами, а действующая политика маршрута — та, что исполняет `dsh-llm-retry` на точке расширения неудачного шага агента. Повторы SDK pi-ai остаются выключенными, поэтому каждая видимая попытка принадлежит долговечным шагам агента и событиям `llm/retry`, а прямые вызовы `ctx.llm.stream()` выполняют ровно одну попытку.
