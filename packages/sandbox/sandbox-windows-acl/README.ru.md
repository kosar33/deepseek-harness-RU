# @deepseek-ai/dsh-sandbox-windows-acl

[English](README.md) | [中文](README.zh.md) | Русский

Бэкенд песочницы для Windows с ограничением записи, обслуживающий [seam песочницы harness](../sandbox/): порт на Node.js/[koffi](https://koffi.dev/) механизма из [huoyaoyuan/windows-acl-restrict-poc](https://github.com/huoyaoyuan/windows-acl-restrict-poc) (`10e4dfb`, зафиксированная ревизия), встающий ступенью `enforcement: 'partial'` под win32 в цепочку [`@deepseek-ai/dsh-sandbox-local`](../sandbox-local/) (режимы `workspace-write` / `read-only`); бэкенды Linux/macOS несёт тот же пакет.

Механизм одной строкой: токен вызывающего дублируется в токен `WRITE_RESTRICTED`, чьи ограничивающие SID несут раздельные возможности рабочей области и приватного временного каталога. SID рабочей области детерминированно выводится из канонического пути рабочей области (`workspaceWriteSid`), поэтому ACE корня рабочей области материализуется один раз на машину на каждую рабочую область, а любая последующая сессия, вызов или перезапуск попадает на пропуск по точному совпадению ACE. Каждая живая пара сессия/рабочая область вместо этого получает случайный временный каталог и выведенный из его пути SID (`tempWriteSid`), так что сессии разделяют задуманные полномочия рабочей области, не наследуя полномочий друг друга во временной области. Windows даёт запись только там, где разрешают ОБА условия: обычный доступ вызывающего И пересечение с ограничивающими SID. Эти SID — первичные списки разрешений и вне их ничего не дают, но проверка также наследует фоновые ACE записи ДРУГИХ ограничивающих SID (logon SID группы keep-alive + Everyone), а ACL NTFS принадлежат файловым объектам, а не путям; границы Everyone и жёстких ссылок — вот почему ступень сообщает частичное, а не полное исполнение.

Прямая опора на сырой ACL-механизм — записанное проектное решение: оно реализует оба режима изоляции без проблем, которые несут отвергнутые контейнерные варианты, — см. [записку о проектировании](../../../.agents/notes/implemented/feature/2026-08-08-windows-acl-restricted-token-sandbox.md) ([mxc](https://github.com/microsoft/mxc/blob/main/docs/process-container/os-version-support.md) требует нижней границы ОС Windows 11 24H2 и тотальных перезаписей host-DACL ради чтения произвольных путей; AppContainer вообще не умеет читать произвольные пути).

## Использование

```ts
import { mkdtempSync, rmSync } from 'node:fs'
import { tmpdir } from 'node:os'
import { join } from 'node:path'
import { AclSandbox, tempWriteSid, workspaceWriteSid } from '@deepseek-ai/dsh-sandbox-windows-acl'

const workspaceRoot = process.cwd()
const tempDir = mkdtempSync(join(tmpdir(), 'dsh-'))

// mode selects the token's restricting-SID list (see Modes below) and must
// match the grant shape. workspace-write requires distinct workspace and
// private-temp identities; pass tempDir: null to disable temp writes.
const sandbox = new AclSandbox({
  writableDirs: [workspaceRoot],
  tempDir,
  writeSid: workspaceWriteSid(workspaceRoot),
  tempWriteSid: tempWriteSid(tempDir),
  mode: 'workspace-write',
})
await sandbox.init() // throws on ANY Win32 failure — never spawns unrestricted

const child = sandbox.spawn({ command: 'pwsh', args: ['-NoProfile', '-Command', '...'], cwd: workspaceRoot })
const { stdout, stderr, exitCode } = await child.wait()

sandbox.dispose() // revokes the revocable (temp) grant, keeps the standing workspace ACE; reports every cleanup failure
rmSync(tempDir, { recursive: true, force: true })
```

Прямой `AclSandbox` требует явного приватного временного каталога (или `tempDir: null`; фоновый корень temp никогда не становится неявной выдачей), выдаёт ACE рабочей области ПОСТОЯННО (dispose() их оставляет — это кросс-экземплярный кэш переиспользования) и выдаёт отдельный temp-SID как отзывный. Серверную сторону переиспользования оформляет класс `AclWriteGrant`: `add(path, standing)` на каждый каталог, `dispose()` отзывает отзывные пути и освобождает SID — контракт раннера ниже. Каждый вызов Win32 API в пакете проверяется; неудачи бросают `Win32Error` с именем API, точным кодом Win32, системным текстом `FormatMessageW` и отказавшим путём/контекстом. Это намеренно: POC игнорировал каждое возвращаемое значение и при отказе `CreateRestrictedToken` молча запускал дочерний процесс с ПОЛНЫМ неограниченным токеном (fail-open). Этот порт по построению действует fail-closed.

## Раннер изоляции

К seam обращена форма **раннер-входа** (`./runner`) — обёртки-префикса argv, которую `@deepseek-ai/dsh-sandbox-local` запускает вместо команды вызывающего, — та же архитектура, что у bwrap/landlock-run/sandbox-exec, поэтому контракт `confine()` seam песочницы остаётся без изменений. Стабильный контракт argv:

```sh
node runner.js --workspace <dir> --temp <dir> --mode <read-only|workspace-write> [--write-sid <S-1-4-…> --temp-write-sid <S-1-4-…>] -- <argv...>
```

Раннер создаёт ограниченный токен, запускает под ним завёрнутый argv, передавая stdio вызывающего напрямую сквозь себя (это каналы вызывающего, объявляемые наследуемыми вокруг запуска — Node сбрасывает наследуемость stdio при старте, и сырые запуски обязаны это компенсировать), заворачивает дочерний процесс в job с `KILL_ON_JOB_CLOSE` (гибель раннера убивает ребёнка), игнорирует собственный консольный Ctrl+C, оставляя его обработку ребёнку, зеркалирует код выхода ребёнка и при выходе отзывает свою самостоятельно управляемую временную выдачу (ACE рабочей области остаются). Любой сбой на стороне раннера печатает `windows-acl-run: <detail>` в stderr и выходит с кодом 127 — правила `RUNNER_FAILURE_RULES` на seam узнают эту сигнатуру, поэтому отказ раннера никогда не принимают за блокировку.

**Переиспользование рабочей области и изоляция temp**: seam материализует ACE детерминированного SID рабочей области ПОСТОЯННО (один раз на рабочую область за жизнь сервера, без отзывов — это кэш переиспользования), затем создаёт случайный приватный временный каталог и отдельный отзывный SID для каждой живой пары сессия/рабочая область. Обе идентичности передаются обязательной парой `--write-sid`/`--temp-write-sid`; раннер сверяет каждую с владеющим ею путём и сам ничего не выдаёт и не отзывает (`manageDacls: false`). Fork получает иную временную возможность, а свежий провайдер даёт новую пару путь/SID даже той же возобновлённой сессии, поэтому мусор после сбоя остаётся инертным, не становясь ни коллизией, ни унаследованной возможностью. Без пары `--temp` называет корень: раннер workspace-write без агента создаёт случайного приватного ребёнка, сам управляет его temp-SID, переписывает TMP/TEMP и удаляет ребёнка при выходе. Рабочая область, равная такому корню или содержащая его, отвергается до любой выдачи, иначе её наследуемый ACE рабочей области авторизовал бы каждого приватного ребёнка; прямой API точно так же отвергает пересечение любого корня записи с фактическим приватным временным каталогом. Повторная выдача постоянного ACE рабочей области после перезапуска идемпотентна: `grantWrite` читает текущий DACL и пропускает `SetNamedSecurityInfoW`, когда точный ACE уже стоит (такое применение заново размножает идентичный ACE по всему дереву — минуты на больших рабочих областях). Известная цена: первая выдача на большом дереве рабочей области один раз на машину на рабочую область блокируется на эту жадную распространённость.

Режимы (список ограничивающих SID токена следует режиму; группа keep-alive — logon SID + Everyone в ОБОИХ режимах — без них ранняя инициализация DLL умирает с `0xC0000142`, а CNG валит pwsh с `0xE0434352`):
- `workspace-write` (logon SID, Everyone, workspace SID, temp SID): рабочая область и ПРИВАТНЫЙ временный подкаталог сессии несут раздельные права записи; прочие адресуемые через ACL записи запрещены, кроме документированных границ Everyone и жёстких ссылок.
- `read-only` (logon SID, Everyone — БЕЗ write-SID): явных выдач write-SID нет. write-SID нарочно остаётся ВНЕ списка: стоящий ACE выдачи рабочей области от прежнего периода workspace-write (понижение через `/permission` или сессия, возобновлённая после сбоя) под read-only остаётся ИНЕРТНЫМ, потому что проверка второго прохода write-restricted даёт лишь то, что несёт ограничивающий список, — а стоящий ACE тем временем избавляет повторное повышение от повторного размножения. Фоновые права Everyone остаются задокументированной частичной границей. Записи в NUL — ФОНОВЫЕ, а не выданные: DACL устройства даёт Everyone read+write+execute (`0x1201BF`), поэтому открыватели, чья маска в него укладывается (cmd `> NUL`, node `\\.\NUL`), могут писать туда в ОБОИХ режимах — песочница не может занулить выдачу устройству NUL, пока Everyone сидит в группе keep-alive. `Set-Content NUL` отказывает в обоих режимах (эффект слоя PowerShell/.NET, закреплён набором тестов read-only — отказывающая сторона не DACL устройства); перенаправление PowerShell `> $null` продолжает работать (оно отбрасывает данные, не открывая NUL).

Authenticated Users отсутствует в ОБОИХ списках — проверка безопасности пространства имён WMI отказывает (`0x80041003`), поэтому CIM-командлеты и `Get-ComputerInfo` (молча возвращающий неполный результат вместо ошибки) недоступны в КАЖДОМ режиме изоляции, а лазейка создания деревьев в корне C:\ (стоящие `AU:(AD)` + `AU:(OI)(CI)(IO)(M)` ACE) закрыта в обоих — модельно-ориентированная документация декларирует этот контракт, а не обещание промпта. INTERACTIVE/LOCAL тоже отсутствуют в ОБОИХ списках: дерево Public хоста даёт запись INTERACTIVE, поэтому записи в Public запрещены — закреплено регрессионной пробой раннера на фоново-записываемый Public (см. записку о проектировании).

Класс `AclSandbox` (явный приватный `tempDir` + `tempWriteSid` или `tempDir: null` для отключения записей во временную область) остаётся программным API для прямых запусков; `AclWriteGrant` — серверная, материализующая половина жизненного цикла выдачи.

## Проверенные границы (свойственны самим ограниченным токенам, а не этому порту)

- **Выдачи Everyone остаются фоновым правом записи.** Everyone обязан оставаться в обоих ограничивающих списках: удаление ломает раннюю инициализацию DLL и CNG. Поэтому внешний объект NTFS, чей обычный DACL даёт Everyone затребованное право записи, проходит обе проверки доступа и остаётся записываемым в обоих режимах. Настоящий набор тестов раннера заводит внешний каталог `Everyone:Modify` и закрепляет такое поведение; провайдер сообщает `enforcement: 'partial'`, чтобы вызывающие могли отвергнуть эту более слабую границу или показать её наружу.
- **Жёсткие ссылки — псевдонимы файлового объекта, а не пути.** Наследуемый ACE рабочей области, размноженный на существующую жёсткую ссылку NTFS, меняет единственный лежащий в основе дескриптор безопасности файла, поэтому тот же объект записываем через внешний псевдоним. Отвергать каждый многократно ссылаемый файл рабочей области неосуществимо для обычных установок pnpm, которые пользуются жёсткими ссылками в своё content-addressable хранилище; нативный набор тестов раннера закрепляет эту щель, а частичный отчёт провайдера называет её последствие.
- **Ограничена запись; чтение, сеть и видимость процессов — нет.** `WRITE_RESTRICTED` пересекает только доступы записи, поэтому изолированный ребёнок может читать любой доступный вызывающему файл и открывать сокеты. Режим `read-only` потому одним этим механизмом не выражается; для более сильной изоляции дополните его политикой на стороне чтения или capability-токеном AppContainer/`S-1-15-2`.
- **Изоляция консоли недоступна.** Под ограниченным токеном дети, созданные с `CREATE_NO_WINDOW` / `CREATE_NEW_CONSOLE`, умирают при инициализации DLL с `STATUS_DLL_INIT_FAILED` (`0xC0000142`). POC пытался исправить это добавлением console logon SID (`S-1-2-1`) в ограничивающий список; на Windows 11 26200 `CreateWellKnownSid(WinLocalLogonSid)` падает с `ERROR_INVALID_PARAMETER` (87), правильный `WinConsoleLogonSid` даёт валидный `S-1-2-1`, но ребёнок всё равно умирает, и финальная ревизия POC убрала и SID, и изоляцию консоли. Потому дети делят консоль хоста; перенаправление stdio идёт через каналы и не страдает.
- **Выдачи ACL — постоянные мутации каталога.** Они переживают гибель процесса посреди работы; ACE рабочей области стоят ПОСТОЯННО ПО ЗАМЫСЛУ (никогда не отзываются — кэш переиспользования), temp-ACE отзывает `dispose()` (а `init()` отзывает уже применённую временную выдачу, когда поздний шаг отказывает). Задокументированная ручная чистка POC (`icacls <dir> /remove '*S-1-4-…'`) на этой платформе падает с `ERROR_NONE_MAPPED` (1332) — отзывайте через этот модуль. Некорректному выключению самолечение для ACE рабочей области не нужно: выведенный SID на следующей подготовке снова попадает на стоящий ACE (минуя применение); ACE write-SID никогда не копит вторую идентичность за перезапуск, потому что идентичность и ЕСТЬ рабочая область.
- **Выдаваемые каталоги должны принадлежать вызывающему.** Неявный `WRITE_DAC` владельца — то, что позволяет песочнице править DACL без повышения привилегий.
- **Фоновый корень temp никогда не выдаётся неявно.** Прямому вызывающему `AclSandbox` в режиме workspace-write нужно предъявить существующий приватный `tempDir` плюс его отдельный `tempWriteSid` либо явно отключить записи во временную область через `tempDir: null`. Фактический временный каталог обязан не пересекаться ни с одним корнем записи. Seam создаёт случайный приватный каталог; вызовы раннера без агента трактуют `--temp` как родительский корень и создают собственного случайного ребёнка, но отвергают рабочую область, равную этому родителю или содержащую его, до любой мутации ACL.
- **Временная возможность изолированного ребёнка приватна для каждой живой пары сессия/рабочая область.** Перед запуском раннер через `SetEnvironmentVariableW` переписывает TMP/TEMP на этот приватный каталог, и ребёнок наследует переписанный блок (семантика bwrap `--tmpfs /tmp`). Temp-ACE и каталог снимаются при освобождении провайдера или после каждого вызова без агента. Сбой может оставить инертный мусор в `%TEMP%`, но возобновлённый провайдер выбирает новый случайный путь и SID вместо коллизии с остатками или их реавторизации. Нативный набор тестов раннера доказывает, что два токена с общим SID рабочей области не могут писать во временные каталоги друг друга.
- **`whoami` и командлеты осмотра токена отказывают под ограниченным токеном.** `GetTokenInformation` над дубликатом ребёнку частично недоступен, поэтому `whoami /all` сообщает ошибки — диагностический шум схемы ограничения, а не операционный отказ; важные поверхности блокировки (запись файлов) не затронуты.

## Известные ограничения и отложенная работа

- **Один список разрешений записи на рабочую область** — единица списка разрешений это write-SID, он же и ЕСТЬ идентичность рабочей области; один экземпляр песочницы на две рабочие области расширяет обе выдачи на оба корня (один SID тогда называл бы два корня). Создавайте по экземпляру на корень рабочей области — seam делает ровно это, ключуясь путём рабочей области.
- **Чистка по замыслу best-effort** — `dispose()` предпринимает каждый отзыв temp и агрегирует неудачи в `AggregateError`; неудача чистки может оставить случайный каталог и его ACE, принадлежащий одному temp-SID. После выхода процесса никакой будущий токен этот SID не носит, поэтому остаток инертен, пока его не подберёт temp-гигиена ОС или ручное удаление каталога.
- **Постоянные ACE рабочей области — невидимый остаток.** Переименование рабочей области выводит новый SID; старые ACE на старом пути остаются (инертные, только write-SID). Грядущая команда чистки может их собрать; из-за них ничто не размножается заново.
- **Каталоги с NULL-DACL не сохраняют идентичность при цикле выдача+отзыв.** Каталог с NULL DACL (редкость — каталоги, созданные Windows, несут настоящие DACL) означает «полный контроль всем»; `grantWrite` строит новый ACL из этого нуля, а круговорот отзыва оставляет ПУСТОЙ (запрещающий всё) DACL вместо исходного NULL DACL. POC ведёт себя так же; настоящие рабочие и временные каталоги несут настоящие DACL, так что это остаётся документированным краевым случаем, а не охраняемым путём.
- **Перехват stdio через канал невозможен для изолированных внуков (шаблон SD по умолчанию у именованных каналов).** Канальный stdio libuv пользуется ИМЕНОВАННЫМИ каналами; `CreateNamedPipeW` без атрибутов безопасности ставит пользовательско-режимный шаблон SD по умолчанию слоя Win32 (строится KernelBase — полный доступ владельцу/SYSTEM/Admins, Everyone/ANONYMOUS только чтение; фиксированный шаблон, который [документирует Microsoft](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)) — НЕ токенный DACL по умолчанию, который ядро применяет при сыром создании с SD-null, — поэтому клиентское открытие запрашивает запись, которой не выдан ни один ограничивающий SID: `spawn(..., { stdio: 'pipe' })` внутри изолированного процесса падает с EPERM — задокументированной POC границей WRITE_RESTRICTED-токенов «нет перенаправления вывода». Запуски с наследуемым (`inherit`/fd) и игнорируемым (`ignore`) stdio работают, а анонимные каналы (CreatePipe — потребитель токенного DACL по умолчанию, как конвейеры PowerShell) работают, ибо DACL ограниченного токена по умолчанию несёт полнодоступный ACE ограничивающего SID (ставится при init). Изолированный процесс потому не может собрать вывод внука через канал; инструментам, обязанным собирать вывод, нельзя работать изолированно.
- **Материализация выдачи — жадное размножение по всему дереву.** `SetNamedSecurityInfoW` над каталогом с наследуемыми ACE немедленно обходит каждого потомка (НЕ лениво по доступу — измерено десятками секунд на больших деревьях рабочих областей). Идентичность на рабочую область платит это один раз на рабочую область на машину (лениво при первом в истории изолированном исполнении, полностью пропускаясь на каждом позднейшем предоставлении, когда точный ACE стоит). Приватные временные каталоги стартуют пустыми, потому их отдельная выдача дёшева. Если рабочая область огромна, первая изолированная запись на этом хосте соразмерно медленна.
- **Изоляция на стороне чтения и сетевая политика вне охвата** — `WRITE_RESTRICTED` пересекает только доступы записи; для более сильной изоляции дополните бэкенд политикой на стороне чтения.
- **Предупреждения о широких каталогах и томах FAT отложены; цели класса FAT остаются записываемыми.** Предупреждения со стороны UI о выдаче необычно широких каталогов или томов FAT-класса (без ACL) ещё не реализованы, а FAT-том как КОРЕНЬ выдачи попросту громко валит выдачу (поддержки ACL нет). Цель FAT-класса ВНЕ выданных корней — другое дело: дескрипторов безопасности у неё нет, поэтому проверка записи ограниченного токена проходит (Everyone сидит в обоих списках), и такие цели записываемы в ОБОИХ режимах изоляции. FAT трактуется как легаси-остаток — без поддержки и без обходной инженерии; эта позиция «только предупреждать» задокументирована здесь, а не устранена.
- **Языковой режим PowerShell различается между режимами изоляции.** Под `read-only` PowerShell не может создать свои пробные файлы AppLocker во temp и осторожно стартует в ConstrainedLanguage: `Add-Type` (компиляция C#, P/Invoke), статические вызовы не-core .NET (`[System.IO.*]::`, `[math]::`, `[Environment]::`), COM-объекты и рефлексия падают с ошибками `Cannot create type` / `Cannot invoke method` («only core types»), а `$ExecutionContext.SessionState.LanguageMode = 'FullLanguage'` отвергается. На поставляемом пути `workspace-write` возможность приватного temp позволяет пробе завершиться, поэтому pwsh остаётся в FullLanguage, пока общехостовая политика WDAC/AppLocker не скажет иного; прямой `AclSandbox`, настроенный с `tempDir: null`, такой гарантии не имеет и может закрыть пробу наглухо, как read-only. Это разделение — стартовое поведение PowerShell, а не часть границы записи ACL. Описание инструмента `pwsh` преподаёт модели поставляемые режимы; вызовы `danger-full-access` идут без изоляции в FullLanguage.
