# @deepseek-ai/dsh-session-persistence

[English](README.md) | [中文](README.zh.md) | Русский

Персистентность сессий — это capability seam. Абстрактный сервис `SessionPersistence` (`ctx.sessionPersistence`) — его Service Definition. Он требует бэкенд персистентности, который долговечно хранит, перезагружает и перечисляет сессии, не определяя реализацию хранилища. Seam следует ролям `dsh-shell` ([capability seams](../../../.agents/notes/implemented/architecture/2026-06-13-capability-seams.md)): этот пакет владеет Service Definition, соседний пакет владеет Service Provider, а Consumer внедряют сервис.

Сохраняемая единица — это именно существующий `SessionEvent` (event-sourced модель — журнал есть источник истины), поэтому параллельного типа «сохраняемого сообщения» нет. Метаданные, которые **не** являются воспроизводимым состоянием диалога (версия формата, cwd, родословная, граница seed, происхождение, глубина делегации), едут отдельно в `SessionHeader`; им владеет `dsh-session`, а отсюда он реэкспортируется.

## Сервисный API (`ctx.sessionPersistence`)

| Метод | Контракт |
|---|---|
| `locate(meta): SessionLocation \| undefined` | Вычисляет абсолютный адрес артефакта конкретной сессии без I/O и материализации. Бэкенды без независимого локального артефакта возвращают `undefined`. |
| `supportsRawArtifacts: boolean` | Явно заявляет, предоставляет ли этот бэкенд по одному дословному артефакту на сессию. Consumer проверяют эту возможность перед вызовом `readRaw`; `false` — это не отсутствие сессии. |
| `readRaw(id, signal?): Promise<SessionRawArtifact \| undefined>` | Читает собственный текст артефакта поддерживаемого бэкенда дословно: декодирует его физическую кодировку, но никогда не реконструирует из событий. `undefined` означает только отсутствие запрошенного артефакта; неподдерживаемый бэкенд отклоняет вызов. |
| `create(meta): Promise<void>` | Регистрирует метаданные новой сессии. МОЖЕТ отложить физическую запись до первого `append` (ленивая материализация). |
| `append(id, events): Promise<void>` | Долговечно сохраняет батч. Append-only; `seq` первого события == сохранённому next-seq после любого ремонта; отклоняет данные, несериализуемые в JSON, называя виновный тип. |
| `prepare(id, signal?): Promise<SessionPreparation>` | Резервирует точную неопубликованную Session, которую использует возобновление. Координатор переиспользует более раннюю инспекцию, когда она доступна, фиксирует ожидающее восстановление и при освобождении ресурсов возвращает неопубликованный резерв в свой ограниченный кэш. |
| `load(id): Promise<{ meta; events }>` | Возвращает неизменяемый сбалансированный логический журнал после конвертации поддерживаемых старых записей того же номера версии формата и фиксации холодного восстановления. Живой load сначала вычищает свой снапшот и отклоняется, пока его ход открыт; холодный load сохраняет прерванный финальный ход и долговечно закрывает его синтетическими событиями `tool/result`/`step/end?`/`turn/end {interrupted}`. Отбрасывается только обрывочный хвостовой фрагмент; зафиксированное повреждение и некорректные записи отклоняются как `SessionPersistenceCorruptionError`, а неподдерживаемая `version` формата или неизвестный этой сборке тип события (без маркера `ignorable` в конверте) отвергается как `SessionFormatUnsupportedError` с названием направления отказа и пути исходного журнала, когда бэкенд хранит один артефакт на сессию. |
| `inspect(id, signal?): Promise<{ meta; events }>` | Возвращает улучшенную, провалидированную, глубоко замороженную логическую картину, не фиксируя восстановление и не публикуя Session. Холодная картина получает находящиеся в памяти синтетические закрывающие события восстановления, пока её физический обрывочный хвост остаётся нетронутым; уже живая картина — это её текущий неизменяемый снапшот, и она может содержать открытый ход. Реализации на координаторе удерживают точную холодную неопубликованную Session в ограниченном LRU для последующего `prepare`, но отбрасывают и перезагружают её, когда меняется сохранённая ревизия. Инспекции одного id разделяют один выполняющийся read. |
| `readFrom(id, fromSeq, signal?): Promise<{ meta; events }>` | Возвращает валидные сохранённые события с `seq >= fromSeq` без кэша подготовки, усечения, закрывающих событий или состояния координатора. `fromSeq` на сохранённом конце или дальше возвращает пустой список событий; отрицательный или не safe-integer `fromSeq` отклоняется. Бэкенды с seek (SQLite) читают только суффикс, если только конвертация поддерживаемой старой записи не требует более ранних записей; последовательные бэкенды (JSONL) разбирают весь артефакт и пропускают вперёд. Отказ из-за неизвестного типа следует этому шаблону доступа: seek-чтение проверяет только возвращённый суффикс, а последовательный fallback отвергает также на неизвестном обязательном событии ниже окна. Предназначено для checkpoint-потребителей, применяющих только события после сохранённого порядкового номера. |
| `list(signal?): Promise<SessionHeader[]>` | Лёгкое перечисление из метаданных, без разбора полного журнала. Опциональный сигнал отменяет работу бэкенда по перечислению. Лениво материализованная сессия с нулём событий в `list` отсутствует. |
| `listSnapshots(signal?): Promise<SessionPersistenceSnapshot[]>` | Лёгкие метаданные плюс непрозрачная брендированная ревизия на каждый журнал, без загрузки журналов событий. Ревизия остаётся равной, пока журнал и его backing-хранилище не меняются, меняется после append или мутирующего ремонта при load и не может совпасть лишь потому, что два хранилища используют один и тот же локальный счётчик. Опциональный сигнал запрашивает отмену работы бэкенда по обнаружению; бэкенды первой стороны доводят начатую работу перечисления до конца, прежде чем отклониться, чтобы ожидаемый вызов был quiescent. |

## Инварианты, которые обязан соблюдать каждый бэкенд

- **Append-only; упавший ход закрывается, а не усекается.** Вычищенные события никогда не переписываются. Сбой может оставить незакрытый финальный ход, чьи события реальны и, возможно, велики; `load` сохраняет их и долговечно дописывает синтетические закрывающие события (классифицированный по риску ошибочный `tool/result` на каждый оставшийся без ответа вызов ассистента, затем `step/end?`+`turn/end {interrupted}`), чтобы сбалансировать журнал и оставить восстановленную историю валидным транскриптом провайдера. Отбрасывается только так и не дописанный целиком обрывочный хвостовой фрагмент.
- **Непрерывный seq.** `load` отклоняет разрыв `seq`/ошибку разбора в **середине** журнала; первый `seq` у `append` должен равняться сохранённому next-seq.
- **Данные, сериализуемые в JSON.** `append` проводит каждый прямой/replay-батч через общую однопроходную lossless-JSON-границу без потерь. События живой `Session` уже глубоко заморожены, но координатор записи всё равно копирует каждое событие в буфер, принадлежащий персистентности.
- **Долговечность.** `append` возвращается, только когда батч стал долговечным.

## Координатор записи

`PersistenceCoordinator` владеет состоянием по id и сериализацией, одним ограниченным контроллером записи на живую сессию, ленивой материализацией, ремонтом аварийного хвоста, принятием сессий и quiescent-освобождением ресурсов. Бэкенд первой стороны компонует его, реализует небольшой интерфейс storage-хуков `PersistenceBackend` и делегирует ему свои методы с состоянием. Поэтому JSONL и SQLite разделяют корректность жизненного цикла, сохраняя разные примитивы хранения; см. [Agent Note о координаторе](../../../.agents/notes/implemented/architecture/2026-06-18-shared-persistence-write-coordinator.md), [упрощение flush-контроллера](../../../.agents/notes/implemented/simplification/2026-07-23-collapse-persistence-flush-state.md) и [решение об ограниченном батчинге](../../../.agents/notes/implemented/architecture/2026-08-08-bounded-session-persistence-write-batching.md).

Каждый `session/event` копирует своё событие в контроллер сессии. Первое ожидающее событие открывает фиксированное окно батчинга; поздние события присоединяются, не сбрасывая его дедлайна. Настроенный `writeBatchMaxDelayMs` ограничивает это намеренное ожидание, а не задержки event loop, инициализации, сериализованных операций или бэкенда. События, допущенные во время записи, образуют новый ограниченный батч. `session/flush` отменяет ожидание и служит общим барьером quiescence, вычищающим события, допущенные во время его работы. Фоновая неудача логируется один раз, сохраняет упорядоченный батч и ставит автоматическую повторную попытку на паузу; новое событие начинает свежее окно, а явный flush или teardown бэкенда повторяют немедленно и выносят наружу повторную неудачу.

Ремонт после сбоя выполняется только на холодном пути. Для живого id `load(id)` снимает снапшот авторитетного журнала в памяти, ждёт его долговечной записи и возвращает его, только когда тот сбалансирован; открытый живой ход отклоняется вместо получения синтетических закрывающих событий прерывания. Для холодного id инспекция читает, провалидирует, замораживает и собирает одну неопубликованную Session; повторная инспекция переиспользует этот граф объектов, лишь пока ревизия его источника остаётся актуальной. `prepare(id)` выполняет ту же проверку перед ремонтом, резервирует точную Session, фиксирует любой ожидающий ремонт оборванного хвоста/прерванного хода и возвращает её для публикации. Принятие при HMR читает через `loadStored`, применяет cwd-проверку координатора и никогда не закрывает активный ход.

При чтении бэкенд конвертирует точно поддерживаемые старые записи того же номера версии формата перед валидацией текущих записей. Сообщения до-identity получают детерминированный id `legacy-message:<session-id>:<event-seq>`; замена содержимого tool-result наследует импортированный id своей цели. До-react-loop `turn/start` теряет свой устаревший trigger, удалённый `steering/message` становится тем же идентифицированным `user/message`, а более старый `turn/end` отображает свою причину завершения, не выдумывая вызывающего, которого старая запись не называла. Координатор использует ту же конвертированную картину для `load`, `inspect`, `readFrom`, притязаний на состояние без владельца и принятия HMR-префикса. Хранилище остаётся append-only: чтения не переписывают старые записи, а последующие дозаписи используют текущий формат. Это узкие исключения при импорте из решений [pre-identity message](../../../.agents/notes/implemented/bug-fix/2026-07-28-load-pre-identity-session-messages.md) и [pre-react-loop session](../../../.agents/notes/implemented/bug-fix/2026-08-04-load-pre-react-loop-sessions.md), а не общее обещание миграции v0.

Когда живая сессия выдаёт `session/disposed`, координатор ждёт её контроллер, сериализует финальную вычистку, затем освобождает состояние, которым владеет именно этот объект `Session`. Неудавшееся увольнение оставляет контроллер в карте живых сессий, чтобы teardown бэкенда мог повторить его. Teardown бэкенда сначала прекращает допуск событий, вычищает каждый оставшийся контроллер, дожидается операций по каждому id и лишь затем закрывает дескриптор хранилища.

Свободные от побочных эффектов запросы `locate`, лёгкий `listSnapshots` и `readStoredRevision` по id остаются во владении бэкенда, потому что описывают топологию хранилища и идентичность ревизий, а не оркестрацию записи. `listSnapshots(signal?)` передаёт точный сигнал вызывающего в обнаружение бэкендов, чтобы наблюдатели могли отменить эту работу, не отсоединяя её.

Хуки `PersistenceBackend<TornMarker>` (единственный контракт между координатором и хранилищем):

| Хук | Роль |
|---|---|
| `name` | Метка бэкенда для `AggregateError` при неудаче освобождения ресурсов. |
| `loadStored(id, signal?)` | Читает сохранённый префикс по id во всех scope хранилища. Используется возобновлением/load, немутирующей инспекцией, живым принятием и пробой на коллизию при создании. Опциональный сигнал принадлежит чтениям только для наблюдения. Возвращённые метаданные идентифицируют `id`; `revision` идентифицирует ровно возвращённые заголовок и события; непрозрачный `tornMarker` присутствует тогда и только тогда, когда обрывочный хвост должен быть усечён. |
| `readStoredRevision(id, signal?)` | Читает текущую ревизию с квалификацией источника для одного id, не загружая его журнал событий. Использует то же представление ревизии, что `loadStored`, и возвращает `undefined`, когда id отсутствует. |
| `loadStoredFrom?(id, fromSeq, signal?)` | Опциональное суффиксное чтение с поддержкой seek позади сервисного `readFrom`: заголовок плюс сохранённые события с `seq >= fromSeq`, без мутаций, без torn-маркера. SQLite реализует его (`WHERE seq >= ?`); бэкенд без него получает fallback координатора — `loadStored` плюс пропуск вперёд. |
| `appendBatch(meta, events, isMaterialized)` | Долговечно дописывает непрерывный батч, при отсутствии материализации выполняя ленивую материализацию **атомарно**. |
| `commitRepair(meta, tornMarker, closers)` | Делает ремонт после сбоя долговечным: усекает обрывочный хвост (при условии `tornMarker !== undefined` — маркер может быть falsy, например seq/offset `0`) и дописывает `closers`. Атомарность **не** требуется. Используется load (усечение + закрывающие события) и живым принятием (только усечение). |
| `list(signal?)` | Перечисляет все сохранённые метаданные, соблюдая опциональную отмену. |
| `close?()` | Опциональный teardown жизненного цикла (например, закрытие дескриптора базы данных); дожидается после drain при освобождении ресурсов. |

Координатор сверяет сохранённый id и сравнивает сохранённый/живой cwd перед ремонтом или живым принятием. Его путь `inspect()` забирает владение свежими значениями бэкенда, один раз провалидирует и замораживает их и удерживает не больше настроенного числа неопубликованных Session, не вызывая `commitRepair`. Удержанный источник переиспользуется или ремонтируется, только пока его ревизия всё ещё равна `readStoredRevision`; иначе координатор перезагружает его. Эта проверка актуальности не добавляет межпроцессного исключения писателей. Повторы при смене ревизии сходятся, пока долговечный журнал не меняется на протяжении одного круга чтение/проверка; непрерывные внешние писатели могут задерживать `load`, `inspect` или `prepare`. `tornMarker` полностью **непрозрачен**: координатор лишь проверяет `!== undefined` и передаёт его туда-обратно в `commitRepair`, никогда не заглядывая в значение (JSONL-бэкенд использует смещение в байтах для усечения, SQLite-бэкенд — seq для удаления). Сторонний бэкенд МОЖЕТ реализовать абстрактный сервис напрямую, без координатора, но обязан предоставить такую же немутирующую инспекцию и заслуживающие доверия лёгкие ревизии снапшотов. См. [Agent Note о write-coordinator](../../../.agents/notes/implemented/architecture/2026-06-18-shared-persistence-write-coordinator.md).

## Типы метаданных и расположения

Реэкспортируется из `dsh-session`: `SessionHeader` (неизменяемые метаданные сессии: `version`, `id`, `createdAt`, `cwd?`, `parentSession?`, `seedLength?`, `origin?`, `delegationDepth?`). `SessionLocation` — это `{ readonly kind: string; readonly path: string }`; его путь — абсолютная цель бэкенда, а не доказательство существования артефакта или наличия в нём невычищенного хода.

## Model Experience

### Возобновлённая история диалога

#### What the model sees

Этот seam не добавляет ни промпта, ни схемы. Возобновление восстанавливает сохранённые поверхностные события как историю сообщений; сохранённые заголовки запросов реконструируют более ранние вызовы, а новый цикл собирает текущий системный промпт, инструменты и префикс сессии для своего следующего запроса. Ремонт после сбоя помечает запрос ассистента без долговечного вызова как `TOOL_NOT_STARTED`; долговечный вызов без результата становится `TOOL_OUTCOME_UNKNOWN`, чей текст позволяет модели повторить read-only или идемпотентную работу, но направляет её проверить побочные эффекты или спросить пользователя вместо слепого повтора.

#### Token effect

Во время обычной персистентности — ноль токенов. Возобновление восстанавливает стоимость удержанной истории и штатно оплачивает текущий конверт запроса; каждый отремонтированный вызов добавляет цитируемый удержанный текст ошибки.

#### KV Cache effect

Персистентность не мутирует живые префиксы запросов. Возобновлённый цикл может переиспользовать кэш провайдера, только когда его реконструированная история, текущий конверт и маршрут модели совпадают; результаты ремонта после сбоя дописываются, не переписывая прежнюю историю.

## Known Limitations and Deferred Work

- **Нет API удаления или удержания** — прореживание сохранённых сессий — внешнее обслуживание бэкенда.
- **`list()` без пагинации и фильтров** — возвращает заголовок каждой сохранённой сессии; нормально для локальных хранилищ, без индексов на масштабе.
- **Синтетические закрывающие события при ремонте — единственный сценарий сбоя** — бэкенд обязан синтезировать закрывающие `tool/result`/`step/end`/`turn/end` при load; частичного возобновления хода, продолжающего прерванный ход вместо его закрытия, нет.
