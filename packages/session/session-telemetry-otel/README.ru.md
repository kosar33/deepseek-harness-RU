# @deepseek-ai/dsh-session-telemetry-otel

[English](README.md) | [中文](README.zh.md) | Русский

Бэкенд OpenTelemetry для [seam телеметрии](../session-telemetry/) — единственная точка входа, которую загружает развёртывание. Его `mode` решает, следует ли seam за событиями сессии вживую, воспроизводит ли канонический журнал только при зафиксированной обратной связи или держит телеметрию локальной. Загружающие режимы компонуют OTel JS SDK как есть (`LoggerProvider` → `BatchLogRecordProcessor` → экспортёр логов OTLP/HTTP) и отображают каждую переданную ему запись на `logger.emit()` под двумя областями инструментирования: записи канала `ledger` — на `@deepseek-ai/dsh-session-sessionTelemetry-otel`, операционные записи — на `@deepseek-ai/dsh-session-sessionTelemetry-otel/ops`. Идентичность ресурса содержит `service.name`/`service.version` из `APP_IDENTITY` пакета `dsh-llm` плюс анонимный `user.id` этого пакета (`$DSH_HOME/.anonymous-user-id` — случайный UUID, создаваемый при первом использовании и сбрасываемый удалением файла), передаваемые один раз на экспортную партию, а не на запись.

## Конфигурация

```yaml
- id: sessionTelemetry-otel
  name: '@deepseek-ai/dsh-session-sessionTelemetry-otel'
  config:
    mode: FULL                # explicit opt-in; default: DISABLED
    shutdownTimeoutMillis: 3000 # optional; defaults to 3000
    exporter:                # passed verbatim to the SDK's OTLP/HTTP log exporter
      url: https://collector.example.com/v1/logs
      headers:
        authorization: !!js `Bearer ${process.env.OTLP_TOKEN}`
    processor: {}            # optional; passed verbatim to BatchLogRecordProcessor
```

| `mode` | Поведение |
|---|---|
| `FULL` | Каждая спроецированная запись, включая операционные записи жизненного цикла, немедленно передаётся в OTel SDK. |
| `FEEDBACK_ONLY` | Каждый `feedback/record` воспроизводит, проецирует и очищает суффикс канонического журнала сессии через это событие. Последующие записи ждут очередного события обратной связи и остаются локальными, если оно не приходит. |
| `DISABLED` | По умолчанию. Ни координатор, ни провайдер, ни процессор, ни экспортёр не конструируются. Ни одна запись телеметрии не покидает процесс. `feedback/record` пишет в журнал `session sessionTelemetry is DISABLED; nothing will be shared and this feedback remains local`; само событие остаётся в локальном журнале сессии. |

Программная конфигурация TypeScript использует экспортируемое перечисление `SessionTelemetryMode` (`SessionTelemetryMode.FULL`, `SessionTelemetryMode.FEEDBACK_ONLY` или `SessionTelemetryMode.DISABLED`); сырые строковые литералы не присваиваемы. Сериализованная конфигурация Cordis продолжает использовать показанные выше строковые значения.

Авторизация выгрузки позитивна и действует по принципу fail-closed. Неизвестный режим прямого конструирования приводит к отказу ещё до чтения транспортной конфигурации. Только `FULL` принимает прямые вызовы `ctx.sessionTelemetry.emit()`. `FEEDBACK_ONLY` даёт своему координатору по требованию закрытую возможность бэкенда и признаёт согласием только тот точный объект `feedback/record`, что уже хранится в `session.events[event.seq]`; независимо испущенное значение шины игнорируется. `DISABLED` никогда не конструирует конвейер SDK, даже когда опции экспортёра заданы.

Смонтированный сервис раскрывает разрешённый режим через свойство `sharing` типа [`SessionTelemetrySharingStatus`](../session-telemetry/README.ru.md#раскрытие-режима-обмена) seam'а (`full` / `feedback-only` / `disabled`), поэтому подтверждение `/feedback` может сообщить, передаётся ли сессия куда-либо и как именно. Раскрытие задаётся в конструкторе и не зависит от захвата: даже `DISABLED` раскрывает `disabled`.

`exporter.url` обязателен в `FULL` и `FEEDBACK_ONLY`, значения по умолчанию не имеет и должен разбираться как `http(s)`; в `DISABLED` он необязателен и не используется. В загружающих режимах `shutdownTimeoutMillis` — положительный конечный внешний предельный срок, принадлежащий DSH и равный по умолчанию 3000 мс, а `processor.maxExportBatchSize`, не являющийся положительным целым, также приводит к отказу при загрузке плагина, потому что SDK такое значение принимает, но затем зависает при остановке. Оба блока конфигурации SDK проходят целиком: каждое поле `OTLPExporterNodeConfigBase` (`headers`, `timeoutMillis`, `compression`, `keepAlive`, …) достигает экспортёра, а пакетирование, темп экспорта (`scheduledDelayMillis`), повторы, границы очереди и политика потерь при затяжном сбое — поведение SDK, настраиваемое через `processor`. Бэкенд не реализует `flush()`: штатной выкачкой владеет пакетный процессор. При остановке OTel ожидает `exporter.forceFlush()` перед завершающим обещанием процессора, ограниченным `exportTimeoutMillis`; если это транспортное обещание так и не разрешается, пакет оставляет ожидание по истечении `shutdownTimeoutMillis`, логирует поглощённую ошибку остановки через координатор и позволяет разборке приложения продолжаться. Предельный срок не может отменить транспорт SDK, поэтому записи, всё ещё ожидающие в этот момент, могут быть потеряны при выходе из процесса.

## Что покидает машину

В загружающих режимах записи несут полный `event.data` в том виде, в каком его возвращает каскад `sessionTelemetry/record` seam'а, — содержимое сообщений пользователя и ассистента, аргументы и результаты инструментов (вывод команд, содержимое файлов), полный системный промпт вместе со схемами инструментов (`request/header`), текст задач todo, сводки компакции, `stderrSummary` хуков, текст обратной связи и `cwd` сессии (локальный путь). Seam не поставляет правил очистки: без смонтированного слушателя `sessionTelemetry/record` это сырая захваченная копия, поэтому развёртывание, экспортирующее за пределы доверенной границы, монтирует собственные правила (см. [README seam'а](../session-telemetry/README.ru.md#каскад-очистки)). `FULL` выполняет очистку в момент дописывания; `FEEDBACK_ONLY` не хранит копии телеметрии и применяет правила, смонтированные на тот момент, когда обратная связь запускает воспроизведение канонического журнала. Учётные данные провайдера в любом случае не появляются никогда: ключи API адаптера — параметры конструктора, а не события сессии, поэтому они структурно отсутствуют в журнале, а значит, и в телеметрии. `DISABLED` не конструирует конвейер SDK и не передаёт бэкенду ни одного захвата.

## Сопоставление полей

Запись seam → запись лога SDK: `time` → `timestamp`/`observedTimestamp`; `severity` → `severityNumber`/`severityText` (INFO 9 / WARN 13 / ERROR 17); `body` → структурированное тело лога; `attributes` дословно. Получатели дедуплицируют по `(session.id, event.seq)` и поднимают оповещения по severity. В `FULL` они могут вдобавок обнаруживать сбои по отсутствию записи `shutdown`: маркер испускается при освобождении ресурсов самой сессии либо при разборке приложения, а маркер, за которым следуют ещё события, означает перезагрузку телеметрии. В `FEEDBACK_ONLY` у высвобожденного префикса обычно нет последующего маркера `shutdown`, так что его отсутствие сигналом сбоя не является. Потоки не самодостаточны между поколениями: возобновлённая сессия продолжает собственный поток своего id с того места, где остановился предыдущий процесс, а поток fork-сессии начинается на унаследованной границе — её префикс живёт в потоке родителя и сшивается через `session.parent_id` + `session.seed_length`. Локальный журнал возобновлённой сессии может содержать синтетические закрыватели, которые никогда не экспортировались; проводной поток верен ровно тем записям, что реально переданы в SDK.

## Опыт модели

Отсутствует, поскольку бэкенд лишь пересылает очищенные записи seam'а в конвейер OTel SDK; он никогда не вносит вклада в запрос к модели.

#### Влияние на KV-кэш

Отсутствует; этот пакет ни собирает, ни отправляет запрос провайдеру.

## Известные ограничения и отложенная работа

- **Экспериментальное дерево upstream** — `@opentelemetry/sdk-logs` по-прежнему публикуется из экспериментального дерева upstream; колебания API SDK затрагивают этот пакет и только его — контракт seam'а не сдвигается.
- **Поведение с живым коллектором принадлежит экспортёру SDK** — аутентификация, TLS, троттлинг и прочее реальное поведение развёртывания OTLP определяются upstream SDK, а не собственным слоем совместимости пакета.
- **Снимок на момент обратной связи** — `FEEDBACK_ONLY` не хранит собственной телеметрической копии до наступления обратной связи. Он читает и очищает текущий канонический журнал в момент записи отзыва; сбой до отзыва не выгружает ничего, а изменения политики до отзыва влияют на то, что экспортирует это воспроизведение.
