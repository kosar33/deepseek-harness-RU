# @deepseek-ai/dsh-session-telemetry

[English](README.md) | [中文](README.zh.md) | Русский

Service Definition телеметрии объявляет контракт `SessionTelemetrySink`, и его координатор захвата передаёт записи сессий любому бэкенду отчётного SDK, реализующему этот контракт. Захват может следовать за живыми событиями сессии либо воспроизводить префикс канонического журнала сессии по требованию. Этот пакет останавливается после вызова `emit()`: пакетирование, повторы, постановка в очередь и политика потерь принадлежат SDK бэкенда; этот пакет их не специфицирует и не оборачивает. Обоснование и отвергнутые альтернативы: [Agent Note о возрождении](../../../.agents/notes/implemented/feature/2026-07-23-session-telemetry-otel-revival.md), [доставка с гейтом обратной связи](../../../.agents/notes/implemented/feature/2026-08-05-feedback-gated-session-telemetry.md) и [воспроизведение по обратной связи без буфера](../../../.agents/notes/implemented/simplification/2026-08-06-buffer-free-feedback-telemetry.md).

## Контракт бэкенда

У `SessionTelemetrySink` три члена: `emit(record)` **ДОЛЖЕН** ставить в очередь без блокировки, поскольку выполняется синхронно во время `session/event` или явного воспроизведения канонического журнала; необязательный `flush()` — подсказка в духе fire-and-forget после окончания хода, и большинство бэкендов её опускают, полагаясь на штатный график пакетирования своего SDK; `shutdown()` выкачивает поставленные в очередь записи и завершается, когда останавливается SDK, а освобождение ресурсов дожидается этого. Реализация, предоставляющая `flush()`, обязана упорядочивать параллельные flush относительно финальной выкачки `shutdown()`. `SessionTelemetryBackend` регистрирует этот API под ключом контекста `sessionTelemetry`; каждый контекст принимает одну реализацию, и повторная загрузка приводит к исключению. Бэкенд конструирует `SessionTelemetryCoordinator` с захватом `live` или `on-demand` и вызывает `captureSession(session, throughSeq?)` в выбранный им момент.

Сервис также несёт обязательный член [`SessionTelemetrySharingStatus`](#раскрытие-режима-обмена) `sharing`: политику обмена, выбранную развёртыванием, которую каждый бэкенд должен раскрывать ориентированным на человека поверхностям подтверждения (подтверждению команды `/feedback`). Потребитель показывает «not configured» лишь тогда, когда сервис телеметрии не смонтирован. Набор значений (`full` | `feedback-only` | `disabled`) закреплён за seam, поэтому любой бэкенд может раскрыть политику, не завися от OTel-пакета.

## Раскрытие режима обмена

Подтверждение записанной единицы обратной связи сообщает, передаётся ли сессия куда-либо и как именно, читая `sharing` смонтированного бэкенда. Бэкенд задаёт это свойство из конфигурации своего развёртывания: `full` (каждое событие передаётся сразу по мере возникновения), `feedback-only` (ничего не передаётся, пока событие `feedback/record` не выпустит через себя ещё не выпущенный префикс) или `disabled` (не передаётся вовсе). Потребители отображают статус в понятный пользователю текст; раскрытие никогда не заявляет доставку — передача есть неблокирующая постановка в очередь, а пакетирование, повторы и политика потерь остаются за SDK бэкенда.

## Точки захвата

В режиме `live` координатор регистрирует, причём всё через эффекты компонующего fiber: `session/created` (усыновление: зафиксировать заголовок, перечитать журнал через проекцию от границы создания — заготовки конструктора из fork/resume никогда не переизлучаются в общий поток и никогда не реэкспортируются), `session/event` (спроецировать, глубоко скопировать, обезличить, затем передать дальше; ноль операций ввода-вывода), `session/flush` (переслать необязательную подсказку `flush()` и вернуть void — ожидаемый параллельный шаг цикла никогда не должен ждать телеметрию), `session/disposed` (захватить операционную запись `shutdown` сессии на её завершающем рубеже, затем снять её с учёта), `agent/error` (единственная ретрансляция с живой шины; набор событий сессии намеренно не содержит записи об операционной ошибке), эффект освобождения ресурсов (захватить shutdown для каждой ещё живой сессии, затем дождаться `shutdown()` бэкенда; сбои превращаются в предупреждения, а не в исключения) и проход усыновления по `ctx.sessions.list()` (горячая перезагрузка не воспроизводит `session/created`). В режиме `on-demand` регистрируется только эффект освобождения ресурсов: `captureSession()` читает канонический журнал через необязательную включительную границу последовательности, тогда как подсказки flush и операционные события остаются локальными.

## Каскад очистки

Каждая запись проходит каскад `sessionTelemetry/record` сразу после проецирования — это точка расширения Service Definition для очистки. Сам пакет не поставляет НИКАКИХ собственных правил: самый внутренний `next()` пропускает запись без изменений, поэтому без смонтированного слушателя записи достигают бэкенда ровно такими, какими были захвачены, а экспортируемые данные ровно настолько чисты, насколько чисты правила, смонтированные развёртыванием. Слушатели накладываются друг на друга, преобразуя возвращаемое значение `next()`; возврат без вызова `next()` заменяет всё нижележащее, а слушатель, бросивший исключение, задерживает эту единственную запись по принципу fail-closed внутри координатора, изолирующего сбой. Живой захват выполняет каскад в момент дописывания; захват по требованию — при воспроизведении канонического журнала, пользуясь правилами, смонтированными на тот момент. Обезличивание затрагивает только исходящую копию; канонический журнал сессии никогда не переписывается.

## Курсор передачи

`WeakMap<Session, seq>` на уровне модуля отмечает наивысший seq, ПЕРЕДАННЫЙ (не путать с доставленным), для каждой сессии. Живой захват сдвигает его в момент дописывания; захват по требованию — только пока `captureSession()` передаёт бэкенду запрошенный префикс. Незахваченный префикс остаётся исключительно в каноническом журнале, поэтому перезагрузка координатора не добавляет никакого принадлежащего телеметрии состояния восстановления. При воспроизведении координатор передаёт повторно только события после курсора (события на курсоре и ниже всё равно восстанавливают состояние проекции чанков); отсутствие курсора безопасно деградирует к повторной передаче от границы создания сессии (`Session.firstLiveSeq` — seq 0 для сессии, рождённой в этом процессе), что поглощается дедупликацией на стороне получателя по `(session.id, event.seq)`. Заготовки конструктора никогда не реэкспортируются: история возобновлённой сессии уже ушла из предыдущего процесса под тем же id, а унаследованный префикс fork живёт в потоке родителя (получатели сшивают по `session.parent_id` + `session.seed_length`). Принятая цена, согласующаяся с доставкой at-most-once: возобновление не дозаполняет записи, которые предыдущий процесс не сумел доставить, — развёртыванию с требованием дозаполнения нужен отложенный outbox, а не воспроизведение. Это намеренное узкое исключение из дисциплины «регистрации являются эффектами»: записи умирают вместе со своими сессиями, значение представляет собой монотонную отметку уровня, а его потеря никогда не является ошибкой.

## Фиксированная проекция чанков

Отправляется только первый `assistant/chunk` каждой пары `(turn, step)`; остальные отбрасываются при захвате и никогда не двигают курсор. Этот единственный чанк и есть сигнал «поток начался»: наличие `step/start`, первого чанка и `assistant/message` плюс причина в `turn/end` отличают «запрос так и не начался» от «поток оборвался на полпути» без обращения к объёму чанков, а время до первого токена остаётся вычислимым. Пропуск чанков делает разрывы в `seq` нормой при передаче — разрыв никогда не является сигналом потери. Все прочие типы событий, включая добавленные плагинами, о которых этот пакет никогда не слышал, проходят целиком.

## Логическая запись

`SessionTelemetryRecord`: `channel` (`ledger` | `ops`), `time` (миллисекунды эпохи), `severity` (предвычисленное: ERROR для `tool/result.isError`, причин ошибок в `turn/end` и `agent-error`; INFO для остальных захватываемых записей, тогда как политики `sessionTelemetry/record` могут назначить WARN), атрибуты, несущие только идентификацию (`session.id`, `event.type`, `event.seq`, плюс `session.cwd`/`session.parent_id`/`session.seed_length`, когда они есть в заголовке) и полная глубокая копия `event.data` в качестве `body` — уже после обезличивания. Операционные записи несут `sessionTelemetry.op` (`agent-error` | `shutdown`) и `session.id`, но намеренно НЕ несут `event.seq`/`event.type` — это сигналы для оповещения, а не записи для суммирования; `agent-error` нормализует произвольное брошенное значение в устойчивое тело `{ name, message }`. Доставка ниже точки передачи — дело SDK бэкенда; дубликаты остаются возможными (повторное усыновление без курсора, повторы SDK), поэтому получатели выполняют дедупликацию по `(session.id, event.seq)`.

## Опыт модели

Отсутствует, поскольку этот пакет лишь наблюдает поток событий сессии и передаёт обезличенные копии отчётному бэкенду; он никогда не вносит вклада в запрос к модели.

#### Влияние на KV-кэш

Отсутствует; этот пакет ни собирает, ни отправляет запрос провайдеру.

## Известные ограничения и отложенная работа

- **Доставка по принципу best-effort** — курсор отмечает переданное, а не доставленное; сессия, освобождённая внутри окна перезагрузки, не может быть усыновлена заново; что бы ни оставалось в очереди бэкенда в момент сбоя, теряется. Долговечный outbox (spool, курсоры на каждый sink, at-least-once) отложен, пока какое-нибудь развёртывание не заявит требование о потерях при сбое — см. [Agent Note о возрождении](../../../.agents/notes/implemented/feature/2026-07-23-session-telemetry-otel-revival.md).
- **Нет встроенных правил обезличивания** — если слушатель `sessionTelemetry/record` не смонтирован, записи покидают процесс ровно такими, какими были захвачены, включая любые учётные данные, попавшие в содержимое файлов или вывод команд; развёртывание, экспортирующее данные в общий коллектор, само отвечает за свой набор правил.
- **Обезличивание по требованию использует текущее состояние** — незахваченные события существуют только в каноническом журнале сессии. Последующий `captureSession()` глубоко копирует и обезличивает их текущие значения той политикой, что смонтирована на тот момент; нет ни снапшота телеметрии на момент захвата, ни долговечного spool, создаваемого до захвата.
