# @deepseek-ai/dsh-settings

[English](README.md) | [中文](README.zh.md) | Русский

Service Definition пользовательских настроек (`ctx.settings`). Один провайдер хранит сырой документ из секций по пространствам имён; плагины регистрируют схему пространства имён и читают разрешённое значение, слоёное как значения по умолчанию схемы, затем композиционный `base` регистранта (его подмножество entry-config из cordis.yml), затем секция пользовательского документа. Без смонтированного провайдера для потребителей ничего не меняется: они продолжают разрешать один entry config, поэтому каждая композиция работает и с настройками, и без них.

## API сервиса

- `documentPath` — абсолютный путь редактируемого пользователем файла провайдера, когда он есть; провайдеры без файла оставляют его `undefined`. Хостовые адаптеры конфигурации выводят из него доступность, тогда как браузерные протоколы выставляют лишь булеву возможность и никогда файловую цель.
- `prepareDocument()` — возвращает тот путь после подготовки документа к нативному редактору. Базовая реализация возвращает `documentPath`; файловый провайдер может сначала материализовать отсутствующий документ.
- `register(ns, schema, { base?, applies? })` — возвращает принадлежащий регистранту `SettingsScope` (`get`/`watch`/`update`). Регистрация — эффект на fiber вызывающего плагина: освобождение того fiber удаляет пространство имён и его наблюдателей. Хранимая секция, отвергаемая схемой, обращает в отказ саму регистрацию; дубликат пространства имён отказывает громко.
- `describe(options?)` — один дескриптор на пространство имён (конверт `schema.toJSON()`, разрешённое значение, отсоединённые слои `base`/`user`, `applies`) для поверхностей конфигурации; именно присутствие поля в `user` помечает его переопределённым пользователем. `describe({ redactSecrets: true })` вычищает поля `role('secret')` из каждого слоя и добавляет slot-список `secrets` (`{ path, set }`); каждая поверхность протокола **ДОЛЖНА** передавать его, а чистый обходчик `redactSecrets(schema, value)` экспортируется для других протоколов.
- `get(ns)` — разрешённое значение, `undefined`, пока пространство имён не зарегистрировано.
- `update(ns, patch)` — глубоко сливает простой объектный patch только в пользовательскую секцию (никогда в `base`), проверяет разрешённого кандидата, персистирует через провайдера, затем фиксирует. Patch может содержать только совместимые с JSON данные: Date, Map, BigInt, не-конечное число или циклическая ссылка обращаются в отказ со своим путём от корня `$` прежде, чем что-либо персистирует (хранилище YAML/JSON молча изменило бы такие значения при перезагрузке). Сбой проверки отвергает прежде, чем что-либо персистирует; read-only провайдер (`writable: false`) отвергает каждую запись. Записи в одно пространство имён сериализуются в порядке вызова.
- `replace(ns, section)` — задаёт пользовательскую секцию целиком: намеренный сброс (`replace({})` заново наследует `base` и значения по умолчанию схемы).
- `mutate(ns, ops)` — применяет упорядоченные правки `{ op: 'set' | 'unset', path }` к секции в том виде, в каком она стоит, когда запись доходит до начала очереди. Это путь удаления для любого вызывающего, держащего НЕПОЛНЫЙ взгляд: поверхность конфигурации читает вычищенный дескриптор, поэтому пересборка секции из него с цельной заменой удалит каждый секрет, который протокол никогда не возвращал, тогда как op называет ровно то единственное поле, что имеет в виду.
- Каждая запись принимает необязательный `expectedRevision`. Каждый дескриптор несёт `revision` пространства имён — монотонный счётчик по его СЫРОЙ секции; запись, чьё ожидание уже не совпадает, отвергается с `SettingsConflictError` (`code: 'SETTINGS_CONFLICT'`, с приложением обеих ревизий) вместо перезаписи того, кто записал первым. Очередь записи упорядочивает записи, но сама по себе не отличает свежего пишущего от держащего устаревший снапшот.
- Разрешённые значения — глубоко замороженные снапшоты. Наблюдатели получают `(next, prev)` после каждой фиксации: вызовы одного callback исполняются асинхронно, по одному за раз, в порядке фиксаций (медленный устаревший вызов никогда не применится после более нового), а сбои — как синхронные броски, так и асинхронные отклонения — локализуются. После возврата disposer'а наблюдения новые вызовы не начинаются (уже очередённый пропускается); начавшийся вызов всё же завершается. Событие `settings/updated` веером расходится по одному слушателю за раз, поэтому один бросающий слушатель не может уморить остальных; отклонение асинхронного слушателя локализуется и логируется, поэтому `INVARIANT`-кодированные сбои перебрасываются только из синхронных слушателей.
- Teardown сервиса отказывает новым записям и запускам наблюдателей, затем выкачивает каждую очередённую запись и каждый начатый вызов наблюдателя прежде, чем освобождение ресурсов завершится; запись, чей fiber регистранта был освобождён на полпути, всё же достигает хранилища, но не фиксируется и никого не уведомляет.

## Контракт провайдера

Подклассы реализуют `writable`, `load()` и `persist(ns, section)`, опционально переопределяют `documentPath` и `prepareDocument()` для одного локального редактируемого пользователем файла и проталкивают внешне наблюдаемые документы через защищённый `publish(doc)`. Инициализация базового сервиса загружает и публикует документ один раз до того, как сервис станет инъецируемым; провайдер с собственной инициализацией (наблюдатель, соединение) сначала делегирует через `yield* super[Service.init]()`. При публикации каждое зарегистрированное пространство имён разрешается заново независимо: недопустимая секция сохраняет за пространством имён последнее добротное значение и предупреждает — живая перезагрузка никогда не валит процесс, — тогда как проверка во время загрузки и во время регистрации отказывает громко.

## События

`settings/updated (ns, next, prev, source)` срабатывает после каждой фиксации; `source` — это `update` (внутрипроцессная запись) или `provider` (внешнее изменение). Для глубокоравного разрешённого значения оно не срабатывает никогда — это адресованное потребителю событие, а потребителю важно лишь то, что значение сдвинулось.

`settings/document-updated (ns, revision)` срабатывает при каждом изменении СЫРОЙ пользовательской секции, независимо от того, изменилось ли разрешённое значение. Поверхностям конфигурации нужно именно это событие: сохранение переопределения, равного композиционному base, оставляет разрешённое значение нетронутым, но меняет то, что говорит документ (поле теперь переопределено, а не унаследовано), и двигает ревизию, которую держит каждый открытый редактор. Локализация сбоев слушателей совпадает с `settings/updated`.

Оба объявления живут в безопасном для клиента subpath-экспорте `./types` вместе с типами `SettingsNamespace` и `SettingsUpdateSource`, которые называют их сигнатуры; корень пакета реэкспортирует те типы. Потребитель вне компиляционной грани Host поэтому читает ровно ту сигнатуру, которую испускает Host, вместо её пересказа.

## Опыт модели

Опосредованно, через плагины-потребители, разрешающие влияющие на модель значения (например маршрут модели по умолчанию) из своих пространств имён; собственная поверхность каждого потребителя документирует эффект.

#### Влияние на KV-кэш

Прямой инвалидации нет; потребитель, вплетающий значение настройки в префикс запроса, владеет тем изменением.

## Известные ограничения и отложенная работа

- **Один пользовательский слой** — разрешение знает значения по умолчанию схемы, один композиционный `base` и один пользовательский документ; оно пока не записывает, какой слой поставил каждое разрешённое значение.
- **`redactSecrets` — не доказанная граница протокола** — обходчик следует по `object`/`dict`/`array`, поэтому `role('secret')`, достигаемый только через union, intersection или transform, возвращается ДОСЛОВНО с пустым списком `secrets`, а `schema.toJSON()` доносит `.default(...)` секретного поля до каждого клиента. Ни один из случаев не отвергается; схема, чьи секреты недостижимы через обходимые контейнеры, **НЕ ДОЛЖНА** регистрироваться на выставленном в протокол пространстве имён. Настоящий ответ — fail-closed `describeForWire()`, отказывающая схеме, чью безопасность она не может доказать, и вычищающая сериализованный конверт и текст ошибки, — и он отложен.
- **Межпроцессная конкурентность определяется провайдером** — seam сериализует записи по пространствам имён только внутри процесса; конкурентные процессы сходятся поведением провайдера (локальный файловый провайдер выполняет read-modify-write под блокировкой писателя, поэтому пространства имён переживают конкурентных пишущих, а конфликты одного пространства разрешаются по принципу «побеждает последняя запись»).
