# @deepseek-ai/dsh-settings

[English](README.md) | [中文](README.zh.md) | Русский

Service Definition пользовательских настроек (`ctx.settings`). Один провайдер хранит сырой документ из секций по пространствам имён; плагины регистрируют схему пространства имён и читают разрешённое значение по слоям: сначала значения по умолчанию схемы, затем композиционный `base` регистранта (его подмножество entry-config из cordis.yml), затем секция пользовательского документа. Без смонтированного провайдера для потребителей ничего не меняется: они продолжают разрешать только entry config, поэтому каждая композиция работает и с настройками, и без них.

## API сервиса

- `documentPath` — абсолютный путь редактируемого пользователем файла провайдера, когда он есть; провайдеры без файла оставляют его `undefined`. Хостовые адаптеры конфигурации выводят из него доступность, тогда как браузерные протоколы предоставляют лишь булеву возможность и никогда — файловую цель.
- `prepareDocument()` — возвращает этот путь после подготовки документа для нативного редактора. Базовая реализация возвращает `documentPath`; файловый провайдер может сначала материализовать отсутствующий документ.
- `register(ns, schema, { base?, applies? })` — возвращает принадлежащий регистранту `SettingsScope` (`get`/`watch`/`update`). Регистрация — эффект на fiber вызывающего плагина: освобождение того fiber удаляет пространство имён и его наблюдателей. Хранимая секция, отвергаемая схемой, срывает саму регистрацию; дубликат пространства имён падает с явной ошибкой.
- `describe(options?)` — один дескриптор на пространство имён (конверт `schema.toJSON()`, разрешённое значение, отсоединённые слои `base`/`user`, `applies`) для поверхностей конфигурации; именно присутствие поля в `user` помечает его переопределённым пользователем. `describe({ redactSecrets: true })` вычищает поля `role('secret')` из каждого слоя и добавляет slot-список `secrets` (`{ path, set }`); каждая поверхность протокола ДОЛЖНА передавать его, а чистый обходчик `redactSecrets(schema, value)` экспортируется для других протоколов.
- `get(ns)` — разрешённое значение, `undefined`, пока пространство имён не зарегистрировано.
- `update(ns, patch)` — глубоко сливает простой объектный patch только в пользовательскую секцию (никогда в `base`), проверяет разрешённый кандидат, персистирует через провайдера, затем фиксирует. Patch может содержать только совместимые с JSON данные: Date, Map, BigInt, не-конечное число или циклическая ссылка отклоняются с указанием пути от корня `$`, прежде чем что-либо персистирует (хранилище YAML/JSON молча изменило бы такие значения при перезагрузке). При сбое проверки операция отклоняется прежде, чем что-либо будет сохранено; read-only провайдер (`writable: false`) отвергает каждую запись. Записи в одно пространство имён сериализуются в порядке вызова.
- `replace(ns, section)` — задаёт пользовательскую секцию целиком: намеренный сброс (`replace({})` заново наследует `base` и значения по умолчанию схемы).
- `mutate(ns, ops)` — применяет упорядоченные правки `{ op: 'set' | 'unset', path }` к секции в том виде, в каком она стоит, когда запись доходит до начала очереди. Это путь удаления для любого вызывающего, держащего НЕПОЛНУЮ картину: поверхность конфигурации читает вычищенный дескриптор, поэтому пересборка секции из него с последующей полной заменой удалит каждый секрет, который протокол никогда не возвращал, тогда как op называет ровно одно подразумеваемое поле.
- Каждая запись принимает необязательный `expectedRevision`. Каждый дескриптор несёт `revision` пространства имён — монотонный счётчик по его СЫРОЙ секции; запись, чьё ожидание уже не совпадает, отвергается с `SettingsConflictError` (`code: 'SETTINGS_CONFLICT'`, с приложением обеих ревизий) вместо перезаписи того, кто записал первым. Очередь записи упорядочивает записи, но сама по себе не отличает того, кто пишет со свежими данными, от того, кто держит устаревший снапшот.
- Разрешённые значения — глубоко замороженные снапшоты. Наблюдатели получают `(next, prev)` после каждой фиксации: вызовы одного callback исполняются асинхронно, по одному за раз, в порядке фиксаций (медленный устаревший вызов никогда не применится после более нового), а сбои — как синхронные броски, так и асинхронные отклонения — локализуются. После возврата disposer'а наблюдения новые вызовы не начинаются (уже стоящий в очереди вызов пропускается); начавшийся вызов всё же завершается. Событие `settings/updated` расходится веером по одному слушателю за раз, поэтому слушатель, бросающий исключение, не может оставить остальных без вызовов; отклонение асинхронного слушателя локализуется и логируется, поэтому `INVARIANT`-кодированные сбои пробрасываются выше только из синхронных слушателей.
- Teardown сервиса отказывает новым записям и запускам наблюдателей, затем выкачивает каждую запись из очереди и каждый начатый вызов наблюдателя, прежде чем завершится освобождение ресурсов; запись, чей fiber регистранта был освобождён посреди выполнения, всё же достигает хранилища, но не фиксируется и никого не уведомляет.

## Контракт провайдера

Подклассы реализуют `writable`, `load()` и `persist(ns, section)`, опционально переопределяют `documentPath` и `prepareDocument()` для одного локального редактируемого пользователем файла и проталкивают внешне наблюдаемые документы через защищённый `publish(doc)`. Инициализация базового сервиса загружает и публикует документ один раз прежде, чем сервис станет доступным для инъекции; провайдер с собственной инициализацией (наблюдатель, соединение) сначала делегирует через `yield* super[Service.init]()`. При публикации каждое зарегистрированное пространство имён разрешается заново независимо: недопустимая секция сохраняет за пространством имён последнее добротное значение и предупреждает — живая перезагрузка никогда не обрушивает процесс, — тогда как проверка во время загрузки и во время регистрации падает с явной ошибкой.

## События

`settings/updated (ns, next, prev, source)` срабатывает после каждой фиксации; `source` — это `update` (внутрипроцессная запись) или `provider` (внешнее изменение). Для глубоко равного разрешённого значения оно не срабатывает никогда — это адресованное потребителю событие, а потребителю важно лишь то, что значение сдвинулось.

`settings/document-updated (ns, revision)` срабатывает при каждом изменении СЫРОЙ пользовательской секции, независимо от того, изменилось ли разрешённое значение. Поверхностям конфигурации нужно именно это событие: сохранение переопределения, равного композиционному base, оставляет разрешённое значение нетронутым, но меняет то, что говорит документ (поле теперь переопределено, а не унаследовано), и сдвигает ревизию, которую держит каждый открытый редактор. Локализация сбоев слушателей совпадает с `settings/updated`.

Оба объявления живут в безопасном для клиента subpath-экспорте `./types` вместе с типами `SettingsNamespace` и `SettingsUpdateSource`, названными в их сигнатурах; корень пакета реэкспортирует те типы. Потребитель вне компиляционной грани Host поэтому читает ровно ту сигнатуру, которую испускает Host, вместо её пересказа.

## Опыт модели

Опосредованно, через плагины-потребители, разрешающие влияющие на модель значения (например, маршрут модели по умолчанию) из своих пространств имён; собственная поверхность каждого потребителя документирует эффект.

#### Влияние на KV-кэш

Прямой инвалидации нет; потребитель, добавляющий значение настройки в префикс запроса, отвечает за это изменение.

## Известные ограничения и отложенная работа

- **Один пользовательский слой** — разрешение знает значения по умолчанию схемы, один композиционный `base` и один пользовательский документ; оно пока не записывает, какой слой поставил каждое разрешённое значение.
- **`redactSecrets` — не доказанная граница протокола** — обходчик следует по `object`/`dict`/`array`, поэтому `role('secret')`, достигаемый только через union, intersection или transform, возвращается ДОСЛОВНО с пустым списком `secrets`, а `schema.toJSON()` доносит `.default(...)` секретного поля до каждого клиента. Ни один из случаев не отвергается; схема, чьи секреты недостижимы через обходимые контейнеры, НЕ ДОЛЖНА регистрироваться на предоставляемом протоколу пространстве имён. Настоящее решение — fail-closed `describeForWire()`, который отказывает схеме, чью безопасность он не может доказать, и вычищает сериализованный конверт и текст ошибки; оно отложено.
- **Межпроцессная конкурентность определяется провайдером** — seam сериализует записи по пространствам имён только внутри процесса; конкурентные процессы сходятся за счёт поведения провайдера (локальный файловый провайдер выполняет read-modify-write под блокировкой писателя, поэтому пространства имён выдерживают конкурентные записи, а конфликты одного пространства разрешаются по принципу «побеждает последняя запись»).
