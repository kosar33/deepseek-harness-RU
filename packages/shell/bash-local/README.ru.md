# @deepseek-ai/dsh-bash-local

[English](README.md) | [中文](README.zh.md) | Русский

Локальный Service Provider для executor seam пакета `@deepseek-ai/dsh-shell` поверх сервиса [`@deepseek-ai/dsh-subprocess`](../../subprocess/subprocess/README.md): `LocalBashExecutor` порождает `bash -c <command>` на каждый вызов как управляемую группу процессов через `ctx.subprocess` и владеет всем bash-специфичным — дефолтами и лимитами команды, классификацией таймаута/отмены, дружелюбным к модели терминальным окружением и обращённым к модели слиянием stdout/stderr для фоновых чтений. Групповая механика (вывод с ограничением через spill, вычищение учётных данных, эскалация kill, освобождение ресурсов) принадлежит сервису subprocess.

Корень пакета экспортирует дефолтный и именованный плагин `LocalBashExecutor`, а также его `Config`.

## Конфигурация

```yaml
- id: bash
  name: '@deepseek-ai/dsh-bash-local'
  config:
    cwd: /path/to/workspace   # default: process.cwd()
    timeoutMs: 120000          # default foreground timeout
    maxTimeoutMs: 600000       # cap for per-call overrides
    maxOutputBytes: 64000      # per-stream in-memory cap; overflow spills to disk
    maxSpillBytes: 67108864    # per-stream full-output spill cap
    graceMs: 3000              # kill escalation and post-exit pipe-drain grace
```

## Поведение

- **Спавн на вызов, без состояния шелла** — каждый вызов — свежий non-login `bash -c` без rc-файлов.
- **Композиционная запись — слой, а не последнее слово** — когда в композиции присутствует провайдер настроек, этот исполнитель регистрирует пространство имён [`bash`](../shell/README.md) данной возможности с записью выше в качестве базы, поэтому пользовательская секция в `settings.yaml` ложится поверх неё, и следующая команда выполняется уже с новыми бюджетами. Значения, которые схема оценить не может (положительные и конечные значения, граница таймера `graceMs`), отвергаются при записи, оставляя работающий исполнитель на его последней хорошей секции; без провайдера или после его отсоединения выполняется то, что задала композиционная запись.
- **Настроенные бюджеты поверх управляемых групп** — `resolve()` заполняет `workdir`/`timeoutMs`/`stdoutMaxBytes` из конфигурации, и каждый спавн передаёт сервису явные байтовые лимиты, spill-лимит и `graceMs`. Grace **ДОЛЖЕН** быть положительным, конечным и не больше [`MAX_TIMER_DELAY_MS`](../../util/timeout/README.md), чтобы Node мог представить его одним таймером. Убийства групп процессов, слив пайпов после выхода, удержание хвоста и ограниченные spill-файлы — механика [`dsh-subprocess-local`](../../subprocess/subprocess-local/README.ru.md). Foreground-запрос `ShellExecRequest.stdoutMaxBytes` может поднять бюджет захвата stdout для одного доверенного вызывающего; stderr и фоновые запуски по-прежнему используют `maxOutputBytes`.
- **Классификация таймаута и отмены** — `run()` объединяет зажатый конфигурацией таймаут и сигнал вызывающего в единый дедлайн; только собственный таймаут исполнителя сообщает `timedOut`, отмена выше по цепочке сообщает `aborted`, а команда, сигнализировавшая себе, не сообщает ни того ни другого ([Agent Note о библиотеке таймаутов](../../../.agents/notes/implemented/architecture/2026-07-06-timeout-deadline-library.md)).
- **Дружелюбное к модели терминальное окружение** — `NO_COLOR=1 TERM=dumb PAGER=cat GIT_PAGER=cat` не даёт пейджерам и ANSI-цвету исказить результаты. Эти значения сливаются как обычные переменные окружения под вычищением учётных данных сервиса и правилами каналов `DSH_*`; явная запись вызывающего всё равно побеждает. См. [Agent Note о stdin/env](../../../.agents/notes/implemented/architecture/2026-06-30-bash-stdin-env-trusted-plugin-api.md) и [Agent Note об управляемом окружении](../../../.agents/notes/implemented/feature/2026-07-10-agent-session-identity-and-log-location.md).
- **Фоновые процессы** — `start()` немедленно возвращает живой дескриптор `ShellProcess` без таймаута, а `readOutput()` сливает чтения stdout/stderr по смещениям в одну поглощающую дельту, помещая stderr под маркером `[stderr]`, когда он есть. Работающий процесс принадлежит сервису subprocess, переживает перезагрузки исполнителя и убивается с ожиданием завершения при освобождении ресурсов сервиса. Id задач, владение, опрос и уведомления принадлежат универсальному рантайму [`ctx.jobs`](../../jobs/jobs/README.md), в котором слой инструментов регистрирует дескриптор.

## Влияние на модель

Косвенно, через `dsh-tool-bash`, который рендерит ограниченные хвосты stdout/stderr этого исполнителя, дельты фоновых процессов, пути spill-файлов и инфраструктурные отказы.

#### Влияние на KV-кэш

Прямой инвалидации нет; любые изменения префикса запроса — забота указанного выше потребителя.

## Известные ограничения и отложенная работа

- **Сам по себе без ограничений** — этот исполнитель всегда выполняет команды с полномочиями процесса harness; развёртываниям, которым нужна изоляция, следует компоновать [`dsh-bash-sandbox`](../bash-sandbox/README.ru.md), а политика allow/deny/ask на уровне вызова относится к `tools/pre-execute`.
- **Ни постоянного шелла, ни PTY** — каждый вызов стартует свежий non-login `bash -c`; персистентность одного лишь cwd и интерактивные терминальные сессии остаются отложенными, пока реальный воркфлоу их не потребует.
- **Только POSIX** — бинарник `bash` жёстко зашит, а групповая семантика нижележащего сервиса является POSIX; Windows не поддерживается.
- **Заметка о неудачном фоновом спавне доставляется однократно** — сервис subprocess не буферизует вывод процесса, который так и не запустился, поэтому исполнитель вставляет `spawn failed: …` ровно в одну дельту `readOutput()`; читатель, отбросивший эту дельту, восстановить её не сможет.

Предостережения эвристики вычищения и удержания spill описаны в [`dsh-subprocess-local`](../../subprocess/subprocess-local/README.ru.md), которому принадлежит эта механика.
