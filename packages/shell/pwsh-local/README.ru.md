# @deepseek-ai/dsh-pwsh-local

[English](README.md) | [中文](README.zh.md) | Русский

Локальный провайдер сервиса PowerShell для seam исполнителей `@deepseek-ai/dsh-shell` поверх сервиса [`@deepseek-ai/dsh-subprocess`](../../subprocess/subprocess/README.md): `PwshLocalExecutor` порождает по вызову управляемый процесс `pwsh -NoLogo -NoProfile -NonInteractive -Command <command>` через `ctx.subprocess` и владеет всем PowerShell-специфичным — разрешением исполняемого файла, умолчаниями и потолками команд, классификацией тайм-аута/отмены, дружественной к модели терминальной средой и обращённым к модели слиянием stdout/stderr для фоновых чтений. Механика группы (вывод с ограничением через spill, вычищение учётных данных, эскалация kill, освобождение ресурсов) принадлежит сервису subprocess.

Строка команды передаётся как ОДИН элемент argv в `-Command`: текст разбирает сам PowerShell, промежуточной оболочки нет, поэтому не существует слоя кавычек оболочки, который нужно экранировать (строковому домену `bash -c` здесь нет эквивалента). Нативные пути Win32 (`C:\...`) проходят без изменений.

Корень пакета экспортирует плагин `PwshLocalExecutor` — и по умолчанию, и именованно, — его `Config`, чистые хелперы `resolvePwshPath`/`candidatePwshPaths` и константы `ENV_OVERRIDES`/`ENCODING_PREAMBLE`, которые исполнитель внедряет в каждый spawn.

## Конфигурация

```yaml
- id: bash
  name: '@deepseek-ai/dsh-pwsh-local'
  config:
    cwd: C:\path\to\workspace   # default: process.cwd()
    timeoutMs: 120000           # default foreground timeout
    maxTimeoutMs: 600000        # cap for per-call overrides
    maxOutputBytes: 64000       # per-stream in-memory cap; overflow spills to disk
    maxSpillBytes: 67108864     # per-stream full-output spill cap
    graceMs: 3000               # kill escalation and post-exit pipe-drain grace
    pwshPath: C:\Program Files\PowerShell\7\pwsh.exe  # explicit executable; else well-known locations, then PATH
```

## Поведение

Windows-собрат `dsh-bash-local`, намеренно повторяющий его семантику вызов-в-вызов:

- **Порождение на каждый вызов, без состояния оболочки** — каждый вызов — свежий неинтерактивный `pwsh -Command` (детерминированно; без файлов профиля). Флаги `-NoLogo -NoProfile -NonInteractive` отключают стартовые баннеры, загрузку профиля и приглашения ввода, которые могли бы искажать вывод инструмента.
- **Композиционная запись — слой, а не последнее слово** — когда в композиции есть провайдер настроек, этот исполнитель регистрирует пространство имён [`bash`](../shell/README.md) этой возможности, используя приведённую выше запись как базу, поэтому пользовательская секция в `settings.yaml` ложится поверх неё, и следующая команда выполняется уже с новыми бюджетами. Пространство имён разделяется с POSIX-семейством, потому что хост компонует ровно одного провайдера `ctx.shell`; документ, написанный на любой платформе, продолжает разрешаться и на другой. Значения, которые схема оценить не может (положительные и конечные значения, граница таймера `graceMs`), отвергаются при записи, оставляя работающий исполнитель на его последней исправной секции.
- **Вывод UTF-8 закреплён** — каждая команда выполняется сначала с `[Console]::OutputEncoding` и `$OutputEncoding`, установленными в UTF-8, чтобы запасной Windows PowerShell 5.1 (или любой хост, чья кодовая страница консоли не UTF-8) не мог исказить не-ASCII вывод: коллектор subprocess декодирует байты как UTF-8. Кодировка ввода остаётся хостовой по умолчанию; pwsh 7 по умолчанию UTF-8 и не затронут.
- **Разрешение исполняемого файла** — `resolvePwshPath` предпочитает явный `pwshPath`, затем на Windows проверяет место установки PowerShell 7, каждую запись PATH (установки Microsoft Store; окружающие кавычки снимаются) и Windows PowerShell 5.1 как устаревшее последнее средство, проверяя каждого кандидата lstat-пробой, принимающей настоящий файл или reparse point в форме ссылки (псевдоним запуска Store-приложения завершается ошибкой на stat из-за ACL своей цели, но lstat видит сам псевдоним); в остальных случаях он откатывается к простому `pwsh`, разрешаемому через PATH. Разрешение — чистая функция `(configured, env, platform)`; оно выполняется при конструировании и снова только тогда, когда сохранённый `pwshPath` отличается от того, по которому был разрешён текущий исполняемый файл, так что постороннее изменение настроек никогда не вызывает повторного зондирования файловой системы.
- **Сконфигурированные бюджеты поверх управляемых групп** — `resolve()` заполняет `workdir`/`timeoutMs`/`stdoutMaxBytes` из конфигурации, и каждый spawn передаёт сервису явные потолки байтов, spill-потолок и `graceMs`. Значение grace **ДОЛЖНО** быть положительным, конечным и не превышать [`MAX_TIMER_DELAY_MS`](../../util/timeout/README.md), чтобы Node мог представить его одним таймером. Завершение дерева (taskkill на Windows, сигналы группе процессов на POSIX), grace слива пайпов после выхода, усечение с удержанием хвоста и ограниченные spill-файлы — механика [`dsh-subprocess-local`](../../subprocess/subprocess-local/README.md). Поле `stdoutMaxBytes` запроса переднего плана может поднять бюджет захвата stdout для одного доверенного вызывающего; stderr и фоновые запуски по-прежнему используют `maxOutputBytes`.
- **Классификация тайм-аута и отмены** — `run()` объединяет свой зажатый конфигурацией тайм-аут и сигнал вызывающего в единый дедлайн; только собственный тайм-аут исполнителя сообщает `timedOut`, отмена выше по цепочке сообщает `aborted`, а самозавершившаяся команда не сообщает ни того, ни другого ([Agent Note о библиотеке тайм-аутов](../../../.agents/notes/implemented/architecture/2026-07-06-timeout-deadline-library.md)). Windows сообщает о принудительном завершении как exit 1 без сигнала, поэтому факты с пометкой сигнала (`signal`, статус `killed`) на Windows остаются прерогативой POSIX; классификация тайм-аут/отмена не зависит от платформы.
- **Дружественная к модели терминальная среда** — `NO_COLOR=1 PAGER=cat GIT_PAGER=cat` (без `TERM=dumb`: это POSIX-понятие; современными рендерерами PowerShell `NO_COLOR` соблюдается) сливаются как обычный env, подчиняясь вычищению учётных данных сервиса и правилам канала `DSH_*`; явная запись вызывающего всё равно побеждает.
- **Фоновые процессы** — `start()` немедленно возвращает живой дескриптор `ShellProcess`, тайм-аут не применяется, а `readOutput()` дескриптора сливает чтения stdout/stderr сервиса по смещениям в одну дельту размеченных секций с вычитывающим курсором. Всё ещё работающий процесс принадлежит сервису subprocess, поэтому переживает перезагрузки исполнителя и завершается вместе с освобождением ресурсов сервиса (его убивают и дожидаются выхода). Всё, что связано с задачами (id, владение, опрос, уведомления), живёт в универсальном рантайме [`ctx.jobs`](../../jobs/jobs/README.md), где слой инструментов регистрирует дескриптор, — этот исполнитель никогда не видит ни сессии, ни реестра.

## Model Experience

Опосредованно — через `dsh-tool-pwsh`, который рендерит ограниченные хвосты stdout/stderr этого исполнителя, дельты фоновых процессов (через общий рантайм задач), пути spill-файлов и инфраструктурные отказы.

#### KV Cache effect

Прямой инвалидации нет; любые изменения префикса запроса — забота указанного выше потребителя.

## Известные ограничения и отложенная работа

- **Сам по себе без ограничений** — этот исполнитель всегда выполняет команды с полномочиями процесса harness; развёртываниям, которым нужна изоляция, следует компоновать вместо него изолирующего bash-исполнителя или политику.
- **Нет персистентной оболочки или PTY** — каждый вызов начинает свежий `pwsh -Command`.
- **Строка команды — текст PowerShell** — у домена `-Command` нет слоя кавычек оболочки, но обращённую к модели команду разбирает сам PowerShell, поэтому синтаксические ошибки PowerShell — отказы команды, а не запуска.
- **Заметка об отказе spawn фонового процесса доставляется один раз** — сервис subprocess не буферизует вывод процесса, который так и не выполнился, поэтому исполнитель внедряет `spawn failed: …` ровно в одну дельту `readOutput()`; читатель, отбросивший ту дельту, восстановить её не сможет.
- **Завершение на Windows не сообщает сигнал** — принудительно убитый процесс завершается как exit 1 с `signal: null`, поэтому классификация статуса по сигналу (POSIX `killed`) на Windows неприменима; остановки, инициированные `kill()`, по-прежнему напрямую проставляют пометку `killed`.
- **Преамбула кодирования предшествует команде** — PowerShell требует `param(...)`, `#requires` и инструкции `using namespace`/`using assembly` в самом верху скрипта, поэтому команда, чья первая инструкция — одна из них, не может выполниться под преамбулой вывода UTF-8. Оберните скрипт с `param(...)` в `& { … }` (param-блок законно возглавляет блок скрипта); у инструкций `using` и `#requires` обхода внутри команды нет (`#requires` внутри `-Command` инертен независимо от позиции) — запускайте такие скрипты из файла.
- **Не-ASCII stdin под Windows PowerShell 5.1 может быть неверно декодирован** — преамбулой закреплена только кодировка вывода; `[Console]::InputEncoding` остаётся хостовым по умолчанию, потому что установка его при перенаправлённом stdin бросает исключение. pwsh 7 по умолчанию UTF-8 и не затронут.

Оговорки эвристики вычищения и удержания spill описаны в [`dsh-subprocess-local`](../../subprocess/subprocess-local/README.md), которому принадлежит эта механика.
