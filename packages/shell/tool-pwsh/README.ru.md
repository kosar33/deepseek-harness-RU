# @deepseek-ai/dsh-tool-pwsh

[English](README.md) | [中文](README.zh.md) | Русский

Обращённый к модели инструмент `pwsh`, регистрируемый над seam'ом исполнителя `ctx.shell`. Предназначен для Windows-композиций, где `ctx.shell` обслуживает исполнитель PowerShell (например, `@deepseek-ai/dsh-pwsh-local`); контракт инструмента — диалект PowerShell: собственные пути `C:\...` и переменные `$env:NAME`. Поведение повторяет `dsh-tool-bash` вызов-в-вызов — исполнение на переднем плане и `run_in_background` через общий рантайм заданий, управляемое окружение `DSH_*` через общий реестр `shell-env`, отрисовку отказа песочницы с поверхностью эскалации `sandbox_permissions` в тот же ход и присущий bash подход к отрисовке маркеров и усечения (чистый выход маркера не даёт).

Требует загруженную реализацию исполнителя и плагин `shell-env`; инструмент остаётся в ожидании, пока не появятся оба (`inject: ['tools', 'bash', 'systemPrompt', 'bashEnv']`).

Корень пакета выставляет только контракт плагина Cordis (`name`, `inject`, `Config`, `apply`); отрисовка результата (`src/render.ts`) и адаптация фоновых заданий (`src/background.ts`) повторяют структуру bash-инструмента и остаются доступны через экспорт `./src/*` пакета.

Плагин также добавляет секцию промпта `tool:pwsh` (порядок 105): ненулевые коды выхода сообщаются маркерами `[exit code: N]`, а прерывание в Windows завершается кодом 1 без маркера сигнала.

## Инструменты

### `pwsh`

| Аргумент | Тип | Примечания |
|---|---|---|
| `command` | string (обязателен) | Запуск через `pwsh -Command`. Между вызовами состояние не сохраняется — используйте `workdir`, а не `cd`. |
| `description` | string (обязателен) | Однострочное резюме команды в действительном залоге (5-10 слов), только для показа в UI/журнале — на исполнение не влияет. |
| `timeoutMs` | number | Переопределение тайм-аута в миллисекундах. Исполнитель применяет свой настроенный дефолт и потолок. |
| `workdir` | string | Рабочий каталог этого вызова. По умолчанию — cwd сессии вызывающего агента (`session.header.cwd`), чтобы каждая сессия работала в собственном воркспейсе; относительный `workdir` разрешается от той же идентичности. |
| `run_in_background` | boolean | Немедленно вернуть идентификатор задания; тайм-аут не применяется. |
| `sandbox_permissions` | string enum | Объявляется, только когда смонтирован исполнитель с песочницей (определён `ctx.shell.sandboxMode`). Более широкий режим песочницы для однократного повторного запуска только что отвергнутой песочницей команды — минимально достаточный более широкий режим, требующий `justification` и одобрения пользователя через `ctx.approval` ДО исполнения. Запрос без расширения прав или неодобримый отказывает, не запуская ничего. |
| `justification` | string | Обязателен вместе с `sandbox_permissions`: одно предложение для пользователя, объясняющее, почему этой конкретной команде нужен более широкий доступ. |

`command`, `workdir` и `timeoutMs` перед исполнением разрешаются от дефолтов конфигурации исполнителя через `ctx.shell.resolve()`. Дефолт workdir применяется на слое инструмента из `session.header.cwd` вызывающего агента ДО `resolve()` — посессионный cwd должен приходить из `exec.agent`, поскольку один исполнитель разделяют N сессий; лишь когда cwd сессии недоступен, исполнитель откатывается к собственной конфигурации / `process.cwd()`.

### Управляемое окружение оболочки

Каждый модельный вызов pwsh — на переднем плане и фоновый — получает заново собранное доверенное окружение `DSH_*` через общий реестр [`dsh-shell-env`](../shell-env/): `DSH_HOME` (абсолютный дом Harness), `DSH_SHELL=1`, `DSH_SESSION_ID` агента и `DSH_SESSION_JSONL`, когда активный бэкенд персистентности его находит. Плагины, добавляющие факты `DSH_*` в `ctx.shellEnv`, действуют на вызовы pwsh в точности как на вызовы bash. Снимок проходит по выделенному каналу `ShellExecRequest.dshEnv`; `process.env` никогда не изменяется. Описание инструмента обучает общему соглашению `$env:DSH_*`, а не называет переменные конкретной персистентности.

Текст результата содержит stdout, необязательную секцию `[stderr]`, затем применимые маркеры усечения, отказа песочницы (с подсказкой эскалации в тот же ход, когда композиция объявляет эскалацию), тайм-аута, сигнала и выхода. Чистый выход (0, без сигнала) маркера не даёт; пустое тело отрисовывается как `(no output)`. Усечение ссылается на безопасный полный spill-файл или сообщает о его недоступности. Тайм-аут сообщается независимо от итогового кода выхода; ненулевой выход остаётся результатом, интерпретируемым моделью, а не `isError`. Windows сообщает принудительное завершение как выход 1 без сигнала, поэтому маркер `[killed by signal: …]` остаётся достоянием POSIX. Лишь отказы инфраструктуры — ошибки spawn и прерывания (`tool call aborted`) — дают `isError`.

Канонический успех — `{ kind: 'foreground', ...ShellRunResult }` для завершившегося процесса на переднем плане (с фактами `sandbox` исполнителя — `mode`/`denied`, необязательными `enforcement`/`runnerFailed` — проецируемыми при наличии) или `{ kind: 'background', jobId }` для опубликованного задания. Отрисовщик сохраняет для фоновых квитанций в точности `started background job <id>`; программные потребители используют типизированные поля, не разбирая отрисованный текст.

При истинном `run_in_background` плагин заранее проверяет `ctx.jobs.start()` до порождения процесса, регистрирует вызывающего агента владельцем и адаптирует возвращённый дескриптор `ShellProcess` в общие хуки отмены/завершения/инкрементального вывода. Рантайм заданий владеет идентификаторами, межсессионной изоляцией, уведомлениями о завершении, ожиданием и очисткой при освобождении ресурсов; этот плагин лишь отображает факты выхода pwsh в вывод задания и детали исхода. `enableRunInBackground: false` убирает параметр и отвергает принудительный фоновый вызов на этапе исполнения.

## Представление в UI

Инструмент владеет собственным намерением рендера `presentCall`/`presentResult`. Вызов на переднем плане — карточка `terminal` с командой, описанием и необязательным cwd; вызов `run_in_background` — карточка `generic` с сырой командой, зеркаля представление фоновых вызовов bash-инструмента. Завершённый результат на переднем плане — тоже карточка `terminal`: маркер выхода становится пилюлей статуса выхода карточки (`exitCode`/`signal`), а тело без маркеров — её выводом; в точности терминальная карточка bash-инструмента через общий разбор статуса выхода из `@deepseek-ai/dsh-shell`. Фоновые квитанции и ошибки исполнения остаются карточками `generic` с отрисованным выводом в fence `console`. Эти презентеры чисты и безопасны при воспроизведении.

## Model Experience

### Системный промпт

#### What the model sees

Каждый запрос в области регистрации этого плагина содержит приведённое ниже руководство pwsh. Скоупированные ограничения инструментов могут скрыть схему, не убирая эту независимо зарегистрированную секцию.

##### Руководство pwsh

```markdown
Non-zero exits are reported as `[exit code: N]` markers; investigate failures before moving on. On Windows a killed process settles as `[exit code: 1]` without a signal marker; treat a bare exit 1 after an interruption as a termination, not a command failure.
```

#### Token effect

Небольшая фиксированная стоимость входа в каждом запросе, пока плагин активен.

#### KV Cache effect

Стабилен по префиксу, пока область регистрации и текст промпта не меняются. Активация плагина или освобождение его ресурсов могут инвалидировать переиспользование из этой секции промпта.

### Схемы инструментов

#### What the model sees

Модель видит порождаемую схему [`pwsh`](../../../docs/tool-catalog.md#deepseek-aidsh-tool-pwsh). Ограничения инструментов, скоупированные агентом, могут убрать определение для этого агента.

#### Token effect

Фиксированная стоимость схемы в каждом запросе, где инструмент видим.

#### KV Cache effect

Стабилен по префиксу, пока видимость и определение инструмента не меняются. Ограничение или изменение конфигурации могут инвалидировать переиспользование с первого изменившегося токена.

### Результат запуска на переднем плане

#### What the model sees

Отрисовщик выдаёт зависимый от данных хвост stdout, затем необязательный `[stderr]` и хвост stderr. Условные строки — в точности `[output truncated; full output: <path>]`, `[sandbox: file access denied under <mode> mode]` плюс подсказка эскалации `[sandbox: escalation available — …]` (только когда композиция объявляет эскалацию), `[timed out after <timeoutMs>ms]`, `[killed by signal: <signal>]` и `[exit code: <exitCode>]` (только ненулевые выходы); пустое тело отрисовывается как `(no output)`.

#### Token effect

До вызова — ноль токенов результата. Вывод ограничен на каждый поток, при этом каждая выданная строка остаётся в истории до компакции.

#### KV Cache effect

Append-only; заново видимое содержимое следует за пригодным для переиспользования префиксом запроса и не инвалидирует существующие записи KV-кэша.

### Результат фонового запуска

#### What the model sees

Фоновый старт отрисовывается в точности как `started background job <id>`; последующие чтения и статус идут через общие инструменты `job_output`/`job_kill`, включая уведомление о потерянном при чтении spill, когда усечение в памяти выбросило непрочитанные байты.

#### Token effect

Квитанция — фиксированная короткая строка; вывод задания ограничен на каждое чтение.

#### KV Cache effect

Append-only; заново видимое содержимое следует за пригодным для переиспользования префиксом запроса и не инвалидирует существующие записи KV-кэша.

### Ошибки инструмента

#### What the model sees

Ошибки валидации и инфраструктуры нормализуются в `Error: <message>`. Стабильные сообщения этого пакета — `invalid command: expected a non-empty string`, `invalid description: expected a non-empty string`, `invalid timeoutMs: expected a positive number, got <value>`, `invalid escalation: sandbox_permissions requires a justification`, `invalid escalation: justification is only valid together with sandbox_permissions`, `invalid justification: expected a non-empty sentence`, `sandbox_permissions is not available in this composition (no sandboxing executor to escalate)`, общие отказы эскалации (не строго более широкий режим / нет сервиса одобрений / нет агента для маршрутизации / нет канала одобрений / пользователь отверг / был отменён), `run_in_background is disabled for this deployment (enableRunInBackground: false)`, `background jobs unavailable: load @deepseek-ai/dsh-jobs and @deepseek-ai/dsh-tool-jobs` и `tool call aborted`.

#### Token effect

Эти удержанные токены добавляет только отказавший вызов; прерванный вызов не добавляет вывода команды.

#### KV Cache effect

Append-only; заново видимое содержимое следует за пригодным для переиспользования префиксом запроса и не инвалидирует существующие записи KV-кэша.

## Известные ограничения и отложенная работа

- **Языковой режим и перехват именованных каналов под песочницей Windows** — под [песочницей Windows ACL](../../sandbox/sandbox-windows-acl/README.ru.md) pwsh в режиме только чтения стартует в ConstrainedLanguage, потому что отказ на запись во временную папку заставляет пробу AppLocker PowerShell отказывать закрыто: `Add-Type`, некорневые статические типы .NET (`[System.IO.*]::`, `[math]::`), COM-объекты и рефлексия падают с ошибками «only core types», и поднять режим изнутри нельзя. Приватная временная папка workspace-write даёт пробе завершиться, поэтому там остаётся FullLanguage, если политика хоста не говорит иного. Оба ограниченных режима отвергают открытие именованных каналов, поэтому порождение процесса с stdio через пайп внутри ограниченной команды падает с EPERM. Описание инструмента обучает модель обоим контрактам; полные ограничения ведёт README бэкенда.
- **Нет постоянной оболочки** — каждый вызов стартует свежий `pwsh -Command`; парная сторона с постоянной оболочкой — [`@deepseek-ai/dsh-tool-pwsh-persistent`](../tool-pwsh-persistent/README.md), держащая один pwsh в области владельца живым между вызовами на Windows (ConPTY) и POSIX-хостах с pwsh.
- **Контракт диалекта PowerShell** — модель должна писать PowerShell (собственные пути, переменные `$env:`), а не bash; перевода между диалектами нет.
- **Идентичность посессионного cwd не канонизируется** — база workdir есть cwd из заголовка сессии как есть, в отличие от канонизируемой по корню песочницы идентичности bash-инструмента. Под ограничивающим исполнителем корень воркспейса политики КАНОНИЗИРУЕТСЯ (общим сервисом политик), поэтому workdir и корень ограничения могут разойтись, когда сырой cwd сессии отличается от своей канонической формы — пробел парности отложен до выделения общей базы shell-инструментов.
