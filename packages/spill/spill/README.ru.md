# @deepseek-ai/dsh-spill

[English](README.md) | [中文](README.zh.md) | Русский

**`SpillStore`** (`ctx.spillStore`) определяет, ЧТО делает бэкенд spill, — сохраняет слишком большой текст инструмента и возвращает обращённый к модели локатор вместе с подсказкой по извлечению, — не говоря, КАК.

Этот пакет — одна треть возможности spill, разделённая так, чтобы каждое занятие развивалось (и заменялось) независимо:

| Package | Role |
|---|---|
| `@deepseek-ai/dsh-spill` (этот) | Service Definition: абстрактный сервис + словарь типов |
| `@deepseek-ai/dsh-spill-local` | Service Provider: приватные файлы с областью видимости сессии на файловой системе хоста |
| `@deepseek-ai/dsh-spill-policy` | Consumer: политика результатов инструментов, уводящая в spill слишком большие финальные результаты |

Разделение зеркалит seam'ы shell/fs. Будущий удалённый или виртуальный бэкенд (например URI `spill://…`, ключ базы данных или специфичный для бэкенда инструмент извлечения) реализует этот Service Definition, не трогая плагин политики.

## API сервиса (`ctx.spillStore`)

| Элемент | Семантика |
|---|---|
| `saveText(input)` | Сохраняет `input.content` дословно; разрешается со `SpillRef` (непрозрачный локатор, точное количество записанных байтов и подсказка по извлечению). **Отказывает при реальной ошибке хранения** (права доступа, ENOSPC, недоступность бэкенда) — как деградировать, решает вызывающий. |

Хранение группируется по сессии-владельцу запроса (`owner`) как namespace момента сохранения; бэкенд выбирает собственное приватное представление и может выводить имена из `suggestedName` вызывающего — никогда не доверяя ему как пути. Seam владеет только хранением: НИКАКОЙ политики удержания (это [`@deepseek-ai/dsh-output-retention`](../../util/output-retention)), НИКАКОЙ замены результатов инструментов (это `@deepseek-ai/dsh-spill-policy`), НИКАКОГО API извлечения или поиска (`retrievalHint` бэкенда говорит модели, что делать с локатором).

## Словарь

`SaveTextSpill` (owner, source, suggestedName, content) — это запрос; `SpillRef` (locator, bytes, retrievalHint) — результат. `SpillLocator` [брендирован](../../util/brand) и рендерится модели как непрозрачная строка — для `dsh-spill-local` это локальный путь, но будущий бэкенд может вернуть URI, ключ или командный токен, не меняя потребителей политики и инструментов. `SpillOwner.sessionId` — namespace хранения момента сохранения: форкнутые сессии наследуют существующие локаторы из посеянного журнала, не копируя и не переоформляя их, а новые spill после форка используют id дочерней сессии. `SpillSource` записывает породившие `toolName`, `callId` и `label` для именования бэкендом и инспекции, а не для контроля доступа. Полные контракты см. в `src/types.ts`.

Обоснование дизайна — в [Agent Note о spill вывода инструментов](../../../.agents/notes/implemented/architecture/2026-07-08-tool-output-spill-files.md), включая то, почему создание принадлежит рантаймному seam'у spill, а не обращённому к модели инструменту `write`.

## Влияние на модель

Косвенно — через потребителей spill, которые отрисовывают локатор бэкенда и подсказку по извлечению.

#### Влияние на KV-кэш

Прямой инвалидации нет; любые изменения префикса запроса находятся во владении названного потребителя.

## Известные ограничения и отложенная работа

- **У seam'а нет API извлечения или удаления** — потребители могут лишь отрисовать локатор бэкенда и его подсказку; семантика жизненного цикла и доступа остаётся специфичной для бэкенда.
- **Хранение — не контроль доступа** — `SpillOwner` разделяет записи по namespace, но не авторизует чтение локатора; свой предел обязан обеспечивать каждый бэкенд и каждый потребитель извлечения.
