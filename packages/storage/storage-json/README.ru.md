# @deepseek-ai/dsh-storage-json

[English](README.md) | [中文](README.zh.md) | Русский

JSON-бэкенд [хаба хранилища](../storage/README.md): один читаемый человеком файл `<unit>.json` на юнит под настроенным корнем, регистрируется как бэкенд `json`. Замысел: [Agent Note о доменном KV-хранилище](../../../.agents/notes/proposed/architecture/2026-07-24-domain-kv-storage-and-workspace.md).

## Модель

- Авторитетно состояние юнита в памяти; каждый примитив записи перепубликует файл целиком через временную запись + fsync + атомарную замену `rename()`. Файл юнита — всегда полное текущее чистое состояние; разборчивость — смысл существования этого бэкенда, масштаб — работа бэкенда SQLite.
- Отсутствующий файл открывается как пустой юнит и материализуется при первой записи. Чужой или непарсируемый файл отвергается с `malformed-medium`; сохранённая версия, расходящаяся с дескриптором, отвергается с `version-mismatch` (миграции нет — до-релизная политика).
- Порядок записей между вызовами принадлежит вызывающему (цепочке записи доменного слоя); каждый отдельный вызов после разрешения атомарен и долговечен.

## Конфигурация

| Ключ | Тип | Умолчание | Значение |
| --- | --- | --- | --- |
| `root` | string | обязателен — умолчания нет (откат к cwd разбросал бы файлы) | Каталог, держащий файлы юнитов; создаётся с `0o700` по требованию |

## Влияние на модель

### Сохраняемые доменные записи

#### Что видит модель

Ничего. Этот бэкенд не добавляет ни промпта, ни инструмента, ни схемы; он сохраняет несессионные доменные данные за `ctx.storage` только для host-сторонних потребителей.

#### Влияние на токены

Ноль токенов живых запросов.

#### Влияние на KV-кэш

Никакого — бэкенд никогда не касается префиксов живых запросов.

## Известные ограничения и отложенная работа

- Долговечность на Windows полагается на libuv'овский `rename()` (`MoveFileExW` с замещением) без явного флага write-through; более строгий Win32-помощник публикации со write-through из бэкенда журнала сессий планируется опустить сюда, когда приземлится аспект append-log (см. миграционный раздел Agent Note).
- Блокировки записи между процессами нет: два процесса, пишущие в один корень, способны перемежать цельные замены файлов (побеждает последняя запись). Текущий потребитель — развёртывания с одним host-процессом; многопроцессная история отложена согласно таблице вне охвата того же Agent Note.
