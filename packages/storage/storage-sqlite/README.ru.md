# @deepseek-ai/dsh-storage-sqlite

[English](README.md) | [中文](README.zh.md) | Русский

SQLite-бэкенд [хаба хранилища](../storage/README.md): регистрируется как бэкенд `sqlite` и обслуживает аспект `kv` поверх одного файла базы данных `node:sqlite` (или `:memory:`). Замысел и компромиссы: [Agent Note о доменном KV-хранилище](../../../.agents/notes/proposed/architecture/2026-07-24-domain-kv-storage-and-workspace.md).

## Модель хранения

Строка на документ: каждая таблица юнита становится физической STRICT-таблицей `"u_<unit>_<table>" (key TEXT PRIMARY KEY, value TEXT)`, чей `value` — JSON-текст записи, поэтому один ключ обновляет одну строку (причина направлять сюда домен с высокой частотой изменений вместо JSON-бэкенда). Идентичность юнита живёт в двух таблицах метаданных — `units` проставляет каждому юниту версию формата при первом открытии и отвергает расходящийся дескриптор с `version-mismatch`; `unit_globals` держит глобальную одиночную строку каждого юнита. Версия физической раскладки живёт в `PRAGMA user_version`; любое иное проставленное значение отвергается (формат не выпущен, миграций нет). Имена юнитов и таблиц проверяются по `UNIT_NAME_RE` хаба до того, как попадут в DDL, так что внешний ввод никогда не интерполируется в SQL-идентификаторы.

Каждый примитив записи — единственный подготовленный оператор: операторная атомарность SQLite удовлетворяет контракту KV без явных транзакций, а порядок записей остаётся ответственностью вызывающего (цепочки записи доменного слоя). Отсутствующие каталог и файлы базы данных создаются только для владельца (`0o700`/`0o600`) — как в SQLite-бэкенде персистентности сессий.

## Конфигурация (schemastery)

```ts
interface Config {
  path: string   // SQLite database file path, or ':memory:' for an in-process DB
  journalMode?: 'wal' | 'delete' | 'truncate' | 'persist'   // journal_mode pragma; default 'wal'
}
```

## Влияние на модель

### Сохраняемые доменные записи

#### Что видит модель

Ничего. Этот бэкенд не добавляет ни промпта, ни инструмента, ни схемы; он сохраняет несессионные доменные данные (записи workspace, будущие сопутствующие метаданные сессий) за `ctx.storage` только для host-сторонних потребителей.

#### Влияние на токены

Ноль токенов живых запросов.

#### Влияние на KV-кэш

Никакого — бэкенд никогда не касается префиксов живых запросов.

## Известные ограничения и отложенная работа

- **`DatabaseSync` синхронен** — каждая запись блокирует цикл событий на своё (однооператорное) время исполнения; на масштабе доменных данных это приемлемо.
- **Нет политики busy-wait или повторов** — другое соединение, держащее транзакцию записи, немедленно отвергает операцию; защиты записи между процессами нет.
- **Открывается только текущая `STORAGE_SQLITE_SCHEMA_VERSION`** — любая иная проставленная версия отвергается, а не мигрирует (до-релизная политика).
- **`openDatabase` дублирует последовательность открытия SQLite из бэкенда персистентности сессий** — вынос в общий слой носителя отложен до запланированной миграции сессионных бэкендов (см. аудит переиспользования в том же Agent Note).
