# @deepseek-ai/dsh-subagent

[English](README.md) | [中文](README.zh.md) | Русский

Seam субагентов позволяет агенту делегировать работу ребёнку через именованного провайдера. Вызывающие пользуются одним сервисным API (`ctx.subagents`); провайдеры решают, работает ли ребёнок в этом процессе, в другом процессе или через будущий транспорт.

[Обзор семейства субагентов](../README.md) сопоставляет реализации и Consumer, обращённые к модели. Этот пакет содержит реестр провайдеров, общими контрактами запросов и результатов, долговечными дескрипторами и оркестрацией продолжаемых детей. За этим контрактом могут сосуществовать несколько именованных провайдеров.

## Сервисный API

Операции `SubagentRuntime`:

| Член | Значение |
|---|---|
| `registerProvider(provider)` | Регистрирует одну доверенную внутрипроцессную реализацию по имени. Регистрация ограничена временем жизни эффекта; её снятие предотвращает новые запуски, но не отзывает запуски, уже возвращённые вызывающим. Дубликаты имён падают с явной ошибкой. |
| `getProvider(name)` | Возвращает провайдера либо `undefined`, когда его нет. |
| `list()` | Возвращает имена провайдеров в порядке вставки. |
| `start(name, request)` | Проверяет обычный запрос вызывающего, разрешает его отсоединённый дескриптор `one-shot`, затем ждёт провайдера, пока не будет опубликован настоящий one-shot ребёнок. Успешное исполнение возвращает принадлежащий держателю `SubagentRun`; отказ означает, что провайдер уже освободил все неопубликованные стартовые ресурсы, а сбои хода или инфраструктуры после публикации завершаются через сам запуск. Продолжаемые дети никогда не создаются этой операцией. |
| `startContinuable(spec)` | Заводит одного долговечного продолжаемого ребёнка и доставляет его начальный промпт. Разрешается значением `{ childId, messageId }`, когда инбокс ребёнка принимает этот промпт, не дожидаясь начала хода и попадания сообщения в журнал Session; любая более ранняя неудача отклоняет операцию без идентификаторов и полностью откатывает ребёнка. Зарезервированный вызывающим `childId` отклоняется, когда живые реестры или настроенная персистентность уже содержат его. Требует `ctx.agents`, персистентности сессий и провайдера с возможностью `prepareContinuable`. |
| `followup(parent, childId, content, { source, signal })` | Доставляет одно последующее сообщение от точного живого прямого родителя как следующий FIFO ход ребёнка, следуя терминологии `Agent.followup()`, и возвращает принятый `MessageId`. Инбокс резидентного ребёнка принимает его напрямую (пробуждая ожидающую активацию); отсутствие ребёнка означает холодное возобновление из его персистентной Session. Требует `ctx.agents`; холодное возобновление требует также персистентности сессий. |
| `interrupt(targetSessionId, authority)` | Прерывает текущий ход одного живого продолжаемого ребёнка по долговечному адресу родителя-человека (`{ kind: 'user', parentSessionId }`) или точному живому агенту-предку (`{ kind: 'ancestor', agent }`). Допуск синхронен, эффект асинхронен: операция выдаёт `Agent.cancel(cause, { keepInbox: true })` и возвращается, не дожидаясь, пока цель увидит сигнал. Незатребованная ожидающая работа инбокса, активация и опубликованные потомки сохраняются; работа, уже взятая в прерываемый ход, обратно в очередь не ставится. Отсутствующая цель — принятый no-op; неверный адрес родителя, а также устаревший, целющийся в себя или не являющийся предком вызывающий отклоняются с `UNAUTHORIZED`. |
| `reportFrom(child, content, { delivery, signal })` | Доставляет одно выбранное сообщение от точного живого продолжаемого ребёнка его точному живому прямому родителю и возвращает принятый стабильный `MessageId`. Тихая доставка вводит next-step контекст без пробуждения; доставка next-step направляет и будит родителя. |
| `registerContinuableSetup(contribution)` | Встраивает необязательную возможность развёртывания в неопубликованный скоуп каждого продолжаемого ребёнка с немедленным отзывом у резидентных детей. |
| `drainContinuableDescendants(parents)` | Закрывает допуск ниже точных живых принадлежащих хосту родительских агентов, останавливает только их видимых продолжаемых потомков, дожидается, пока материализации, допущенные ниже этих корней, не завершатся публикацией или откатом, затем освобождает выбранные леса, начиная с детей. Запрет на допуск действует, пока каждый точный родитель не покинет реестр; несвязанные родительские леса и допуск в масштабе менеджера остаются живыми. |
| `drainContinuableChildren(parent, childIds)` | Освобождает только перечисленных резидентных продолжаемых прямых детей одного точного живого родителя, рекурсивно и начиная с детей. Операция не закрывает допуск и не трогает соседей, принимает отсутствующие id как no-op и отклоняет резидентного ребёнка, принадлежащего другому родителю. Это teardown, поэтому в отличие от `interrupt()` она не сохраняет ожидающую работу инбокса. |
| `listChildren(parentSessionId, signal?)` | Перечисляет прямых субагентов на сессиях с их режимом `one-shot`/`continuable`, активностью `running`/`inactive`, классифицированной по происхождению подсказкой `hasChildren` на один уровень и диагностикой по каждому ребёнку, в порядке `createdAt`, затем id, без загрузки или возобновления. Читает живое хранилище сессий и опциональную персистентность сессий напрямую (перечисление только по живым, когда персистентности нет) и требует смонтированного реестра `sessionProjections`; не требует `ctx.agents`, менеджера продолжений или какого-либо сервиса запросов. |
| `listDescendants(rootSessionId, signal?)` | Разворачивает полное дерево сессий корня в стабильном pre-order из того же корпуса с предпочтением живых, добавляя каждому вхождению субагента долговечные `parentId` и `depth` относительно корня. Обычные сессии и one-shot дети остаются узлами обхода, чтобы обнаруживались продолжаемые потомки под ними. Идентичность, диагностика, зависимости и отмена следуют `listChildren()`. |

`SubagentStartRequest.label` — необязательная короткая долговечная отображаемая метка для one-shot ребёнка на сессии. Делегация, видимая модели, передаёт своё существующее `description`; вызывающим нижнего уровня не нужно придумывать презентационные метаданные. Продолжаемые запуски всегда несут собственную обязательную метку. `signal` обязателен и является каноническим каналом отмены для one-shot `start`. Отмена до публикации заставляет `start()` отклониться после отката; отмена после публикации отменяет оставшуюся работу хода возвращённого запуска, не скрывая его id. Запрос может также выбрать модель, потребовать структурированный результат, ограничить глубину делегации, сузить инструменты ребёнка или задать персону ребёнка. Для продолжаемого запуска или follow-up сигнал вызывающего управляет поиском, материализацией и допуском только до принятия инбоксом; после этого активацией независимо управляет менеджер, поэтому более поздняя отмена вызывающим не отменяет принятый ход и не освобождает ребёнка.

Право на follow-up исходит от точного живого прямого родителя, записанного в долговечном заголовке ребёнка. Холодное возобновление проверяет это право перед реконструкцией и снова в финальном, свободном от ожиданий промежутке допуска в инбокс, поэтому родитель, снятый с регистрации или заменённый во время материализации, не может авторизовать доставку. Поле `source` follow-up записывает, кто передал доставленное сообщение, и не даёт никаких прав.

Внутрипроцессные запросы, дескрипторы, результаты и полезные нагрузки событий — доверенные типизированные значения, заимствуемые как неизменяемые. Сервис не клонирует и не замораживает их; сериализация и проверка враждебного ввода лежат на настоящих границах процессов, воркеров, персистентности и моделей.

## Возможности

Стартовые функции объявляются в `provider.capabilities`, потому что сервис ДОЛЖЕН отклонить неподдерживаемый one-shot запрос до создания ребёнка:

- `outputSchema` — требует структурированный итоговый результат.
- `depthLimit` — применяет `maxDepth`.
- `toolFilter` — применяет запрошенное ограничение инструментов ребёнка.
- `persona` — применяет персону для каждого ребёнка.

Каждый внутрипроцессный ребёнок собирается одним вызовом, `applyChildComposition(childCtx, parent, composition)`, который присоединяет композицию agent-preset родителя перед применением собственной персоны и фильтра инструментов ребёнка. Именно присоединение даёт ребёнку его возможности: когда каждая строка, видимая модели, находится на агентской плоскости, ребёнок, ничего не присоединивший, дошёл бы до модели с пустым реестром инструментов ([`dsh-agent-presets`](../../preset/agent-presets/README.md)). Передача родителя параметром намеренна — она делает непредставимой сборку ребёнка БЕЗ этого присоединения в местах вызова, что и есть дефект, предотвратить который призван этот единственный вызов. Развёртывание, не формирующее набор пресетов, ничего не присоединяет, и ему ничего не нужно: его строки, видимые модели, находятся в композиции хоста, где ребёнок уже разрешает их через глобальный слой реестра инструментов.

`childSessionMeta()` записывает id присоединённого пресета в долговечный заголовок ребёнка по той же причине, по какой сессия верхнего уровня записывает свой: пресет решает, какие схемы инструментов и секции промпта видела модель, поэтому холодное чтение истории ребёнка должно восстановить ту композицию, а не заданную развёртыванием по умолчанию. Он читается из живой цепочки скоупов родителя, а не из заголовка родителя, потому что родитель, сменивший пресет, пока был пуст, работает на новой композиции, тогда как его заголовок всё ещё называет старую.

Создание продолжаемого ребёнка — это необязательный метод `SubagentProvider.prepareContinuable?()`: само его наличие является проверкой возможности, поэтому сервис отклоняет настроенный продолжаемый запуск на провайдере без него, тогда как провайдер с ним может всё же обслуживать обычные one-shot делегации. Метод возвращает только отсоединённый `ContinuableCreateSpec` (`{ seed? }`) — данные, никогда не возможность: он не несёт ни агента, ни `AgentHandle`, ни доставки промпта, ни результата, ни освобождения ресурсов, ни операции возобновления, потому что резервированием идентичности, композицией, созданием агента, доставкой промпта, холодным возобновлением, владением и освобождением ресурсов после подготовки управляет менеджер продолжений. One-shot `SubagentRun` представляет одну одноразовую делегацию на переднем плане с одним результатом и без операции холодного возобновления. Сервис может вызывать одного провайдера конкурентно для разных сиблингов: каждый запуск или подготовка владеет своими изменяемыми данными и путём отмены, и сбой, результат или очистка одной операции НЕ ДОЛЖНЫ завершать или освобождать другую. Провайдер может организовать внутреннюю очередь собственной ёмкости, не меняя этот контракт независимости.

## Долговечный дескриптор

Service Definition владеет версионированным словарём событий сессии `subagent/descriptor` (`src/descriptor.ts`): `snapshotSubagentDescriptor()` проверяет и отсоединяет запись до работы провайдера, а `foldSubagentDescriptor()` проверяет полную полезную нагрузку текущей версии перед извлечением её из загруженного журнала ребёнка. Каждый локальный запуск на сессии дописывает один дескриптор с именем провайдера и lifecycle `mode`. Дескриптор `one-shot` опционально несёт принадлежащую вызывающему долговечную отображаемую `label`; дескриптор `continuable` требует свою долговечную метку создания и дополнительно записывает разрешённые `agentOptions.provider`/`model` ребёнка и опциональные `persona`/`toolFilter` для холодного возобновления. Это явные поля, а никогда merge-extensible объект `AgentOptions`, чтобы постороннее значение расширения не могло сломать продолжение. Дескриптор опускает `subagentDepth` (`delegationDepth` персистентного заголовка — монотонная нижняя граница) и `outputSchema` (контракт результата активации). Событие только журнальное: без `surfaceOp`, отсутствует в истории модели и удерживается append-only журналом сквозь компакцию. Искажённые полезные нагрузки текущей версии — повреждение; неподдерживаемые версии этот рантайм классифицировать не может.

## Глубина делегации

Seam задаёт словарь глубины, разделяемый Service Providers и Consumer: объявлением `AgentOptions.subagentDepth`, `assertSubagentMaxDepth` и `delegationDepthOf(agent)`. Персистентный `SessionHeader.delegationDepth` авторитетен и монотонен — рантайм-опции могут углублять счёт, но никогда не понижать его, поэтому возобновлённый ребёнок не может быть пересчитан как верхнеуровневый.

`inheritsParentContext` описателен, а не исполним. Он говорит лишь, видит ли ребёнок завершённую историю беседы родителя (`fork` видит; `spawn` и out-of-process one-shot провайдеры — нет), а не наследует ли он инструменты, сервисы или права.

## Делегированная политика

Оба внутрипроцессных пути делегации фиксируют скоуп разрешений ребёнка на границе делегации через общие helper'ы дочернего агента. `captureDelegatedPolicyOverrides(parent)` делает снапшот явного переопределения песочницы сессии родителя (`sandboxPolicy.overrideOf()`) и фиксирует политику подтверждений ребёнка на `'never'` всякий раз, когда возможность подтверждений входит в композицию — независимо от собственной политики родителя, — поэтому делегированный ребёнок действует только внутри унаследованного скоупа песочницы, и каждый запрос подтверждения (например, эскалация `sandbox_permissions`) отклоняется детерминированно вместо ожидания промпта, за которым никто не следит (оба сервиса — опциональные потребители `ctx.get`). `appendDelegatedPolicyOverrides()` записывает каждое значение в собственный журнал ребёнка как событие `sandbox/mode` или `approval/policy` с `source: 'delegation'` во время неопубликованной настройки, после любого fork seed — поэтому свежая политика побеждает устаревшее состояние seed, а эффективная политика ребёнка остаётся восстанавливаемой из одного его журнала. Песочница по умолчанию для развёртывания никогда не копируется: непереключённый родитель не проставляет `sandbox/mode`, и его ребёнок динамически следует развёртыванию по умолчанию. Продолжаемый запуск захватывает политику до первого await и засеивает только свежую материализацию; холодное возобновление воспроизводит персистентные события делегации вместо повторного захвата родителя, поэтому смена родителя после создания никогда не изменит долговечного ребёнка задним числом. Каждый внутрипроцессный ребёнок также получает скоупированное утверждение runtime-контекста (`subagent:delegation`), сообщающее, что скоуп фиксирован и задача, требующая более широкого доступа, заканчивается сообщённым ограничением, а не повторами. См. Agent Notes о политике делегации [one-shot](../../../.agents/notes/implemented/feature/2026-07-25-subagent-policy-inheritance.md) и [continuable](../../../.agents/notes/implemented/feature/2026-08-10-continuable-subagent-policy-inheritance.md).

## Владение и жизненный цикл one-shot

`provider.start(request): Promise<SubagentRun>` — граница передачи владения; инструмент делегации тоже пользуется ею внутри своего фонового пути one-shot на основе Task. До исполнения провайдер владеет настройкой и ДОЛЖЕН при каждой неудаче отменять, откатывать и доводить неопубликованные ресурсы до quiescence. После исполнения запуском владеет вызывающий и ДОЛЖЕН вызывать `dispose()` на каждом пути; оставшаяся работа промпта и хода принадлежит `SubagentRun.result`.

`SubagentRun.result` разрешается в `{ output, structured?, diagnostic?, stopReason }`. Сбои уровня ребёнка разрешаются с причиной, отличной от `completed`; отклониться может лишь сбой инфраструктуры, который seam не способен представить. Провайдер может добавить безопасный `diagnostic` к незавершённому результату после удаления входов инструментов, содержимого файлов, значений окружения, учётных данных и сырых полезных нагрузок протокола и ограничения полного текста 4096 байтами UTF-8. Общий тип результата не определяет категории провайдеров или стадии жизненного цикла: out-of-process провайдер может вывести фиксированный отображаемый текст из своих привязанных к версии структурных фактов о продукте и наблюдаемого исхода процесса, а потребители рендерят этот текст, не разбирая его. Поле не является выводом ассистента: потребители показывают его отдельно, и оно не входит в `subagent/end.lastAssistantMessage`. `dispose()` идемпотентен, отменяет оставшуюся работу и ждёт и завершения результата, и quiescence ресурсов ребёнка. Отклонение результата остаётся на `result`; `dispose()` отклоняется только из-за независимого сбоя освобождения ресурса. `output` и поле `lastAssistantMessage` события `subagent/end` пользуются экспортируемыми helper'ами `AssistantOutputFold`/`finalAssistantOutput`, чтобы выбрать последнее непустое сообщение ассистента ребёнка либо накопленный текст ассистента, когда такого сообщения нет. `output` равен `[]`, а поле события отсутствует, когда ребёнок не произвёл ни того ни другого ([`SubagentResult`](../../../docs/subsystems/subagent.ru.md#итоговый-результат-subagentresult) определяет контракт итогового результата).

Локальный запуск публикует обычного дочернего агента/сессию до исполнения `start()`, возвращает этот общий id сессии как `SubagentRun.id`, предоставляет точного ребёнка как `SubagentRun.localAgent`, записывает `request.parent.session.id` в заголовок `parentSession` ребёнка и дописывает разрешённый дескриптор внутри начального хода. Удалённые провайдеры вместо этого генерируют id жизненного цикла со скоупом родителя и возвращают `localAgent: undefined`; без локальной дочерней сессии их one-shot запуски не входят в перечисление по трассам.

## Продолжаемые дети и активации

Продолжаемый ребёнок имеет одну долговечную Session и максимум одну процессно-локальную **активацию** — один период резидентности реконструированного дочернего агента, а не границу запроса, результата, отмены или Task. Инбокс агента — единственная очередь ходов, поэтому менеджер продолжений владеет резидентностью, тогда как цикл агента владеет всем упорядочиванием и исполнением ходов. Ни один продолжаемый путь не создаёт Task или промежуточной обёртки с результатом.

Менеджер выводит три внутренних условия резидентности из quiescence агента и множества принадлежащих ему детей вместо поддержания второй машины состояний: running (активный допуск, открытый ход или будящая работа инбокса), waiting (quiescence, но всё ещё владеет хотя бы одним неосвобождённым ребёнком) и settled (quiescence при освобождении каждого принадлежащего ребёнка, тогда менеджер освобождает `AgentHandle` и снимает активацию). Каждое сообщение продолжения пользуется `Agent.followup()` и становится одним FIFO ходом без steering текущего хода. Маршрутизация зависит только от резидентности: running ставит в очередь, waiting будит того же агента, а отсутствие активации холодно возобновляет новую.

Менеджер резервирует идентичность ребёнка, разрешает долговечный дескриптор, вызывает `ctx.agents.create()` (или `ctx.agents.resume()` для холодного возобновления) через приватный скоуп владельца активации, устанавливает возвращённый `AgentHandle` в активацию, устанавливает владение продолжаемым родителем, где оно есть, и затем подаёт промпт. Холодное возобновление никогда не диспетчеризуется через провайдера, потому что персистентная Session уже держит начальный префикс, а свёрнутый дескриптор — весь вход реконструкции.

### Доставка итога

Когда резидентная активация завершается, менеджер сообщает долговечному прямому родителю ребёнка, в собственном потоке ходов родителя, что ребёнок произвёл всё, что собирался. Доставка безусловна для каждого ребёнка, чей id вызывающий реально получил: она не рассматривает, вызывал ли ребёнок `report`, потому что те окончания, которым больше всех нужен отчёт, — потолок токенов, сбой модели, отмена, teardown — как раз те, где ребёнок не успел выбрать. Материализация, откаченная до первого принятого сообщения, молчит — вызывающему уже сообщено, что ребёнок не установлен. Сообщение несёт причину остановки эпохи, финальное содержимое ассистента, если оно было, и долговечное описание происхождения `{ kind: 'subagent-settled', form: 'notice', senderSessionId: <child-id> }` — это иной kind источника, чем созданный самим ребёнком `subagent-report`, поэтому транскрипт никогда не припишет ребёнку слов, написанных рантаймом.

Два правила упорядочивания делают доставку надёжной, а не зависящей от удачи, и оба объясняют, почему она принадлежит менеджеру, а не внешнему слушателю `subagent/end`. Во-первых, отправка происходит **до** освобождения владения ребёнком, пока родитель ещё учитывает ребёнка своим и потому структурно не может быть признан завершённым. Во-вторых, родитель, сам являющийся резидентной активацией, получает сообщение через тот же учёт будящего допуска, что и report, поэтому окно между синхронной отправкой и микротаском, который её допускает, не принимается за quiescence — `Agent.status` сворачивает обслуживание контекста в `idle`, а будящая отправка за обслуживанием лишь взводит отложенное пробуждение. Без любого из этих правил родитель может быть освобождён, когда уведомление ещё лежит в очищаемом `cancel()` инбоксе, — и оно молча теряется.

Idle-родитель получает уведомление как один обычный последующий ход. Занятого родителя вместо этого направляют (steering) к ближайшей границе шага, поэтому несколько детей, завершающихся вместе, обходятся в один шаг, а не по ходу на каждого; steering вместо инъекции также означает, что драйвер, завершившийся между чтением статуса и отправкой, всё же получит сообщение. Родитель, чья собственная ветка дерева уже находится в teardown, получает уведомление инъекцией, без пробуждения: `Agent.followup()` на родителе в quiescence начинает ход, а `cancel()` не взводится против последующего, поэтому пробуждение во время teardown потратило бы запрос к модели на агента, которого хост вот-вот освободит, — по разу на слой дерева, ведь уведомление каждого слоя затем будит слой выше. Инъецированное сообщение достигает родителя, всё ещё читающего инбокс, и журнал в любом случае записывает отчёт, но оно не переживёт собственного освобождения этого родителя: `AgentHandle.dispose()` — это cancel с `keepInbox: false`, долговечно отменяющий незатребованное уведомление. Поэтому у возобновлённого родителя нет ожидающего уведомления для чтения: `list_agents` говорит ему, какие дети существуют и кто жив, а кто сохранён, тогда как сам исход остаётся в собственной Session ребёнка, куда `send_message` добирается, возобновляя этого ребёнка. Родитель, покинувший реестр, — не ошибка: уведомление отбрасывается, а собственная Session ребёнка остаётся долговечной записью. Доставка никогда не блокирует и не ломает teardown — отклонённая отправка логируется, ибо удержание ребёнка ради повтора уведомления навсегда закрепило бы всю его родословную в `waiting`.

Родительская активация под управлением продолжений записывает id каждой дочерней сессии в множество `ownedChildren` прежде чем ребёнок сможет работать, и освобождается только после того, как активация каждого принадлежащего ребёнка завершит освобождение `AgentHandle` (начиная с детей). Teardown распространяет отмену агента сверху вниз до ожидания медленных потомков, тогда как освобождение handle'ов по-прежнему начинается с детей. Агенты верхнего уровня и прочие не-продолжаемые агенты не имеют активации и остаются вне этого графа ожидания. Финальное завершение ждёт best-effort `ctx.sessions.flush(child.session)` перед освобождением handle. Отклонение слушателя логируется без сбоя активации, потому что участие слушателя не идентифицирует бэкенд персистентности; поэтому при возобновлении персистентное состояние может отсутствовать или оказаться устаревшим.

## События жизненного цикла

Сервис выдаёт пару `subagent/start`/`subagent/end` для каждого one-shot запуска и каждой резидентной продолжаемой эпохи активации, поэтому продолжаемые дети наблюдаемы тем же словарём, что и one-shot запуски, без раскрытия того, материализовал ли их менеджер, разбудил или холодно возобновил. Для one-shot запуска он прикрепляет наблюдателя результата до синхронного `subagent/start`, поэтому даже уже завершившийся ребёнок всё равно производит `subagent/start` до `subagent/end`; продолжаемая эпоха, потерпевшая неудачу до резидентности, не выдаёт ни одного события этой пары. Пара использует единый созданный сервисом `runId`; флаг `local` — снапшот точного `localAgent` провайдера (всегда true для продолжаемого ребёнка), поэтому наблюдатели никогда не выводят идентичность или локальность запуска из многоразовых имён провайдеров/сессий. Поле `provider` содержит имя провайдера, записанное при первом создании ребёнка, и не претендует на текущую регистрацию: принятый one-shot запуск может завершиться после удаления провайдера, а холодно возобновлённая эпоха читает начальное имя провайдера из своего дескриптора, не вызывая и не регистрируя этого провайдера.

События запусков скоупируются на делегирующего родителя. Каждый слушатель независимо изолирован: синхронный throw или отклонённый возвращённый промис логируется, не лишая обслуживания остальные слушатели и не меняя запуск.

Добавления и удаления провайдеров также выдают `subagent/provider-added` и `subagent/provider-removed`. Consumer вроде инструмента, видимого модели, используют эти события, потому что Cordis может загружать плагины-сиблинги конкурентно; порядок конфигурации не доказывает порядок регистрации.

Продолжаемые дети не создают `SubagentRun` или Job'ы. Менеджер продолжений напрямую владеет одной процессно-локальной активацией и удерживаемым `AgentHandle` на каждую резидентную дочернюю сессию, пользуется инбоксом агента как единственным FIFO и выполняет холодное возобновление из долговечного дескриптора. Точная живая идентичность прямого родителя авторизует доставку родитель→ребёнок. Точная живая идентичность ребёнка авторизует report'ы; менеджер выводит получателя из долговечного `parentSession`, а `MessageSource` записывает отправителя, не давая прав. Право на прерывание намеренно шире права на доставку: человек предъявляет долговечный адрес прямого родителя, чтобы живой ребёнок оставался остановимым, пока его родительский агент офлайн, и любой точный живой предок, записанный в родословной материализации активации, может остановить своего потомка, ибо остановка хода идемпотентна и не доставляет содержимого.

Когда доступен `ctx.sessionProjections`, сервис регистрирует две проекционные единицы. `subagentTiming` сбрасывается на каждом дескрипторе, чтобы работа предков из fork seed не попадала в итог ребёнка, затем накапливает активное время `turn/start` → `turn/end` и удерживает границы `active.since` и `active.through` того же среза для открытого хода; пока ход открыт, `active.through` следует за последним свёрнутым событием, давая неактивному потребителю консервативную границу сбоя без подмешивания более новых метаданных сессии. `subagent` сворачивает долговечную идентичность — режим плюс метка создания — из событий `subagent/descriptor` с той же дисциплиной сброса «последний побеждает», поэтому дескриптор предка из fork seed стоит лишь до тех пор, пока его не перекроет собственный дескриптор ребёнка; искажённая полезная нагрузка или неизвестная версия сворачивается в сериализуемый сентинел `null` — неотличимый от журнала без дескриптора и переживающий каждый кадр JSON push, чтобы потребитель заменил устаревшую идентичность, а не хранил её, — и никогда не бросает исключений.

`registerContinuableSetup()` позволяет необязательным пакетам добавлять скоупированные на ребёнка возможности, не обучая менеджер продолжений их именам. Вклады устанавливаются синхронно до публикации активации, откатываются вместе с неудавшейся настройкой и освобождаются вместе со скоупом ребёнка. Новые выдачи возможностей ожидают следующую активацию, тогда как снятие вклада немедленно отзывает каждую резидентную установку.

## Модель сбора

Инструмент, видимый модели, собирает синхронно по умолчанию: он ждёт результат ребёнка и освобождает запуск перед возвратом. One-shot фоновая делегация регистрирует простой Task в инструменте, чьи универсальные инструменты статуса, сбора и отмены ведут дальнейшее взаимодействие, и сохраняет переданное моделью `description` как опциональную отображаемую метку. Продолжаемая фоновая делегация вызывает `ctx.subagents.startContinuable()` и возвращает только долговечный id ребёнка; ребёнок владеет собственными ходами с момента принятия инбоксом, поэтому нет ни Task, ни обещания результата — вызывающий отправляет последующую работу инструментом follow-up `send_message`, а `interrupt()` останавливает только текущий ход, не освобождая ребёнка, и долговечная дочерняя Session остаётся источником подробного вывода ребёнка. Менеджер продолжений существует, только пока доступен `ctx.agents`, а персистентность сессий разрешается на каждую операцию продолжения. Независимо от этого `listChildren()` перечисляет объединение с предпочтением живых из живого хранилища сессий и опциональной персистентности — только по живым, когда персистентности нет, ибо холодного ребёнка тогда тоже не возобновить, — и подаёт долговечные режим/метку каждого ребёнка из зарегистрированной проекционной единицы `subagent`: снапшот водяного знака реестра для живого ребёнка; для холодного — долговечную строку кэша проекций, когда та подаёт идентичность собственного суффикса, — её гейт `seq` доказывает, что значение новее fork seed, где собственный дескриптор ребёнка после дописывания неизменяем, — иначе одну инспекцию персистентности с ограниченной конкуренцией, свёрнутую через реестр, чей результат всё равно ДОЛЖЕН назвать перечисленный жизненный цикл (перевыпущенный id деградирует в диагностику `corrupt`). Завершающееся исключением чтение кэша не выносит вердикта — кэш — производные данные, — и тихо проваливается к этому авторитетному повторному свёртыванию. Проекционное свёртывание — единственный авторитет классификации; само перечисление дескрипторы не разбирает. Поданная идентичность даёт строку ребёнка; завершившийся кандидат, чьё свёртывание не подало идентичности, — диагностика `corrupt`, неудавшаяся инспекция — переходная `unavailable`, повторяемая при следующем перечислении, а работающий кандидат, у которого пока нет идентичности, опускается (окно создания до дописывания его дескриптора). Оно никогда не консультируется с менеджером продолжений, регистрациями агентов, активациями или провайдерами. Каждая строка ребёнка выводит свою читаемую в момент запроса подсказку `hasChildren` из объединённых заголовков с долговечным `origin: 'subagent'`; она не читает журналы событий потомков, и основанный на дескрипторах каталог детей остаётся авторитетным при раскрытии. Сервисные потребители вроде UI могут удерживать оба режима и выбирать fallback для непомеченного one-shot ребёнка; видимый модели инструмент `list_agents` проецирует только вхождения `continuable`, уточняет статус через живой реестр агентов, отображает storage-only в его возобновляемое-но-нетерминальное состояние `ready` (`running`/`idle`/`ready`) и обходит `listDescendants()` для скоупа `descendants`. Перечисление пересылает сигнал вызывающего в каждое чтение персистентности, проверяет отмену вокруг каждого из этих await и репортит каждый замеченный abort как код `CANCELLED` ошибки `SubagentError`; несмонтированный реестр проекций падает с явной ошибкой `SUBAGENT_CONTROL_PROJECTIONS_UNAVAILABLE`, а отсутствие хранилища сессий — с `SUBAGENT_CONTROL_SESSION_STORE_UNAVAILABLE`. См. [Agent Note о фоновых задачах субагентов](../../../.agents/notes/implemented/feature/2026-07-08-background-subagent-tasks.md), [Agent Note о продолжаемых фоновых субагентах](../../../.agents/notes/implemented/feature/2026-07-21-continuable-background-subagents.md), [Agent Note о долговечном каталоге](../../../.agents/notes/implemented/feature/2026-07-22-durable-subagent-catalog-and-list-agents.md), [Agent Note о слитом сервисе](../../../.agents/notes/implemented/simplification/2026-07-26-merge-subagent-control-service.md), [capability-seam Agent Note](../../../.agents/notes/implemented/feature/2026-06-21-subagent-capability-seam.md) и `src/types.ts` для полных контрактов.

Продолжаемые активации ждут best-effort финального flush сессии, не считая участие слушателя подтверждением долговечности. One-shot запуски сохраняют best-effort чекпоинтинг сессий, поэтому завершённый one-shot ребёнок обнаружим после освобождения, только когда его сессия действительно добралась до персистентности; сервис не выдумывает вхождение каталога из истории Task, когда того чекпоинта нет.

## Влияние на модель

### Уведомление о завершении

#### Что видит модель

Одно родительское сообщение роли user, начинающееся с исхода — `Background subagent <child-id> finished and will do no further work unless you send it more.` или соответствующей строкой для остановленного, исчерпавшего лимит, отказавшегося или потерпевшего неудачу ребёнка, — за которым следует `Its closing message:` и финальное содержимое ассистента ребёнка либо `It left no closing message.`, когда того не было. Это единственный прямой вклад сервиса на стороне родителя; схемы делегации, продолжение родителя и обнаружение, а также скоупированный на ребёнка `report` принадлежат `dsh-tool-subagent`, `dsh-tool-subagent-control` и `dsh-tool-subagent-report`.

#### Влияние на токены

Одно уведомление на каждую завершённую активацию в запросе родителя, размером с финальное сообщение ребёнка. Ребёнок, который и отправляет report, и завершается, стоит родителю оба.

#### Влияние на KV-кэш

Append-only у родителя: уведомление следует за его переиспользуемым префиксом запроса. Достижение idle-родителя начинает один независимый запрос к модели; достижение занятого — нет.

### Утверждение о делегированном скоупе ребёнка

#### Что видит модель

Снапшот runtime-контекста каждого внутрипроцессного ребёнка несёт приведённое ниже утверждение `subagent:delegation`, после предложений о песочнице и политике подтверждений.

##### Текст утверждения о делегированном скоупе

```markdown
You are a delegated subagent: your permission scope was fixed when you were started and cannot be widened from inside this session — operations that require approval are rejected automatically. When the job needs access beyond that scope, do not retry the denied operation; state the limitation in your reply so the delegating agent can handle it.
```

#### Влияние на токены

Одно фиксированное утверждение в каждом снапшоте runtime-контекста ребёнка; ни одного в запросах родителя.

#### Влияние на KV-кэш

Стабильно по префиксу внутри ребёнка: утверждение никогда не меняется за жизнь ребёнка, поэтому записывается один раз в первый снапшот runtime-контекста. На стороне родителя прямой инвалидации нет; названные Consumer инструментов отвечают за любые изменения префикса запроса.

## Известные ограничения и отложенная работа

- **Дети ACP остаются one-shot и не перечисляемы по трассам** — запуск ACP не имеет локальной дочерней сессии среди сессий родителя. ACP `prepareContinuable` требует сохранения удалённого id сессии в специфичных для провайдера данных дескриптора и объявления продолжения для каждого ребёнка, поскольку поддержка ACP `loadSession` согласуется для каждого ребёнка по отдельности, а не следует из наличия метода. Удалённые провайдеры требуют также отдельного контракта владения активацией с эквивалентным аутентифицированным управлением и quiescence начиная с детей, прежде чем поддерживать продолжаемых детей.
- **Нет продолжения от пользователя хоста** — `followup()` требует точного живого прямого родителя. Только `interrupt()` принимает пользовательское право по долговечному адресу родителя, потому что остановка хода идемпотентна и не доставляет содержимого; будущему адаптеру хоста нужно конкретное аутентифицированное взаимодействие, прежде чем seam получит возможность доставки пользователю.
- **Сообщения продолжения никогда не выполняют steering** — сообщения продолжения родитель→ребёнок ставятся в очередь как последующие ходы ребёнка. Report'ы ребёнок→родитель — независимый next-step ввод и могут продлить открытый ход родителя.
- **Окно пробуждения при сходимости отмены** — будящий follow-up, принятый после выдачи сигнала прерывания, но до того, как активный драйвер станет idle, остаётся в очереди до следующей будящей отправки. Issue #1838 отвечает за защёлку пробуждения agent-loop, которая затрагивает и обычную отмену сессии.
- **Процессно-локальная резидентность** — инбокс активации и граф владения не координируют два процесса harness; конкурентный доступ к одному хранилищу персистентности по-прежнему требует долговечного mailbox и межпроцессного lease-протокола.
- **Нет воспроизведения принятых, но не записанных в журнал сообщений** — только сообщения, записанные в журнал Session ребёнка, восстановимы вместе с источником, который их передал. Сбой может потерять принятый начальный промпт или follow-up, так и не дошедший до журнала; позднее авторизованное сообщение может холодно возобновить ребёнка, но потерянное сообщение автоматически не воспроизводится.
- **Нет долговечного mailbox для report'ов** — report'ы требуют живого прямого родителя и дают идентичность принятия, а не доставку ровно один раз или квитанцию о прочтении.
- **События жизненного цикла доступны только для наблюдения** — влияющий на запуски API продолжения или решений на основе `subagent/end` ожидает конкретного потребителя.
