# dsh-atomic-write

[English](README.md) | [中文](README.zh.md) | Русский

Нулевая по зависимостям атомарная замена файлов, разделяемая хранилищами на файлах, которые никогда не должны оставлять на диске частичное, перехваченное через symlink или более широкое, чем задумано, содержимое — документ пользовательских настроек (`dsh-settings-file`) и хранилище учётных данных (`dsh-credentials-local`).

## Поверхность

```ts
import { withFileLock, writeFileAtomic } from '@deepseek-ai/dsh-atomic-write'

declare const text: string
declare const render: (previous: string) => string

await writeFileAtomic('/home/u/.dsh/settings.yaml', text, { mode: 0o600 })

// Read-modify-write against the same file from several processes.
await withFileLock('/home/u/.dsh/settings.yaml', async () => {
  await writeFileAtomic('/home/u/.dsh/settings.yaml', render(text), { mode: 0o600 })
})
```

`writeFileAtomic` фиксирует одну уже отрендеренную строку. Контракт — в том порядке, в котором сбои пытались бы его обойти:

- **Временный файл с эксклюзивным созданием** (`wx`, случайный суффикс): открытие отказывается следовать по symlink, подброшенному по угадываемому временному пути.
- **Свежий inode проносит `mode` через переименование**: замена файла с более широкими разрешениями сужает их без гонки chmod. `mode` обязателен, чтобы решение о разрешениях оставалось видимым в каждом месте вызова (с поправкой на umask процесса, как у всякого свежего inode).
- **`rename` заменяет сам symlinked-целевой объект**, но не пишет сквозь него в то, на что тот указывает.
- **Сосед по тому же каталогу** удерживает переименование в одной файловой системе, поэтому подмена остаётся атомарной.
- Родительские каталоги создаются; при любом сбое временный файл удаляется, а сбой выбрасывается дальше; читатели наблюдают либо старое, либо новое полное содержимое.

`withFileLock` сериализует пишущих одного файла между процессами — для циклов «прочитал–отрендерил–зафиксировал», которые голая атомарная фиксация сама по себе сделать безопасной не может. Замок — соседний `<filename>.lock`, созданный через `wx`, поэтому читатели никогда не конкурируют; ожидающие отступают экспоненциально и завершаются по таймауту, а не блокируются навсегда. `EEXIST` опознаёт конкуренцию напрямую; `EPERM` — только когда свежий `lstat` подтверждает существование пути замка, что покрывает поведение эксклюзивного создания Windows, не пряча несвязанный сбой разрешений. Конкурент никогда не удаляет существующий замок: возраст не отличает сбившегося владельца от приостановленного живого пишущего.

Как долго конкурент ждёт — свойство операции, которую выполняет держатель, поэтому она задаётся при каждом вызове через `waitMs`. Значение по умолчанию рассчитано на чистую файловую работу; держатель, чей цикл включает сетевой обход туда-обратно — мутацию учётных данных, обновляющую истёкший токен, — указывает большее значение, ибо сохранение умолчания провалило бы всех остальных пишущих этого файла на всё время ожидания. Темп повторов остаётся фиксированным: он определяет, как часто конкурент спрашивает, и ни у одного вызывающего нет причины его менять.

## Влияние на модель

Отсутствует: это чистый примитив файловой системы; ничто здесь не доходит до запроса к модели.

#### Влияние на KV-кэш

Отсутствует; ничто здесь не входит в префикс запроса.

## Известные ограничения и отложенная работа

- **Атомарно, но не долговечно** — ни `fsync` файла, ни его каталога, поэтому после сбоя переименование может наблюдаться откатанным. Файловые хранилища здесь при загрузке перечитывают и переопубликовывают состояние, оставляя долговечность политикой вызывающего.
- **Только строковое содержимое** — формы для `Buffer` или потока не появится, пока какой-то потребитель не запросит её.
- **Осиротевшие замки требуют вмешательства оператора** — процесс, вышедший с удерживаемым замком, может оставить соседний файл. Позднейшие пишущие истекают по таймауту, не удаляя его; оператор удаляет замок только убедившись, что ни один пишущий им больше не владеет. Один лишь возраст файла — небезопасное свидетельство брошенности.
