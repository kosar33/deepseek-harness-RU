# dsh-launch-environment

[English](README.md) | [中文](README.zh.md) | Русский

Окружение данного запуска в виде одного неизменяемого снапшота, который помнит, **какой слой предоставил каждое значение**. Потребители разрешают обращённые к пользователю значения по нему, а не по `process.env`, потому что слои неравнозначны по доверию, а сплющенное представление их не различает.

| Слой | Source id | Что это |
|---|---|---|
| Унаследованное окружение процесса | `process` | То, что передали запускающая оболочка, задача CI или контейнер, — явное намерение этого запуска |
| `<invocation cwd>/.env` | `project-env` | Проект, в котором запущен harness; продукт доверяет ему настройку собственного агента |
| `$DSH_HOME/.env` | `user-env` | Собственные машинные умолчания пользователя |

Значения при этом тоже попадают в `process.env` — его читают дерево `--config` пользователя и сторонние библиотеки, — но это сплющенное представление не является авторитетом ни для чего, что разрешает сам harness.

## Разрешение

`get(name)` ищет по всем слоям, начиная с самого доверенного. `getFrom(name, sources)` ищет только по названным слоям, не меняя этот порядок доверия.

**Пропуск слоя — это отказ, а не понижение** — вызывающий, которому нельзя принимать некий слой никогда, просто не включает его в список, так что никакой будущий перенос порядков не впустит его обратно. Адаптеры провайдеров называют все три, потому что продукт доверяет проекту, в котором работает; механизм существует для тех решений, где это не так.

Имена сопоставляются так, как это делает платформа: точно на POSIX, без учёта регистра на Windows. Учитывающий регистр поиск там выстроил бы слои неверно — `deepseek_api_key` из оболочки и `DEEPSEEK_API_KEY` из проектного `.env` для ОС являются одной переменной, и обращение с ними как с двумя позволило бы проекту победить.

```ts
import type { Context } from '@deepseek-ai/cordis'
import { launchEnvironmentOf } from '@deepseek-ai/dsh-launch-environment'

declare const ctx: Context
const endpoint = launchEnvironmentOf(ctx).get('DEEPSEEK_BASE_URL')?.value
```

`launchEnvironmentOf(ctx)` возвращает снапшот лончера, когда продуктовый CLI загрузил дерево, и в противном случае — унаследованное окружение в качестве единственного слоя. Этот fallback не ослабляет правил: хост SDK или голый `cordis.yml` не обнаружили никаких файлов, так что всё, что у них есть, действительно является окружением, с которым они были запущены.

## Известные ограничения и отложенная работа

- **Снапшот — не граница дочерних процессов** — каждый слой вдобавок материализуется в `process.env`, так что обычные проектные переменные достигают дочерних процессов сквозь очистку [`dsh-subprocess`](../../subprocess/subprocess/README.ru.md). [Контракт `.env` продуктового лончера](../../boot/app-boot/README.ru.md#профили) отвергает bootstrap-переменные до материализации.
- **Нет слоя на рабочее пространство** — проектный слой — это *вызывающий* каталог, зафиксированный при запуске. Рабочее пространство, выбранное позже в веб-интерфейсе, намеренно не даёт ничего: следование за ним позволило бы собственному рабочему пространству модели менять окружение harness посреди сессии.
