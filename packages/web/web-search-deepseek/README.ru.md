# @deepseek-ai/dsh-web-search-deepseek

[English](README.md) | [中文](README.zh.md) | Русский

`WebSearchProvider` на базе [DeepSeek](https://deepseek.com) для seam'а веб-возможностей харнесса ([web capability seam](../web/README.md)) (`ctx.web`). Он вызывает **Anthropic-совместимый Messages API** DeepSeek (`POST {baseURL}/messages`) с включённым нативным серверным инструментом `web_search_20250305` и отображает структурированные блоки `web_search_tool_result`, возвращаемые DeepSeek, в нормализованный `WebSearchResult` этого seam'а.

Это пакет **реализации**: он регистрирует провайдера в `ctx.web`, разрешает его учётные данные для каждого поиска через необязательный seam `ctx.credentials`, записывает вспомогательный запрос в инициирующую сессию Agent, когда та существует, и не регистрирует инструмента, видимого модели. Как и `@deepseek-ai/dsh-llm-deepseek`, это плагин-функция/плагин-пространство имён (`inject: ['web']`). Anthropic-совместимый формат протокола — внутренняя деталь провайдера: он **не** делает этого провайдера зависимым от `ctx.llm`.

## Чем он отличается от выделенного поискового эндпоинта

Exa и Perplexity предоставляют выделенные поисковые эндпоинты; у DeepSeek такого нет. Вместо этого провайдер выполняет **полный вызов модели Messages** с серверным инструментом `web_search`, поэтому один поиск стоит целый ход модели по задержке и токенам — тяжелее чистого эндпоинта извлечения. DeepSeek исполняет поиск на своей стороне и возвращает **структурированные** блоки `web_search_tool_result`; провайдер разбирает эти блоки и **никогда не извлекает** URL из прозы модели.

**Строгий режим**: если ответ не содержит блока `web_search_tool_result` (нативный поиск не сработал), провайдер бросает `WebError` с кодом `WEB_PROVIDER_ERROR`, а не деградирует до извлечения из прозы.

Он переиспользует ссылку на учётные данные `DEEPSEEK_API_KEY` (нового секрета нет), но **не** `$DEEPSEEK_BASE_URL`: эндпоинт поиска — это Anthropic-совместимая база (`https://api.deepseek.com/anthropic/v1`), отличная от базы chat-completions (`https://api.deepseek.com`), которую использует LLM-адаптер. Смонтированный сервис учётных данных авторитетен; без него провайдер обращается к окружению запускающего процесса. Ссылка разрешается для каждого поиска, поэтому ключ, сохранённый или сменённый на странице Web Models, попадает в следующий вызов без перезапуска.

## Конфигурация

| Ключ | По умолчанию | Значение |
|---|---|---|
| `apiKey` | опущен | Литеральный ключ API DeepSeek. Предпочитайте `apiKeyEnv`, чтобы секрет не попадал в конфигурацию; непустой литерал имеет приоритет. |
| `apiKeyEnv` | `DEEPSEEK_API_KEY` | Ссылка на учётные данные, разрешаемая для каждого поиска через `ctx.credentials` либо из окружения процесса, когда этого seam'а нет. Отсутствующее значение приводит вызов к сбою `WEB_PROVIDER_CREDENTIAL_MISSING`. |
| `baseURL` | `https://api.deepseek.com/anthropic/v1` | База Anthropic-совместимого эндпоинта; добавляется `/messages`. Откатывается к `$DEEPSEEK_SEARCH_BASE_URL` из любого слоя окружения; не переиспользуйте `$DEEPSEEK_BASE_URL` — он принадлежит LLM-адаптеру chat-completions. Неразбираемое значение делает провайдера недоступным. |
| `model` | `deepseek-v4-flash` | Имя модели в формате Anthropic. |
| `apiVersion` | `2023-06-01` | Значение заголовка `anthropic-version`. |
| `maxTokens` | `4096` | Верхняя граница (положительное целое) числа генерируемых токенов для запроса Messages. |
| `maxUses` | `5` | Максимум использований серверного инструмента `web_search` на один запрос (положительное целое). |

```yaml
- id: web-search-deepseek
  name: '@deepseek-ai/dsh-web-search-deepseek'
  config:
    apiKeyEnv: DEEPSEEK_API_KEY
    baseURL: https://gateway.internal/anthropic/v1
```

Запись выше — базовый слой секции настроек `web-search-deepseek`: пользовательский слой поверх неё достигает СЛЕДУЮЩЕГО поиска, потому что провайдер проецирует секцию при каждом вызове, а не захватывает её при регистрации. Выбор провайдера в seam'е поэтому никогда не мерцает при смене эндпоинта или модели. `apiKey` несёт `role('secret')`, поэтому никогда не попадает в ответ `describe()` ни в одном слое — поверхность конфигурации узнаёт лишь то, что домен учётных данных хранит значение для ссылки, названной в `apiKeyEnv`, но никогда — то, что какой-то слой содержит литеральный ключ.

## Отображение результатов

DeepSeek не возвращает генерируемого провайдером содержимого ответа, которое этот провайдер принимал бы как `content`, поэтому `content` опускается. `sources[]` берётся из элементов `web_search_result` внутри блоков `web_search_tool_result`: `url` ← `url`, `title` ← `title`, а `publishedAt` ← `page_age`. Фрагменты живут отдельно как записи `cited_text` с ключом по URL в `citations[]` текстового блока; провайдер объединяет их, оставляя `snippet` отсутствующим, когда выдержки нет.

Результаты дедуплицируются по URL, потому что один запрос может показать ту же страницу в разных поисках. DeepSeek предоставляет `maxUses`, а не регулятор количества результатов, поэтому seam обеспечивает `maxResults`, усекая `sources[]` и устанавливая `truncated`.

Сбои провайдера становятся `WEB_PROVIDER_ERROR`; отмена вызывающим — `WEB_ABORTED`. HTTP-редиректы отвергаются до контакта с целью из `Location` и проявляются как `WEB_PROVIDER_ERROR`.

## Журналирование запросов

Непосредственно перед отправкой поиск, исполняемый под инициирующим Agent, дописывает событие сессии `web/deepseek-search-llm-request`, существующее только в журнале. Оно содержит разрешённый эндпоинт, версию API и точное тело JSON без секретов, отправленное DeepSeek; заголовки и учётные данные исключены. Сбои учётных данных и отмены до отправки события не создают, тогда как более поздние сбои HTTP или ответа оставляют предпринятый запрос зафиксированным в журнале. Прямые программные вызовы провайдера вне Agent не имеют инициирующей сессии для журналирования.

## Влияние на модель

### Вспомогательный поисковый запрос DeepSeek

#### Что видит модель

Отдельная модель DeepSeek получает ровно `Perform a web search for the query: <query>` как текст пользователя и одно определение нативного серверного инструмента `web_search`. Этот запрос не является частью контекста модели беседы.

#### Влияние на токены

На каждый поиск расходуются отдельные входные и выходные токены провайдера; `maxTokens` ограничивает генерируемый вывод, а `maxUses` — использования нативного поиска.

#### Влияние на KV-кэш

Независимо от кэша запроса беседы. Вспомогательная инструкция и определение нативного инструмента могут образовать стабильный префикс, но каждое изменение запроса или маршрута модели предотвращает повторное использование с первого же различия.

### Результат инструмента беседы, опосредованно

#### Что видит модель

Через [`dsh-tool-web`](../tool-web/README.ru.md) модель беседы видит дедуплицированные URL, заголовки, даты и фрагменты цитирования из структурированных поисковых блоков; проза провайдера ответом не считается. Точные сбои этого провайдера включают практическое сообщение об отсутствующих учётных данных `DeepSeek search credential resolution failed: <error>`, а также `DeepSeek search aborted`, `DeepSeek search request failed: <error>`, `DeepSeek returned no web_search_tool_result blocks; the request may not have triggered native web search` и `DeepSeek returned an unprocessable response body: <error>`; сбои HTTP сохраняют сообщение провайдера. Обёрткой ошибки владеет потребитель.

#### Влияние на токены

Ноль прямых токенов беседы от регистрации. Токены результата растут с числом возвращённых источников и фрагментов, затем seam обеспечивает запрошенную границу источников.

#### Влияние на KV-кэш

Append-only; новое видимое содержимое следует за повторно используемым префиксом запроса и не инвалидирует существующие записи KV-кэша.

## Известные ограничения и отложенная работа

- **Один поиск стоит полный ход модели Messages** — задержка плюс генерируемые токены, с числом серверных поисков до `maxUses`; выделенного эндпоинта извлечения DeepSeek не предоставляет.
- **Доступность динамических учётных данных разрешается внутри операции** — синхронный контракт `available()` может установить существование резолвера, но не способен опросить асинхронное хранилище учётных данных. Поэтому выбранный провайдер без ключа приводит поиск к сбою `WEB_PROVIDER_CREDENTIAL_MISSING`; стабильная схема `web_search` остаётся зарегистрированной. Отмена со стороны вызывающего идёт наперегонки с этой локальной preflight-проверкой, но не способна заставить произвольный бэкенд учётных данных сам остановить работу.
- **Избыточно возвращённые источники всё равно стоят токенов** — при отсутствии регулятора количества результатов в протоколе `maxResults` обеспечивается только постфактум усечением в seam'е.
- **Результаты без цитирования не имеют `snippet`** — источник получает его, только когда цитирование (`cited_text`) в текстовом блоке совпадает с его URL.
