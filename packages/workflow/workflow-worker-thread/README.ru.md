# @deepseek-ai/dsh-workflow-worker-thread

[English](README.md) | [中文](README.zh.md) | Русский

Этот пакет реализует `WorkflowEngine` с одним воркер-потоком Node на запуск. Воркер исполняет оркестрирующий скрипт; дочерние агенты остаются на стороне хоста, а доступ к ним идёт через `ctx.subagents` по типизированному протоколу хост/воркер.

Корень пакета экспортирует плагин движка по умолчанию и его `Config`; модули протокола воркера, рантайма и сессии остаются приватными для реализации. Исполнительная точка входа `./worker` остаётся целью spawn движка.

У этого разделения одна главная цель: синхронный цикл скрипта не может блокировать цикл событий harness, а скрипт, игнорирующий отмену, может быть принудительно завершён вместе со своим воркером. Это не песочница безопасности.

## Граница доверия и изоляции

Скрипты воркфлоу пишутся моделью и несут ту же предпосылку доверия, что и уже имеющийся у модели доступ к bash. `node:vm` внутри воркера — механизм формирования API, а не граница безопасности: вырвавшийся скрипт может вернуть себе возможности Node с привилегиями процесса хоста.

При этом воркер обеспечивает полезное сдерживание:

- Работа по CPU и синхронные циклы скрипта не занимают цикл событий хоста.
- `worker.terminate()` даёт освобождению ресурсов настоящую окончательную остановку.
- Воркер стартует с пустым окружением, кроме ещё не собранной обвязки загрузчика, поэтому окружающие учётные данные не просачиваются через `process.env`.
- Сообщения хост/воркер переносят данные structured-clone с проверкой на простой JSON на границе скрипта.

Настоящая песочница для недоверенных скриптов потребовала бы другого движка за тем же seam воркфлоу.

## Контракт скрипта

`meta` воркфлоу — данные, предоставленные хостом, а не исполняемый текст скрипта. Движок проверяет обязательные `name` и `description`, отвергает неизвестные поля и делает синтаксическую проверку тела до возврата запуска.

Внутри воркера скрипт получает `args` и следующие хуки:

- `agent(prompt, { label, phase, schema, model })` запускает один субагент на стороне хоста. Со схемой он возвращает структурное значение, иначе — финальный текст. Обычная неудача ребёнка даёт `null`.
- `parallel(thunks)` исполняет thunks в рамках настроенного лимита конкурентности.
- `pipeline(items, ...stages)` передаёт `(previous, item, index)` без барьера между стадиями.
- `phase(title)` и `log(message)` испускают наблюдательское повествование.

Неизвестные опции, искажённые аргументы, неподдерживаемые схемы, сработавшие потолки, неудачи старта провайдера и неудачи результатов инфраструктуры — фатальные ошибки воркфлоу. Таймеры, файловый API и глобалы Node намеренно не внедряются, хотя оговорка о доверии выше остаётся в силе.

## Последовательность запуска

`start()` валидирует meta, разбирает тело, разрешает зарегистрированный нормализованный маршрут провайдера и любой действующий на этот запуск общий потолок детей до создания воркера или публикации `workflow/start`. Запрошенный `maxTotalAgents` ДОЛЖЕН быть положительным безопасным целым, не превосходящим настроенный потолок развёртывания движка. Режим исходников устанавливает трансформации TypeScript через bootstrap с data-URL; собранный режим передаёт лежащий рядом `lib/worker.cjs` путём файловой системы, потому что VFS-хук pkg ожидает CommonJS. Оба работают под обычным Node. Рукопожатие ready/go не даёт отмене стартового сигнала, соревнующейся с загрузкой воркера, исполнить начальный синхронный кусок скрипта.

Для каждого вызова `agent()`:

1. Воркер отправляет `child-start` с промптом и опциями в виде простых данных.
2. Хост вызывает переопределение провайдера из стартового запроса, а если его нет — настроенного провайдера, через асинхронный `SubagentRuntime.start`, передавая родителя воркфлоу и один канонический сигнал отмены на запуск. Выбор провайдера действует на каждого ребёнка в этом запуске и не виден скрипту.
3. Если старт отклоняется, хост отправляет `child-start-error`; старт провайдера уже дошёл до quiescence, и ни одно событие жизненного цикла ребёнка не испускается.
4. Если старт выполняется, пока воркфлоу ещё допускает работу, хост регистрирует запуск, наблюдает `result`, затем отправляет `child-started`. Даже уже завершившийся результат пересылается вслед за этим, сохраняя порядок «старт раньше результата».
5. Воркер испускает парные повествовательные `workflow/agent-start` и `workflow/agent-end` и запрашивает освобождение ребёнка после сбора.

Старты провайдера отслеживаются отдельно от опубликованных детей. Если отмена, смерть воркера или нормальное завершение воркфлоу закрывают допуск, пока старт ещё ожидается, общий сигнал прерывает его. Провайдер, который всё же выполнится после закрытия, освобождается хостом и никогда не объявляется воркеру.

## Граница значений

Значения, покидающие скрипт, проходят через `materializeFromRealm`, который принимает простой, беспотерьный JSON и отвергает экзотические прототипы, функции, символы, циклы, разреженные массивы, неконечные числа и вложенный `undefined`. Обход выполняется в воркере и определяет ключи объектов как свойства-данные, поэтому `__proto__` не может мутировать прототип.

Результаты детей проецируются и снимаются в снапшот до пересечения от хоста к воркеру. Это настоящая граница сериализации, как между процессами; она намеренно отличается от доверенных внутрипроцессных полезных нагрузок событий воркфлоу и субагентов, которые являются заимствуемыми неизменяемыми значениями.

## Отмена и освобождение ресурсов

`WorkflowRun.cancel()` запоминает первую причину, велит воркеру отмениться, прерывает единственный сигнал, разделяемый каждым ожидающим и опубликованным ребёнком, и взводит таймер `disposeGraceMs`. Хуки воркера затем бросают `CANCELLED` на следующем await. Если запуск к дедлайну остаётся незавершённым, хост разрешает его как отменённый, составляет пары осиротевшим событиям жизненного цикла детей и завершает воркер.

У seam субагентов один канал отмены: сигнал запроса. Отдельного RPC отмены ребёнка нет. Демонтаж опубликованных детей идёт через `run.dispose()`; ожидающие старты провайдера остаются во владении провайдера, пока их промис не отклонится или не выполнится.

Нормальное завершение тоже прерывает ожидающие старты и начинает освобождение опубликованных fire-and-forget детей до того, как результат станет внешне завершённым. Условие quiescence хоста охватывает и ожидающие старты, и освобождения опубликованных детей, поэтому очистка не забывает асинхронную стартовую транзакцию.

`dispose()` идемпотентен. Он отменяет запуск, немедленно начинает ведомое хостом освобождение, ждёт результата плюс quiescence детей в пределах той же отсрочки, безусловно завершает воркер и проводит финальную зачистку выживших. Освобождение каждого ребёнка мемоизировано, поэтому RPC воркера, отмена хостом, очистка после смерти и публичное освобождение сходятся в одну операцию.

## Гарантии исхода и событий

Терминальный исход определяется по принципу first-wins в точках заявки хоста. Принятая внешняя отмена пересиливает более поздний неотменённый результат воркера; результат или смерть воркера, заявленные первыми, не могут быть переписаны реентерабельными callback-ами очистки.

Ошибка воркера, неудача сообщения или преждевременный выход закрывают приём сообщений до очистки, затем разрешают `error`, если отмена уже не владеет запуском. Поздние сообщения в очереди не могут создать детей или повествовать после этой логической границы.

Хост ведёт учёт всех пересланных стартов детей. Штатно завершающийся воркер поставляет их события завершения; смерть или принудительное завершение синтезирует недостающее завершение как отменённое. Поэтому каждый пересланный `workflow/agent-start` составляет пару ровно однажды, хотя очистка после уже пришедшего результата воркфлоу может завершиться позже.

## Конфигурация

| Ключ | По умолчанию | Значение |
|---|---|---|
| `provider` | `spawn` | Хостовый провайдер субагентов, используемый `agent()`. |
| `maxConcurrentAgents` | `0` | Потолок конкурентных `agent()`; `0` разрешается из доступного параллелизма CPU. |
| `maxTotalAgents` | `1000` | Всего вызовов `agent()` в одном запуске. |
| `maxItemsPerCall` | `4096` | Элементы, принимаемые одним вызовом `parallel()` или `pipeline()`. |
| `syncTimeoutMs` | `5000` | Тайм-аут VM для начального синхронного куска скрипта. |
| `disposeGraceMs` | `5000` | Предел до принудительного завершения/остановки и для публичного освобождения. |

Владеющий потребитель может задать `WorkflowStartRequest.subagentProvider` и `WorkflowStartRequest.maxTotalAgents` для одного запуска. Это политика уровня движка, а не хуки скрипта или обращённые к модели опции; обычный инструмент `workflow` оставляет оба незаданными. Действующий на один запуск общий потолок детей может понизить, но никогда не повысит настроенный потолок `maxTotalAgents`.

## Model Experience

### Запросы дочерних агентов

#### What the model sees

Каждый вызов скриптом `agent()` отправляет свой промпт дословно и опциональные модель или схему структурного вывода провайдеру субагентов. Каждый ребёнок видит собственный контекст того провайдера; повествование phase и log остаётся на наблюдательских событиях.

#### Token effect

Оплачивается потенциально много независимых контекстов детей, ограниченных `maxConcurrentAgents`, `maxTotalAgents` и `maxItemsPerCall`; они никогда не присоединяются к истории родителя напрямую.

#### KV Cache effect

Независимо от кэша родительского запроса и от соседних детей. Каждый ребёнок может переиспользовать только побайтово идентичный префикс при собственном провайдере, модели, промпте и схеме; его дальнейшая история растёт append-only.

### Результат родительского инструмента, опосредованно

#### What the model sees

Через [`dsh-tool-workflow`](../tool-workflow/README.md) успех показывает только материализованное финальное JSON-значение и число детей в обёртке того потребителя. Этот движок поставляет стабильные ошибки, включая `workflow script does not parse: <error>`, `invalid meta: <violations>`, `agent() requires a non-empty prompt string`, `agent() could not start a child: <error>`, `child agent run failed: <error>`, а также свои точные сообщения валидации `parallel()`, `pipeline()`, `phase()`, опций, схем и JSON-границы. Промежуточные выводы детей доступны скрипту, но не родительской модели.

#### Token effect

Ноль прямых родительских токенов от этого движка. Размер финального результата ограничен потребителем инструмента и удерживается до компакции.

#### KV Cache effect

Append-only; заново видимое содержимое следует за переиспользуемым префиксом запроса и не инвалидирует существующие записи KV-кэша.

## Known Limitations and Deferred Work

- **Воркер/vm — не граница безопасности** — написанный моделью код может вырваться из `node:vm` и достичь процессных полномочий воркера; развёртыванию враждебного кода нужен движок с отдельным процессом или контейнером.
- **За каждый запуск платится один воркер-поток** — пула, прогретого рантайма или межзапускного кэша скриптов нет.
- **Таймеры, файловая система и сеть извне не внедряются, но вырвавшийся код всё ещё может достичь Node** — отсутствующие глобалы — API переносимости, а не сдерживание.
- **Принудительная остановка может сообщить только о наблюдаемых хостом стартах** — `agentsStarted` исключает вызовы на стороне воркера, всё ещё стоящие в очереди за конкурентностью, когда принудительная остановка делает их неизвестными.
- **Межрилмовые ошибки не проходят `instanceof Error` внутри скриптов** — авторы воркфлоу ДОЛЖНЫ ветвиться по стабильным полям вроде `name` и `code`.
